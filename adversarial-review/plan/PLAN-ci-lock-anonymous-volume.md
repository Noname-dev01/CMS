# CI 잠금 컨테이너의 익명 볼륨 정리

> 작성일: 2026-11-09 / v3 (적대적 리뷰 2라운드 ship)
> 로드맵 근거: 64차 후속 후보 — `plan/PLAN-prod-path-verification.md` "이슈"(231행)·"후속"(238행)의 "`ci_cleanup`의 익명 볼륨 정리(`docker rm -v`)"
> 위험 변경: 없음. 스키마·인가 정책·`SecurityConfig`·의존성·Java 코드 변경 없음. 실행 사이 배타 잠금의 **획득·해제 시점과 조건은 바꾸지 않는다**(해제할 때 같이 지우는 대상만 늘어난다).

## Context

`scripts/ci/_prod-ci-common.sh`의 배타 잠금은 기동하지 않는 컨테이너 `cms-ci-prod-lock`이다(`ci_acquire_lock`, `docker create … <mariadb 고정 이미지> true`). mariadb 이미지가 `VOLUME /var/lib/mysql`을 선언하므로 **`docker create`만으로 빈 익명 볼륨이 하나 생긴다.** `ci_cleanup`은 `docker rm "$CI_LOCK_NAME"`으로 잠금을 푸는데 `-v`가 없어 그 볼륨이 남는다. CI 러너는 폐기되므로 문제가 없지만, 로컬에서 `CMS_CI_DISPOSABLE_DOCKER=1`로 돌리거나 같은 방식으로 잠금을 잡는 일회성 검증(`PLAN-prod-path-verification.md` D2, `PLAN-password-reset-timing.md`)을 할 때마다 하나씩 쌓인다.

### 정찰 실측 (2026-11-09, Docker 29.1.3, 같은 고정 mariadb 이미지, 별도 이름의 임시 컨테이너)

| 확인 | 결과 |
|---|---|
| `docker create` 후 `docker inspect .Mounts` | `volume <64자 해시> /var/lib/mysql` 1개 |
| `docker rm`(옵션 없음) 후 그 볼륨 | **남음** |
| `docker rm -v` 후 그 볼륨 | 사라짐 |
| 이름 붙은 볼륨을 붙인 컨테이너를 `docker rm -v` | 이름 붙은 볼륨은 **남음**(익명 볼륨만 지운다) |
| `docker run --rm <같은 이미지> true` 전후 볼륨 목록 | 차이 없음(`--rm`은 익명 볼륨도 지운다) |

다른 경로 확인: `prod-backup.sh`·`prod-restore.sh`·`prod-backup-restore-roundtrip.sh`의 `docker run`은 모두 `--rm`, 앱 이미지(`Dockerfile`)에는 `VOLUME`이 없고, compose의 db 서비스는 `/var/lib/mysql`에 이름 붙은 볼륨 `cms_db_data_prod`를 붙인다(`down -v`가 지움). **누수 지점은 잠금 컨테이너 한 곳뿐이다.**

## 범위

**포함**: `ci_cleanup`의 잠금 제거를 `docker rm -v`로, 잠금이 남았을 때 사람에게 안내하는 문구 2곳(`ci_acquire_lock`의 실패 메시지, 잠금 설명 주석)을 D3의 조건부 안내로.

**제외**

| 항목 | 이유 |
|---|---|
| 이미 쌓인 익명 볼륨 자동 정리 | 익명 볼륨에는 라벨이 없어 "이번 실행(또는 이 스크립트)이 만든 것"임을 증명할 수 없다. `docker volume prune` 같은 일괄 삭제는 다른 프로젝트 볼륨을 지울 수 있다 — "이번 실행이 만든 자원만 지운다" 원칙 위반 |
| 다른 일회성 계획 문서의 잠금 절차 문구 | 이미 끝난 작업의 기록이다. 다시 쓰지 않는다 |
| 잠금 방식 자체 변경 | 아래 D1 |

## 핵심 설계 결정

### D1. 볼륨을 지우는가, 애초에 만들지 않는가

| 선택지 | 판단 |
|---|---|
| A. 해제 때 `docker rm -v` | **채택** — 한 단어 변경, 로드맵이 지목한 처방. `-v`는 익명 볼륨만 지우고 이름 붙은 볼륨은 건드리지 않는다(실측) |
| B. 잠금 생성 때 `--mount type=tmpfs,destination=/var/lib/mysql`로 볼륨 생성 자체를 막기 | 기각 — 사람이 수동으로 `docker rm`할 때도 새지 않는 장점은 있으나, 기동하지 않는 컨테이너에 tmpfs를 붙이는 낯선 형태를 들이고, 잠금 컨테이너가 같은 이름으로 다른 도구(일회성 검증)에서도 만들어지므로 그쪽 생성 명령과 형태가 갈라진다. A의 수동 안내 문구 수정으로 같은 효과를 얻는다 |
| C. `VOLUME`이 없는 이미지(alpine 등)로 잠금 생성 | 기각 — 새 이미지 참조는 digest 고정과 `scripts/ci/check-image-refs.sh` 일치 검사 대상이 늘어난다. 이미 받아 둔 mariadb 이미지를 재사용하는 현재 이유(추가 pull 없음)도 사라진다 |

**왜**: 문제는 "해제할 때 짝이 되는 자원을 같이 지우지 않는 것"이다. 해제 지점을 고치는 것이 원인에 맞고 가장 작다.

### D2. 해제 조건·시점은 그대로

`CI_HOLDS_LOCK=1`이고 정리(`down -v`)가 성공했을 때만 해제한다는 기존 규칙을 유지한다. 정리 실패 때는 잠금과 함께 그 익명 볼륨도 남는다 — 잠금을 남기는 것이 다음 실행을 막는 의도된 안전장치이고, 볼륨은 잠금 컨테이너에 딸린 것이라 사람이 안내대로 `docker rm -v`하면 함께 지워진다. `|| true`(해제 실패를 종료 코드에 반영하지 않음)도 그대로다.

### D3. 수동 안내 문구는 "CI 잠금임을 확인한 경우에만 `-v`"

SIGKILL 등으로 잠금이 남으면 스크립트는 자동으로 빼앗지 않고 사람에게 `docker rm`을 안내한다. 안내를 그대로 따르면 같은 누수가 생긴다. 그러나 실패 분기는 **같은 이름의 컨테이너가 있는지만** 보므로, 그 컨테이너가 이 스크립트가 만든 잠금이라는 보장이 없다. 익명 볼륨이라고 해서 버려도 되는 데이터라는 뜻은 아니다(1라운드 지적).

| 경로 | 처리 |
|---|---|
| 자동 해제(`ci_cleanup`, `CI_HOLDS_LOCK=1`) | 무조건 `docker rm -v` — 이번 실행이 `docker create`에 성공한 바로 그 컨테이너다 |
| 수동 안내(`ci_acquire_lock` 실패 메시지, 잠금 설명 주석) | **조건부**: `docker inspect`로 ⓐ `cms.ci.run` 라벨이 있고 ⓑ 한 번도 기동되지 않았으면(`State.StartedAt`이 `0001-01-01T00:00:00Z`) `docker rm -v`, 아니면 이 스크립트의 잠금이 아니므로 지우지 말고 소유자를 확인하라고 안내 |

확인 명령은 안내 문구에 그대로 넣는다: `docker inspect cms-ci-prod-lock --format '{{index .Config.Labels "cms.ci.run"}} {{.State.StartedAt}}'`. 마운트 목록 확인은 넣지 않는다 — 라벨과 미기동 두 조건으로 CI 잠금을 식별하기에 충분하고, 안내가 길어질수록 따르지 않게 된다.

라벨·미기동 조건은 **진행 중인 정상 실행의 잠금도 만족한다.** 그래서 이 조건은 기존 안내의 "진행 중인 실행이 없음을 먼저 확인"을 대신하지 않고 그 뒤에 붙는다(순서: 실행 없음 확인 → 라벨·미기동 확인 → `-v`).

자동 판정(라벨이 있으면 스크립트가 알아서 지움)은 하지 않는다 — 기존 "남은 잠금을 자동으로 빼앗지 않는다" 규칙(진행 중인 실행일 수 있음)을 그대로 둔다.

## 성공 기준

1. 로컬에서 `CMS_CI_DISPOSABLE_DOCKER=1 bash scripts/ci/prod-smoke.sh`가 통과하고, 실행 전후 `docker volume ls -q` 목록이 같다(새로 생긴 볼륨 0개). 실행 전 dev 자원(`cms-db-dev`, `cms_db_data_dev`, `cms_notice_attachments_dev`)과 기존 볼륨이 그대로다.
2. 잠금 획득 후 preflight에서 실패하는 경로(`CI_OWNS_STACK=0`)에서도 잠금과 그 익명 볼륨이 함께 사라진다.
3. 정리 실패 경로(`down -v` 실패)에서는 잠금이 **남는다**(기존 안전장치 유지).
4. 잠금 경합(이미 잠금이 있을 때 두 번째 `ci_acquire_lock`)은 기존처럼 중단되고, 선점한 잠금과 그 볼륨을 건드리지 않으며 새 볼륨을 남기지 않는다.
5. 수동 안내 문구 2곳이 D3의 조건(라벨·미기동 확인 후에만 `-v`, 아니면 지우지 말고 소유자 확인)과 확인 명령을 담고, 그 확인 명령이 CI 잠금과 다른 컨테이너를 실제로 구분한다(F6).

## 놓치기 쉬운 실패 모드와 고정 방법

셸 스크립트용 자동 시험 체계(bats·shellcheck)는 이 저장소에 없다. 새로 들이는 것은 이번 범위를 넘는 도구 추가라(“검증되지 않은 새 의존성은 먼저 제안”) 하지 않고, **실제 Docker로 하는 실기 시나리오**로 고정한다. 하네스는 세션 scratchpad의 일회성 스크립트이고 커밋하지 않는다(결과는 이 문서 "검증 결과"에 기록).

| # | 실패 모드 | 확인 방법 |
|---|---|---|
| F1 | `-v`가 이름 붙은 볼륨(prod·dev 데이터)까지 지움 | 정찰 실측 C(이름 붙은 볼륨 보존) + 성공 기준 1에서 dev 볼륨 보존 확인 |
| F2 | preflight 실패 경로에서 해제가 일어나지 않거나 볼륨이 남음 | 하네스 S2: 고정 이름 자원 대신 `.env.prod` 존재로 preflight를 실패시키고(가짜 파일, 실행 뒤 제거) 잠금·볼륨 부재 확인 |
| F3 | 정리 실패 때 잠금까지 지워 다음 실행이 막히지 않음 | 하네스 S3: `CI_COMPOSE`를 실패하는 명령으로 바꿔 `ci_cleanup`을 부르고, 잠금이 남는지·종료 코드 1인지 확인한 뒤 수동 `docker rm -v`로 정리 |
| F4 | 경합에서 진 쪽의 실패한 `docker create`가 볼륨을 남기거나, 진 쪽 정리가 선점자 잠금을 지움 | 하네스 S4: 잠금을 먼저 만든 상태에서 하위 셸로 `ci_acquire_lock` 실행 → 실패, 볼륨 목록 변화 0, 선점 잠금·볼륨 그대로 |
| F5 | 변경 후 실제 게이트 전체가 깨짐(문법 오류 등) | 성공 기준 1(로컬 전체 `prod-smoke.sh`) + PR CI `prod-smoke` |
| F6 | 수동 안내의 확인 명령이 CI 잠금이 아닌 같은 이름의 컨테이너를 잠금으로 오인 | 하네스 S5: 별도 임시 이름으로 ⓐ `ci_acquire_lock`과 같은 형태(라벨·미기동) ⓑ 라벨 없는 컨테이너 ⓒ 라벨은 있으나 한 번 기동한 컨테이너를 만들어 안내의 확인 명령 출력이 ⓐ만 "지워도 됨" 조건을 만족하는지 확인 |

F5와 F6의 분량 차이(전체 기동 vs 문구 확인)는 의도다 — 경로마다 실제로 깨질 수 있는 것을 본다.

## 리스크

| 리스크 | 대응 |
|---|---|
| `docker rm -v`의 의미가 Docker 버전마다 다를 가능성 | `-v`/`--volumes`는 오래된 안정 옵션이고 "익명 볼륨만"이 문서화된 동작이다. 로컬(29.1.3) 실측 + PR CI 러너에서 `prod-smoke` 통과로 확인 |

## 구현·검증 결과 (2026-11-09)

### Context

계획 v3 그대로 구현했다. 계획과 달라진 결정은 없다. 브랜치 `fix/ci-lock-anonymous-volume`.

### 핵심 확정 사항

- 자동 해제(`ci_cleanup`)는 `docker rm -v "$CI_LOCK_NAME"`. 조건(`CI_HOLDS_LOCK=1` + 정리 성공)과 `|| true`는 그대로다.
- 수동 안내(잠금 설명 주석, `ci_acquire_lock` 실패 메시지)는 다음 순서를 따른다: 실행 없음 확인 → `docker inspect … --format '{{index .Config.Labels "cms.ci.run"}} {{.State.StartedAt}}'`가 `<토큰> 0001-01-01T00:00:00Z`인지 확인 → 그럴 때만 `docker rm -v`. 그 외에는 지우지 않고 소유자를 확인한다.

### 구현 파일

- `scripts/ci/_prod-ci-common.sh` — 주석(잠금에 익명 볼륨이 딸리는 이유, 수동 해제 조건), 실패 메시지, 해제 명령.

### 검증 결과

하네스(`lock-harness.sh`, 세션 scratchpad, 커밋하지 않음)를 실제 Docker 29.1.3과 고정 mariadb 이미지로 실행했다.

| 시나리오 | 수정 전 | 수정 후 |
|---|---|---|
| S2 preflight 실패(가짜 `.env.prod`) | 잠금은 해제됐지만 **볼륨 1개가 남음**(FAIL, 실패가 재현됨. 남은 볼륨은 생성 시각으로 특정해 지움) | 잠금 해제, 새 볼륨 0개 |
| S3 정리 실패(`CI_COMPOSE=(false)`) | — | 종료 코드 1, 잠금과 딸린 볼륨 1개가 남음(안전장치 유지), 수동 `rm -v` 뒤 새 볼륨 0개 |
| S4 잠금 경합 | — | 두 번째 획득 실패, 선점 잠금 라벨 그대로, 볼륨 증감 0, 새 안내 문구 출력 확인 |
| S5 수동 확인 명령 판별 | — | ⓐ 라벨 있음·미기동 → `tok 0001-01-01T00:00:00Z`로 허용, ⓑ 라벨 없음 → `' 0001-…'`로 불허, ⓒ 기동 이력 있음 → `tok 2026-11-09T10:31:08…Z`로 불허 |

S2~S5 전체 실행 전후 `docker volume ls` 목록이 같았다.

로컬 `CMS_CI_DISPOSABLE_DOCKER=1 bash scripts/ci/prod-smoke.sh`는 두 번 실행했다.

- 1회차: 이미지 빌드 단계에서 Docker 오류로 실패(아래 "이슈"). 다만 이 실행이 **스택을 소유한 뒤 실패하는 경로**를 실제로 거쳤다. 정리가 돌았고, 실행 전후 볼륨 목록·컨테이너 이름 목록이 같았으며 `.env.prod`가 없었다.
- 2회차: **`prod-smoke 전체 통과`**(백업·복구 왕복 포함, 90초). 실행 전후 볼륨 목록·컨테이너 이름 목록이 같았고 `.env.prod`가 없었다. dev 자원(`cms-db-dev`, 기존 볼륨)은 그대로였다.

Java 코드를 바꾸지 않았으므로 `./gradlew test`는 이 변경의 영향을 받지 않는다. 그래도 PR 전에 전체를 1회 실행한다(프로젝트 규칙).

### 이슈

- 1회차 `prod-smoke.sh`의 이미지 빌드가 마지막 `unpacking to docker.io/library/cms-prod-app:latest`에서 `failed to prepare extraction snapshot … parent snapshot sha256:78d4… does not exist: not found`로 실패했다. Gradle 빌드와 레이어 내보내기는 끝난 뒤였다. Docker Desktop 이미지 저장소(containerd 스냅샷) 쪽 오류로 보이지만 원인은 확인하지 않았다. 같은 조건으로 재실행하니 재현되지 않았다. 스크립트나 앱 코드와 무관한 일시적 환경 오류로 보고 `docs/troubleshooting.md`에는 기록하지 않았다(원인 미규명).
- 로컬에 남은 dangling 볼륨 3개(`cms-cap_db_cap`, `cms-cap_files_cap`, 2026-11-06 생성 익명 볼륨 1개)는 지우지 않았다. 범위 밖 결정 그대로다. 익명 볼륨 1개는 생성 시각으로 보아 이전 일회성 검증의 잠금이 남긴 것일 수 있지만 증명할 수 없다. 필요하면 사람이 `docker volume ls -f dangling=true`와 생성 시각·내용을 보고 판단한다.

### 후속

- 회귀 방지 장치는 PR CI `prod-smoke`의 통과뿐이다. 러너가 폐기되므로 볼륨 누수 자체를 CI가 잡지는 못한다. 셸 시험 체계 도입은 별도 제안 사항이다.
- 로드맵 반영은 `/updateRoadmap`이 한다.
