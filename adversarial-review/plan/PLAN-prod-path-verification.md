# prod 경로 실기 확인 — 브라우저 골든 패스·실제 HIBP 호출

> 작성일: 2026-11-07 / v3
> 로드맵 근거: "후속 과제 — ① prod 프로파일 완료 시 발견"의 미확인 항목(prod 프로파일 브라우저 골든 패스), 62차 기록의 미확인(prod 컨테이너 경로의 실제 HIBP 호출)
> 위험 변경: 없음(스키마·인가 정책·코드·설정 변경 없음). 검증 중 결함이 나오면 별도 계획으로 분리한다.

## Context

prod 스택은 CI `prod-smoke`가 PR마다 기동하지만 다음은 확인하지 않는다.

- **화면**: `prod-smoke.sh`는 curl로 로그인·보안 응답만 본다. 브라우저에서 정적 리소스를 받고 비루트 `appuser`가 볼륨에 파일을 쓰는 흐름은 prod 이미지로 확인한 기록이 없다. 지금까지 Playwright 회귀는 dev 프로파일 기준이었다.
- **HIBP**: `_prod-ci-common.sh`가 `CMS_PASSWORD_BREACH_CHECK_ENABLED=false`로 끈다. 검사는 판정 불가일 때 통과시키므로(fail-open), 호출이 실패해도 화면에서는 정상처럼 보인다.

## 범위

**포함**: 로컬 Docker의 실제 prod 스택(`scripts/prod-up.sh` 경로)에서 브라우저 골든 패스, 권한 경계, 재기동 후 데이터 유지, 실제 HIBP 호출.

**제외**

| 항목 | 이유 |
|---|---|
| 실제 SMTP 발송 | 사용자 결정(2026-11-07). 더미 자격증명에서 응답 계약만 본다. 실제 발송·재설정 링크 왕복은 미확인으로 남긴다 |
| 운영망의 HIBP 접근 | 호스트가 없다. 로컬 Docker 망의 결과는 운영망을 보증하지 않으므로 실배포 때 다시 확인한다 |
| ingress·TLS·`Secure` 쿠키 | `docs/verification/deployment-edge.md` 범위 |
| Turnstile 실제 키 | 도메인 확정이 선행 |
| 스크립트·CI 변경 | 코드 변경 없음이 이번 작업의 기본값 |

## 핵심 설계 결정

### D1. 스택 기동: `scripts/prod-up.sh` + 합성 `.env.prod`

| 선택지 | 판단 |
|---|---|
| A. `scripts/prod-up.sh` + 직접 만든 합성 `.env.prod` | **채택** — 실제 운영 기동 경로이고 검사를 켠 채로 띄울 수 있다 |
| B. `scripts/ci/prod-smoke.sh` 재사용 | 기각 — 검사가 꺼져 있고, 종료 때 스택을 지워 화면 검증을 이어 갈 수 없다 |
| C. `bootRun --spring.profiles.active=prod` | 기각 — 이미지·`appuser`·볼륨 권한을 거치지 않아 확인하려는 대상이 빠진다 |

**왜**: 확인 대상이 "prod 컨테이너 경로" 자체다.

`.env.prod` 값은 이번 실행에서 무작위로 만들고 출력하지 않는다. `MAIL_USER`·`MAIL_PASS`는 더미, `APP_BASE_URL=http://127.0.0.1:8080`, 검사 변수는 비워 기본값(켜짐)을 쓴다.

### D2. 자원 안전: 사전 부재 확인 후 이번 실행이 만든 것만 지운다

compose 이름·볼륨 이름이 고정이고 다른 체크아웃·로컬 CI도 같은 이름을 쓴다. 사전 확인과 생성 사이의 경합을 막으려고, **부재 확인 전에 CI와 같은 잠금 컨테이너 `cms-ci-prod-lock`을 만들고 정리가 끝난 뒤 지운다**(`_prod-ci-common.sh`의 `ci_acquire_lock`과 같은 방식, 라벨에 이번 실행 토큰). 잠금을 못 잡으면 다른 실행이 있다는 뜻이므로 빼앗지 않고 중단한다. 잠금을 잡은 뒤 다음을 확인하고, 하나라도 있으면 **중단하고 사용자에게 묻는다**.

- `.env.prod` 파일, 컨테이너 `cms-app-prod`·`cms-db-prod`, 볼륨 `cms_db_data_prod`·`cms_notice_attachments_prod`, 127.0.0.1:8080 점유

정찰(2026-11-07) 시점에는 모두 없었다. 실행 직전에 다시 확인한다.

합성 DB 이름은 이번 실행 토큰을 넣어 만든다(`cms_verify_<토큰>`). 정리는 `docker compose -f docker-compose.prod.yml --env-file .env.prod down -v` 후 `.env.prod` 삭제 → 잠금 제거 순서다. **`-v` 직전에 잠금 라벨의 토큰과 `cms-db-prod`의 `MYSQL_DATABASE`가 이번 실행 값인지 대조**하고, 다르면 지우지 않고 사용자에게 알린다. dev 자원(`cms-db-dev`, `cms_db_data_dev`, `cms_notice_attachments_dev`)과 `cms-cap_*` 볼륨은 건드리지 않고, 정리 뒤 그대로인지 확인한다. 실패로 중단될 때도 사후 분석이 필요하면 스택을 남기고 알린 뒤 정리한다.

### D3. HIBP 판정: 거부 응답을 양성 증거로 쓴다

| 선택지 | 판단 |
|---|---|
| A. 유출 값 거부(양성) + 정상 값 통과·WARN 없음 + 호출 차단 시 WARN(대조) | **채택** |
| B. 비밀번호를 한 번 바꾸고 WARN이 없는지만 확인(`docs/deployment.md` 절차) | 기각 — 로그 수집이나 검사 설정이 잘못돼도 "WARN 없음"으로 통과한다 |
| C. 컨테이너에서 `curl`로 API 호출 | 기각 — 런타임 이미지의 JDK `HttpClient`·CA 저장소 경로와 다르다 |

**왜**: 거부(400 `PASSWORD_REJECTED`)는 앱이 실제로 HIBP 응답을 받아 해석해야만 나온다. fail-open이라 "거부되었다"만이 호출 성공의 직접 증거다.

유출 값은 공개 사전 단어로 된 15코드포인트 이상 문자열을 쓰고, 호스트에서 range API로 횟수 1 이상임을 먼저 확인한다(호스트 쪽 양성 확인이 없으면 "미유출이라 통과"와 구분되지 않는다).

대조 시험은 저장소 밖 임시 compose 오버라이드로 `extra_hosts: api.pwnedpasswords.com:127.0.0.1`을 넣어 앱 컨테이너만 재생성한다. 호출이 막힌 상태에서 WARN이 실제로 남고 변경이 통과하는지 본다. 끝나면 오버라이드 없이 재생성한다. 저장소의 `docker-compose.prod.yml`은 바꾸지 않는다.

`prod-up.sh`의 호스트 변수 가드는 자식 셸에서만 적용되므로, **compose를 직접 부르는 모든 셸(H3 재생성·복원, 정리)에서 `scripts/_prod-env-guard.sh`의 `prod_env_guard_unset_host_vars`를 먼저 호출**한다. 재생성 뒤마다 `docker inspect`로 컨테이너의 `CMS_PASSWORD_BREACH_CHECK_ENABLED` 값(비었거나 `true`)과 `HostConfig.ExtraHosts`(차단 중에만 있음)를 확인한다.

### D3-1. 로그 증거: 구간별로 저장한다

컨테이너를 지우는 단계(H3 차단·복원, R1, 정리) 전에 `docker logs`를 scratchpad 파일로 저장하고 컨테이너 ID를 함께 적는다. H1·H2·H3은 조작 직전·직후 시각(`docker logs --since`)으로 구간을 잘라 판정한다 — "WARN 없음"과 "WARN 1건"은 그 요청 구간 기준이다. L1은 저장한 로그 전체를 대상으로 한다. 저장 파일에는 합성 값만 있고 커밋하지 않는다.

### D4. 브라우저 도구: Playwright MCP 일회성 실행

| 선택지 | 판단 |
|---|---|
| A. Playwright MCP로 사람처럼 조작 | **채택** — 프로젝트 표준 실기 검증 절차(`library-docs-lookup`) |
| B. `prod-smoke`에 브라우저 단계 추가 | 기각 — CI 시간·유지 비용이 늘고 "코드 변경 없음"을 벗어난다. 필요하면 별도 제안 |

스크린샷은 세션 scratchpad에 두고 커밋하지 않는다. 합성 자격증명이 화면에 보이지 않는 장면으로 찍는다.

### D5. 결과 기록: 이 계획 문서에만

| 선택지 | 판단 |
|---|---|
| A. 이 문서의 "구현·검증 결과"에 기록 | **채택** — 요청받지 않은 절차 문서를 늘리지 않는다 |
| B. `docs/verification/prod-golden-path.md` 신설 | 기각 — 실배포 때 환경이 달라져 다시 써야 한다. HIBP 재확인 절차는 이미 `docs/deployment.md`에 있다 |

로드맵 완료 반영은 `/updateRoadmap` 몫이고, 이번 작업에서 로드맵 파일을 직접 고치지 않는다.

### D6. 결함 처리: 멈추고 분리한다

결함이 나오면 먼저 데이터·환경을 확인한 뒤 원인과 증거를 보고하고, 수정은 별도 브랜치·별도 승인으로 진행한다. 이번 브랜치에 코드 수정을 섞지 않는다. 수정을 기다리느라 진행할 수 없는 항목은 "미확인(결함 #n 대기)"으로 표시하고 완료로 쓰지 않는다.

## 검증 단계와 성공 기준

사전 기록: `git rev-parse HEAD`, `git status --short`(문서 외 변경이 없어야 빌드 대상이 master와 같다).

### 기동

- [ ] **S1** `scripts/prod-up.sh`가 0으로 끝나고 health 200, `RestartCount` 0, 이미지 실행 사용자가 `appuser`(UID 10001)
- [ ] **S2** 빈 DB에 Flyway 전 버전 적용, 부트스트랩 ADMIN 1건 생성, 기동 로그에 `유출 비밀번호 검사가 꺼져` 없음

### 브라우저 골든 패스(ADMIN)

- [ ] **G1** 로그인 폼 → 대시보드. 콘솔 오류 0, 정적 리소스 응답에 4xx·5xx 0(`favicon` 포함 여부는 결과에 그대로 적는다)
- [ ] **G2** 게시판 만들기 → **영속성 확인용 글** 작성(CSRF가 필요한 쓰기 왕복) → 본문 이미지·첨부파일 업로드 → DB에 행 확인 → 볼륨에 파일 존재·소유자 `10001`. 이 글은 R1까지 지우지 않는다
- [ ] **G3** 비로그인 컨텍스트에서 공개 목록·상세·본문 이미지 표시, 첨부 다운로드 sha256이 원본과 일치
- [ ] **G4** 프로필 이미지 업로드 → 화면 표시(`profile` 네임스페이스 쓰기)
- [ ] **G5** 왕복 원복: **첨부 없는 별도 글**을 만들어 공개 상세 200 → 삭제 → 공개 상세 404 → 휴지통 복원 → 비노출 유지(공개 상세 404). 첨부가 있는 글의 삭제가 409인 것은 정상 계약이다(`PostService.deletePost`)

### 권한 경계

- [ ] **B1** MANAGER 생성(유출 검사를 거치는 경로) → 그 계정으로 로그인, 권한 없는 게시판·ADMIN 화면이 사이드바에 없고 URL 직접 접근 403
- [ ] **B2** 게시판 A·B를 둔다. ADMIN이 A의 READ만 부여 → MANAGER에게 A만 보임. 그 뒤 유효한 CSRF 토큰으로: B의 게시글 목록·상세·첨부 다운로드 403, A의 게시글 생성·수정 403(READ만 있음). 게이트는 "어느 게시판이든 READ"라서 이 단계가 게시판별 판정(`@RequireBoardPermission`)을 확인한다
- [ ] **B3** 비로그인으로 `/admin` 접근 → 로그인 302. 비로그인 CSRF 토큰 없는 `POST /admin/api/**` → 401(JSON). 인증 세션의 CSRF 토큰 없는 같은 POST → 403
- [ ] **B4** ADMIN 인증 상태에서 `/actuator/env` 403, `/swagger-ui.html` 404(HTML 오류 페이지, 스택트레이스 없음)

### 실제 HIBP

- [ ] **H0** 호스트에서 유출 값의 range 응답 횟수 ≥ 1 확인(SHA-1 앞 5자만 전송)
- [ ] **H1** 내 비밀번호 변경에 유출 값 입력 → 화면에 거부 문구, 응답 400 `PASSWORD_REJECTED`, 로그인 유지, 비밀번호 그대로
- [ ] **H2** 무작위 값으로 변경 → 성공, 세션 폐기, 새 값으로 재로그인, 옛 값 거부, 그 요청 구간에 검사기 WARN 전체(`유출 비밀번호 검사`로 시작 — `불가`·`중단` 모두) 없음
- [ ] **H3** 대조: 재생성 전 로그 저장 → 호출 차단 상태 확인(`ExtraHosts`) → 무작위 값으로 변경 → 성공 + 그 요청 구간에 WARN 1건(예외 클래스명만, 비밀번호·해시·접두부 없음). 로그 저장 → 오버라이드 없이 재생성·복원 확인 → H1 재확인

### 재기동

- [ ] **R1** **직전에 새로 로그인해 보호 화면 200을 확인한 쿠키를 보관**하고 로그 저장 → `scripts/prod-down.sh` → `scripts/prod-up.sh`(운영 재배포 경로). 보관한 쿠키로 보호 화면 접근 시 로그인 302(세션 무효), 재로그인 성공, 게시글·첨부(sha256 동일)·프로필 이미지 유지, ADMIN 1건 그대로

### 메일 응답 계약(더미 자격증명)

- [ ] **M1** 재설정 요청이 존재·미존재 계정 모두 200. 발송은 비동기이므로 **존재 계정의 `비밀번호 재설정 메일 발송 실패` 로그(또는 성공 로그)가 나올 때까지 기다린 뒤**(소켓 상한 기준 최대 약 70초, 넘으면 미확인으로 기록) 다음으로 넘어간다. `exceptionType`을 기록한다 — 인증 실패인지 DNS·연결·TLS 실패인지 이 로그만으로 구분되지 않으면 그대로 적는다. 로그에 토큰·자격증명 없음. **실제 발송 확인이 아니다**

### 로그·정리

- [ ] **L1** 저장한 로그 전체에서 `ERROR`·스택트레이스를 전수 확인하고, 각 건을 예상된 것(M1의 메일 실패 등)과 결함으로 분류
- [ ] **C1** 합성 비밀번호·`.env.prod` 값이 저장소에 없고 `git status`에 `.env.prod` 없음. 정리 뒤 prod 컨테이너·볼륨·잠금 없음, dev 자원 그대로

## 놓치기 쉬운 실패 모드

| # | 실패 모드 | 고정 수단 |
|---|---|---|
| 1 | 런타임 이미지의 CA·DNS 문제로 HIBP 호출이 실패하는데 fail-open이라 조용히 통과한다 | H1(거부가 나와야 통과). H3으로 WARN 부재의 의미를 대조 |
| 2 | 볼륨 소유권 때문에 `appuser` 파일 쓰기가 실패한다 | G2·G4, 볼륨 파일 소유자 확인 |
| 3 | 이미지에 템플릿·정적 리소스가 빠지거나 prod에서만 경로가 달라진다 | G1 네트워크·콘솔 전수 |
| 4 | prod에서 평문 HTTP 쿠키·CSRF가 어긋나 curl은 되는데 브라우저 쓰기가 실패한다 | G2의 fetch 쓰기, B3 |
| 5 | 고정 이름 자원 정리가 다른 데이터를 지우거나 합성 시크릿이 저장소에 남는다 | D2 잠금·삭제 전 대조, C1 |

이번 작업은 자동 시험을 추가하지 않는다(코드 변경 없음). 위 수단은 실기 단계이고 결과는 재실행으로만 다시 확인된다. CI에서 회귀를 잡지 않는다는 한계로 기록한다.

## 작업 단계

1. 브랜치 `test/prod-path-verification` 생성(미커밋 로드맵 문서 4개 처리는 승인 때 함께 정한다)
2. 잠금 → 사전 확인 → 합성 `.env.prod` → S1·S2
3. G1~G5 → B1~B4 → H0~H3 → R1 → M1 → L1
4. 정리 C1
5. 결과를 이 문서와 `plan/README.md`에 기록

## 리스크

| 리스크 | 대응 |
|---|---|
| 외부 전송: HIBP로 공개 값·무작위 값의 SHA-1 앞 5자, Gmail로 더미 자격증명 인증 시도 | 실제 비밀번호·개인정보 없음. 모두 합성 값 |
| Windows Git Bash 경로 변환·개행으로 스크립트가 환경 문제로 실패 | 결함으로 보기 전에 환경부터 확인(`docs/deployment.md`의 `MSYS_NO_PATHCONV` 사례) |
| HIBP 일시 장애로 H1 실패 | H0을 같은 시점에 함께 보고 앱 결함과 구분 |
| Docker 볼륨에 합성 데이터가 남음 | C1에서 제거 확인 |

## 수용하는 한계

- 로컬 Docker 망과 평문 HTTP 기준이다. 운영망 접근, TLS, `Secure` 쿠키는 보증하지 않는다.
- 실제 SMTP 발송과 재설정 링크 왕복은 미확인으로 남는다.
- 이번 결과는 이 커밋 기준의 일회성 확인이며 이후 변경의 회귀를 막지 않는다.

## 구현·검증 결과 (2026-11-07)

### Context

첫 실배포 전에 prod 컨테이너 경로의 미확인 항목을 로컬 Docker에서 확인했다. 기준 커밋은 `3e22999`이고, 빌드 당시 작업 트리에는 문서 변경만 있었다. **결함은 나오지 않았고 코드·설정 변경도 없다.**

### 핵심 확정 사항

- **prod 이미지의 HIBP 호출이 실제로 동작한다.** 유출 값이 400 `PASSWORD_REJECTED`로 거부됐다. 호출을 막으면 WARN이 남고 통과하므로 "WARN 없음"도 판단 근거로 쓸 수 있다.
- **브라우저 골든 패스가 prod 이미지에서 동작한다.** 비루트 `appuser`의 볼륨 쓰기, CSRF가 필요한 쓰기, 공개 화면, 게시판별 권한을 포함한다.
- **재배포 경로에서 데이터가 유지되고 세션은 무효가 된다.**

### 구현 파일

코드·스크립트·설정 변경 없음. 이 문서와 `plan/README.md`만 바꿨다.

### 계획과 달라진 점

- 스크린샷·업로드 파일을 Playwright 허용 경로 제약으로 scratchpad 대신 gitignore 대상 `.playwright-mcp/verify/`에 두었다가 끝나고 지웠다(스크린샷은 scratchpad로 복사).
- 합성 자격증명은 브라우저 입력을 위해 작업 기록에 나타났다. 이번 스택과 함께 폐기된 값이다.
- G5 첫 시도(글 2)는 도구가 확인 창을 가로채 측정값을 잃어, 새 글(글 3)로 다시 측정했다.

### 이슈

검증 대상의 결함은 없다. 관찰 사항은 다음과 같다.

| 관찰 | 판단 |
|---|---|
| `posts.html` 모달에서 삭제할 때 `aria-hidden` 포커스 경고 | prod와 무관한 접근성 경고, 동작에는 영향 없음 |
| 재설정 요청 응답 시간이 존재 계정 0.113초, 미존재 0.016초 | **각 1회 측정이라 결론을 낼 수 없다.** 계정 열거 신호일 가능성이 있어 반복 측정이 필요하다 |
| 잠금 컨테이너 생성으로 빈 익명 볼륨이 남음 | mariadb 이미지의 `VOLUME` 때문이고, `docker rm`에 `-v`가 없어 생긴다. `ci_cleanup`도 같아 로컬 실행 때 누적될 수 있다(이번 볼륨은 지웠다) |
| 세션 쿠키에 `Secure` 없음 | 평문 HTTP 검증 경로의 현재 동작이다. `deployment-edge.md` 범위 |
| Playwright 스크립트 1회가 첨부 업로드 뒤 120초 넘게 멈춤 | 원인은 확인하지 못했다. 서버 쓰기는 성공했고 앱 로그에 오류가 없으며, 나눠 실행하니 재현되지 않았다 |

### 후속

- **여전히 미확인:** 실제 SMTP 발송과 재설정 링크 왕복, 운영망의 HIBP 접근, TLS·`Secure` 쿠키. 실배포 때 확인한다.
- **후보:** 재설정 요청 응답 시간 반복 측정, `ci_cleanup`의 익명 볼륨 정리(`docker rm -v`).
- **회귀 방지 없음:** 일회성 확인이라 이후 변경은 다시 확인해야 한다.
- 로드맵 반영은 `/updateRoadmap`이 한다.
