## Context

지금 메뉴 관리 화면은 ① 같은 부모 안 순서 변경(`PUT /admin/api/menus/order`, 드래그마다 즉시 호출), ② 별도 "상위 메뉴 변경" 폼(`PATCH /{id}/parent`)으로 나뉘어 있고, 메뉴는 **2단까지만** 허용한다. 요구는 다음과 같다.

1. 드래그 앤 드롭으로 **어디로든** 이동(다른 부모 포함, 깊이는 **최대 3단으로 확장**, 하위 메뉴는 **서브트리째** 이동).
2. 드래그는 **초안(draft)** 으로만 화면에 반영하고, 트리 하단 **[반영]** 버튼을 눌러야 서버에 적용된다. 누르지 않으면 적용되지 않는다.
3. 드롭한 **정확한 위치**에 배치된다.
4. 공용(`ALL`) 메뉴를 관리자 전용(`ADMIN`) 부모 아래로 옮기는 구조는 **거부**한다(이전의 "경고만 표시" 폐기).

### 왜 "초안 + 일괄 반영"이 서버 설계를 단순하게 하는가

드래그마다 호출하는 방식에서는 호출 한 번이 "부모 하나 + 위치 하나"만 바꾸므로 (a) 임시 상태에서 깊이·순환 규칙을 매번 지켜야 하고(A를 B 아래로, B를 C 아래로 같은 조합이 중간 상태 때문에 막힘), (b) 부모 변경과 순서 확정이 두 호출로 갈라져 원자적이지 않으며, (c) 잠금을 호출별로 설계해야 해 교착 경로가 많다(#69 계획 결정 9). 최종 구조를 **한 번에** 보내면 검증은 "최종 구조가 유효한가" 하나로 줄고, 잠금은 "전체 행을 한 번 잠그고 검증·저장"하는 단일 경로가 된다.

## 설계

### 결정 1 — 엔드포인트와 요청 형태

`PUT /admin/api/menus/structure` (ADMIN 전용. URI에 동사를 쓰지 않는 컨벤션 — 명사 `structure`, 전체 구조의 교체이므로 `PUT`).

```json
{
  "menus": [
    { "menuNo": 1, "baseUpMenuNo": null, "baseOrd": 0, "upMenuNo": null },
    { "menuNo": 5, "baseUpMenuNo": 3,    "baseOrd": 2, "upMenuNo": 1 }
  ]
}
```

- `menus`는 **전체 메뉴(비활성 포함)** 를 담는다. 같은 `upMenuNo` 안의 **배열 순서가 새 `ord`(0..n-1)** 가 된다 — 클라이언트가 `ord` 값을 보내지 않으므로 중복·간격 같은 `ord` 유효성 문제가 없다.
- `baseUpMenuNo`/`baseOrd`는 초안을 만든 시점(트리 조회 시점)의 값이다 — 결정 3의 낙관적 검사용.
- 별도 개수 상한은 두지 않는다(리뷰 P2-8: 형제 집합 상한과 달리 전체 상한은 데이터가 늘면 반영이 영구히 막히는 복구 불가 상태를 만든다). 대신 잠금 후 **요청 크기 > DB 전체 행 수**이면 즉시 400(비정상 대용량 본문 방어)이고, 정상 요청은 결정 3의 집합 일치로 자연히 제한된다. 본문 `null`/빈 목록 400. 각 항목의 `menuNo` 중복 400.
- `upMenuNo`·`baseUpMenuNo`는 정수 또는 `null`만 허용한다(`#69`의 `JsonNode` 토큰 검증 패턴 재사용 — 필드 없음/`""`/`"null"`/`10.9`가 승격·이동으로 둔갑하는 것 방지, `docs/troubleshooting.md`). `baseOrd`는 정수 또는 `null`(레거시 `ord` null 행).

응답: `{ "changed": <실제로 바뀐 행 수> }` — 무변경 요청도 200(멱등).

### 결정 2 — 잠금 규약

1. 트랜잭션의 **첫 애플리케이션 테이블 조회가 잠금 읽기**여야 한다(#69와 동일 — 비잠금 읽기가 REPEATABLE READ 스냅샷을 일찍 고정하면 뒤이은 검증이 오래된 값을 본다).
2. **전체 메뉴 행을 `menuNo` 오름차순으로 잠근다.** 구현은 `findAllForUpdate()`(`@Lock(PESSIMISTIC_WRITE)` + `order by menuNo`) 한 번 — 개별 `findByIdForUpdate` 반복이 아니다.
3. 이 경로가 구조(부모·순서)를 바꾸는 **유일한** 쓰기 경로이므로 이동끼리는 교착이 없다(같은 순서로 전체를 잠그므로 직렬화).
4. 다른 경로와의 관계: 일반 수정·비활성화·재활성화·하위 생성은 자기 행(+부모 행)만 잠근다. 이 경로가 전체 행을 `menuNo` 오름차순으로 잠그는 동안 그 경로들과 교착이 가능한가 → **리뷰 쟁점 1**(재활성화는 자식→부모 순서로 잠그므로 `menuNo` 오름차순과 어긋날 수 있다. 교착은 정합성이 아니라 가용성 문제로, InnoDB가 한쪽을 롤백하고 409로 응답하는 기존 계약을 따른다는 방침이며, 잠금 후 최신값 재검증이 정합성을 보장한다).
5. 메뉴는 관리자 전용 소규모 데이터(수십 건)라 전체 잠금의 가용성 비용은 작다고 판단한다. 비용은 구조 반영 중 일반 수정이 잠깐 대기하는 정도다.

### 결정 3 — 낙관적 검사(낡은 초안)

잠금 후 현재 DB 상태와 요청을 비교한다. **하나라도 다르면 409 `RESOURCE_CONFLICT`**(롤백, 화면은 서버 상태로 새로고침 + 안내).

- 요청의 메뉴 집합 ≠ 현재 **트리 도달 가능 메뉴 집합**(루트에서 `upMenuNo` 사슬로 도달 가능한 행 — `assembleTree`와 같은 기준. 다른 관리자가 생성·삭제함) → 409. **고아·루트 없는 순환 행**(트리 응답에서 제외되는 행, 리뷰 P2-7)은 비교에서 빼고 **잠금만 하며 수정하지 않는다** — 그렇지 않으면 화면이 볼 수 없는 행 때문에 새로고침해도 영구 409가 된다. 요청의 `upMenuNo`가 도달 불가 행을 가리키면 400.
- 어떤 행의 현재 `(upMenuNo, ord)` ≠ `(baseUpMenuNo, baseOrd)` → 409

`useYn`·`accessRole` 같은 다른 필드는 구조 반영의 입력이 아니므로 base에 넣지 않는다. 다만 **검증은 잠근 최신 값**으로 한다(결정 4) — 초안을 만든 뒤 다른 관리자가 비활성화·권한 변경을 했어도 최종 구조의 유효성은 현재 값 기준으로 판정된다.

### 결정 4 — 최종 구조 검증 (잠근 최신 엔티티 기준, 이 순서)

**저장 범위 ≠ 검증 범위 (리뷰 P2-5)**: 기존 생성·수정 경로는 임의의 비음수 `ord`를 허용하므로, 손대지 않은 그룹을 `0..n-1`로 재번호하면 `ord`만 바뀐 행이 생긴다. 이를 "변경된 메뉴"로 취급하면 무관한 기존 위반(권한 불일치·4단 이상) 때문에 반영이 막힌다.
- **저장 범위(재번호)**: 요청 배열 순서가 현재 순서(base)와 다르거나 구성원이 바뀐 **부모 그룹만** `0..n-1`로 다시 매긴다. 순서·구성이 그대로인 그룹의 행은 `ord`가 `100`이어도 쓰지 않는다(`updateDate` 보존).
- **검증 범위**: `upMenuNo`가 **바뀐 메뉴 T와 그 서브트리**(T 자신 + 모든 자손)만 아래 3~6번 규칙을 검사한다. `ord`만 바뀐 행은 검증 대상이 아니다. "새로 생기거나 악화되는 위반"의 정의 = T 서브트리 안에서, 최종 구조가 규칙을 위반하는 경우. 이동하지 않은 서브트리의 기존 위반은 이 반영을 막지 않는다(순환만은 전체에서 항상 검사 — 순환은 이동 없이는 생길 수 없으므로 실제로는 이동된 T 사슬에서만 발생).

| 순서 | 검사 | 응답 |
|---|---|---|
| 0 | 요청 본문 검증(상한·중복·토큰 타입) | 400 |
| 1 | 집합 일치·base 일치(결정 3) | 409 |
| 2 | `upMenuNo`가 요청 안에 없는 메뉴를 가리킴 | 400 |
| 3 | **순환**: 이동된 T의 조상 사슬이 T 자신에 도달 | 400 |
| 4 | **깊이**: 이동된 T 서브트리 안에서 최종 깊이 > 3 | 400 |
| 5 | **활성 메뉴가 비활성 부모 아래**(`useYn` 최신값, T 서브트리 범위) | 400 |
| 6 | **권한 불일치**: T 서브트리 안에서 조상 사슬(새 부모 위쪽 포함)에 `ADMIN` 메뉴가 있는데 그 아래 `ALL` 메뉴가 있음 | 400 |
| 7 | 반영: 위 "저장 범위"대로 재번호, 부모가 바뀐 행은 `changeParent`, 값이 이미 같은 행은 **쓰지 않는다** | 200 |

6번 규칙의 근거: `accessRole`은 사이드바 노출 제어이고 MANAGER에게는 `ADMIN` 부모가 제외돼 자식도 안 그려지므로(`getSidebarMenus`), `ALL`이 `ADMIN` 조상 아래에 있으면 의도치 않게 숨는다. 이전엔 경고만 했지만 결정 3에 따라 거부한다.

**기존 데이터 호환(리뷰 쟁점 2)**: 이미 DB에 6번 규칙을 위반하는 행(예: dev의 `ADMIN` 그룹 아래 `ALL` 자식)이나 3단 초과 행이 있을 수 있다. 구조 반영은 **전체 구조를 검증**하므로, 무관한 위반 때문에 반영이 막힐 수 있다. 선택지: (a) 위반 행도 새 구조에서 같이 고치게 강제(막힘), (b) 이번 요청에서 **바뀐 행이 관련된 위반만** 검사. → 리뷰에서 결정. 초안은 (b) — "변경된 메뉴 자신과 그 서브트리"가 위반일 때만 400.

### 결정 7 — 화면 (PR C, `manage.html`)

- 상태: `draft`(드래그가 만든 초안) 유무 = **dirty**. 초안은 jstree 인스턴스 자체가 들고 있고, 반영 시 `get_json`으로 구조를 읽어 요청을 만든다. 서버에는 **드래그 중에 아무 호출도 하지 않는다**(`handleMoveNode`는 dirty 플래그와 변경 건수만 갱신).
- base: 마지막 트리 조회 응답의 `data.upMenuNo`·`data.ord` 스냅샷을 보관해 요청의 `baseUpMenuNo`/`baseOrd`로 보낸다.
- 버튼: 트리 하단 **[반영]**(dirty일 때만 활성)·**[취소]**(초안 폐기 = 서버 상태 재조회). 문구 "반영 대기 중 N건"(N = 부모 또는 위치가 base와 다른 메뉴 수).
- `check_callback`(서버 결정 4의 범위와 **같은 규칙**): 이동 대상은 단일 노드(`is_multi`·`is_foreign` 금지). **같은 부모 안 재정렬은 깊이·권한·활성 상태 검사 없이 항상 허용**한다(서버도 `ord`만 바뀐 행은 검증하지 않으므로 — 기존 4단 자손이나 `ADMIN→ALL` 위반을 가진 메뉴도 재정렬할 수 있어야 한다, 리뷰 3라운드). **부모가 바뀌는 드롭에만** 순환(자기 자손 아래 금지)·깊이(새 부모 깊이 + 이동 서브트리 높이 ≤ 3)를 검사한다. 권한 불일치·비활성 부모 규칙은 서버가 판정하되, **부모가 바뀌는 드롭에 한해** 알려진 위반은 드롭을 막는 편이 좋다 — 화면에도 같은 순수 함수로 검사한다(서버가 최종 판정, 화면은 UX 보조).
- **진입 규칙(리뷰 P2-4)**: 화면 진입 시 "비활성 포함"을 **기본으로 켠다**. 드래그는 `treeScope === 'all'`(비활성 포함 전체 조회가 끝난 상태)에서만 허용하고(`canDrag()`가 검사), 활성만 보기로 바꾸면 드래그를 막고 "비활성 포함을 켜면 구조를 편집할 수 있습니다"를 안내한다. 첫 드래그 이전에 전체 조회와 base 확보가 끝나 있으므로 dirty 중 `loadTree()`로 초안이 사라지는 일이 없다.
- dirty 동안: "비활성 포함" 토글은 **잠그고**, 저장·삭제·추가(최상위·하위)·초기화 버튼은 비활성화하고 "먼저 반영하거나 취소하세요" 안내. 노드 선택(폼 채우기)은 허용 여부 **리뷰 쟁점 5**(선택은 서버 읽기만 하므로 허용 가능하나 폼이 이후 PATCH와 섞일 수 있음 → 초안 중엔 선택은 허용하되 편집 폼은 읽기 전용).
- 이탈 경고: dirty일 때 `beforeunload`. 반영 성공 시 사이드바는 재로드 후 반영(기존과 같음 — `loadTree()`가 사이드바를 갱신하지 않으므로 반영 성공 메시지에 "새로고침 후 사이드바에 반영" 명시, 또는 반영 성공 시 페이지 재로드).
- 결과 메시지는 기존 `queuedNotice`(트리 영역 알림) 방식을 재사용한다. 409면 "다른 관리자가 먼저 메뉴를 변경했습니다. 서버 상태로 새로고침했습니다." 표시 후 재조회.
- 제거: 이번 작업 중 만든 폼 관련 JS/HTML은 이미 워킹트리에서 제거했으나 커밋 전 변경이다 → PR C에서 일관되게 정리(폼·`handleMoveParent`·`refreshMoveSection`·`lastTreeData` 없음).

### 결정 9 — 구조·권한 불변식 전역 적용 (리뷰 P2-2·P2-6, 사용자 결정 2026-10-01)

**(a) `ord`는 구조 반영 API만 바꾼다.** `MenuUpdateRequest`·`MenuCreateRequest`에서 `ord` 필드를 제거한다(Jackson 기본이 알 수 없는 속성을 무시하므로 낡은 클라이언트가 `ord`를 보내도 에러 없이 무시됨 — 구현 시 `FAIL_ON_UNKNOWN_PROPERTIES` 실제 설정 확인). 생성은 항상 `resolveNextOrd`(맨 끝). 화면의 "순서" 입력(`menuOrderInput`)·`buildPayload`의 `ord`도 제거한다. 변경 시점은 **PR C**(화면과 같은 PR — 폼이 `ord`를 보내는 동안 DTO를 먼저 바꾸면 혼동). 회귀 테스트: "관리자 A가 구조 반영 → 낡은 폼을 연 B가 이름만 수정 → 순서가 되돌아가지 않음".

**(b) 권한 불일치 규칙을 구조 반영·생성·`accessRole` 수정 세 경로에 모두 적용한다.** 규칙: **`ALL` 메뉴의 조상 사슬에 `ADMIN` 메뉴가 있으면 안 된다.**
| 경로 | 검사 | 응답 |
|---|---|---|
| 구조 반영 | 결정 4의 6번(이동된 서브트리 범위) | 400 |
| 하위 생성(`createMenu`) | 새 메뉴가 `ALL`(기본값 포함)인데 부모 포함 조상 사슬에 `ADMIN`이 있음 | 400 |
| `accessRole` 수정 | ① `ADMIN → ALL`로 바꾸는데 자기 조상 사슬에 `ADMIN`이 있음 ② `ALL → ADMIN`로 바꾸는데 자기 서브트리에 `ALL` 자손이 있음 | 400 |
`ADMIN` 아래 `ADMIN`은 허용(전용 그룹의 전용 자식). 기존 위반 행은 **그 행이 관련된 변경이 있을 때만** 걸린다 — 무관한 수정(이름·URL)은 검사하지 않는다.

**(c) 동시성**: 위 세 경로의 검사는 조상·자손을 읽으므로 한 행 잠금으로는 직렬화되지 않는다(조상의 `accessRole` 변경과 자식 생성이 동시에 일어나면 위반이 생길 수 있다). 따라서 **구조 반영·생성·`accessRole`이 포함된 수정은 모두 전체 행 잠금(`findAllForUpdate`, `menuNo` 오름차순)을 첫 조회로 쓴다.** 수정은 요청에 `accessRole`이 있으면(현재 화면은 매번 보낸다) 전체 잠금, 없으면 기존 단일 행 잠금. 이 경로들끼리는 같은 순서로 전체를 잠그므로 교착이 없고, 비활성화·재활성화(자식→부모 개별 잠금)와의 사이만 InnoDB 교착 탐지 → 409(결정 2의 4번 방침)로 둔다. 비용: 생성·수정이 메뉴 테이블 전체에 직렬화되지만 관리자 전용·수십 건 규모라 수용한다 — **리뷰 쟁점 4로 재검증 요청**. 구현은 PR B(서비스 규칙·잠금 + 테스트), 화면 영향은 없다(서버 400 메시지를 폼 오류로 표시).

**(d) B~C 사이 기존 부모 이동 API(리뷰 2라운드 P2-1)**: PR B가 새 불변식을 도입하는 순간부터 기존 `PATCH /{id}/parent`(PR C에서 삭제)도 같은 규칙을 지켜야 한다 — 위반은 동시 실행 없이도 만들어지고 한 번 생기면 API를 지워도 남는다. 그래서 PR B에서 `moveMenu`가 "공용(`ALL`) 서브트리를 `ADMIN` 조상 아래로" 이동하려 하면 **400으로 거부**한다(기존: 허용 + `warnings`). 같은 변경으로 `MenuServiceMoveTest`의 경고 성공 케이스를 거부 케이스로 바꾸고 `MenuMoveResponse.warnings`는 항상 빈 리스트가 된다(필드 삭제는 PR C). `moveMenu`는 기존 두 행 잠금을 유지한다(이 경로는 PR C에서 사라지므로 전체 잠금으로 바꾸지 않는다 — 단 권한 검사에 필요한 조상 사슬은 잠근 새 부모 N의 `upMenuNo`로 판단: 깊이가 2단 고정이라 N이 최상위이므로 조상은 N 하나).

**(e) 생성의 `ord` 오버플로(리뷰 2라운드 P2-2)**: `createMenu`는 전체 행 잠금(결정 9c) 안에서 `resolveNextOrd`로 새 `ord`를 정한다. 같은 부모 그룹의 최대 `ord`가 `Integer.MAX_VALUE`이면 `+1`이 음수로 넘쳐 맨 앞에 놓이므로, 이 경우에만 **그 형제 그룹을 현재 순서(`ord` 오름차순, null 먼저, 동률 `menuNo`) 그대로 `0..n-1`로 재번호한 뒤 새 메뉴를 `n`으로 생성**한다. 이것은 (a)의 "구조는 구조 반영 API만 바꾼다"에 대한 **유일한 명시적 예외**다(순서를 보존하므로 사용자가 본 순서는 달라지지 않는다). PR B에 포함(생성 경로를 전체 잠금으로 바꾸는 PR). 회귀 테스트: 최대 `ord=2147483647` 형제가 있는 그룹에서 생성해도 새 메뉴가 **마지막**이고 기존 형제 상대 순서가 유지됨.

## 알려진 위험·리뷰 쟁점

1. **전체 행 잠금 ↔ 기존 개별 행 잠금 경로(재활성화 자식→부모 등)의 교착 가능성.** 방침: 교착은 409로 허용(가용성), 정합성은 잠금 후 최신값 재검증으로 보장. 이 방침이 맞는지, 더 안전한 순서 규약이 있는지.
2. **기존 위반 데이터(3단 초과·ADMIN 아래 ALL)로 무관한 반영이 막히는 문제** — 변경 서브트리만 검사하는 안(b)이 불변식을 충분히 지키는가.
3. 과거 감사 로그 호환 — `MENU_REORDER`/`MENU_MOVE` 상수 유지가 동기화 테스트·라벨 테스트와 충돌하지 않는가.
4. (결정 9c) 생성·`accessRole` 수정까지 전체 행 잠금으로 직렬화하는 방침의 타당성 — 현재 화면은 PATCH마다 `accessRole`을 보내므로 모든 수정이 전체 잠금이 된다. 잠금 범위를 줄일 대안(조상 사슬만 위에서 아래로 잠금 등)과의 비교, 비활성화·재활성화와의 교착 가능성.
5. dirty 중 노드 선택·폼 편집 허용 범위.
6. 낙관적 검사 `baseOrd` 비교가 **레거시 `ord` null/중복** 행에서 항상 일치하는가(클라이언트가 받은 값을 그대로 돌려주므로 일치해야 하나, 서버가 `ord`를 정규화하는 다른 경로가 동시에 있으면 의도치 않은 409가 늘 수 있다).
7. 초안 편집 중 "비활성 포함" 고정 — 활성 메뉴만 보다 초안을 만들 때 비활성 형제가 요청에서 빠져 집합 불일치로 항상 409가 되는 경로가 없는지.
8. 사이드바 3단 UI(SB Admin 2 중첩 collapse) 모바일/접힘(toggled) 상태에서의 표시.
