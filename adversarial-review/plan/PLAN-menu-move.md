## Context

지금은 메뉴의 부모(`upMenuNo`)를 생성 시에만 정할 수 있고 수정으로 바꿀 수 없다(`Menu.update()`가 부모를 제외, `MenuUpdateRequest`에도 필드 없음). 이동하려면 삭제 후 재생성뿐인데, 그러면 (1) `menuNo`가 바뀌어 감사 로그 `targetId` 참조가 끊기고, (2) 활성 하위 메뉴가 있는 메뉴는 비활성화가 409로 막혀 사실상 이동할 수 없다. 이 계획은 **`menuNo`를 유지한 채 부모를 바꾸는 전용 API**와 화면의 **"상위 변경" 폼**을 추가한다.

### 정찰에서 확정한 사실

| 사실 | 근거 |

| 부모는 생성 시에만 정해지고 수정 경로에 없다. 그래서 지금까지 모든 코드가 **"메뉴의 부모는 불변"** 을 암묵 전제로 썼다 | `Menu.java`(update에 upMenuNo 없음), `MenuUpdateRequest.java` |

## 핵심 쟁점과 결정

> 결정 1~5는 사용자에게 사전 고지한 권장 기본값이며 **승인 단계에서 다시 확정받는다**. 결정 6~9는 설계 중 새로 생긴 사용자 결정 사항이다.

### 결정 1 — 엔드포인트와 요청 형태

`PATCH /admin/api/menus/{id}/parent`, 본문 `{ "upMenuNo": <정수|null> }`(ADMIN 전용). `null`은 **최상위로 승격**을 뜻한다. URI는 명사(`parent`)라 API 컨벤션에 맞고, `PATCH /{id}`와 경로 깊이가 달라 충돌하지 않는다.

**요청 검증 (리뷰 1라운드 P1-2)**: 본문 `{}`는 필드가 "없음"인데 자바 `Long`으로는 `null`과 구분되지 않고, 더 나쁘게는 Jackson의 **기본 강제 변환**이 `""`·`" "`·`"null"` 문자열을 `null`로, `10.9`를 `10`으로 바꿔 **잘못된 입력이 실제 최상위 승격이나 다른 부모 이동이 될 수 있다**(setter 호출 전에 변환됨). 그래서 DTO는 이 필드를 **`JsonNode`로 받아** 원본 토큰을 그대로 검사한다.
- 필드 없음(자바 `null`) → 400
- JSON `null`(`NullNode`) → 최상위 승격
- JSON **정수**(`isIntegralNumber()` && `canConvertToLong()`) → 그 메뉴 번호
- 그 외 전부(문자열 `""`·`" "`·`"null"`·`"10"`, 소수 `10.9`·`10.0`, 불리언, 배열, 객체, 범위를 넘는 정수) → 400 `VALIDATION_ERROR`
- 검증은 DTO의 `@AssertTrue` 메서드(`@JsonIgnore`)로 하고, "명시 여부"를 담는 **별도 필드를 두지 않는다**(클라이언트가 JSON으로 조작할 수 없음).

### 결정 2 — 깊이·이동 가능 범위 (사용자 결정 사항 ①)

사이드바가 2단이므로 **이동 완료 시점의 결과는 항상 2단 이하**여야 한다(생성 API는 여전히 더 깊게 만들 수 있다 — 결정 6). 검증은 **모두 잠근 최신 값**으로 하며, 우선순위(먼저 걸리는 것이 응답)는 다음과 같다(리뷰 1라운드 P2-7). **이 표의 400/404/200은 필요한 두 잠금을 모두 얻는 데 성공했을 때의 검증 순서**이며, 잠금 대기 중 교착이 나면 검증 결과와 무관하게 409(결정 9)가 먼저 나올 수 있다(2라운드 P2-2).

| 순서 | 검사 | 응답 |
|---|---|---|
| 0 | 요청 본문 검증(결정 1) | 400 |
| 1 | N이 T 자신 (락 전, id만 비교) | 400 |
| 2 | (락 획득 — 쟁점 A) T 없음 / N 없음(N이 null이 아닐 때) | 404 |
| 3 | **무변경 판정**: 잠근 T의 `upMenuNo`가 요청과 같음(둘 다 `null` 포함) | **200 무변경**(`ord`·`updateDate` 유지, 경고 없음) — 아래 검사보다 **먼저** |
| 4 | 새 부모 N이 최상위가 아님(`N.upMenuNo != null`) | 400 |
| 5 | T에 **자식이 하나라도 있음**(활성·비활성 무관, `existsByUpMenuNo`) | 400 |
| 6 | 활성 T를 비활성 N 아래로 이동(결정 4) | 400 |
| 7 | 이동(결정 3), 경고 계산(결정 5) | 200 |

- 무변경 판정을 먼저 두는 이유: 자식이 있는 최상위 T에 `{"upMenuNo":null}`을 보내거나 기존 생성 API로 만든 3단 메뉴에 현재 부모를 다시 지정하는 요청이 "이미 원하는 상태"인데 400이 되면 멱등성이 깨진다.
- 순환은 "자식 없는 T" + "N은 최상위" 규칙으로 구조적으로 불가능하다(T가 N의 조상일 수 없음).
- 비활성 자식도 "자식 있음"으로 본다: 비활성 자식이 재활성화될 때 3단이 되기 때문이다. 그래서 `existsByUpMenuNoAndUseYnTrue`가 아니라 **`existsByUpMenuNo`**(신규)를 쓴다.

### 결정 3 — 이동 후 위치

새 부모 아래 **맨 끝**(`형제 max(ord)+1`, 형제가 없으면 0), 최상위 승격도 최상위 형제의 맨 끝. 위치 지정은 재조정 API로 한다(합치면 두 API의 잠금 규약이 섞임). 원래 부모의 남은 형제 `ord`에는 빈 자리가 생기지만 표시 순서(`ord asc, menuNo asc`)는 안 깨지고 다음 재조정이 0..n-1로 정리한다(무해). 계산은 생성과 같은 `resolveNextOrd` 재사용(동시 생성과의 `ord` 중복은 기존과 같이 `menuNo` tie-breaker로 결정적).

### 결정 4 — 활성 불변식

**활성 T를 비활성 N 아래로 옮기면 400**(비활성 T는 비활성 N 아래로 가능). 검증은 **잠근 N의 최신 `useYn`**. N 비활성화(`deactivateMenu`)는 N 행을 잠근 뒤 "활성 자식 존재"를 조회하고, 이동도 N 행을 잠그므로 둘이 직렬화된다(둘 중 하나가 먼저 커밋한 뒤 다른 쪽이 그 결과를 본다).

### 결정 5 — 노출 범위(accessRole) 충돌 경고

**허용하되 응답 `warnings`에 담고 화면이 표시**한다. 조건: N이 `ADMIN` 전용이고 T가 `ALL`(공용) — MANAGER에게는 N이 제외돼 T도 사이드바에서 사라진다. 문구 예: "상위 메뉴가 관리자 전용이라 MANAGER에게는 이 메뉴가 사이드바에 표시되지 않습니다." 최상위 승격에는 경고 없음. 거부하지 않는 이유: 의도된 구성일 수 있고 노출 범위는 표시만 제어한다(실제 접근 차단은 `SecurityConfig`).

### 결정 6 — 생성 API 깊이 검증을 이번 범위에 넣을지 (사용자 결정 사항 ②)

`createMenu`는 깊이를 검증하지 않아 화면의 "선택 아래 하위 추가"로 2단 메뉴 아래에 3단 메뉴를 만들 수 있고, 만들어진 메뉴는 사이드바에서 조용히 사라진다. 이동 API는 "결과는 항상 2단"을 지키므로 생성만 열려 있으면 규칙이 반쪽이다.

| 선택지 | 평가 |
|---|---|
| A. 이번 PR에 포함(생성 시 부모가 최상위가 아니면 400) | 일관성 확보. 하지만 **기존 API 계약 변경(새 400)** 이고 "한 PR = 한 관심사"에서 벗어난다 |
| **B (권장). 이번 범위 밖, 별도 후속 PR** | 이동 PR을 작게 유지. 이동 자체의 안전(자식 검사·잠금)은 생성 검증에 의존하지 않는다(생성이 T 행을 잠그므로 직렬화됨). 남는 구멍은 이번에 새로 생기는 것이 아니라 기존 것 |

**기본값: B.** 알려진 한계로 기록: 이동 뒤 T(이제 2단)에 하위 생성을 하면 3단이 만들어질 수 있다("항상 2단"은 **이동 완료 시점**의 제한이다).

### 결정 7 — 비활성 자식·무변경 이동 (사용자 결정 사항 ③)

- 비활성 자식이 있는 메뉴도 이동 거부(결정 2 검사 5).
- 이미 그 부모 아래에 있는 메뉴를 같은 부모로 옮기는 요청은 **200 무변경**(멱등, 검사 3).

### 결정 8 — 감사 로그

새 액션 `MENU_MOVE`: `AdminActionTypes` 상수 + `ALL` + 활동 로그 화면 라벨("메뉴 상위 변경"). `targetType="MENU"`, `targetIdExpression="menuNo"`.
**기록 계약(리뷰 1라운드 P2-5, 기존 Aspect 계약 그대로)**: 서비스 호출이 **성공하면 SUCCESS + `targetId`=이동한 메뉴 번호**, 서비스 호출이 예외로 끝나면(400 검증·404·409 등) **FAIL + `targetId`=null**(`AdminActionLogAspect.logFailure`는 항상 null). 컨트롤러의 DTO 검증(`@Valid`)에서 거부돼 서비스에 진입하지 않은 요청은 기록되지 않는다. 이전 부모·새 부모는 로그에 남지 않는다(payload 컬럼 없음, 스키마 변경 없이 한계 수용 — 재조정과 동일).

### 결정 9 — 교착을 "409로 종료"하는 계약으로 허용한다 (사용자 결정 사항 ⑤, 리뷰 1라운드 P1-1)

v1은 "전역 순서 `(−깊이, menuNo)` + 사전 읽기 + `TransactionTemplate`"으로 **무교착**을 주장했으나 반례가 성립해 철회한다.

**반례(검증됨)**: 최상위 `N=10`(활성), 최상위 `T=20`(비활성·자식 없음). ① 재조정 R이 루트 목록 `[10,20]`을 읽고 첫 잠금 전에 정지 ② 이동 M이 `10→20` 순서로 잠그고 T를 N 아래로 옮겨 커밋 ③ R이 낡은 목록대로 N(10)을 잠금 ④ 재활성화 U가 T(20)를 잠근 뒤 부모 N(10)을 기다림 ⑤ R이 다음 행 T(20)를 기다림 → **R은 N을, U는 T를 잡고 서로 기다린다.** 원인은 재조정이 "스냅샷으로 정한 잠금 목록"을 그 뒤에 바뀐 계층에서도 그대로 쓰기 때문이며, 부모가 바뀔 수 있는 한 어떤 정적 잠금 순서도 "스냅샷 → 잠금" 구조를 막지 못한다.

| 선택지 | 평가 |
|---|---|
| A. v1 방식(전역 순서 + 사전 읽기 + `TransactionTemplate`) | 반례를 못 막는다(재조정 쪽 잠금 목록이 낡음). 사전 읽기·별도 트랜잭션·재검증으로 복잡도만 늘고 무교착 증명은 불가 — **기각** |
| B. 트리 구조 변경 경로 **전체**에 전역 뮤텍스(고정 앵커 행 또는 `GET_LOCK`) | 무교착이 증명되지만 생성·수정·비활성화·재활성화·재조정 등 **기존 변경 경로를 모두 고쳐야** 하고 동시성이 떨어진다 — 이 PR의 범위·위험을 크게 넘어 **기각** |
| **C (채택). 교착은 InnoDB 탐지로 한쪽을 롤백하고 응답은 409로 종료(기존 핸들러 계약), 정합성은 잠금 후 최신값 검증으로 보장** | 데이터 오염이 아닌 **가용성** 문제로 한정된다. 재시도로 해소. 잠금 순서는 요청의 두 id만으로 정하는 단순 규칙(쟁점 A)이며 사전 읽기·별도 트랜잭션이 없다 |

**계약**: 교착이 나면 InnoDB가 한쪽 트랜잭션을 롤백하고 `PessimisticLockingFailureException`이 `GlobalApiExceptionHandler`를 통해 **409 `RESOURCE_CONFLICT`("동시 변경과 충돌했습니다. 다시 시도해주세요.")** 로 응답한다(기존 핸들러). 롤백된 쪽은 어떤 행도 바꾸지 않는다. 사용자에게 보이는 영향: 아주 드문 동시 조작에서 한 번 실패 메시지가 뜨고 다시 시도하면 된다.

### 쟁점 A — 잠금 규약

**잠글 행**: 이동 대상 T와 새 부모 N(최상위 승격이면 T만). **원래 부모 O는 잠그지 않는다** — T가 O를 떠나는 것은 O의 어떤 불변식도 깨지 않는다(O 비활성화와 경합해도 "활성 자식 존재" 조회가 이동 전이면 409, 후면 통과 — 둘 다 안전).

| 잠글 이유 | 잠금 |
|---|---|
| T에 자식이 동시에 생기는 것 차단(하위 생성이 부모 T 행을 잠금) → "자식 없음" 검사를 최신값으로 | T |
| N이 동시에 비활성화되거나 다른 곳으로 이동되는 것 차단 → "N 활성·N 최상위" 검사를 최신값으로 | N |

**잠금 순서**: 요청의 두 id(`T`, `N`)만으로 정한 **`menuNo` 오름차순**(둘 다 있을 때 작은 쪽 먼저). 사전 읽기·깊이 판정 없음. 이유:
- 같은 형제 집합을 오름차순으로 잠그는 **재조정**과 같은 방향이라, **최상위 형제끼리의 일반적인 동시 조작(루트 재조정 ↔ 최상위 메뉴 이동)** 이 서로 교착하지 않는다(테스트 ⑤가 잘못된 순서를 교착으로 잡는다).
- 이동끼리는 같은 규칙이라 서로 사이클이 없다. 승격이면 잠금은 T 하나.
- 알려진 교착 계열(모두 결정 9의 계약으로 409 종료, 정합성 위반 없음): ① 재조정이 계층 변경 전 스냅샷으로 잠그는 중 이동+재활성화가 겹치는 3자 경합(반례), ② **이미 그 부모 아래인 메뉴의 무변경 이동**과 그 메뉴의 재활성화(재활성화는 자식→부모 순서라 부모 id가 작으면 서로 반대 방향), ③ 이동·재활성화가 둘씩 얽히는 4자 이상 경합, ④ **결국 거부될 이동 요청 ↔ 재활성화**(2라운드 P2-2): 활성 루트 `A=10` 아래 비활성 자식 `B=20`이 있을 때 이동 M이 "A를 B 아래로"(N이 최상위가 아니라 원래는 400)를 요청하고 U가 B를 재활성화하면 `M이 A 잠금 → U가 B 잠금 → M이 B 대기 → U가 A 대기`로 교착 — 사전 계층 변경도 3자·4자 경합도 필요 없고, 거부될 요청이라도 **검증은 두 잠금을 얻은 뒤**라 검증 전에 교착할 수 있다(N이 T의 자식인지는 잠금 전에 알 수 없음). 모두 같은 메뉴를 여러 관리자가 동시에 건드려야 한다.

**잠금 후 최신값 검증**: 모든 검사(결정 2의 3~6)는 잠근 엔티티로 한다. 잠금 조회(`findByIdForUpdate`)가 이 트랜잭션의 **첫 애플리케이션 테이블 조회**이고(연결 획득·`setAutoCommit(false)` 같은 JDBC 트랜잭션 시작 처리는 InnoDB 일관 읽기 스냅샷을 고정하지 않으며, 저장소는 OSIV가 꺼져 있고 `Menu`에 선행 연관 조회 매핑도 없다 — 2라운드 확인) 뒤이은 비잠금 읽기(`existsByUpMenuNo`, `max ord`)는 잠금 획득 뒤에 실행되므로 REPEATABLE READ 스냅샷이 잠금 이후에 만들어져 검사가 최신값을 본다. 즉 "잠금 뒤 조회라서 언제나 최신"이 아니라 **그 전에 비잠금 읽기가 없다는 조건까지 포함해서** 성립하므로 **잠금 전에 비잠금 읽기를 하지 않는다** — 통합 테스트로 순서를 고정.

**감사 커밋 순서**: `moveMenu`는 다른 감사 대상 서비스 메서드처럼 `@Transactional` + `@AdminActionLogged`이며 컨트롤러가 최상위에서 직접 호출한다. `AdminActionLogAspect`의 커밋 순서 보장은 "최상위 트랜잭션 진입점일 때"로 한정된다는 기존 계약(`log/CLAUDE.md`)과 같은 전제이며, 이 메서드를 다른 `@Transactional` 메서드 안에서 참여 호출하지 않는다(현재 호출처는 컨트롤러뿐). 정상 커밋과 커밋 시점 실패에서 감사 SUCCESS/FAIL이 올바르게 남는지 통합 테스트로 확인한다.

### 쟁점 B — 재조정 API 보정(부모 불변 가정 깨짐)

재조정의 잠금 루프는 "스냅샷엔 O의 자식이었지만 잠금 시점엔 다른 그룹"인 행(이동된 T)을 만날 수 있다. **잠근 각 형제의 `upMenuNo`가 요청 `upMenuNo`와 같은지 확인하고, 다르면 409**(적용 없이 롤백)를 추가한다(기존 `siblingsChanged()` 재사용). 이 PR 범위에 포함하는 이유: 부모 이동이 도입하는 새 경합에 대한 필수 보정이며 변경은 검사 한 줄 + 테스트다. 이 검사는 교착을 막지 못한다(결정 9) — **데이터 오염**(다른 그룹 행에 ord 기록)만 막는다.

### 쟁점 C — 응답과 DTO

- 요청 DTO `MenuMoveRequest`: `JsonNode upMenuNo` + `@AssertTrue @JsonIgnore` 검증 메서드 + `@JsonIgnore` 결과 접근자 `Long`(결정 1). Swagger 문서에는 `@Schema(type = "integer", format = "int64", nullable = true)`로 정수·null임을 표시.
- 응답 200 `MenuMoveResponse { menuNo, upMenuNo, ord, warnings }`. 전역 `default-property-inclusion: non_null` 때문에 최상위 결과의 `upMenuNo: null`은 기본적으로 키가 생략되므로 **`upMenuNo`에 `@JsonInclude(ALWAYS)`**를 적용해 **키가 존재하고 값이 `null`**인 것을 계약으로 한다(리뷰 P2-6). `warnings`는 항상 배열(빈 배열 포함). `menuNo`가 최상위에 있어야 감사 Aspect가 `targetId`를 뽑는다.
- `Menu.changeParent(Long upMenuNo, Integer ord, LocalDateTime now)` 도메인 메서드 신규(`upMenuNo`·`ord`·`updateDate`만 변경). `@Setter`/`@DynamicUpdate` 추가 없음.
- 리포지토리: `existsByUpMenuNo(Long)`(파생)만 추가. (v1의 사전 읽기용 `ParentRef` 프로젝션은 사전 읽기 폐기로 삭제.)

### 쟁점 D — 화면: "상위 변경" 폼 (사용자 결정 사항 ④, 설계 제약)

- 제약(UI): Thymeleaf + jstree 3.3.12 + jQuery, 신규 라이브러리 없음. 후보는 최상위 메뉴뿐. #68의 상태 규칙(`treeScope`·`loadSeq`·`selectSeq`·`busy`)을 따르되 아래를 보강한다(리뷰 1라운드 P2-3).
- 메뉴를 선택해 편집 모드일 때만 폼 아래에 **"상위 메뉴 변경"** 영역(`<select id="moveParentSelect">` + `<button id="btnMoveParent">`). 선택지는 **"(최상위)" + `lastTreeData`(현재 그려진 트리 세대의 데이터)의 최상위 메뉴(자기 자신 제외)**, 현재 부모가 미리 선택돼 있다. **후보와 자식 여부는 항상 지금 그려진 트리 세대(`lastTreeData`)에서 계산**하고, 선택한 메뉴가 그 트리에 없으면(예: 필터 변경으로 사라짐) 영역을 비활성화하고 "선택한 메뉴가 현재 트리에 없습니다"를 표시한다.
- 선택한 메뉴에 자식 노드가 있으면(현재 트리 기준) 영역을 비활성화하고 "하위 메뉴가 있는 메뉴는 이동할 수 없습니다"를 표시한다(활성만 보기에서 숨은 비활성 자식은 서버가 400으로 알려 줌).
- 클릭 → 확인 대화상자("‘X’를 ‘Y’ 아래로 옮깁니다. 맨 끝에 배치됩니다.") → `PATCH /admin/api/menus/{id}/parent`(`X-CSRF-TOKEN` 필수).
- **이동 결과(성공 경고·실패 메시지)는 폼이 아니라 트리 영역 알림으로만 표시한다**: 성공 시 `warnings`는 `#treeWarning`(`alert-warning`), 실패는 `#treeAlert`. 이동 중에 다른 메뉴를 선택해도 그 폼에 이 메시지가 뜨지 않는다.
- **`queuedNotice` 메커니즘**(P2-3 b): 이동 핸들러는 결과 메시지를 `queuedNotice = { kind, text }`에 넣고 `resetSelectionState()` 후 `loadTree()`를 부른다. **`loadTree()`가 최신 세대로 실제 적용되거나(성공) 최신 세대로 실패한 시점에** `queuedNotice`를 표시하고 비운다. 더 최신 조회에 밀려 응답이 폐기된 조회는 소비하지 않으므로 메시지는 마지막으로 적용되는 재조회에서 표시된다("`await loadTree()` 뒤에 표시"의 허점 보완). #68의 재조정 실패 메시지도 같은 메커니즘으로 옮긴다(같은 결함 계열, 같은 파일).
- **이동 중 노드 선택 무시**: `busy`인 동안 `handleSelectNode`는 즉시 반환한다(이동 진행 중 새 폼이 채워져 완료 후 초기화되는 혼란 방지). 이동 시작 시 `selectSeq`를 올리고, 필터 변경·재조회 시작 시에도 이미 올라간다(#68 규칙).
- 저장·삭제·재정렬과 `busy`로 상호 배제. 드래그로 다른 부모에 놓는 방식은 만들지 않는다(#68 `check_callback`은 "같은 부모만" 유지).
- **사이드바는 `loadTree()`가 갱신하지 않는다**(서버 렌더링 `AdminSidebarAdvice`, 페이지 로드 때 실행) — 이동 뒤 사이드바 반영은 **페이지 재로드가 필요**하며 화면 문구·검증도 그렇게 다룬다.

## 리스크

- 중간. 잠금 규약이 단순해졌지만(요청의 두 id 오름차순, 사전 읽기 없음) **교착을 409로 허용하는 계약**을 사용자가 수용해야 한다(결정 9). 정합성(불변식)은 잠금 후 최신값 검증으로 보장하고, 일반 경합(루트 재조정 ↔ 최상위 이동)은 테스트 ⑤가 무교착을 확인하며, 알려진 교착은 ⑧이 "잠금 예외는 정확히 하나·HTTP 409는 피해자에 따라 하나 또는 둘·M의 이동 유지·R의 ord 불변·부분 반영 없음"으로 고정한다.
- 화면 상태 규칙이 늘어(`queuedNotice`·`lastTreeData`·`busy` 중 선택 무시) `manage.html` 변경이 작지 않다 → #68의 경쟁 검증을 이동 폼에도 반복하고 재조정 실패 메시지 이관의 회귀를 함께 확인한다.
- 재조정의 실패 메시지 표시 방식을 같은 파일에서 바꾸므로 #68 회귀(409 시 메시지 유지) 확인이 필요하다.
- **사용자 결정·고지 사항**: (1) 화면은 드래그가 아니라 별도 "상위 변경" 폼, (2) 결과는 항상 2단 — 자식 있는 메뉴(비활성 자식 포함)는 이동 거부·새 부모는 최상위 메뉴만, (3) 이동 후 위치는 새 부모 아래 맨 끝, (4) 활성 메뉴는 비활성 부모 아래로 이동 불가, (5) 공용 메뉴를 관리자 전용 부모 아래로 옮기면 허용하되 경고, (6) **생성 API 깊이 검증은 이번 범위 밖**(이동 뒤 2단 메뉴에 하위 생성 시 3단이 생길 수 있음), (7) 이미 그 부모 아래면 200 무변경(자식·깊이 검사보다 먼저 판정), (8) 감사 로그: 성공만 대상 번호 기록·실패는 null·이전/새 부모는 안 남음, (9) **아주 드문 동시 조작에서 교착이 나면 한쪽이 409로 끝나고 재시도하는 계약을 수용**(전역 뮤텍스는 범위·위험 때문에 기각), (10) 재조정 API에 잠근 형제의 부모 재검사 추가, (11) 요청 본문은 정수·`null`만 허용(문자열·소수 등은 400), 이동 결과 메시지는 폼이 아니라 트리 영역에 표시, 사이드바 반영은 페이지 재로드 필요.

## 완료 기준

- [ ] `PATCH /admin/api/menus/{id}/parent`가 T를 N 아래 맨 끝(또는 최상위 맨 끝)으로 옮기고 `menuNo`를 유지하며, 검사 우선순위(결정 2)대로 400/404/200을 반환한다. 무변경은 자식·깊이 검사 앞에서 200이며 `ord`·`updateDate`를 바꾸지 않는다. ADMIN 외 401/403, CSRF 없는 PATCH 403.
- [ ] 요청 본문은 정수 또는 JSON `null`만 허용한다: 필드 없음·`""`·`" "`·`"null"`·`"10"`·`10.9`·`10.0`·불리언·배열·객체·범위 초과 정수는 400이고 서비스를 호출하지 않는다(MockMvc). 최상위 결과 응답에 `upMenuNo` 키가 존재하고 값이 null이다.

- [ ] 재조정과의 경합(정합성): 스냅샷 이후 이동된 형제를 만나면 재조정이 409이고 어떤 ord도 바뀌지 않는다. 루트 재조정 ↔ 최상위 이동(일반 경합)은 교착 없이 완료된다(잘못된 잠금 순서를 이 테스트가 잡음 — 변이 실험으로 확인). **알려진 교착 반례는 잠금 예외가 정확히 하나이고(HTTP 409는 피해자에 따라 하나 또는 둘), 이동은 유지되며 R의 ord는 불변이고 부분 반영이 없다**(통합 테스트, 특정 피해자 선택에 의존하지 않음).
- [ ] 활동 로그: 이동 성공은 `MENU_MOVE` SUCCESS + `targetId`=이동한 메뉴 번호, 서비스 호출 실패는 FAIL + `targetId` null(DTO 검증 거부는 미기록), 커밋 시점 실패에서 SUCCESS가 남지 않는다. 활동 로그 화면에 라벨이 보이고 동기화 테스트가 통과한다.

  - **P2-3 수용** — 이동 결과 메시지를 트리 영역 알림으로 옮기고 `queuedNotice`(재조정 실패 메시지 포함)로 마지막 적용 재조회에서 표시, 이동 중 노드 선택 무시, 후보·자식 여부를 `lastTreeData` 세대 기준으로 계산, 사이드바 반영은 페이지 재로드 필요를 명시.
  - **P2-4 수용(구조 단순화)** — 사전 읽기 폐기로 `TransactionTemplate`이 불필요해져 `@Transactional`로 복귀, "최상위 진입점" 전제는 기존 계약(`log/CLAUDE.md`)과 동일하게 명시하고 정상 커밋·커밋 시점 실패의 감사 결과를 통합 테스트 ⑨로 확인.
  - **P2-5 수용** — FAIL `targetId`는 항상 null인 기존 Aspect 계약대로 완료 기준·결정 8을 "성공=대상 번호, 실패=null"로 정정(Aspect 변경 없음).
  - **P2-6 수용** — `MenuMoveResponse.upMenuNo`에 `@JsonInclude(ALWAYS)`로 키 존재·null을 계약화(전역 `non_null` 때문), 검증 추가.
  - **P2-7 수용** — 무변경 판정을 잠근 최신 T 기준으로 자식·깊이 검사보다 먼저 하도록 우선순위 표를 명시, 자식 있는 최상위·3단 데이터 테스트 추가.
  - 부수 확인 반영 — "항상 2단"은 이동 완료 시점의 제한(생성은 3단을 만들 수 있음)으로 표현, `log/CLAUDE.md`의 감사 대상 메서드 수 갱신을 범위에 추가.
- v3 변경 (2026-09-30, 2라운드 codex no-ship — P2 2건 수용, 기각 없음):
  - P2-1 수용 — 테스트 ⑧과 리스크·완료 기준의 "정확히 한쪽만 409·다른 쪽은 성공"이 쟁점 B의 부모 재검증과 충돌: 이동이 이미 커밋돼 R의 루트 스냅샷에 현재 N의 자식인 T가 들어 있으므로 **R이 교착 피해자가 아니어도 부모 불일치로 409**가 난다. "잠금 예외는 정확히 하나, HTTP 409는 피해자에 따라 하나 또는 둘"로 정정하고, 피해자 (a) R / (b) U 두 경우 모두 M의 이동 유지·R의 ord 불변·U 성공 여부에 맞는 T 활성 상태를 특정 피해자에 의존하지 않고 단언하며 M의 커밋된 이동을 "부분 반영"으로 오인하지 않도록 명시.
  - P2-2 수용 — 교착 계열에 ④ **결국 거부될 이동 요청 ↔ 재활성화**(활성 루트 A 아래 비활성 자식 B에서 "A를 B 아래로" ↔ B 재활성화)를 추가: 사전 계층 변경·3자·4자 경합 없이 성립하는 2자 교착이며 N이 T의 자식인지는 잠금 전에 알 수 없다. 결정 2의 검사 우선순위 표는 "두 잠금을 모두 얻는 데 성공했을 때의 검증 순서"이고 교착 409가 먼저 나올 수 있음을 명시. 결정 9(교착 허용)는 철회하지 않음.
  - 보충 반영 — 정합성 전제 표현을 "이 트랜잭션의 첫 DB 접근"에서 "**첫 애플리케이션 테이블 조회**"로 정정(연결 획득·`setAutoCommit(false)`는 InnoDB 스냅샷을 고정하지 않음), "그 전에 비잠금 읽기가 없다"는 조건까지 포함해 성립함을 명시. 테스트 ⑤는 N의 실제 락 대기 관측 뒤 재조정을 해제, ⑨의 커밋 시점 실패는 서비스 내부 예외가 아니라 **실제 커밋 단계 예외**로 유발(기존 `AdminActionLogCommitOrderIntegrationTest` 방식 재사용).
