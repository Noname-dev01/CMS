# 기능 개발 워크플로우 (사이드바 동적 렌더링 작업에서 정립)

> 작성일: 2026-07-09 (같은 날 적대적 리뷰 단계 추가) · 실증 사례: `sidebar-dynamic-rendering-plan.md`
> 요점 한 줄: **"코드를 읽기 전에 계획하지 않고, 리뷰받지 않은 계획으로 구현하지 않고,
> 승인 없이 스키마를 바꾸지 않고, 테스트 통과로 끝내지 않고 실제 화면으로 확인한다."**

## 단계별 프로세스

### 1. 정찰 — 계획 전에 코드부터 읽는다
- 변경 대상과 그 주변(호출부·유사 패턴·기존 컨벤션)을 실제 파일로 확인한다. 추측 금지.
- 재사용할 기존 패턴을 식별한다 (예: `TestMemberLoader` 시드 패턴, `AdminViewAdvice` 모델 주입,
  `@AllowedRoles` 검증 패턴).
- **테스트 구조도 이 단계에서 본다** — 구현 파급이 테스트에 어디까지 미치는지
  (예: `@WebMvcTest`가 모든 `@ControllerAdvice`를 포함 → 새 advice의 의존 빈이 전 슬라이스에 필요).
- 이 단계의 목표는 "핵심 쟁점 발견"이다 (예: Menu에 역할 필드가 없다 → 스키마 변경 불가피).

### 2. 설계 — 쟁점을 하나씩 결정한다 (sequential-thinking)
- 쟁점별로 선택지 2~3개를 놓고 트레이드오프로 결정한다. 결정에는 반드시 "왜"를 남긴다.
- 과설계를 경계한다 (예: MANAGER 전용 메뉴 개념이 없으므로 2값 enum이 정직한 모델링).
- UI/프레임워크 제약을 설계 제약으로 명문화한다 (예: SB Admin 2는 2단까지 → 2단 렌더링 제한).
- 리스크를 식별한다 (예: 공유 fragment 오류 = 전 화면 장애 → 회귀 검증 필수로 지정).

### 3. 적대적 리뷰 — 구현 전에 계획을 공격받는다 (plan-review-loop 스킬)
- 설계 결과를 **`adversarial-review/plan/PLAN-<기능>.md`로 먼저 저장**한다.
  계획이 파일로 존재해야 리뷰 대상·개정 이력의 원본이 된다.
  해당 작업의 계획서가 `plan/`에 **이미 있으면 새로 만들지 않고 그 문서를 갱신**해
  리뷰 대상으로 쓴다 (`plan/README.md` 인덱스에서 확인).
  (구형 명명 `adversarial-review/<기능>-plan.md`는 2026-07-14 폐기 — 기존 파일은 그대로 두되
  신규 계획은 `plan/PLAN-*.md`로 작성한다.)
- 리뷰 절차의 원본은 **전역 스킬 `~/.claude/skills/plan-review-loop/SKILL.md`**다 (2026-08-27 프로젝트 로컬에서 전역으로 이동 — 다른 프로젝트에서도 재사용). 에이전트가 codex CLI를
  직접 비대화형으로 호출한다 (계획 문서 **전문을 프롬프트에 포함**, 실패 시 1회 재시도 후
  자체 적대적 리뷰로 폴백·출처 명시). 사용자에게 `/codex:adversarial-review` 실행을
  요청하던 구방식(2026-07-12 이전)은 폐기됐다.
  사용자가 직접 시작할 때는 `/plan-review-loop adversarial-review/plan/PLAN-<기능>.md`를 실행한다.
- 리뷰 결과가 돌아오면 **트리아지 전에 리뷰 지적 원문(전체 목록)을 사용자에게 그대로 보여준다**.
  원문이 영어 등 외국어면 **반드시 전체를 한국어로 번역해서 보여준다**
  (코드 식별자·기술 용어는 원형 유지, 내용 누락·축약 금지).
  요약이나 트리아지 결과만 제시하고 원문을 생략하지 않는다 — 사용자가 에이전트의 판단을
  원문과 대조해 검증할 수 있어야 한다.
- 그다음 리뷰 지적을 **트리아지**한다 — 무비판 수용 금지, 리뷰어도 틀릴 수 있다.
  트리아지 제시 시 지적별로 원문을 인용하고 판단을 붙인다:
  - **수용**: 타당한 지적 → 계획에 반영하고 무엇이 바뀌었는지 명시
  - **반박**: 부당하거나 현 단계에 과한 지적 → 근거와 함께 기각 사유를 기록
  - **사용자 결정**: 트레이드오프가 갈리는 지적 → 선택지로 정리해 사용자에게 질문
- 반영 결과는 계획 문서 상단에 **개정 이력**으로 남긴다
  (기존 관행: "vN 변경(리뷰 N차 + 사용자 결정 반영): 결정 1 — ..." 형식,
  `A-1-activity-log-view-plan.md` v5 참조).
- 라운드 반복·종료 판정은 plan-review-loop 스킬의 기준을 따른다: 실질 지적이 소진되어
  ship 판정이 나거나, 새 지적이 전부 기존 수용·기각의 반복이면 종료. "결정 필요" 항목이
  나오면 사용자에게 질문 후 대기, 5라운드 도달 시 남은 쟁점을 정리해 계속할지 질문.

### 4. 승인 — 리뷰를 통과한 계획을 제시하고 확인받는다
- 계획 문서: 핵심 설계 결정(왜 포함) → 작업 단계 → 리스크 순.
  **리뷰 반영 내역(수용/반박/결정 대기)을 함께 요약**한다.
- **스키마 변경·인가 정책 변경은 반드시 사전 고지**하고 명시적 승인을 받는다 (CLAUDE.md 규칙).
- 구현 중 설계를 조정하게 되면(예: nullable Role → MenuAccessRole enum) 이유와 함께
  **즉시 투명하게 보고**하고 진행한다. 몰래 바꾸지 않는다.

### 5. 구현 — 브랜치 + 태스크 분해 + 의존 방향 순서
- GitHub Flow: `feat/…` 브랜치 생성. master 직접 작업 금지.
- 태스크를 5~6개로 분해해 진행 상태를 추적한다.
- **레이어 의존 방향의 안쪽부터 바깥으로**: 도메인(엔티티/enum) → DTO·Service → 시드/설정 →
  웹 계층(advice/controller) → 템플릿·JS.
- 단계 사이에 `./gradlew compileJava`로 빠른 컴파일 검증을 끼워 넣는다.
- 스키마 변경 시 Flyway 마이그레이션 파일(`src/main/resources/db/migration/`)을 함께 작성한다.
  머지된 마이그레이션 파일은 수정하지 않는다 (`docs/migration-guide.md` 참고).

### 6. 테스트 — 신규 케이스 + 구조적 파급 + 전체 통과
- 새 동작마다 테스트 추가: 기본값, 왕복(round-trip), 필터/경계, 레거시 호환(null 정규화) 케이스.
- 1단계에서 파악한 구조적 파급을 처리한다 (예: 슬라이스 테스트 5곳에 목 빈 추가).
- `./gradlew test` 전체 통과가 기준. DB 접속 테스트는 Testcontainers(`MariaDbContainerSupport`)가
  일회용 MariaDB를 자동 기동하므로 로컬 DB 기동·env 주입은 불필요하다 — 실패 시 **Docker 가용성**
  (Docker Desktop 미기동 등)과 코드 문제를 구분해 진단한다.

### 7. 실기 검증 — 테스트 통과 ≠ 화면 동작 (Playwright)
- 골든 패스 순서: 로그인 → 대상 화면 → 핵심 기능 → 데이터 왕복(저장→DB 확인→재조회→원복).
- **역할별 시나리오**: ADMIN과 MANAGER 각각 로그인해 노출 차이 + 숨긴 URL 직접 접근 차단(이중 확인).
- 기존 화면 회귀 확인 + 스크린샷 증적.
- 이상 현상을 만나면 코드를 의심하기 전에 **데이터/환경을 먼저 조회**한다
  (예: 빈 사이드바 = 버그가 아니라 dev DB의 비활성 잔여 데이터).

### 8. 기록 — 문서와 메모리 갱신
- CLAUDE.md 현행화 (낡은 서술 갱신, 신규 API/컴포넌트 반영).
- 3단계에서 저장한 `adversarial-review/plan/PLAN-<기능>.md`에 구현·검증 결과를 갱신
  (Context → 핵심 확정 사항 → 구현 파일 → 검증 결과 → 이슈 → 후속 형식).
  `plan/README.md` 인덱스에 해당 행이 있으면 완료 표시를 갱신한다.
- 비자명한 이슈는 `docs/troubleshooting.md`, 세션성 요령은 메모리에.
- **커밋/PR은 사용자 확인 후** 진행.

## 안티패턴 (하지 않는 것)
- 코드 안 읽고 계획 작성, 추측으로 API 사용
- 리뷰를 건너뛰고 구현 시작, 리뷰 지적의 무비판 수용 또는 근거 없는 무시
- 승인 없는 스키마/인가 정책 변경, 조용한 설계 변경
- 테스트만 돌리고 "완료" 선언 (화면 미확인)
- 무관한 리팩터링 끼워 넣기
- 에러 패턴만 보고 성급한 조치 (원인 데이터 확인 먼저)
