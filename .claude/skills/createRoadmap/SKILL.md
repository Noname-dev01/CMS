# 로드맵 작성 (프로젝트 전체 분석 → 개선 작업 발굴 → 로드맵 정리)

추가 지시사항: $ARGUMENTS

## 상시 규칙

- 모든 출력은 **한국어**.
- 확인되지 않거나 확실하지 않은 부분은 추측하지 말고 질문한다.
- 파일 경로·클래스명은 **실제 코드를 읽고 확인한 것만** 적는다. 추측한 경로 금지.

## 절차

1. **[분석]** 프로젝트를 전체적으로 훑어 개선 후보를 수집한다. 다음 관점을 모두 포함한다:
   - **기능 추가**: CLAUDE.md·계획 문서에 미구현으로 명시된 기능 (현재 코드와 대조해 여전히 유효한지 확인)
   - **리팩토링**: 중복 코드, 레이어 위반, 컨벤션 불일치, 커진 클래스/메서드
   - **보안·안정성**: 인가 누락, 검증 부재, 트랜잭션 경계 문제 등 방치 비용이 큰 결함
   - **테스트·인프라**: 테스트 공백, CI/빌드 개선 여지
   - 코드베이스의 `TODO`/`FIXME` 주석
   - GitHub 열린 이슈/PR: `gh issue list`, `gh pr list`
   - 기존 계획 문서: `adversarial-review/*.md`, `docs/` 하위 계획류 — 계획만 있고 미착수인 항목
   - 기존 `adversarial-review/project-direction-roadmap.md`의 미완료 항목
2. **[선정·우선순위]** 후보 중 로드맵에 올릴 작업을 고르고 레버리지 기준으로 우선순위를 매긴다 (기본 5개 내외, 후보가 많고 가치가 분명하면 더 담아도 된다):
   - 다른 작업의 선행 조건을 풀어주는가 (의존성 해소)
   - 보안·데이터 정합성 등 방치 비용이 큰가
   - 사용자 가치 대비 구현 범위가 합리적인가
   각 항목에 유형(기능 추가/리팩토링/보안/테스트 등)과 선정 이유를 한 줄로 남기고, 아깝게 탈락한 후보도 간단히 언급한다.
3. **[로드맵 작성]** 선정한 작업을 `adversarial-review/project-direction-roadmap.md`에 정리한다.
   각 항목에 **반드시 포함**:
   - **유형** — 기능 추가 / 리팩토링 / 보안 / 테스트·인프라 등
   - **목표** — 완료 시 무엇이 가능해지는지 한 문단
   - **수정해야 할 정확한 파일** — 실제로 읽고 확인한 경로 목록 (신규 파일은 "신규" 표시)
   - **단계별 작업 순서** — 의존 방향 안쪽(도메인)부터, 스키마 변경 시 Flyway 마이그레이션 단계 포함
   - **완료 기준** — 테스트·실기 검증 등 객관적으로 판정 가능한 조건 (updateRoadmap이 이 기준으로 사실확인한다)
   기존 로드맵 파일이 이미 있으면: 완료 이력은 보존하고, 기존 미완료 항목과 겹치는 신규 항목은
   병합·갱신한다. 기존 항목을 로드맵에서 내리게 될 경우 임의로 삭제하지 말고 질문한다.
4. **[보고]** 작성한 로드맵을 우선순위 순으로 요약 보고하고 종료한다.
   다음 작업 선택이 필요하면 `/suggestRoadmap` 실행을 안내한다.
   이 스킬이 스스로 구현에 착수하지 않는다.

## 세 스킬의 역할 구분

- **createRoadmap**: 로드맵의 최초 작성 또는 전면 재구성 (프로젝트 전수 분석 수반)
- **suggestRoadmap**: 미완료 항목 중 다음 작업 후보 3개 추천 → 사용자 선택 → `/feature` 연결
- **updateRoadmap**: 완료한 작업을 사실확인 후 완료로 반영
