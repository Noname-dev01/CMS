# 로드맵 갱신 (완료 작업 사실확인 → 완료 반영)

완료한 작업: $ARGUMENTS (비어 있으면 `git log`와 최근 머지된 PR에서 추론하고, 어떤 작업을 완료 처리할지 먼저 확인받는다.)

## 상시 규칙

- 모든 출력은 **한국어**.
- 로드맵에 없는 작업을 임의로 추가하거나 항목을 삭제하지 않는다 — 상태 갱신만 한다.
- **사실확인 없이 완료 처리하지 않는다.** 주장이 아니라 코드·테스트·git 이력이 근거다.
- 확실하지 않으면 추측하지 말고 질문한다.

## 절차

1. **[로드맵 읽기]** `adversarial-review/project-direction-roadmap.md`를 읽는다.
   파일이 없거나 위치가 바뀌었으면 `adversarial-review/`에서 roadmap 문서를 찾고, 그래도 없으면 질문한다.
2. **[완료 후보 식별]** 완료 처리할 항목을 식별한다. 인자가 없으면 `git log`·머지된 PR에서 추론하되,
   어느 항목을 완료 처리할지 사용자에게 먼저 확인받는다. 로드맵의 어느 항목인지 애매하면 후보를 제시하고 질문한다.
3. **[사실확인]** 각 완료 후보에 대해 로드맵에 적힌 **완료 기준**을 실제로 검증한다:
   - 해당 파일·클래스가 실제로 존재하고 로드맵의 목표대로 구현되었는지 코드를 읽어 확인
   - 관련 테스트가 존재하고 통과하는지 확인 (필요 시 `./gradlew test --tests "..."` 실행)
   - 관련 커밋/PR이 실제로 머지되었는지 git 이력으로 확인
   기준을 **모두 충족한 항목만** 완료 처리한다. 일부만 충족했으면 부분 완료 상태와 남은 작업을 명시하고,
   완료 처리 여부를 질문한다.
4. **[완료 반영]** 검증을 통과한 항목을 완료 상태로 표시한다 (기존 문서의 표기 방식을 그대로 따른다 —
   체크박스·상태 컬럼 등). 완료 날짜와 관련 PR 번호가 확인되면 함께 기록한다.
5. **[부수 완료 점검]** 남은 미완료 항목 중 이번 작업에 딸려 함께 해결된 항목이 있으면 지적한다
   (임의 완료 처리하지 않고 3번과 동일한 사실확인 + 사용자 확인 후 반영).
6. **[보고]** 완료 반영 결과(항목·근거·날짜/PR)를 요약 보고하고 종료한다.
   다음 작업 선택이 필요하면 `/suggestRoadmap` 실행을 안내한다.

## 세 스킬의 역할 구분

- **createRoadmap**: 로드맵의 최초 작성 또는 전면 재구성 (프로젝트 전수 분석 수반)
- **suggestRoadmap**: 미완료 항목 중 다음 작업 후보 3개 추천 → 사용자 선택 → `/feature` 연결
- **updateRoadmap**: 완료한 작업을 사실확인 후 완료로 반영
