# 커밋 → PR 생성 워크플로우

추가 지시사항: $ARGUMENTS

## 상시 규칙

- 모든 출력·커밋 메시지·PR 제목/본문은 **한국어** (코드 식별자·기술 용어는 원형 유지).
- 커밋 메시지 접두사는 기존 이력 스타일을 따른다: `기능:` `수정:` `정리:` `문서:` 등 + 명사형 요약.
- **커밋 실행 전 반드시 분할 계획을 보여주고 승인을 받는다.** 승인 없이 커밋·push·PR 생성 금지.

## 절차

1. **[현황 파악]** `git status`, `git diff`, 최근 커밋 이력을 확인한다. 변경이 없으면 그 사실을 보고하고 종료한다.
2. **[제외 대상 점검]** 다음은 커밋에 포함하지 않는다. 스테이징돼 있으면 계획에서 빼고 그 사실을 보고한다:
   - `adversarial-review/` 계획 문서 (.gitignore 대상 — 실수로 추적 중이면 경고)
   - 빌드 산출물 (`build/`, `src/main/generated/`), IDE 설정, `.env*` 등 민감 파일
3. **[커밋 분할 계획]** 변경을 **작업 단위별로 세분화**해 계획을 제시한다. 커밋마다:
   - 커밋 메시지 초안 (한국어, 접두사 포함)
   - 포함 파일 목록
   - 분할 근거 한 줄
   서로 무관한 변경을 한 커밋에 섞지 않는다. 계획 제시 후 **승인을 기다린다.**
4. **[브랜치 확인]** 현재 `master`면 변경 성격에 맞는 브랜치를 먼저 만든다
   (`feat/` `fix/` `refactor/` `security/` `test/` `chore/` + kebab-case). master 직접 push 금지.
5. **[커밋 실행]** 승인받은 계획대로 커밋한다. 계획에 없던 파일이 새로 생겼으면 멈추고 질문한다.
6. **[PR 생성]** push 후 `gh pr create`로 PR을 생성한다. base는 `master`.
   본문 구성: 요약(변경 이유 포함) → 주요 변경사항 → 테스트 내역 (`./gradlew test` 결과 등).
   PR URL과 함께 결과를 보고한다. CI 확인·squash merge·브랜치 삭제는 사용자 몫임을 안내하고,
   **머지가 끝나면 `/updateRoadmap`으로 로드맵 완료 반영**을 하라고 함께 안내한다
   (updateRoadmap의 사실확인은 머지 여부를 검증하므로 머지 전에 실행하면 완료 처리되지 않는다).

## 금지 사항

- `--no-verify`, force push 금지.
- 커밋 분할 계획에 없던 리팩터링·정리 커밋을 끼워 넣지 않는다.
