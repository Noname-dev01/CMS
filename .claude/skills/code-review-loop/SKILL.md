# 코드 적대적 리뷰 루프 (feature → **code-review-loop** → commitPR)

리뷰 초점(선택): $ARGUMENTS

## 상시 규칙 (매 라운드 공통 — 사용자가 다시 말하지 않아도 항상 적용)

- 모든 출력은 **한국어**. 리뷰 원문이 영어면 전체를 한국어로 번역해 보여준다 (코드 식별자·기술 용어는 원형 유지, 누락·축약 금지).
- 리뷰 결과는 **원문 전체를 먼저 보여준 뒤** 트리아지한다. 요약만 제시하고 원문을 생략하지 않는다.
- 확인되지 않거나 확실하지 않은 부분은 추측하지 말고 질문한다.
- 이 스킬은 **커밋·push·PR 생성을 하지 않는다** — 그건 `/commitPR` 담당. 여기서는 워킹 트리 수정까지만.
- 지적 반영 시 무관한 리팩터링을 끼워 넣지 않는다.

## 리뷰 실행 방법

`/codex:review` 명령은 `disable-model-invocation: true`라 Skill 도구로 호출할 수 없다.
대신 동일한 실체인 codex-companion 스크립트를 Bash로 직접 실행한다:

1. **스크립트 경로 해석**: `CLAUDE_PLUGIN_ROOT`가 설정돼 있으면 `${CLAUDE_PLUGIN_ROOT}/scripts/codex-companion.mjs`.
   아니면 Glob으로 `~/.claude/plugins/cache/openai-codex/codex/*/scripts/codex-companion.mjs`를 찾아
   **가장 높은 버전 디렉터리**를 선택한다 (플러그인 업데이트로 버전 경로가 바뀔 수 있으므로 경로 하드코딩 금지).
2. **실행** (foreground, 리뷰는 수 분 걸릴 수 있으므로 timeout 600000):
   ```bash
   node "<해석된 경로>/codex-companion.mjs" review "--wait --scope working-tree"
   ```
   - 커밋 전 워킹 트리 변경을 리뷰하는 것이 기본. 이미 커밋된 브랜치를 리뷰해야 하면 `--scope branch --base master`.
   - 사용자가 리뷰 초점을 전달했으면 `review` 대신 `adversarial-review` 서브커맨드를 쓰고 초점 텍스트를 뒤에 붙인다
     (`review`는 초점 텍스트를 지원하지 않는다).
3. **폴백**: 실행이 실패하면 1회 재시도하고, 그래도 실패하거나 스크립트/CLI가 없으면
   **직접 적대적 코드 리뷰를 수행**하고 출처가 codex가 아닌 자체 리뷰임을 명시한다.
   (관점: 인가·경계 검증 누락, 데이터 정합성, 트랜잭션·동시성, 실패 경로, CSRF 누락, 회귀 위험)
   실패를 이유로 라운드를 중단하지 않는다.

## 라운드 절차

0. **[사전 확인]** (첫 라운드만) `git status`로 리뷰할 변경이 있는지 확인한다. 워킹 트리가 깨끗하고
   브랜치 diff도 없으면 그 사실을 보고하고 종료한다.
1. **[리뷰 실행]** 위 "리뷰 실행 방법"대로 리뷰를 돌린다.
2. **[원문 표시]** 리뷰 결과 전체(verdict·요약·지적사항, 파일 경로·라인 번호 원형 유지)를 한국어로 그대로 보여준다.
3. **[트리아지]** 지적별로 원문을 인용하고 판단을 붙인다:
   - **수용** (타당) → 반영 예정 수정 내용 명시
   - **반박** (부당/과함/오탐) → 근거와 함께 기각 사유 기록
   - **결정 필요** (트레이드오프가 사용자 몫) → 선택지로 정리해 질문하고, 답을 받을 때까지 해당 항목 반영 보류
4. **[반영]** 수용 항목을 코드에 반영한다:
   - 수정 후 `./gradlew compileJava`로 컴파일 확인, 영향받는 테스트를 실행한다.
   - 수정이 설계 변경 수준으로 커지면(스키마·인가 정책·API 계약 변경) 반영하지 말고 멈춰서 보고한다.
   - 라운드별 트리아지 결과(수용/기각과 사유)를 대화에 기록해 다음 라운드 리뷰가 같은 지적을 반복하면 식별할 수 있게 한다.
5. **[종료 판정]** 다음 중 하나면 루프를 멈춘다. 아니면 1로 돌아가 다음 라운드를 자동 진행한다:
   - 리뷰가 실질적 지적 없이 통과(approve/지적 0건)했다 → **[마무리]**로
   - 새 지적이 전부 이전 라운드에서 기각·수용 완료된 내용의 반복이다 → 동일하게 통과 처리, **[마무리]**로
   - **결정 필요** 항목이 나왔다 → 질문 후 대기
   - 5라운드에 도달했다 → 남은 쟁점을 정리해 보고하고 계속할지 질문

## 마무리 (→ /commitPR 연결)

1. `./gradlew test` 전체를 실행해 최종 그린 상태를 확인한다. 실패하면 원인을 진단하고 해결 후 재확인한다.
2. 루프 결과를 요약 보고한다: 총 라운드 수, 수용·기각·보류 건수, 반영으로 바뀐 파일 목록.
3. `/commitPR`로 넘어갈지 질문하고, 사용자가 동의하면 **Skill 도구로 `commitPR` 스킬을 호출**한다
   (커밋 분할 승인 등은 commitPR 자체 절차가 처리한다). 동의 없이 스스로 커밋 단계로 넘어가지 않는다.

## 금지 사항

- 리뷰 지적의 무비판 수용 금지 — 모든 수용에는 "왜 타당한지"를 한 줄이라도 붙인다.
- 리뷰를 실행하지 않고(폴백 자체 리뷰 포함) 통과를 주장하지 않는다.
- 결정 필요 항목을 임의로 판단해 반영하지 않는다.
