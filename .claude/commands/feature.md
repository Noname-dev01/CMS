다음 작업을 구현해줘: $ARGUMENTS

작업 방식은 docs/development-workflow.md의 8단계 워크플로우를 그대로 따라줘. 특히:

1. **[정찰]** 계획을 세우기 전에 관련 코드를 실제로 읽어줘 — 변경 대상, 재사용할 기존 패턴,
   그리고 테스트 구조(구현 파급이 테스트 어디까지 미치는지)까지. 추측 금지.
   이 단계의 목표는 "핵심 쟁점 발견"이야.
2. **[설계]** 쟁점별로 선택지 2~3개와 트레이드오프를 놓고 결정하고, 모든 결정에 "왜"를 남겨줘.
   과설계를 경계하고, UI/프레임워크 제약은 설계 제약으로 명문화해줘.
3. **[적대적 리뷰]** 설계 결과를 adversarial-review/plan/PLAN-<기능>.md로 저장한 뒤
   (해당 작업의 계획서가 adversarial-review/plan/에 **이미 있으면 새로 만들지 말고 그 문서를
   갱신해 리뷰 대상으로 사용**해줘 — plan/README.md 인덱스에서 확인),
   `plan-review-loop` 스킬(.claude/skills/plan-review-loop/SKILL.md)의 라운드 절차를 그대로 수행해줘 —
   codex CLI 직접 호출(계획 문서 전문 포함, 실패 시 1회 재시도 후 자체 리뷰 폴백) →
   리뷰 원문 전체를 한국어로 표시 → 지적별 트리아지(수용/반박/결정 필요) →
   계획 반영 + 개정 이력("vN 변경: ..." 형식, 기각 사유 포함) → ship 판정까지 라운드 반복.
   상시 규칙·종료 판정·금지 사항도 해당 스킬 문서를 따라줘.
   ship 판정이 나면 루프를 멈추고 4단계(승인)로 넘어가줘.
4. **[승인]** 리뷰를 통과한 계획을 핵심 설계 결정(이유 포함) → 작업 단계 → 리스크 순으로,
   리뷰 반영 내역(수용/반박/결정 대기) 요약과 함께 제시하고 내 승인을 받은 뒤에만
   코드를 수정해줘. 스키마 변경·인가 정책 변경은 반드시 별도로 고지해줘.
5. **[구현]** feat/ 브랜치를 만들고 태스크를 분해한 뒤, 도메인 → DTO·Service → 웹 계층 →
   템플릿·JS 순서(의존 방향 안쪽부터)로 구현해줘. 단계 사이에 ./gradlew compileJava로
   컴파일 확인해줘. 스키마 변경 시 Flyway 마이그레이션 파일
   (src/main/resources/db/migration/)을 함께 작성해줘 — 머지된 마이그레이션 파일 수정 금지.
6. **[테스트]** 새 동작마다 테스트를 추가(기본값·왕복·경계·레거시 호환)하고
   ./gradlew test 전체를 통과시켜줘. 실패 시 환경 문제(DB 미기동, env 오염)와
   코드 문제를 구분해 진단해줘.
7. **[실기 검증]** Playwright로 ADMIN/MANAGER 각각 로그인해서 골든 패스 → 데이터 왕복
   (저장→DB 확인→원복) → 숨긴 URL 직접 접근 차단 → 기존 화면 회귀를 확인하고
   스크린샷을 남겨줘. 이상 현상은 코드보다 데이터/환경을 먼저 의심해줘.
   Playwright를 쓸 수 없는 환경이면 그 사실을 명시하고 완료를 주장하지 마.
8. **[기록]** CLAUDE.md를 현행화하고, 3단계의 adversarial-review/plan/PLAN-<기능>.md에
   구현·검증 결과를 갱신해줘 (Context → 핵심 확정 사항 → 구현 파일 → 검증 결과 →
   이슈 → 후속 형식). plan/README.md 인덱스에 해당 행이 있으면 완료 표시도 갱신해줘.
   커밋/PR은 내가 확인한 뒤에만 — 진행 시 `/code-review-loop`로
   코드 리뷰 게이트를 먼저 통과한 뒤 `/commitPR`로 처리해줘.

공통 원칙:
- 구현 중 계획과 달라지는 결정이 생기면 이유와 함께 즉시 보고하고 진행해줘.
- 무관한 리팩터링을 끼워 넣지 마.
- 에러 패턴만 보고 성급하게 조치하지 말고 원인 데이터를 먼저 확인해줘.
