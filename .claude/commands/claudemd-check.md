CLAUDE.md를 실제 코드베이스와 대조해 검증하고, 승인받은 사실 오류/누락만 반영해줘.
**검증 → 승인 → 반영** 3단계로 진행하고, 승인 전에는 CLAUDE.md를 절대 수정하지 마.

검증 대상:
- 기본 대상: 프로젝트 루트 CLAUDE.md
- 추가로 사용자가 지정한 대상 또는 범위: $ARGUMENTS (비어 있으면 CLAUDE.md 전체만)

# 1단계: 검증 + 리포트

중요:
- 추측하지 말고 실제 파일을 열어서 확인해.
- **"미확인"은 코드만 읽어서는 확인할 수 없는 항목에만 허용한다** — 예: 실제 기동해야 아는 런타임 동작,
  외부 서비스(SMTP 등) 의존 동작, DB를 띄워야 아는 데이터 상태. 파일을 열어 확인할 수 있는 항목은
  끝까지 열어 확인하고 미확인으로 남기지 마. 불가피하게 미확인으로 남긴 항목에는
  "왜 확인 불가인지 + 확인하려면 무엇이 필요한지(실행 명령 등)"를 반드시 병기해.
  (과거 3회 실행 모두 "미확인 마저 확인해줘" 재요청이 발생했다 — 미확인 남발이 원인.)
- 현재 코드와 맞지 않는다고 해서 지향 규칙을 낮추지 마.

## 1-A. 사실 항목 검증

다음 항목이 실제 코드와 맞는지 확인해줘.

- 패키지 구조
- 클래스명
- 주요 설정 파일
- 엔드포인트 경로
- 컨트롤러 매핑
- DTO / Request / Response 클래스
- 도메인 모델
- Enum 값
- Repository / Service 구조
- 보안 설정
- Spring Security matcher
- CSRF 설정
- 인증 / 인가 흐름
- 예외 처리 구조
- API 응답 형식
- 테스트 코드에 명시된 계약
- 빌드 / Gradle / QueryDSL / Swagger(SpringDoc) 설정 — Spring REST Docs는 이 프로젝트에서 사용하지 않음
- Flyway 마이그레이션 관련 기술 (마이그레이션 파일 목록·버전과 CLAUDE.md 설명 일치 여부)
- 프로파일별 설정
- 기타 CLAUDE.md에 사실처럼 적힌 내용

각 항목을 다음 중 하나로 분류해줘: 정확함 / 사실 오류 / 사실 누락 / 애매함 / 미확인

사실 오류 또는 사실 누락은 다음 형식으로 작성해줘.

- 위치:
- 현재 CLAUDE.md 내용:
- 실제 코드 확인 결과:
- 왜 문제인지:
- 권장 수정 문안:

## 1-B. 지향 규칙 검증

다음 항목은 "현재 코드의 사실"이 아니라 "앞으로의 목표 / 규칙"으로 취급해줘.

- RESTful 설계 규칙
- 코딩 컨벤션
- API 명명 규칙
- 마이그레이션 표
- 향후 리팩토링 방향
- 테스트 작성 원칙
- 보안 강화 원칙
- 운영 안전성 원칙

중요:
- 지향 규칙은 현재 코드와 달라도 CLAUDE.md를 현재 코드에 맞춰 낮추지 마.
- 대신 현재 코드 중 이 규칙을 아직 따르지 않는 부분을 목록으로 알려줘.
- 지향 규칙 자체가 모호하거나 위험하면 "규칙 개선 후보"로만 분리해줘.
- 1-B 항목은 CLAUDE.md 수정 대상으로 판단하지 마.

## 1-C. 리포트 저장

리포트를 아래 형식으로 `adversarial-review/claude-md-verification-<YYYY-MM-DD>.md`에 저장해.
같은 날짜 파일이 이미 있으면 덮어쓰지 말고 `-2`, `-3` 접미사를 붙여.

# 2단계: 승인

- 반영 대상(사실 오류/누락)이 **0건이면** 그 사실을 보고하고 여기서 종료해.
- 1건 이상이면 반영 대상 목록과 각각의 수정 문안을 제시하고 **사용자 승인을 기다려**.
  일부만 승인하면 승인된 항목만 반영해.

# 3단계: 반영 (승인 후에만)

## 수정해도 되는 것

- 사실 오류: 패키지 구조, 클래스명, 존재하지 않는 클래스/파일 언급, 엔드포인트 경로,
  도메인 모델 필드, Enum 값, 보안·CSRF 설정, 예외 처리 흐름, API 응답 계약,
  Gradle / QueryDSL / Swagger / Flyway 설정, 프로파일 설정에 대한 잘못된 설명
- 사실 누락 중 향후 작업자에게 필요한 내용

## 수정하면 안 되는 것

- RESTful 설계 목표, 코딩 컨벤션, 마이그레이션 표, 향후 리팩토링 방향,
  테스트 작성 원칙, 보안 강화 원칙, 운영 안전성 원칙
- "현재 코드는 아직 안 따르지만 앞으로 지켜야 하는 규칙"
- 단순 취향 문구, 검증되지 않은 추정

## 반영 규칙

- 수정 직전에 해당 실제 파일을 다시 열어 최종 확인 후 반영해 (리포트 작성 시점과 달라졌을 수 있다).
- 승인받지 않은 항목, 확인 못 한 항목은 수정하지 마.
- 반영 후 다음을 보고해:
  - 수정 요약 (반영한 오류/누락 목록)
  - 반영하지 않은 항목과 이유
  - 지향 규칙을 현재 코드에 맞춰 낮춘 부분이 없는지 자가 점검 결과
- 반영 완료 후 저장해둔 검증 리포트 하단에 "반영 결과" 섹션을 추가해 어떤 항목이 언제 반영됐는지 기록해.
