## 로그인 상태 유지 없음 (2026-11-12 제거 — `adversarial-review/plan/PLAN-remember-me-removal.md`)

관리자 세션은 **폼 로그인만** 만든다. 2026-11-10~12에 넣었던 로그인 상태 유지(remember-me 영속 토큰 7일, #225·#227)와 그 위의 민감 작업 재인증(비밀번호 모달·`@RequireFullAuthentication`·재인증 API, #228·#230)·세션 화면의 같은 기기 안내(#231)는 **모두 제거했다**(사용자 결정 — 관리자 페이지라 쿠키 탈취 시 7일 읽기·수정 노출을 남기지 않는다). 토큰 테이블은 V16이 지운다(평문 토큰). URL 접근 규칙(위 표)은 바뀌지 않았다.

- **다시 넣으려면** 새 계획부터 세운다. 옛 설계(폐기 표·사후 검증·탈취 처리·재인증 승격 순서)는 `PLAN-remember-me-login.md`·`PLAN-sensitive-reauthentication.md`·`PLAN-content-delete-reauthentication.md`와 `docs/troubleshooting.md`의 두 항목(Spring Security 7 remember-me 함정, 세션 ID 교체와 레지스트리 만료 표시)에 남아 있다. 세션을 끊는 모든 경로가 쿠키로 되살아나지 않게 묶는 일이 핵심이었다.
- **이미 발급된 `remember-me` 쿠키**는 읽는 필터도 DB 행도 없어 효과가 없다(지우지 않는다). 필터 체인에 `RememberMeAuthenticationFilter`가 없음은 `RememberMeRemovalIntegrationTest`가 고정한다.
- 세션 유휴 만료는 Boot 기본 30분이다(별도 설정 없음).

### 같은 세션의 폼 로그인 직렬화 (`LoginSessionMutexFilter`, #228 도입 → 2026-11-12 독립 방어로 유지)

- Spring Security 7.0.7은 폼 로그인의 세션 ID 교체만 세션 뮤텍스 안에서 하고, 레지스트리 등록·컨텍스트 저장·성공 처리기는 그 밖에서 한다. 같은 세션의 두 탭이 **서로 다른 계정**으로 동시에 로그인하면 "실제 인증 회원 ≠ 레지스트리 회원"인 세션이 남을 수 있고, 강제 만료는 레지스트리에서 회원의 세션을 찾으므로 그 세션은 실제 회원이 강등·비활성화돼도 끊기지 않는다(요청마다 상태를 다시 보는 장치가 없고 `ROLE_ADMIN`은 DB를 보지 않는다). ADMIN은 두 번째 계정을 직접 만들 수 있어 혼자서도 이 상태를 만들 수 있다.
- 그래서 `LoginSessionMutexFilter`(빈 아님, `UsernamePasswordAuthenticationFilter` 앞)가 **세션이 이미 있는** `POST /admin/login`의 나머지 체인을 `WebUtils.getSessionMutex(session)` 안에서 실행한다(재진입이라 Spring 전략과 교착하지 않음). 비용은 같은 세션의 로그인끼리 BCrypt·DB 시간 동안 줄을 서는 것뿐이다.
- 시험: `LoginSessionMutexFilterTest`(뮤텍스 보유·통과 대상), `ConcurrentFormLoginIntegrationTest`(레지스트리 등록 직전에 스파이로 멈춰 다른 탭 로그인이 뮤텍스에서 기다림을 `Thread.State`로 확인 → 컨텍스트 회원 = 레지스트리 회원 → 그 회원 만료로 401. 변이: 필터 등록 제거 → 실패). 실제 서버에서 이 경합이 얼마나 쉽게 나는지는 측정하지 않았다. 경위는 `docs/troubleshooting.md` "세션 ID를 바꾸면 이미 만료 처리한 세션이 되살아날 수 있다 / 폼 로그인의 레지스트리 등록은 세션 뮤텍스 밖이다".

## 무인증 공개 엔드포인트 레이트리밋

- **무인증 공개 엔드포인트 레이트리밋** (`cms.rate-limit.*`, `com.cms.config.ratelimit`, 2026-08-12 도입): `/{siteKey}/notices/**`(GET·HEAD)·비밀번호 재설정 API 2종(POST)에 토큰 버킷 기반 최소 방어를 적용한다. "N회/기간"은 버스트 상한 N + 평균 N/기간을 뜻하며(엄격한 슬라이딩 상한 아님), 정확한 유량 계약을 보장하는 게이트웨이가 아니다. 저장소는 Caffeine(`maximumSize` + 버킷별 `Expiry`)이며, **fail-open을 운영 위험으로 명시 수용**한다 — 캐시가 포화되는 극단적 상황(대량 IP 회전 공격 등)에서는 개별 IP의 정확한 누적치 보장이 흐트러질 수 있다(메모리 상한·무제한 신규 키 수용·IP별 완벽한 정확성을 동시에 요구하려면 Redis 같은 외부 원자적 저장소가 필요하나 이번 범위·인프라 제약을 벗어나 기각). 필터는 `CsrfFilter` **다음**에 위치한다 — CSRF 검증 실패 요청이 quota를 소비하면 외부 사이트가 피해자 브라우저로 토큰 없는 form POST를 반복시켜 피해자 IP의 quota를 고갈시키는 교차 사이트 공격이 가능해지기 때문이다. 키는 `request.getRemoteAddr()` 고정(`X-Forwarded-For` 등은 위조 가능해 미사용). 상세 설계·리뷰 이력은 `adversarial-review/plan/PLAN-public-endpoint-rate-limit.md` 참조. **예외 1건(2026-11-02 승인, `PLAN-content-image-rate-limit.md`)**: 규칙 설정 `exempt-authenticated: true`인 규칙은 로그인한(익명이 아닌) 요청이 버킷을 쓰지 않고 통과한다 — 현재 `content-image`(`/content-images/*`) 하나뿐이고(`SitePublicRateLimitConventionTest`가 고정), 관리 편집기(Quill) 이미지는 스크립트로 자리표시를 만들 수 없어 같은 IP 익명 방문자가 버킷을 비우면 깨지던 문제의 해법이다. 익명 한도(240/60초)·URL 인가 규칙은 불변이고 면제는 다음 규칙 평가로 넘어가지 않는다. 공개 상세 본문 이미지는 외부 스크립트 `board-content-image-fallback.js`가 실패 시 안내 상자로 바꾼다.
