## 로그인 상태 유지 없음 (2026-11-12 제거 — `adversarial-review/plan/PLAN-remember-me-removal.md`)

관리자 세션은 **폼 로그인만** 만든다. 2026-11-10~12에 넣었던 로그인 상태 유지(remember-me 영속 토큰 7일, #225·#227)와 그 위의 민감 작업 재인증(비밀번호 모달·`@RequireFullAuthentication`·재인증 API, #228·#230)·세션 화면의 같은 기기 안내(#231)는 **모두 제거했다**(사용자 결정 — 관리자 페이지라 쿠키 탈취 시 7일 읽기·수정 노출을 남기지 않는다). 토큰 테이블은 V16이 지운다(평문 토큰). URL 접근 규칙(위 표)은 바뀌지 않았다.

- **다시 넣으려면** 새 계획부터 세운다. 옛 설계(폐기 표·사후 검증·탈취 처리·재인증 승격 순서)는 `PLAN-remember-me-login.md`·`PLAN-sensitive-reauthentication.md`·`PLAN-content-delete-reauthentication.md`와 `docs/troubleshooting.md`의 두 항목(Spring Security 7 remember-me 함정, 세션 ID 교체와 레지스트리 만료 표시)에 남아 있다. 세션을 끊는 모든 경로가 쿠키로 되살아나지 않게 묶는 일이 핵심이었다.
- **이미 발급된 `remember-me` 쿠키**는 읽는 필터도 DB 행도 없어 효과가 없다(지우지 않는다). 필터 체인에 `RememberMeAuthenticationFilter`가 없음은 `RememberMeRemovalIntegrationTest`가 고정한다.
- 세션 유휴 만료는 Boot 기본 30분이다(별도 설정 없음).

### 같은 세션의 폼 로그인 직렬화 (`LoginSessionMutexFilter`, #228 도입 → 2026-11-12 독립 방어로 유지)

- Spring Security 7.0.7은 폼 로그인의 세션 ID 교체만 세션 뮤텍스 안에서 하고, 레지스트리 등록·컨텍스트 저장·성공 처리기는 그 밖에서 한다. 같은 세션의 두 탭이 **서로 다른 계정**으로 동시에 로그인하면 "실제 인증 회원 ≠ 레지스트리 회원"인 세션이 남을 수 있고, 강제 만료는 레지스트리에서 회원의 세션을 찾으므로 그 세션은 실제 회원이 강등·비활성화돼도 끊기지 않는다(요청마다 상태를 다시 보는 장치가 없고 `ROLE_ADMIN`은 DB를 보지 않는다). ADMIN은 두 번째 계정을 직접 만들 수 있어 혼자서도 이 상태를 만들 수 있다.
- 그래서 `LoginSessionMutexFilter`(빈 아님, `UsernamePasswordAuthenticationFilter` 앞)가 **세션이 이미 있는** `POST /admin/login`(그리고 `POST /admin/login/totp`·`GET`·`POST /admin/login/totp-enrollment`·`POST /admin/login/passkey`)의 나머지 체인을 `WebUtils.getSessionMutex(session)` 안에서 실행한다(재진입이라 Spring 전략과 교착하지 않음). 비용은 같은 세션의 로그인끼리 BCrypt·DB 시간 동안 줄을 서는 것뿐이다.
- 시험: `LoginSessionMutexFilterTest`(뮤텍스 보유·통과 대상), `ConcurrentFormLoginIntegrationTest`(레지스트리 등록 직전에 스파이로 멈춰 다른 탭 로그인이 뮤텍스에서 기다림을 `Thread.State`로 확인 → 컨텍스트 회원 = 레지스트리 회원 → 그 회원 만료로 401. 변이: 필터 등록 제거 → 실패). 실제 서버에서 이 경합이 얼마나 쉽게 나는지는 측정하지 않았다. 경위는 `docs/troubleshooting.md` "세션 ID를 바꾸면 이미 만료 처리한 세션이 되살아날 수 있다 / 폼 로그인의 레지스트리 등록은 세션 뮤텍스 밖이다".

## 2단계 인증(TOTP) (2026-11-14 — `adversarial-review/plan/PLAN-totp-two-factor.md`, 이슈 #251)

**ADMIN은 필수, MANAGER는 선택이다**(2026-11-18 필수화 — `PLAN-totp-required-admin.md`, 이슈 #256. 필수 판정은 `TotpAuthorities.isRequired(Role)` 한 곳이고 코드 상수다 — 설정으로 바꾸지 않는다). 등록·해제·비밀값 보관은 `com.cms.admin.member`의 `CLAUDE.md`. 여기에는 로그인 경로의 계약만 둔다.

- **중간 상태는 둘이다**: 2단계 사용 회원의 비밀번호 통과 → `TOTP_PENDING`(코드 화면), **필수 역할(ADMIN)의 미등록** 회원의 비밀번호 통과 → `TOTP_ENROLLMENT_REQUIRED`(강제 등록 화면 `/admin/login/totp-enrollment`). 둘 다 프로바이더가 만들고 역할 권한이 없어 모든 관리 게이트가 따로 막지 않아도 거부한다(완전 권한 + 허용 목록 방식은 목록 하나만 빠져도 2단계 없는 ADMIN이 열려 기각). 접근 거부 처리기는 두 상태 모두 "아직 로그인 안 함"으로 다뤄 화면은 그 상태의 화면으로 302, `/admin/api/**`는 JSON 401을 준다(`TotpAuthorities.isIntermediate`). 강제 등록 상태에서 `/admin/login/totp`도 등록 화면으로 302다.
- **강제 등록 화면**(`TotpEnrollmentLoginController`, 서버 렌더링·JS 없음): GET이 등록 대기를 보여 준다(QR·설정 키) — **세션에 같은 회원의 유효한(10분 안) 대기가 있으면 재사용**하고 없음·만료·회원 불일치일 때만 새로 발급한다(`MemberTotpService.resumeOrStartEnrollment`, 2026-11-19 이슈 #277 — 전에는 GET마다 새로 발급해, 다른 관리 주소가 모두 이 화면으로 302하는 상태에서 새로고침·주소 이동만으로 스캔한 QR이 무효가 됐다). 재사용은 유효기간을 연장하지 않고, 재사용이어도 이미 등록된 회원이면 409 → 세션 종료다. 보안 설정 화면의 등록 API는 여전히 부를 때마다 대체한다. POST가 현재 비밀번호 + 코드로 확정한다(보안 설정과 같은 `MemberTotpService` — 비밀번호를 다시 받는 이유는 중간 상태 쿠키만 훔친 사람이 자기 인증기를 등록하지 못하게). 낡은 대기(다른 탭·10분·회원 불일치)는 컨트롤러가 먼저 보고 `?expired`(새 QR, 카운트 없음), 오답은 **같은 대기로** 화면을 다시 그리고(실패는 `failed_login_count`), 그 밖의 실패(409 등)는 세션 종료 후 `/admin/login-error`. 성공하면 복구 코드를 **그 응답에서만** 그리고(세션·리다이렉트에 두지 않음) 서비스가 본인 전 세션을 만료하므로 다시 로그인 → 코드 화면 → 완전 권한이다. **완료 화면을 그리기 전에 컨트롤러가 현재 세션을 직접 무효화한다** — 레지스트리 만료 표시만 남은 세션 쿠키로는 그 화면의 CSS 요청까지 `ConcurrentSessionFilter`가 로그인으로 302해 스타일 없는 화면이 된다(실기 검증에서 발견, `TotpLoginBrowserTest`가 완료 화면 로드 중 CSS 응답 200을 고정 — 시험 서버는 `Cache-Control: no-store`라 캐시로 가려지지 않지만, 처음 302된 요청이 세션을 무효화하므로 **그 뒤 요청으로 단언하면 놓친다**). GET·POST 모두 `LoginSessionMutexFilter` 대상이고(같은 세션의 다른 계정 재로그인과 직렬화 — 인가 판정도 필터 뒤라 뮤텍스 안), 컨트롤러가 그 안에서 `TotpSessionPromoter.isLiveFor`(레지스트리 항목 생존 + 레지스트리 회원 = 요청 회원)를 확인한다.
- **배포 시점의 기존 세션**: 요청마다 등록 여부를 다시 보지 않는다 — 재기동이 메모리 세션을 끊는 것에 기댄다(Boot 4.0.8 `server.servlet.session.persistent` 기본 `false`, 이 저장소에 설정 없음, Tomcat 11.0.26). 배포 뒤 "재기동 전 ADMIN 쿠키 → 로그인 302" 확인이 출시 필수 항목이다(`docs/deployment.md`). 세션 영속을 켜면 이 전제가 깨진다.

- **중간 상태 = 역할 권한이 없는 인증**: 2단계를 켠 회원이 비밀번호를 통과하면 `TotpAwareAuthenticationProvider`가 권한 `{TOTP_PENDING}` 하나뿐인 토큰을 만든다. 모든 관리 게이트(`hasRole`·`featureReadGate`·`@PreAuthorize`·`AdminPermissionEvaluator`)가 역할 권한을 보므로 따로 막지 않아도 거부된다. 접근 거부 처리기는 이 상태를 "아직 로그인 안 함"으로 다뤄 화면은 코드 화면으로 302, `/admin/api/**`는 JSON 401을 준다. 권한 축소를 성공 처리기가 아니라 **프로바이더에서** 하는 이유: 성공 처리기는 컨텍스트가 세션에 저장된 뒤에 돈다(Spring Security 7.0.7 `AbstractAuthenticationProcessingFilter` 바이트코드).
- **`AuthenticationProvider` 빈은 하나만**: 7.0.7의 전역 인증 관리자는 이 타입의 빈이 **정확히 하나**일 때만 그 빈을 쓴다(둘 이상이면 INFO 로그만 남기고 아무것도 등록하지 않는다 — `InitializeAuthenticationProviderBeanManagerConfigurer`). 새 프로바이더 빈을 추가하면 2단계가 조용히 사라지므로 `TotpPendingAuthorizationIntegrationTest`가 실제 체인에서 `TOTP_PENDING` 발급을 고정한다(변이: 빈 제거 → 7건 중 6건 실패). `@EnableMultiFactorAuthentication`은 쓰지 않는다 — 켜면 같은 이름 재로그인 때 기존 권한이 병합된다(`shouldPerformMfa`).
- **비밀번호 단계 성공 처리기**: 재확인 스냅샷에 2단계 사용 여부가 있고 **토큰 종류와 지금 기대되는 종류가 다르면 거부**한다 — 기대 종류는 사용 중 → `TOTP_PENDING`, 미사용이고 필수 역할 → `TOTP_ENROLLMENT_REQUIRED`, 그 밖 → 완전 권한(로그인 진행 중 등록·해제·승격·강등 커밋 경합). 그래서 **2단계 없는 ADMIN 완전 토큰은 성공 처리기에서 언제나 거부된다**. 강제 등록 상태도 `checkActive`(리셋 없음)·principal 원래 역할 비교·방문 기록 없음(등록 뒤 코드로 다시 로그인할 때 기록)이다. 중간 상태는 `checkActive`(실패 횟수 **리셋 없음** — 리셋하면 2단계 오답 뒤 비밀번호 재로그인으로 대입 제한이 무력화된다)를 쓰고, 세션에 `TotpPendingState{memberId, since}`를 두고 코드 화면으로 보낸다. 방문 기록·알림 정리는 2단계 통과 때 `recordCompletedLogin`이 한다.
- **승격**(`TotpLoginController` → `TotpLoginService` → `TotpSessionPromoter`): 대기 표지(회원 일치·**5분**) → 레지스트리 항목(만료 아님) → 회원 행 잠금 한 트랜잭션에서 상태·역할·해시·등록 재확인(상태·역할·해시 비교는 `CustomUserDetails.matchesCurrent` — 패스키 단독 로그인 `verify`와 같은 메서드)과 코드 판정·소비·실패 기록(5회 → 잠금)을 하고 **커밋된 결과만** 돌려준다 → 그 뒤에야 세션 생성을 금지한 저장소(`setAllowSessionCreation(false)`)로 원래 역할 컨텍스트를 저장하고, 저장 전후로 같은 세션 ID·레지스트리 항목 생존을 다시 본다(어긋나면 무효화). **세션 ID는 바꾸지 않는다** — 바꾸면 만료 표시가 옮겨지지 않아 만료된 세션이 되살아날 수 있다(위 troubleshooting 항목). `POST /admin/login/totp`는 `LoginSessionMutexFilter`의 대상이다(같은 세션의 이중 제출·재로그인과 직렬화).
- **잔여 위험(수용)**: 중간 세션 쿠키를 훔친 공격자는 피해자가 코드를 낸 뒤의 세션을 함께 쓴다(HttpOnly·5분 만료로 수용). 로그인 진행 중 등록 커밋이 겹치면 옛 세션 ID로 먼저 시작한 요청이 밀리초 동안 완전 권한을 지연 로딩할 수 있다(공격자가 주인의 등록 시점을 정할 수 없어 수용, 계획서 R8).
- **패스키로 2단계 통과**(2026-11-19, `PLAN-passkey-second-factor.md` 결정 4, 이슈 #259 PR1): 같은 `GET`·`POST /admin/login/totp`를 쓴다(URL 규칙·뮤텍스·컨벤션 무변경). GET은 유효한 패스키가 있으면 어설션 대기 `PasskeyAssertionState{assertionId, memberId, options, issuedAt}`(5분 — 같은 회원·남은 수명 2분 30초 이상이면 재사용, 아래 "챌린지 공유")를 세션에 두고 옵션 JSON을 별도 패스키 폼의 `data-options`로 그린다(코드 폼의 `required`가 막지 않게 따로 제출). POST에 `passkeyCredential`이 있으면 기존 대기 표지·레지스트리 확인 뒤 어설션 대기를 판정해 회원·폼 `assertionId`·5분이 맞으면 **검증 전에 꺼내 지우고**, 맞지 않으면 검증 전에 `?passkeyExpired`(카운트 없음 — 만료·다른 회원이면 지우고 `assertionId`만 다르면 남긴다, 아래 "챌린지 공유"), 맞으면 `TotpLoginService.verifyPasskey`(코드 판정과 같은 회원 행 잠금 트랜잭션: 재확인 → TOTP·핸들·유효 패스키 없음이면 `REJECTED` → **응답 `userHandle`이 있으면 본인 핸들과 대조**(서명 대상이 아니고 7.0.7이 검증기에 넘기지 않는다 — 코드 리뷰에서 발견) → 라이브러리 검증 → 돌려받은 핸들·자격 행이 이 회원의 유효한 것인지 직접 대조 → 실패는 `member_totp.failed_attempts`(5회 잠금, `?passkeyError`) → 성공은 **flush 뒤** 벌크 리셋) → 같은 승격. **`http.webAuthn()`을 켜지 않고 WebAuthn `AuthenticationProvider`를 만들지 않는다** — Spring의 패스키 필터·프로바이더는 성공 처리기 재확인·중간 상태·잠금을 거치지 않는다. `PasskeyModuleWiringIntegrationTest`가 실제 필터 체인(WebAuthn 패키지 필터 없음)·폼 로그인 인증 관리자(`TotpAwareAuthenticationProvider` + 익명 프로바이더만)·핸들러 매핑(`/webauthn/**` 없음)을 고정한다. 검증 연산만 `com.cms.admin.member.passkey.PasskeyRelyingParty`로 쓴다(`com.cms.admin.member`의 `CLAUDE.md` "패스키").
- **패스키 단독 로그인**(2026-11-19, `PLAN-passkey-login.md`, 이슈 #280 PR2): 로그인 화면 [패스키로 로그인]이 비밀번호·2단계를 건너뛰고 원래 역할의 완전 권한을 준다(UV `REQUIRED`, discoverable — `allowCredentials` 비움). ADMIN 2단계 필수 요건은 이것으로 충족된다고 해석한다(패스키 = 기기 + 생체/PIN, 패스키는 TOTP 사용 회원만 가진다 — 필수 판정·프로바이더 무변경).
  - **입구**: 직접 만든 `AbstractAuthenticationProcessingFilter` `PasskeyLoginFilter`(빈 아님)를 `PasskeyLoginConfigurer`가 `UsernamePasswordAuthenticationFilter` 뒤에 둔다. `configure` 시점에 `HttpSecurity` 공유 객체의 `SessionAuthenticationStrategy`(동시 세션 제어·세션 ID 교체·레지스트리 등록)·`SecurityContextRepository`를 넣고 성공 처리기는 같은 `VisitLoggingAuthenticationSuccessHandler`다 — 폼 로그인과 같은 세션 계약. 필터의 인증 관리자는 통과용 람다이고 **`AuthenticationProvider` 빈을 만들지 않는다**. `LoginSessionMutexFilter` 대상이다.
  - **챌린지**: 로그인 화면 GET(`AdminMainController`)이 `PasskeyLoginState{loginId, options, issuedAt}`(5분)를 세션에 두고 옵션을 패스키 폼의 `data-options`로 그린다. 옵션은 `PasskeyRelyingParty.discoverableRequestOptions()`가 직접 만든다(라이브러리 옵션은 UV `PREFERRED` 고정이고 전역 커스터마이저는 2단계 옵션까지 바꾼다). 제출은 `loginId`·5분이 맞으면 검증 전에 꺼내 지우고, 아니면 검증 전에 `?passkeyExpired`(아래 "챌린지 공유").
  - **챌린지 공유**(2026-11-20, `PLAN-passkey-challenge-stale-tab.md`, 이슈 #293 — 코드 화면의 `PasskeyAssertionState`도 같다): 세션의 챌린지는 하나이고 **같은 세션의 탭들이 나눠 쓴다**. ① 화면 GET(만료·오류 안내 GET 포함)은 남은 수명이 `REUSE_MIN_REMAINING`(TTL의 절반, 2분 30초) 이상이면 재사용하고(`PasskeyLoginService.resumeOrStart`·`TotpLoginService.resumeOrStartPasskeyAssertion` — 코드 화면은 같은 회원일 때만, 유효 패스키 존재 판정이 재사용보다 먼저) 아니면 새로 발급한다. ② **GET은 새로 발급한 값만 세션에 쓴다**(재사용이면 쓰지 않는다) — GET은 세션 뮤텍스 밖이라 재사용 값을 다시 쓰면 그사이 제출이 소비한 챌린지가 되살아나 두 번째 검증이 가능해진다(래치 시험 `reuseDoesNotResurrectConsumed*`). ③ 제출은 식별자 일치 ∧ 5분 이내만 꺼내 지우고 검증한다 — **검증에 도달하는 유일한 갈래가 검증 전에 지우므로 1회용이다**. 만료·쓸 수 없는 값(코드 화면은 다른 회원 포함)은 지우고, 5분 이내인데 식별자만 다르면(다른 탭의 옛 화면) 남긴다 — 이어지는 만료 안내 GET이 그것을 재사용해 탭들이 한 챌린지로 모인다. 수용: 재사용 화면의 남은 수명은 최소 2분 30초, 재사용된 코드 화면 옵션의 `allowCredentials`는 발급 시점 목록, 한 탭이 **성공**한 뒤 남은 탭의 제출은 CSRF 토큰 교체로 판정 전 403(새로고침 — 기존 동작). 브라우저 BFCache 복원은 화면을 다시 불러도 젊은 챌린지면 같은 식별자다(`PasskeyBrowserTest`는 문서 표지 속성의 소멸로 재로드를 확인한다).
  - **판정 순서(트랜잭션 셋 — 필터가 각 빈을 프록시로 부른다)**: `PasskeyLoginService.identify`(읽기 전용: 파싱 → 응답 `userHandle` 필수 → rawId의 자격 행 → 회원 아이디) → `CustomUserDetailsService.loadUserByUsername`(만료 잠금 해제·상태 검사 — 폼 로그인과 같은 판정) → `PasskeyLoginService.verify`(**첫 DB 작업이 회원 행 잠금** → 재확인 → TOTP·핸들 → 응답 `userHandle` = 본인 핸들 → 유효 패스키 → 라이브러리 검증 → 돌려받은 핸들 대조 → `member_totp` 실패 횟수 0). **식별과 검증을 한 트랜잭션으로 합치지 않는다** — InnoDB 스냅샷이 잠금 전 첫 읽기 때 만들어져 옛 `member_totp`를 읽고 전체 컬럼 UPDATE가 다른 요청의 사용 스텝을 되돌린다(`PasskeyLoginIntegrationTest.verifyReadsFreshTotpAfterLock`, 변이 확인). 같은 클래스 안의 진입 메서드로 묶어도 `@Transactional`이 적용되지 않으니 서비스에 묶음 메서드를 두지 않는다.
  - **성공 처리기**: `PasskeyLoginAuthenticationToken`은 검증 때 읽은 TOTP 등록 시각을 싣고, 재확인 스냅샷(`MemberSnapshot.totpEnabledAt`)과 같을 때만 통과한다(로그인 중 TOTP 해제 또는 해제 → 재등록 커밋 거부). 그 밖의 토큰 종류 판정은 그대로다. 성공 시 세션의 중간 상태 표지(`TotpPendingState`·`PasskeyAssertionState`·`PasskeyLoginState`)를 지운다. 거부는 `/admin/login?passkeyError`.
  - **실패**: 모든 실패는 필터에서 `AuthenticationException`으로 바꾼다(예상 밖 예외는 `AuthenticationServiceException` + ERROR — 500 없음). 안내는 둘(`?passkeyExpired`·`?passkeyError`)이고 계정 상태를 나누지 않는다. **실패 횟수를 세지 않는다**(서명은 추측 불가, 세면 남의 계정을 잠그는 수단) — 대신 레이트리밋 `admin-passkey-login`. 이미 인증된 세션(완전·중간 상태)에서의 실패는 폼 로그인 실패와 같이 기존 인증을 그대로 둔다.
  - **서명 횟수 역행**(결정 8): 저장 값보다 커지지 않으면 두 패스키 경로 모두 거부하되 세지 않는다(`com.cms.admin.member`의 `CLAUDE.md` "패스키").
  - **조건부 UI(아이디 칸 자동 완성)**(2026-11-20, `PLAN-passkey-conditional-ui.md`, 이슈 #285 — 서버·URL·레이트리밋 무변경): 로그인 화면은 기능이 켜져 있으면 아이디 입력에 `autocomplete="username webauthn"`을 그리고, 패스키 폼의 `data-conditional="true"`를 본 `passkey-login.js`가 페이지를 열 때 `mediation: "conditional"` 요청을 시작한다(2단계 코드 화면은 표지가 없어 버튼만). **조건부 요청과 버튼은 화면의 챌린지 하나를 나눠 쓴다** — 서버가 제출 때 꺼내며 지워 한 챌린지로 검증되는 어설션은 최대 1개다(새 옵션 API를 만들지 않는다). JS는 `phase`(`idle`·`conditional`·`modal`·`submitted`) 하나로 대기 요청을 많아야 하나로 두고 비동기 지점 뒤에 다시 본다: 버튼은 조건부 요청을 `abort()`하고 **끝나기를 기다린 뒤** 모달을 시작, 조건부 실패는 알리지도 다시 시작하지도 않음(즉시 거부하는 환경의 바쁜 반복 방지), 버튼 실패 뒤에만 1회 재시작, 비밀번호 폼 제출도 같은 상태(이중 POST·계정 전환 방지), BFCache 복원(`pageshow.persisted`)은 새로고침. 조건부 요청은 브라우저 수명 제한이 없어(WebAuthn L3 `lifetimeTimer` 무한대) 오래 열어 둔 화면은 서버 5분 만료(`?passkeyExpired`)로 끝난다. 같은 세션의 다른 탭과의 챌린지 공유는 위 "챌린지 공유"(#293 — 옛 탭 제출이 최신 탭의 챌린지를 지우던 #285의 수용 위험을 해소). 실제 기기 자동 완성 목록·BFCache 복원은 #281에서 확인한다. 시험: Chromium 가상 인증기는 조건부 요청에 대기 없이 응답해(자격 있으면 성공, 없으면 즉시 `NotAllowedError`) 대기·경쟁은 `com.cms.support.PasskeyRequestHarness`(초기화 스크립트로 `navigator.credentials.get`·지원 판정·폼 제출을 감싼다)로 만든다 — **제출을 네트워크(`page.route`)에서 붙잡으면 Playwright `evaluate`가 끝나지 않으므로** 페이지 안에서 붙잡고, 화면 이동을 일으키는 호출은 `later`(다음 태스크)로 부른다.
- **CBOR 변환기 제거**(`HttpMessageConverterConfig`, 2026-11-19 구현 중 발견): 패스키 라이브러리(webauthn4j)가 전이로 `jackson-dataformat-cbor`를 끌어오면 Spring MVC가 `JacksonCborHttpMessageConverter`를 기본 변환기에 더해 모든 `@RequestBody` API가 `application/cbor` 본문(앱 JSON 설정을 거치지 않는 별도 매퍼)을 받게 된다. 앱은 CBOR를 쓰지 않으므로 지운다(→ 415). 같은 시험이 고정한다.
- **"로그인 사용자" 판정**: 공개 레이트리밋 면제(`RateLimitFilter`)·공개 전송 상한 면제(`PublicTransferInterceptor`)는 `TotpAuthorities.isFullyAuthenticated`를 쓴다 — "익명이 아니면 로그인"으로 보면 중간 상태(두 종류 모두)도 면제받는다. 새 면제 판정을 만들 때도 이것을 쓴다.

## 무인증 공개 엔드포인트 레이트리밋

- **무인증 공개 엔드포인트 레이트리밋** (`cms.rate-limit.*`, `com.cms.config.ratelimit`, 2026-08-12 도입): `/{siteKey}/notices/**`(GET·HEAD)·비밀번호 재설정 API 2종(POST)에 토큰 버킷 기반 최소 방어를 적용한다. "N회/기간"은 버스트 상한 N + 평균 N/기간을 뜻하며(엄격한 슬라이딩 상한 아님), 정확한 유량 계약을 보장하는 게이트웨이가 아니다. 저장소는 Caffeine(`maximumSize` + 버킷별 `Expiry`)이며, **fail-open을 운영 위험으로 명시 수용**한다 — 캐시가 포화되는 극단적 상황(대량 IP 회전 공격 등)에서는 개별 IP의 정확한 누적치 보장이 흐트러질 수 있다(메모리 상한·무제한 신규 키 수용·IP별 완벽한 정확성을 동시에 요구하려면 Redis 같은 외부 원자적 저장소가 필요하나 이번 범위·인프라 제약을 벗어나 기각). 필터는 `CsrfFilter` **다음**에 위치한다 — CSRF 검증 실패 요청이 quota를 소비하면 외부 사이트가 피해자 브라우저로 토큰 없는 form POST를 반복시켜 피해자 IP의 quota를 고갈시키는 교차 사이트 공격이 가능해지기 때문이다. 키는 `request.getRemoteAddr()` 고정(`X-Forwarded-For` 등은 위조 가능해 미사용). 상세 설계·리뷰 이력은 `adversarial-review/plan/PLAN-public-endpoint-rate-limit.md` 참조. **예외 1건(2026-11-02 승인, `PLAN-content-image-rate-limit.md`)**: 규칙 설정 `exempt-authenticated: true`인 규칙은 로그인한(익명이 아닌) 요청이 버킷을 쓰지 않고 통과한다 — 현재 `content-image`(`/content-images/*`) 하나뿐이고(`SitePublicRateLimitConventionTest`가 고정), 관리 편집기(Quill) 이미지는 스크립트로 자리표시를 만들 수 없어 같은 IP 익명 방문자가 버킷을 비우면 깨지던 문제의 해법이다. 익명 한도(240/60초)·URL 인가 규칙은 불변이고 면제는 다음 규칙 평가로 넘어가지 않는다. 공개 상세 본문 이미지는 외부 스크립트 `board-content-image-fallback.js`가 실패 시 안내 상자로 바꾼다.
- **로그인 입구 두 곳**(규칙 id·버킷이 따로다): 패스키 단독 로그인 `admin-passkey-login`(POST `/admin/login/passkey`, 30/60초 — 아래 "패스키 단독 로그인")과 **비밀번호 로그인 `admin-password-login`**(POST `/admin/login`, **20/600초 = 버스트 20 + 30초에 1회**, 2026-11-19, `PLAN-password-login-rate-limit.md`, 이슈 #284). 비밀번호 쪽은 계정별 실패 잠금(5회)과 별개로 여러 계정 대입·BCrypt 부하(없는 아이디도 더미 해시 비교)를 IP 단위로 억제한다. 필터가 폼 로그인 처리 필터·`LoginSessionMutexFilter`보다 앞이라 한도 초과 요청은 인증 프로바이더·세션 뮤텍스까지 가지 않는다. **두 로그인 입구의 한도 초과는 429가 아니라 로그인 화면 302 `/admin/login?rateLimited`다**(2026-11-20, 이슈 #288, `PLAN-login-rate-limit-notice.md` — 규칙 설정 `login-redirect: true`, 이동 위치는 코드 상수 `RateLimitFilter.LOGIN_RATE_LIMITED_PATH`, `Retry-After` 없음). `RateLimitFilter.reject`의 분기 순서가 계약이다: API 경로(JSON 429) → `login-redirect`(302) → 그 밖(429 화면). 기동 검증이 `login-redirect`를 **POST 전용 규칙에만** 허용하고(GET이면 이동한 로그인 화면이 다시 걸려 루프), `SitePublicRateLimitConventionTest`가 플래그 규칙을 두 로그인 입구로 고정한다. 프록시 접근 로그로 추적하려면 응답 `Location`을 기록해야 한다(`docs/deployment.md`). MockMvc(spring-test 7.0.9)는 값 없는 쿼리 `?rateLimited`를 null 값 파라미터로 넣어 `@RequestParam`이 null이 된다(Tomcat은 빈 문자열) — 화면 안내 시험은 `.param("rateLimited", "")`로 보낸다. **2단계 화면(`/admin/login/totp`·`/admin/login/totp-enrollment`)은 제외**다 — 비밀번호를 통과한 세션만 오고 오답이 계정별로 잠긴다(코드는 `member_totp.failed_attempts`, 강제 등록의 비밀번호는 `failed_login_count`). **수용 위험**: 같은 `remoteAddr` 뒤의 공격자는 없는 아이디로 30초에 1건만 보내도 그 IP의 비밀번호 로그인을 계속 막는다(계정 잠금 없음) — 프록시 뒤에서 원 IP 전달(#239) 없이 배포하면 모든 관리자가 한 버킷을 쓰므로 **#239 해결 전 실배포 금지**(`docs/deployment.md`). 경로 변형(`;`·`%2F`·`//`·`/./`)은 방화벽 400, 끝 슬래시·대소문자 변형은 로그인 처리 밖(302)이라 우회가 안 된다. 시험 `PasswordLoginRateLimitIntegrationTest`(가짜 `Ticker`, 프로바이더 스파이 — 변이: 규칙 제거·패턴 `/admin/login/**`·GET 추가·필터를 `CsrfFilter` 앞으로 → 각각 실패). 로그인 화면 302는 `RateLimitResponseTest`(플래그 규칙 302·컨텍스트 경로·API 규칙의 JSON 우선)·`RateLimitPropertiesValidationTest`(GET 혼합 기동 실패) — 변이: 플래그 분기 제거·검증 조건 제거·yml 플래그 제거·API/리다이렉트 순서 교환 → 각각 실패.
