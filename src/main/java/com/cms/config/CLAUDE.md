| 그 외 모든 경로 | **기본 거부** (`anyRequest().denyAll()`, 2026-09-29 승인, 감사 M-08) — 비인증은 `/admin/login` 302, 인증(ADMIN·MANAGER)은 403. **새 엔드포인트는 반드시 위 표에 접근 규칙을 추가해야 한다**(누락 시 즉시 차단). `/admin` 아래 핸들러는 추가로 **인가 선언 컨벤션**(읽기 전용 GET/HEAD 페이지만 면제, 그 밖의 모든 핸들러와 모든 API는 `@RequirePermission`·`@RequireBoardPermission`(게시판 게이트 안 — 경로에 `{boardId}` 필수)·`hasRole('ADMIN')` 중 하나 — `AdminEndpointAuthorizationConventionTest`, 상세는 `com.cms.admin.permission`의 `CLAUDE.md`)도 지켜야 하며, 어기면 CI가 실패한다. 이 보장은 명시 허용 규칙에 매칭되지 않는 경로에 한정 — 정적 예약 접두사 하위는 위 컨트롤러 금지 규칙이 지킨다. 설계 근거·검증 이력은 `adversarial-review/plan/PLAN-default-deny-authorization.md` |

## 로그인 상태 유지 (remember-me, 2026-11-10 승인 — 이슈 #222, `adversarial-review/plan/PLAN-remember-me-login.md`)

URL 접근 규칙은 바뀌지 않았다. 구성 요소는 `config/auth`: `AdminRememberMeServices`(Spring `PersistentTokenBasedRememberMeServices` 확장)·`RememberMeTokenRepository`(테이블 `persistent_logins`, V15)·`RememberMeLoginVerificationFilter`(`RememberMeAuthenticationFilter` 바로 뒤, 빈이 아님)·`RememberMeTokenRevokeListener`·`RememberMeDeviceRevoker`·`RememberMeKey`(기동마다 무작위 — 재기동해도 DB 토큰은 유효)·`LoginVisitRecorder`(폼·자동 로그인 공용 방문 기록).

- **유효 기간 7일**(자동 로그인마다 토큰 교체 → 마지막 사용 후 7일), 쿠키 `remember-me`·HttpOnly·`Secure`는 `request.isSecure()`(세션 쿠키와 같은 정책 — 프록시 뒤 판정은 `docs/verification/deployment-edge.md`).
- **기기 = 시리즈**. 로그인이 쓰는 시리즈(DB 정식 값)를 principal(`CustomUserDetails.rememberMeSeries`)과 세션 속성 `REMEMBER_ME_SERIES`에 기록한다. `series`·`token` 칼럼은 `ascii_bin`(대소문자만 바꾼 시리즈가 같은 행을 찾지 못하게).
- **폐기 표** — 항상 **토큰 삭제 → 세션 만료** 순서(자동 로그인 사후 검증과 경합하지 않는 근거):

| 사건 | 범위 | 경계 |
|---|---|---|
| `AdminSessionRevokeEvent`(역할·상태 변경, 본인 비밀번호 변경, 재설정, 자동 잠금) | 그 회원의 모든 토큰 | `RememberMeTokenRevokeListener` **BEFORE_COMMIT**(원 트랜잭션 — 실패하면 원 변경도 롤백). AFTER_COMMIT JDBC 쓰기는 커밋이 보장되지 않아 쓰지 않는다 |
| 수동 단일 만료 | 그 세션의 시리즈 + 같은 시리즈의 모든 세션(같은 기기) | `AdminSessionManageService` — 삭제 실패면 세션도 그대로(같은 핸들 재시도) |
| 수동 회원 단위 만료 | 그 회원의 토큰 − 현재 세션의 시리즈 | 현재 세션 시리즈는 레지스트리 principal에서 읽는다 |
| 명시적 로그아웃 | 이 기기(principal·레지스트리·쿠키·세션 속성 네 출처) + 같은 시리즈의 세션 | `AdminRememberMeServices.logout` → `RememberMeDeviceRevoker` |
| 만료 세션의 후속 요청(`ConcurrentSessionFilter`가 로그아웃 핸들러 호출) | 없음 — 쿠키만 취소 | 지우면 회원 단위 만료가 보존한 현재 기기 시리즈가 사라진다 |
| 탈취 감지(교체된 옛 쿠키 재사용) | 그 회원의 모든 세션 + 모든 토큰 | `processAutoLoginCookie`를 **한 번의 조회**로 직접 구현해(라이브러리의 사전·재조회 어긋남 제거) **세션 만료 → 토큰 삭제 → 세션 만료**(만료는 레지스트리만 — DB 무관). 뒤의 만료가 그 사이 현재 토큰으로 등록·검증을 마친 세션을 잡는다. 삭제가 실패하면 그 회원을 **메모리 차단 목록**에 올려 삭제가 성공할 때까지 그 회원의 자동 로그인을 거부하고 매번 재시도한다(남은 행으로 공격자의 최신 쿠키가 다시 들어오지 못하게 — 단일 인스턴스 메모리라 재기동하면 사라진다). 500 대신 익명 |

- **같은 기기의 세션이 여럿일 수 있다**: 브라우저가 세션 쿠키만 잃고 remember-me로 복원하면 서버에 남은 옛 세션과 새 세션이 같은 시리즈다. 그래서 세션 관리 화면에서 옛 세션을 만료하면 **같은 기기의 현재 세션도 끊긴다**(실기 확인 — "현재 세션은 만료할 수 없다"는 핸들 단위 보호일 뿐이다).
- **사후 검증**: 쿠키 자동 로그인은 세션 등록 뒤 `RememberMeLoginVerificationFilter`가 시리즈 행 존재와 **그 회원이 탈취 차단 목록에 없음**을 본다(없으면·조회 실패면 세션 무효화·컨텍스트 초기화·쿠키 취소 — fail-closed). 방문 기록(U3)은 통과 뒤. 폼 로그인은 `VisitLoggingAuthenticationSuccessHandler`가 같은 확인을 하고, 거부 경로는 방금 만든 시리즈 행을 지우고 쿠키를 취소한다. **폼 로그인의 remember-me 쿠키는 이 확인을 모두 통과한 뒤에만 싣는다**(`issuePendingCookie`) — 거부 응답에 발급 쿠키가 실리면 행 삭제가 실패했을 때 그 값으로 재인증할 수 있다. `loginSuccess`는 이 브라우저의 옛 시리즈(쿠키·세션 속성)를 먼저 지우고, 그 정리가 예외로 끝나면 이미 저장된 인증을 지운다(폼 로그인은 컨텍스트 저장이 `loginSuccess`보다 앞). `updateToken` 0행은 실패다.
- **권한 부족은 403 유지**: Spring 7 `ExceptionTranslationFilter`는 remember-me 인증의 `AccessDeniedException`을 익명처럼 진입점으로 보내고 그 전에 컨텍스트를 비운다 → 진입점 람다가 예외의 `getAuthenticationRequest()`로 판별해 접근 거부 처리기를 직접 부른다.
- **인증 출처 보존**: `AdminSecurityService.refreshAuthentication`은 `RememberMeAuthenticationToken`을 같은 타입으로 다시 만들고 시리즈를 옮긴다.
- **만료 행 정리**(2026-11-11, `adversarial-review/plan/PLAN-remember-me-token-purge.md`): 스케줄러 없이 **로그인 성공 시**(`LoginVisitRecorder` — 폼·자동 로그인 공용, ADMIN·MANAGER) `RememberMeTokenRepository.purgeExpired`가 **모든 회원의** `last_used < now − 7일` 행을 지운다(행은 로그인할 때만 생기므로 로그인이 정리를 맡는다). 지켜야 할 것: ① 조건은 만료 판정과 같은 **엄격 부등호**, 유효 기간은 `AdminRememberMeServices.VALIDITY_SECONDS` 하나 ② 기준 시각은 **`Timestamp.from(Instant)`로 바인딩** — 쓰기(`Date` → JVM 시간대 `Timestamp`)와 같은 변환이라 시간대 무관, `LocalDateTime.now(clock)`을 바인딩하면 UTC JVM에서 9시간 어긋나 유효한 행을 지운다 ③ 범위 DELETE가 아니라 일관 읽기로 고른 뒤 **시리즈마다 `AND last_used < ?`를 다시 확인**하며 지운다 ④ 로그인 응답 대기 상한 — 조회·DELETE 모두 `SET STATEMENT max_statement_time=3, innodb_lock_wait_timeout=1, lock_wait_timeout=1`(BEFORE_COMMIT 폐기가 행을 쥐면 행 잠금 기본 50초, 다른 연결이 이 표만 `LOCK TABLES`로 잡으면 메타데이터 잠금 기본 1일 대기 — 후자는 remember-me를 쓰지 않는 로그인까지 멈춘다), 첫 실패에서 중단, 조회부터 잰 경과가 다음 삭제 전 2초(`PURGE_BUDGET`)를 넘으면 중단 — 남은 행은 다음 로그인(점진적 정리, 부분 삭제 허용) ⑤ 실패는 ERROR 로그만, 로그인은 계속. 스키마 변경 없음(`last_used` 인덱스 없음 — 표가 작고 조회는 잠그지 않는다).
- **수용한 한계**: 쿠키 탈취 시 7일 노출(계정·권한·세션·비밀번호 같은 민감 작업과 **복구할 수 없는 콘텐츠 삭제**는 아래 "민감 작업 재인증"으로 비밀번호 확인을 요구하지만 콘텐츠 수정과 휴지통으로 복원되는 게시글 삭제는 여전히 가능), 여러 탭 동시 복원의 오탐 탈취(토큰·세션 전부 끊김), 폼 로그인의 세션 등록 ~ 시리즈 기록 수 ms 창의 수동 단일 만료(best-effort), 로그인이 없는 기간에는 만료 행이 남는다(인증에 쓸 수 없고 늘지도 않는다).
- **시험**: `RememberMeTokenPurgeIntegrationTest`(만료 행 정리 8건 — `MutableClock` 밀리초 경계·다른 회원 행·자동 로그인 경로·조회 후 갱신·실패 격리·부분 삭제 재시도·잠긴 행·누적 대기·표 단독 `LOCK TABLES`, 변이 6종 확인, UTC JVM 통과), `RememberMeLoginIntegrationTest`(25건 — 경합은 `@MockitoSpyBean RememberMeTokenRepository`·`LoginVisitRecorder`로 결정적 재현, 변이 9종이 의도한 시험에서 실패함을 확인). `SecurityConfig`를 가져오는 슬라이스 시험은 `RememberMeTestConfig`(mock)를 함께 import한다.

## 민감 작업 재인증 (2026-11-11 승인 — 인가·인증·로그인 경로·동시성 변경, `adversarial-review/plan/PLAN-sensitive-reauthentication.md` v10)

쿠키 자동 로그인(remember-me)으로만 인증된 세션은 아래 18개 API(계정·인증 7 + 복구할 수 없는 콘텐츠 삭제 11, 2026-11-12 확대)를 실행할 수 없고 **403 `REAUTHENTICATION_REQUIRED`**를 받는다. 화면 공용 스크립트 `/js/admin/reauth.js`가 이 응답을 받으면 **그 자리에서 비밀번호 모달**을 띄우고, 재인증 API로 세션을 완전 인증으로 바꾼 뒤 같은 요청을 한 번 다시 보낸다(화면 이동·초안 손실 없음). URL 접근 규칙(위 표)·스키마·의존성은 바뀌지 않았다. 처음(v4)에는 "다시 로그인"으로 재인증했으나 사용자가 불편을 문제 삼아 모달로 바꿨다.

- 대상(승인 목록 — `FullAuthenticationConventionTest.APPROVED`): `POST /admin/api/members`, `PATCH /admin/api/members/{id}`, `PUT /admin/api/members/{id}/permissions`, `DELETE /admin/api/sessions/{handle}`, `DELETE /admin/api/sessions?memberId=`, `PATCH /admin/api/members/me`(이메일 = 재설정 채널), `PATCH /admin/api/members/me/password`(현재 비밀번호 오답이 실패 잠금·레이트리밋 밖이라 쿠키 세션의 무제한 추측 경로가 됐다 — 정답·오답 모두 같은 403).
- **복구할 수 없는 콘텐츠 삭제 11종**(2026-11-12 승인 — 인증 경로 변경, URL 규칙·스키마 무변경, `adversarial-review/plan/PLAN-content-delete-reauthentication.md` v3): 배너·팝업·게시판 정의(소프트 삭제지만 복원 기능이 없고 게시판 권한 행이 지워진다)·게시글 첨부·FAQ·FAQ 분류·문의(방문자 원본)·미디어·메뉴(영구삭제)·정적 페이지(개정 이력까지)·사이트의 `DELETE`. **제외**(`FullAuthenticationConventionTest.DELETE_EXEMPT`, 사유 필수): 게시글 삭제(휴지통으로 복원 가능 — 가장 자주 쓰는 삭제), 본인 쪽지 삭제, 오류 화면 `CustomErrorController#handleError`(메서드 제한 없는 매핑). 본인 프로필 이미지 초기화는 기존 `EXEMPT`. **수정(PATCH/PUT)은 대상이 아니다** — 탈취 쿠키로 본문 덮어쓰기·비노출 전환은 여전히 가능하고, 이 확대는 "한 번에 되돌릴 수 없게 지우는 것"만 막는다.
- **새 `DELETE` API는 표지 또는 사유 있는 면제가 필수다**: `FullAuthenticationConventionTest`가 **모든** `com.cms` 컨트롤러의 DELETE 핸들러(메서드 제한 없는 매핑 포함)를 검사한다 — 컨트롤러 목록이 아니라 HTTP 메서드로 고르므로 새 도메인도 자동으로 들어온다. 복원 수단이 있는 소프트 삭제라면 `DELETE_EXEMPT`에 사유를 적는다.
- 구성: 표지 `@RequireFullAuthentication`(메서드 전용, `@Target(METHOD)`) + `FullAuthenticationInterceptor`(등록 `FullAuthenticationWebMvcConfig`, 모든 경로 — 표지로 대상 판정) + `ReauthenticationRequiredException` → `GlobalApiExceptionHandler`. 판정은 `AuthenticationTrustResolver.isFullyAuthenticated`(인증 없음·익명·remember-me 거부 — fail-closed). 거부는 INFO 로그 1줄(아이디·메서드·핸들러, 본문 없음).
- **인가 선언과 직교**: 핸들러의 `@PreAuthorize`("누가")는 그대로이고 표지는 "어떻게 인증됐는가"다 — 인가 선언 컨벤션(`AdminEndpointAuthorizationConventionTest`)의 "선언 하나" 규칙을 건드리지 않으려고 `@PreAuthorize` 식 확장이 아니라 인터셉터로 했다.
- **순서**: 보안 필터(URL 게이트) → 인터셉터 → 본문 바인딩·`@Valid`·메서드 보안. 그래서 **URL 규칙에서 막히는** 역할 부족은 기존 `ACCESS_DENIED`가 먼저이고(remember-me MANAGER의 ADMIN 전용 API — 회원·권한·세션, 게시판 정의·사이트·메뉴 삭제), **메서드 보안에서 판정하는 위임 기능**(배너·팝업·FAQ·문의·미디어·정적 페이지 — URL 게이트는 기능 단위 READ만 본다, 첨부 — 게시판 `UPDATE`)은 READ는 있고 그 동작 권한이 없는 MANAGER의 쿠키 세션이 먼저 403 `REAUTHENTICATION_REQUIRED` → 재인증 뒤 `ACCESS_DENIED`를 받는다(수용 — 버튼이 숨겨진 경우라 직접 호출·권한 회수 직후뿐이고, 인터셉터에 권한 판정을 넣으면 "누가/어떻게" 직교가 깨진다), 쿠키 세션은 잘못된 본문이어도 400이 아니라 403이며 서비스가 돌지 않는다. 세션 없이 쿠키만으로 바로 쓰는 요청은 `CsrfFilter`(세션 저장소)가 자동 로그인보다 먼저라 기존 401 `UNAUTHORIZED`이고 토큰도 교체되지 않는다.
- 쿠키 세션은 재인증 전까지 remember-me다(`refreshAuthentication`이 타입 보존). 화면: 6개 화면(`member/admin-create`·`admin-manage`·`admin-my-info`·`admin-settings`·`permission/manage`·`session/manage`)이 `reauth.js`를 불러 민감 호출 7곳만 `CmsReauth.fetch`로 보낸다. 콘텐츠 삭제는 10개 화면(`banner`·`popup`·`board/manage`·`board/posts`(첨부만)·`faq`(공용 `write()`가 `DELETE`일 때만)·`inquiry`·`media`·`menu`·`page`·`site`)의 삭제 호출만 `CmsReauth.fetch`이고 안내 배너(`reauth-notice`)는 두지 않는다(늘 쓰는 화면이라 소음 — 모달 본문이 이유를 말한다). 403에 고정 문구를 쓰던 오류 함수(`banner`·`faq`·`inquiry`·`media`·`board/posts`)는 `code === "REAUTHENTICATION_REQUIRED"`일 때만 서버 문구를 보인다. `admin/fragments/reauth-notice.html`(`sec:authorize="isRememberMe()"`)이 "저장할 때 비밀번호를 한 번 더 확인합니다"를 미리 알린다. 모달을 취소하면 원래 403이 돌아가 화면이 서버 문구를 보인다(`permission/manage`·`session/manage`는 이 코드일 때만 서버 문구). `reauth.js` 계약: 진행 중 재인증 Promise 하나 공유·확인 중 제출 잠금·원 요청별 재시도 1회·성공 세대 번호로 늦은 403은 모달 없이 재시도, **Bootstrap 4는 전환 중 `show()`/`hide()`를 무시**하므로 완전히 열리기(`shown`) 전에는 입력·확인·취소를 잠그고 다음 표시는 이전 모달이 완전히 닫힌(`hidden`) 뒤에 시작, 검증 요청은 **10초 제한**(`AbortController`) 뒤 다시 조작 가능. **겹친 모달(2026-11-12)**: Bootstrap 4는 문서에 `focusin.bs.modal` 하나만 두고 재인증 모달의 `hide()`가 그것을 해제해 아래 모달이 열린 채 Tab이 배경 화면으로 빠졌다 → `hidden`에서 남은 최상위 `.modal.show`에 같은 이름·같은 규칙으로 포커스 제약을 다시 걸고(아래 모달이 닫힐 때 Bootstrap의 `off`가 해제), 열기 전 포커스 요소가 그 모달 안에서 아직 포커스 가능하면 그리로, 아니면 모달 루트로 포커스를 돌린다. 계약은 "삭제 버튼으로 복귀"가 아니라 "모달 안에 머문다"다(요청 전에 버튼을 비활성화하는 화면은 그 요소를 잃는다). 마지막 요소 다음 Tab은 Bootstrap 기준선과 같이 문서 밖(`body`)으로 나갔다가 다음 Tab에 모달로 돌아온다.
- **재인증 API** `POST /admin/api/members/me/reauthentication`(`AdminReauthenticationController` → `ReauthenticationService`, 본문 `{"password"}`, 상시 허용 게이트 안이라 `SecurityConfig` URL 규칙 무변경): 폼 로그인과 같은 `AuthenticationManager`로 **현재 principal의 아이디**를 검증한다(아이디는 요청에서 받지 않는다). 오답은 **폼 로그인과 같은 실패 카운터**(`LoginFailureService.recordFailure` — 이번 실패로 잠겼는지 반환) → 잠기지 않았으면 400 `REAUTHENTICATION_FAILED`, 이번 실패로 잠겼거나 계정이 잠김·비활성·변경 강제면 세션을 무효화하고 401 `UNAUTHORIZED`(모달은 로그인 화면으로 이동). **집계 자체가 예외면 세션을 끝낸다**(401) — 폼 로그인은 그 요청이 이미 실패로 끝나 집계 실패를 관용해도 되지만, 재인증은 세션을 유지한 채 반복할 수 있어 같은 관용이 무차별 대입 공백이 된다(코드 리뷰). 이미 완전 인증인 세션은 비밀번호만 확인하고 아무것도 바꾸지 않는다. 감사·방문 기록은 남기지 않는다(폼 로그인 성공도 감사가 아니다). **폼 로그인 경로 밖의 비밀번호 검증이다 — 폼 로그인에 보호가 추가되면 이 서비스에도 맞춘다.**
- **승격 순서(요청 시작 때의 세션 S에만, S의 세션 뮤텍스 안)**: ⓪ S의 지금 인증이 같은 주체인지 — **객체 동일성이 아니라 (회원, 기기 시리즈)**로 본다(같은 회원의 자기수정 `refreshAuthentication`이 인증 객체를 새로 만들기 때문). 같은 회원·시리즈의 remember-me면 계속, **같은 회원의 완전 인증이면 다른 탭이 먼저 승격한 것이라 204·변경 없음**(탭은 세션을 공유), 그 밖(다른 회원·다른 기기)이면 세션 종료 → ① `AdminSessionService.changeSessionIdIfActive` — **레지스트리 모니터 안에서** 옛 항목이 없거나·만료됐거나·다른 회원이면 교체하지 않고, 아니면 `changeSessionId()`(세션 고정 방지) 후 새 ID 항목이 없으면 직접 옮김 → ② 폼 로그인 성공 처리기와 같은 DB 재확인(`ACTIVE`·역할·해시) + 시리즈 행 생존 + 탈취 폐기 대기 아님 → ③ **새** `SecurityContext`(시리즈를 옮긴 새 principal, 공유 컨텍스트 객체는 수정하지 않음) → ④ S에 직접 `setAttribute`(무효화됐으면 예외 → 새 세션을 만들지 않고 401) → ⑤ 레지스트리 현재 ID 항목·컨텍스트가 같은 회원인지 사후 확인. 어느 단계든 어긋나면 S 무효화 + 401. CSRF 토큰은 바꾸지 않는다(화면이 같은 헤더로 원 요청을 다시 보낸다).
- **왜 만료를 모니터로 직렬화하나(실측)**: Spring Security 7.0.7 `SessionRegistryImpl`은 ID 변경 이벤트에서 옛 항목을 지우고 새로 등록해 **만료 표시를 옮기지 않는다** → 만료가 ID 교체와 겹치면 끊은 세션이 되살아난다. 그래서 `AdminSessionService`의 **모든** 만료 메서드(`expireByHandle`·`expireSessionsWithSeries`·`expireSessionsForUserId`·`expireSessionsFor`)와 교체가 같은 모니터를 쓴다. **레지스트리 항목에 `expireNow()`를 직접 부르는 새 코드를 서비스 밖에 쓰지 않는다**(수동 단일 만료도 `expireByHandle`로 옮겼다). 모니터 안에서는 DB를 쓰지 않는다. 잠금 순서는 항상 세션 뮤텍스 → 레지스트리 모니터.
- **왜 폼 로그인도 세션 뮤텍스 안인가(실측)**: Spring은 폼 로그인의 ID 교체만 세션 뮤텍스 안에서 하고, 레지스트리 등록(미리 읽은 ID로)·컨텍스트 저장·`loginSuccess`는 밖이다 → 같은 세션의 다른 탭 로그인과 승격이 겹치면 "실제 인증 ≠ 레지스트리 회원"이 남는다(두 탭 동시 로그인도 같다). `LoginSessionMutexFilter`(빈 아님, `UsernamePasswordAuthenticationFilter` 앞)가 **세션이 이미 있는** `POST /admin/login`의 나머지 체인을 `WebUtils.getSessionMutex(session)` 안에서 실행한다. 같은 세션의 로그인·재인증은 BCrypt·DB 시간 동안 줄을 선다(수용). 상세 경위는 `docs/troubleshooting.md` "세션 ID를 바꾸면 이미 만료 처리한 세션이 되살아날 수 있다".
- **새 계정·인증 상태 변경 API**를 `AdminMemberController`·`MemberPermissionController`·`AdminSessionController`·`AdminReauthenticationController`에 추가하면 표지를 붙이거나 `FullAuthenticationConventionTest.EXEMPT`에 사유와 함께 넣어야 CI가 통과한다. 이 세 컨트롤러 **밖에** 그런 컨트롤러를 새로 만들면 `ACCOUNT_CONTROLLERS`에 추가한다(시험이 스스로 알 수 없는 한계).

## 무인증 공개 엔드포인트 레이트리밋

- **무인증 공개 엔드포인트 레이트리밋** (`cms.rate-limit.*`, `com.cms.config.ratelimit`, 2026-08-12 도입): `/{siteKey}/notices/**`(GET·HEAD)·비밀번호 재설정 API 2종(POST)에 토큰 버킷 기반 최소 방어를 적용한다. "N회/기간"은 버스트 상한 N + 평균 N/기간을 뜻하며(엄격한 슬라이딩 상한 아님), 정확한 유량 계약을 보장하는 게이트웨이가 아니다. 저장소는 Caffeine(`maximumSize` + 버킷별 `Expiry`)이며, **fail-open을 운영 위험으로 명시 수용**한다 — 캐시가 포화되는 극단적 상황(대량 IP 회전 공격 등)에서는 개별 IP의 정확한 누적치 보장이 흐트러질 수 있다(메모리 상한·무제한 신규 키 수용·IP별 완벽한 정확성을 동시에 요구하려면 Redis 같은 외부 원자적 저장소가 필요하나 이번 범위·인프라 제약을 벗어나 기각). 필터는 `CsrfFilter` **다음**에 위치한다 — CSRF 검증 실패 요청이 quota를 소비하면 외부 사이트가 피해자 브라우저로 토큰 없는 form POST를 반복시켜 피해자 IP의 quota를 고갈시키는 교차 사이트 공격이 가능해지기 때문이다. 키는 `request.getRemoteAddr()` 고정(`X-Forwarded-For` 등은 위조 가능해 미사용). 상세 설계·리뷰 이력은 `adversarial-review/plan/PLAN-public-endpoint-rate-limit.md` 참조. **예외 1건(2026-11-02 승인, `PLAN-content-image-rate-limit.md`)**: 규칙 설정 `exempt-authenticated: true`인 규칙은 로그인한(익명이 아닌) 요청이 버킷을 쓰지 않고 통과한다 — 현재 `content-image`(`/content-images/*`) 하나뿐이고(`SitePublicRateLimitConventionTest`가 고정), 관리 편집기(Quill) 이미지는 스크립트로 자리표시를 만들 수 없어 같은 IP 익명 방문자가 버킷을 비우면 깨지던 문제의 해법이다. 익명 한도(240/60초)·URL 인가 규칙은 불변이고 면제는 다음 규칙 평가로 넘어가지 않는다. 공개 상세 본문 이미지는 외부 스크립트 `board-content-image-fallback.js`가 실패 시 안내 상자로 바꾼다.
