# CLAUDE.md — com.cms.admin.page

이 디렉터리(정적 페이지 관리: 약관·개인정보처리방침·소개 등) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조. 설계 결정·적대적 리뷰 5라운드 기록은 `adversarial-review/plan/PLAN-static-page.md`(2026-10-11). 공개 측은 `com.cms.publicweb.page`의 `CLAUDE.md`(`/pages/**`).

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

- **모델 — 본문은 개정 테이블에만 있다**(V37): `site_page`(슬러그·`current_revision_no`·`version`·`use_yn`·`footer_yn`)와 `site_page_revision`(`(page_id, revision_no)` 복합 PK, 제목·본문·개정일). 현재 본문은 `page ⨝ revision(current_revision_no)`로 읽는다 — 페이지 행에 본문을 두면 현재 본문과 개정이 어긋날 수 있다. **개정은 수정·삭제하지 않는다**(페이지 삭제 때 개정을 먼저 지우고 페이지를 지운다, FK RESTRICT). 엔티티는 연관관계 매핑 없이 ID 값만 가진다.
- **`version`과 `current_revision_no`는 다른 값이다**: 개정 번호는 본문(제목·본문)이 바뀐 저장에서만 오르고, **`version`은 본문·노출·푸터 중 무엇이든 바뀌면 오른다**(아무것도 안 바뀐 저장은 둘 다 그대로 — 200 + 현재 상태). 수정·삭제 요청은 화면이 가진 `version`을 싣고, 잠금 아래에서 다르면 **409**다. 개정 번호로 낡은 화면을 검사하면 "노출 끄기 → 낡은 화면의 제목 수정"이 비공개 페이지를 되살린다(리뷰 R1-1, `SitePageApiIntegrationTest.staleBodyAfterMeta`가 고정). 증가는 `Math.incrementExact`라 `int` 한계에서 쓰기 전에 예외로 실패한다(음수 개정이 저장되지 않는다, R5-1).
- **잠금**: 수정·삭제는 첫 DB 조회가 페이지 행 `FOR UPDATE`(`findByIdForUpdate`) → `version` 비교 → 쓰기다. 개정 번호 중복은 이 잠금으로 직렬화되고 복합 PK가 최종 방어선이다. **생성**은 잠글 행이 없어 슬러그 유니크 키가 직렬화 수단이다(사전 `existsBySlug` + `saveAndFlush`의 `DataIntegrityViolationException`을 409로). 시험: `SitePageConcurrencyIntegrationTest`(같은 `version` 8요청 → 정확히 하나 200, 같은 슬러그 8요청 → 하나 201, 수정↔삭제 직렬화).
- **슬러그**(`SiteSlug`): `^[a-z0-9]+(-[a-z0-9]+)*$`, 2~50자, 자동 소문자화 없음(대문자는 400), 예약어 `revisions`·`new`·`edit`·`index`(지금 `/pages` 아래 고정 경로는 없지만 로드맵 확정 결정), 중복 409. **생성 후 변경할 수 없다**(수정 요청에 슬러그가 없다 — 변경을 허용하면 공유된 URL이 깨지고 리다이렉트 표가 필요하다). DB 콜레이션은 `utf8mb4_general_ci`라 대소문자를 구분하지 않지만 소문자만 허용돼 영향이 없다.
- **본문에 이미지를 넣을 수 없다**: 본문 이미지의 출처·참조·공개 판정이 게시판에 묶여 있어(`com.cms.admin.contentimage`) 정적 페이지가 쓰려면 그 도메인 전체를 건드려야 한다 — ⑧ 미디어 라이브러리 몫. `ContentBodyPolicy.sanitizePage`(`HtmlContentSanitizer.sanitize(html, allowImages=false)`)가 **모든 `img`를 제거**하고, 출력 때도 `ContentBodyPolicy.sanitizeForPageOutput`으로 같은 규칙을 한 번 더 적용한다(DB 직접 수정으로 들어온 `img`도 렌더되지 않는다). 편집기는 `NoticeEditor.create(…, { allowImages: false })`로 이미지 서식·툴바 버튼·파일 붙여넣기 업로드를 끈다.
- **본문 상한은 게시글과 다르다**: 보이는 글자 50,000자(+마지막 문단 종료 1자), 정리 후 500,000바이트, **요청 원문 600,000바이트**(`@MaxUtf8Bytes` — sanitizer가 원문을 파싱하기 **전에** 거른다, R3-1). 게시글(`ContentBodyPolicy.sanitize`)은 10,000자·200,000바이트 그대로다(`PageBodyPolicyTest`가 둘 다 고정).
- **권한 — 기능 단위 위임 `SITE_PAGE`**(`DELEGABLE`): 핸들러는 전부 `@RequirePermission(feature = SITE_PAGE, action = …)` — 목록·상세 = READ, 등록 = CREATE, 수정 = UPDATE, 삭제 = DELETE. URL 게이트(`/admin/site-page/manage`·`/admin/api/site-pages`·`/admin/api/site-pages/**`)는 `AdminFeature.SITE_PAGE.gatePatterns`에서 `SecurityConfig`의 `DELEGABLE` 루프가 만든다(관리자 쪽 `SecurityConfig` 수정 없음). 화면 버튼은 `myPermissions`(`"SITE_PAGE:CREATE"` 등)로 숨길 뿐 서버 판정(403)이 최종이다. 이름이 `PAGE`가 아닌 것은 `@AdminPage`와의 혼동을 피하려는 것이다. 롤백 후 재배포 시 권한 부활 주의는 `docs/deployment.md` "정적 페이지".
- **응답 형태**: 등록·수정 응답은 상세와 같은 `SitePageDetailResponse`(현재 본문 + **최근 20건** 개정 요약 + `revisionCount` + 최신 `version`)다 — 화면이 바로 다음 저장에 쓸 `version`을 얻는다. 목록·개정 요약은 **`content`를 읽지 않는 프로젝션**(`SitePageSummaryRow`·`SitePageRevisionSummaryRow`)이다. 개정 요약은 `revision_no BETWEEN`의 PK 범위 조회(OFFSET 없음)다. `auditLabel`은 `@JsonIgnore`라 JSON에 나가지 않는다.
- **감사**: `SITE_PAGE_CREATE`·`SITE_PAGE_UPDATE`·`SITE_PAGE_DELETE`(`targetType=SITE_PAGE`, `targetId`=페이지 ID, `targetLabel`=`rev=N`/`rev=N 유지`(메타만)/`rev=N 변경 없음`/삭제 시 마지막 `rev=N` — 시스템 생성값이라 사용자 입력이 없다). **실패 행의 `errorMessage`는 `safeErrorMessage` 고정 문구**("정적 페이지 등록에 실패했습니다." 등)다 — 저장·커밋 예외 메시지에 SQL·제목·본문이 섞여 감사 테이블에 사본이 남지 않게 한다(쪽지 선례, 대가로 4xx의 구체 사유는 HTTP 응답으로만 전달된다). 감사는 최선 노력이라 개정은 있는데 로그가 없을 수 있고 **개정별 작성자 추적은 보장하지 않는다**(작성자 컬럼 없음). 서버 로그의 프레임워크 예외 출력은 `safeErrorMessage`의 보호 범위가 아니다(쪽지와 같은 한계).
- **삭제는 하드 삭제**(개정 포함): 소프트 삭제 상태를 만들지 않는다 — 비공개 수단은 `useYn=false`가 있다. 개정 단독 삭제·개정별 숨김은 없다(알려진 한계: 실수로 올린 민감 정보를 그 개정에서만 지울 수 없다).
- **화면은 메뉴 구조 편집과 한 화면이다**(2026-10-11, `PLAN-content-menu-unify.md`, 방법 3′): `templates/admin/page/manage.html`이 셸(탭·새로고침 안내·의존성 로딩·탭 해시 `#pages`/`#menu`), 이 패널은 `templates/admin/page/fragments/page-tab.html`의 `pagePanel`·`pageScript` 조각이다. 게이트는 `SITE_PAGE` 그대로(ADMIN은 항상, MANAGER는 조회 권한)이고 **MANAGER에게는 메뉴 탭·모달·jstree·탭 내비게이션이 렌더링되지 않으며 머리글도 "정적 페이지 관리"**다. 탭 해시(`#pages`·`#menu`)는 문서를 열 때 읽고 `hashchange`로도 따라가며 탭을 누르면 `replaceState`(이력을 쌓지 않고 `hashchange`도 일으키지 않음)로 갱신한다. 스크립트 조각은 의존성 로딩 **뒤**에 둔다(앞이면 `$`·`NoticeEditor` 없음). 저장 버튼 id는 메뉴 탭의 `btnSave`와 겹치지 않게 `pageBtnSave`다. 메뉴 탭과의 새로고침 조정: `window.ContentScreen.isPagePanelBusyOrDirty()`(저장·삭제·로딩 중이거나 `isDirty()`)를 메뉴가 반영 전에 확인하고, `content:menu-applying`(true)이 오면 입력·저장·삭제를 잠근다(성공은 문서 교체까지 유지, 실패 시에만 false). `isDirty()`는 신규 작성에서도 노출·푸터 플래그를 본다. 시험: `ContentManagePageIntegrationTest`(중복 id 없음·모달이 패널 밖·스크립트 배치 순서·MANAGER 응답에 메뉴 마크업 없음·메뉴 API 403·옛 URL 302).
- **정적 페이지 패널**(`pagePanel`): 왼쪽 목록(슬러그·제목·상태·개정), 오른쪽 등록/수정 폼(이미지 없는 Quill, 슬러그는 등록 때만 입력) + 개정 요약(노출 중이면 공개 개정 링크). 저장 성공 응답으로 폼의 `version`을 갱신하고, **409는 입력을 지우지 않고** 목록에서 다시 선택해 최신 내용을 불러오라고 안내한다. 슬러그·제목은 `textContent`로만 삽입한다. 메서드 보안 403의 `message`가 영문이라 고정 한국어 문구를 쓴다.
- 시험: `PageBodyPolicyTest`·`SitePageDomainTest`(슬러그·`incrementExact`)·`SitePageApiIntegrationTest`(생명주기·감사 라벨·정리·검증·낡은 화면 4종·삭제 검증·개정 요약 상한·`int` 오버플로·실패 감사 고정 문구)·`SitePagePermissionMatrixIntegrationTest`(핸들러 5 × 권한 7조합)·`SitePageConcurrencyIntegrationTest`·`SitePageMigrationTest`, 그리고 `SecurityConfigTest`의 `/pages/**`·관리 게이트.
