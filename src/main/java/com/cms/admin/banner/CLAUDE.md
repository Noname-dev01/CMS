# CLAUDE.md — com.cms.admin.banner

이 디렉터리(공개 메인 배너 관리) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조. 설계 결정·적대적 리뷰 5라운드 기록은 `adversarial-review/plan/PLAN-public-home-banner.md`(2026-10-10). 공개 측은 `com.cms.publicweb.home`의 `CLAUDE.md`(공개 메인 `/`·배너 이미지 `/banners/{id}/image`).

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

- **권한 — 카탈로그의 첫 기능 단위 위임(`DELEGABLE`) 기능 `BANNER`**: 핸들러는 전부 `@RequirePermission(feature = BANNER, action = …)`이다 — 목록·상세·**관리자 이미지 보기** = READ, 등록 = CREATE, 수정(`PUT /{id}`)·**순서 저장(`PUT /order`)** = UPDATE, 삭제 = DELETE. URL 게이트(`/admin/banner/manage`·`/admin/api/banners`·`/admin/api/banners/**`)는 `AdminFeature.BANNER.gatePatterns`에서 `SecurityConfig`의 `DELEGABLE` 루프가 만든다(`SecurityConfig` 수정 없음). 화면 버튼은 `myPermissions`(`"BANNER:CREATE"` 등, `AdminSidebarAdvice`)로 숨길 뿐 서버 판정(403)이 최종이다. `PUT /order`와 `PUT /{id}`는 같은 컨트롤러에 함께 있고 `PUT /order`가 순서 저장으로 동작함을 `BannerApiIntegrationTest`·`BannerPermissionMatrixIntegrationTest`가 고정한다 — 새 `PUT` 경로를 `/{id}` 형태 아래에 추가할 때는 이 두 시험이 계속 통과하는지 확인한다.
- **스키마(V33~V34)**: `banner`(제목·링크·`storage_key`·기간 NULL 허용·`use_yn`·`ord`, **하드 삭제**) + `banner_lock`(가드 행 id=1, V34가 시드). 날짜 컬럼은 `datetime(6)`. 노출은 `use_yn ∧ [display_start, display_end)`(시작 포함·종료 **미포함**)이며 기간이 비면 `use_yn`만 본다.
- **동시성 — 가드 행 `banner_lock`을 `FOR UPDATE`로 먼저 잠근다**(생성·삭제·순서 저장의 **첫 DB 조회**): 배너 행이 하나도 없는 빈 테이블에서는 "전체 행 잠금"이 잠글 행이 없어 직렬화가 되지 않는다(리뷰 R1-1 — 갭 잠금·격리 수준에 기대지 않는다). 가드를 잡은 **뒤에** 비잠금 읽기(`count`·`findMaxOrd`)를 한다. 순서 저장은 가드 뒤 `findAllForUpdate`(id 순 행 락)로 전 행을 잠그고 읽는다 — `Banner`에 `@DynamicUpdate`·`@Version`이 없어 비잠금 스냅샷으로 `ord`를 바꾸면 전 컬럼 UPDATE가 방금 커밋된 단건 수정(숨김 처리 등)을 되돌리기 때문이다(코드 리뷰 R1)(스냅샷이 잠금 이후에 확정). 단건 수정(`PUT /{id}`)은 가드 없이 대상 행만 `findByIdForUpdate` — 잠금 순서는 항상 가드 → 행이라 순환 대기가 없다. 가드 행이 없으면 `IllegalStateException`(조용히 잠금 없이 진행하지 않는다). 시험: `BannerConcurrencyIntegrationTest`(빈 테이블 12개 동시 등록 = 정확히 10개·`ord` 0..9 중복 없음·실패한 요청의 파일 없음, 상한 직전 2개 동시 등록 = 하나만, 가드 락 실증, 마지막 삭제↔등록, 순서 저장↔등록; **변이 실험으로 `lockGuard()` 제거가 2건 실패함을 확인**).
- **상한과 이미지 예산**: `MAX_BANNERS = 10`(초과 409) — 공개 메인이 활성 배너 **전부의 이미지를 매번** 내려받으므로(`no-store`) 총량을 제한한다. 이미지는 png·jpeg·gif, **2MB, 한 변 2560px, 총 4,000,000픽셀**, 헤더 검사만(`ImageFileValidator.Limits`, 본문 이미지의 5MB·4096²보다 작은 배너 전용 예산), 애니메이션 거부(공용 검증기). **이미지 교체는 없다**(삭제 후 재등록) — 파일 삭제 시점·동시성 경로가 하나 더 늘어서 범위에서 뺐고 ⑧ 미디어 라이브러리에서 해결한다.
- **저장 위치와 정리**: `FileStorage`의 **`banner` 네임스페이스**(예약 네임스페이스 — 루트 API `load/open/delete`는 `banner/…` 키에 닿지 못한다, `LocalDiskFileStorageTest`). 등록은 롤백 시 정리(`deleteOnRollback` 네임스페이스 오버로드), 삭제는 **커밋 후** 파일 삭제(`deleteAfterCommit`) — 실패하면 "행 없는 파일"이 남고 `docs/deployment.md` 수동 회수 **⑤-3**이 정리한다. **기존 수동 회수 ⑤는 `banner/`를 제외해야 한다**(제외하지 않으면 정상 배너가 고아로 삭제됨 — 리뷰 R4-1).
- **수정은 `PUT` 전체 교체**(제목·링크·시작·종료·노출 여부 모두 요청에 포함, 링크·시작·종료의 `null`·빈 문자열 = 해제): 최종 값에 `DisplayPeriod.normalize`→`requireValid`를 적용하므로 만료 배너의 종료만 지워 되살리기·한쪽만 바꿔 역전되는 경우가 한 규칙으로 판정된다(R2-2). 낡은 폼이 방금 다른 관리자가 바꾼 노출 여부를 덮을 수 있는 stale-form 한계는 메뉴 관리와 같고 수용한다.
- **기간 규칙은 `com.cms.common.display.DisplayPeriod`가 원본**(⑦ 팝업·④ 예약 게시가 재사용): `normalize`(분 단위 절단 — 소수 초 입력이 저장 후 `start == end`를 만들거나 시작을 앞당기는 것을 막는다)·`requireValid`(`start < end`)·`isActive`(`[start, end)`). DB 조건은 `BannerRepository.findDisplayable*`가 같은 의미로 고정한다 — 두 표현의 일치는 `BannerRepositoryDataJpaTest`가 **저장·flush·영속성 컨텍스트 초기화·재조회 후** 경계(시작 직전·시작·종료 직전·종료)로 대조한다. 판정 시각은 주입된 KST `Clock`(`LocalDateTime.now(clock)`, 서비스가 호출당 1회).
- **링크 검증**: 저장은 `@SafeLinkUrl`(`common/web/validation`, `SafeUrls.isSafeMenuUrl` 위임 — 같은 출처 경로 ∨ 외부 http(s), 빈 값 통과)이고 **출력 시 `PublicBanner.from`이 한 번 더 거른다**(DB 직접 수정 방어 — 통과 못 하면 링크 없는 배너). 외부 링크는 새 탭 + `noopener noreferrer`.
- **관리자 이미지 보기**(`GET /admin/api/banners/{id}/image`): 공개 경로가 비노출·기간 외 배너를 404로 막으므로 관리 화면 미리보기는 노출 여부와 무관하게 파일을 읽는 이 전용 엔드포인트를 쓴다(READ 권한, `FileStorage.load(key, "banner")` byte[] — 5MB 이하 소수 관리자 요청이라 스트리밍이 필요 없다).
- **화면**(`templates/admin/banner/manage.html`): 노출 시작·종료는 **날짜(`date`) 입력 + 시·분 `<select>` 두 개씩**이다(`datetime-local`과 `time` 입력의 팝업은 값을 골라도 바깥을 클릭할 때까지 열려 있어 사용자 요청으로 분리·select로 대체, 2026-10-10 — select 목록은 고르면 바로 닫힌다) — 날짜가 비면 제한 없음(`null`), 날짜만 있으면 00:00(시·분 중 하나만 골랐으면 나머지는 00), **시·분을 골랐는데 날짜가 없으면 요청 전에 입력 오류**(조용히 버리지 않는다). 목록(썸네일·제목·기간·**서버가 계산한 상태 배지**(HIDDEN > SCHEDULED > EXPIRED > ACTIVE — 브라우저 시계에 의존하지 않는다)·▲▼) + 등록(`multipart`)/수정 폼. 정렬은 드래그가 아니라 **▲▼ 버튼 + [순서 저장]**(`PUT /order`, 전체 최종 순서) — 초안이 있는 동안 다른 저장·삭제·새로고침은 잠기고 `beforeunload`가 경고한다. 순서 저장은 요청 집합이 현재 집합과 다르면 409(낡은 화면, 새로고침), 같으면 `ord=0..n-1`을 매기되 값이 같은 행은 쓰지 않는다. 제목은 `textContent`로만 삽입(`<b>`가 글자로 보임을 실기 확인). 메서드 보안 403의 `message`가 영문이라 고정 한국어 문구를 쓴다.
- **감사**: `BANNER_CREATE`·`BANNER_UPDATE`·`BANNER_DELETE`(`targetType=BANNER`, `targetId`=배너 ID)·`BANNER_ORDER`(`targetId` 없음). 제목은 사용자 입력이라 `targetLabel` 없음. `AdminActionTypes`와 `templates/admin/log/manage.html` 라벨은 동기화 시험이 고정한다.
- **롤백 후 권한 부활(R2-1)**: 배너 도입 전 앱으로 롤백했다가 재배포하면 이전 앱의 "전체 회수"가 남긴 `BANNER` 행이 되살아난다 — `docs/deployment.md` "공개 메인(`/`)과 배너"의 정리 트랜잭션이 필수.
- 시험: `BannerServiceTest`(검증 순서·잠금 순서·상한·정규화·`PUT` 의미·삭제 콜백·순서 저장 쓰기 최소화)·`BannerRepositoryDataJpaTest`·`BannerApiIntegrationTest`(생명주기·감사·파일 정리·링크·이미지 검증·공개 이미지 404 동일·공개 메인 순서/이스케이프/위험 링크 제거)·`BannerPermissionMatrixIntegrationTest`·`BannerConcurrencyIntegrationTest`·`BannerMigrationTest`, 그리고 `com.cms.admin.permission`의 BANNER 판 시험(권한 PUT·역할 변경).
