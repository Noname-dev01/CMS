# CLAUDE.md — com.cms.admin.board

이 디렉터리(범용 게시판) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조. 설계 결정·적대적 리뷰 기록은 `adversarial-review/plan/PLAN-board.md`(PR A = 게시판 정의 + 게시판별 권한, PR B = 게시글·첨부·본문 이미지·공개·검색·게시판 삭제). 공개 측은 `com.cms.publicweb.board`의 `CLAUDE.md`.

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

## 게시판 정의 (PR A, 2026-10-08)

- **게시판**(`Board`): `name`(100자, 공백 거부, 중복 허용 — 화면은 `#id`를 함께 보인다)·`publicYn`(공개 사이트 노출)·`attachmentYn`(**새** 첨부 업로드 허용 — 끄면 새 업로드만 400이고 기존 첨부의 조회·다운로드·삭제는 그대로)·`deleted`(소프트 삭제). 정렬은 id 순.
- **API·화면은 ADMIN 전용**: `GET·POST /admin/api/boards`, `GET·PATCH·DELETE /admin/api/boards/{boardId}`, 화면 `GET /admin/board/manage`(`@AdminPage`). 카탈로그 게이트 밖이라 `/admin/**` ADMIN 캐치올이 막고 핸들러도 `hasRole('ADMIN')`. 메뉴는 V2 시드(`BOARD_ADMIN` = ADMIN_ONLY라 MANAGER 사이드바에 없다).
- **게시판 삭제**(`DELETE /admin/api/boards/{boardId}`, PR B에서 **게시글 검사와 함께** 도입 — 검사 없는 삭제가 먼저 배포되면 PR B → PR A 롤백 중 게시글이 있는 게시판을 지울 수 있다, 리뷰 R1-5): 게시판 행 `FOR UPDATE` → 살아 있는(`deleted=0`) 게시글이 있으면 **409**(노출 여부 무관) → 소프트 삭제 + 그 게시판의 `member_board_permission` 행 전부 삭제(`deleteByBoardId` 벌크). 지운 행이 있으면 `PermissionChangedEvent(null)`(캐시 무효화는 전역 generation이라 회원 ID를 쓰지 않는다). 권한 버전은 올리지 않는다 — 낡은 권한 화면의 PUT은 게시판 존재 확인에서 400. 감사 `BOARD_DELETE`. 삭제된 게시판의 행은 테이블에 남고 복원 API는 없다.
- **게시판 행 잠금 규칙**: 수정·삭제는 `findByIdAndDeletedFalseForUpdate`(PESSIMISTIC_WRITE). 권한 저장은 부여할 게시판들을 `findAllByIdInForShare`(PESSIMISTIC_READ, id 순), **게시글 생성은 그 게시판 한 행을 `findByIdAndDeletedFalseForShare`(PESSIMISTIC_READ)**로 잠가 게시판 삭제(`FOR UPDATE`)와 직렬화한다 — 삭제 검사 직후 생기는 고아 게시글이 없다. 잠금 순서는 권한 PUT이 회원 → 게시판, 게시판 삭제가 게시판 → 권한 행이라 순환이 없다. 시험은 `AbstractBoardDeleteRaceTest`(ON·OFF 두 서브클래스, 아래).
- **내 게시판 목록**(`GET /admin/api/members/me/boards`, `MyBoardController`, `hasAnyRole('ADMIN', 'MANAGER')`): 기존 ALWAYS `MY_INFO` 게이트 안이라 `SecurityConfig` 변경 없음. ADMIN은 미삭제 게시판 전부·전 동작, MANAGER는 READ가 유효한 게시판만 + 게시판별 허용 동작(쓰기는 같은 게시판 READ 의존). 게시글 관리 화면의 게시판 선택·버튼 표시용이며 서버 판정을 대신하지 않는다.
- 게시판별 권한의 판정·저장·캐시는 `com.cms.admin.permission`의 `CLAUDE.md` "게시판별 권한".

## 게시글·첨부 (PR B, 2026-10-08)

- **게시글**(`Post`): 공지(`Notice`)와 같은 구조 — `useYn`(노출)·`deleted`(소프트 삭제)가 별도, 본문은 정리된 HTML(MEDIUMTEXT), `authorId`는 작성자 userId 스냅샷, `boardId`는 plain `Long`(연관관계 매핑 없음, DB FK RESTRICT). 인덱스 `(board_id, deleted, use_yn, create_date)`. 본문 검증은 공지와 같은 `ContentBodyPolicy`(형식 표식 `contentFormat=HTML` 필수·보이는 글자 10,001·정리 HTML 200,000바이트·이미지만 있는 본문 허용).
- **관리 API**(`PostController`, `/admin/api/boards/{boardId}/posts`): 목록·상세 = `READ`, 생성 = `CREATE`, 수정 = `UPDATE`, 삭제 = `DELETE`. **전부 `@RequireBoardPermission`이고 경로 변수 이름은 반드시 `boardId`다**(다르면 SpEL이 null → 403). 목록은 `keyword`(제목)·`useYn`·페이지 크기 100 clamp·정렬 화이트리스트 + `id` 보조 정렬(`PostRepositoryImpl`, QueryDSL — 게시판 소속 조건이 항상 붙는다).
- **IDOR**: 게시글 조회는 `(postId, boardId)`, 첨부 조회는 `(attachmentId, postId)` 조합이라 다른 게시판 경로로 접근하면 ADMIN도 같은 404다. 권한이 없는 게시판은 존재 여부와 무관하게 403(판정기가 대상 존재를 보지 않는다).
- **잠금**: 생성 = 게시판 `FOR SHARE`, 수정·삭제·첨부 업로드·첨부 삭제 = 게시글 `FOR UPDATE`(첨부 개수 상한 5개 검사와 동시 삭제 경합을 직렬화) 후 게시판 미삭제 확인(삭제됐으면 404). 게시글 삭제는 **첨부가 남아 있으면 409**(공지와 같은 오펀 방지) — 첨부 삭제는 `UPDATE`라 DELETE만 가진 MANAGER는 첨부 있는 글을 지울 수 없다.
- **첨부**(`PostAttachmentController`·`PostAttachmentService`, `post_attachment`): 업로드·삭제 = `UPDATE`, 목록·다운로드 = `READ`. 검증은 공지와 같은 `AttachmentFilePolicy`(10MB·글당 5개·확장자+Content-Type 화이트리스트). **게시판 `attachmentYn=false`면 새 업로드만 400**("첨부를 허용하지 않는 게시판입니다"). 파일은 **스토리지 루트**(네임스페이스 없음)에 저장하고 롤백 시 정리(`FileStorageTransactionSupport.deleteOnRollback`), 삭제는 커밋 후(`deleteAfterCommit` 루트 오버로드). **수동 회수 절차(`docs/deployment.md`)의 ②·⑤가 게시글 참조·첨부를 보존해야 한다** — 이 조건을 빼면 게시글 파일이 지워진다.
- **본문 이미지**(`com.cms.admin.contentimage`의 `BoardContentImageController`, `POST /admin/api/boards/{boardId}/content-images`): 핸들러 선언은 그 게시판의 `READ`이고 서비스가 **같은 게시판의 CREATE∨UPDATE를 재판정**(403)한다. 이미지는 `BOARD:{boardId}` 출처로 저장되고 게시글 저장 시 `replaceRefs("POST", postId, "BOARD", boardId, imageIds)`가 **같은 게시판 출처가 아니면 400**(다른 게시판·공지 이미지 거부 — 기존 참조 유지). 공개 판정은 `contentimage`·`publicweb.board`의 `CLAUDE.md`.
- **감사**: `BOARD_CREATE`·`BOARD_UPDATE`·`BOARD_DELETE`(`targetType=BOARD`), `POST_CREATE`·`POST_UPDATE`·`POST_DELETE`(`targetType=POST`), `POST_ATTACHMENT_UPLOAD`·`POST_ATTACHMENT_DELETE`(`targetType=POST_ATTACHMENT`) — `targetId`는 대상 ID, **`targetLabel` 없음**(게시판 이름·게시글 제목은 사용자 입력). 라벨은 `AdminActionTypes`와 `templates/admin/log/manage.html`을 동기화 테스트가 고정한다.
- **화면**: 게시판 관리 `templates/admin/board/manage.html`(저장 중 입력·작성 전환 잠금, 늦은 목록 응답 폐기, 삭제 버튼·409 안내), 게시글 관리 `posts.html`(`GET /admin/board/posts`, `@AdminPage`, URL 게이트 = BOARD 기능 단위 READ). 옛 공지 화면(`notice/manage.html`)의 구조·비동기 보호(세대 토큰·`AbortController`·저장 토큰)를 옮겼고 ①-2에서 공지 화면이 삭제돼 이 화면이 유일한 편집 화면이다. 상단의 "내 게시판" 선택으로 게시판을 고르고(`?boardId=&id=` 진입 지원), 편집기(`notice-editor.js`)는 **페이지에 하나만** 만들어 게시판을 열 때마다 `setUploadUrl`로 업로드 출처만 바꾼다(진행 중 업로드는 무효화). 게시판별 허용 동작(`actions`)과 게시판 `attachmentYn`으로 버튼을 숨길 뿐 서버 판정(403)이 최종이다. 게시판 이름·제목은 `textContent`/`escapeHtml`로만 넣는다.
- **최종 수정자**(`post.updater_id`, V5, 2026-10-27, `PLAN-board-definition.md` "PR 0 상세 설계"): **`updateDate`와 `updaterId`는 항상 같은 쓰기에서 함께 바뀐다** — 엔티티 메서드 `update(…, updaterId, now)`·`softDelete(updaterId, now)`·`touch(updaterId, now)`가 둘을 같이 받는다(`updateDate`를 바꾸는 새 메서드를 만들면 수정자도 받게 한다). 생성 시에는 작성자로 채우므로 **NULL은 V5 이전에 만들어져 이후 손대지 않은 글뿐**이다(백필 없음). 첨부 업로드·삭제도 수정이다 — `PostAttachmentService`가 게시글 `FOR UPDATE`로 받은 엔티티에 성공 경로 끝에서 `touch`(실패는 롤백). 현재 사용자는 `AdminSecurityService.getCurrentAdminUserId()`로 **행 잠금 전에** 읽고 null이면 403(`AccessDeniedException`) — 그래서 **서비스를 직접 부르는 시험은 `CustomUserDetails` 주체가 필요하다**(`@WithMockUser`는 회원 아이디가 없어 403, 별도 스레드는 그 스레드에 따로 심는다 — `PostConcurrencyIntegrationTest`). 노출은 관리 API(`PostResponse`·`PostSummaryResponse`)와 `posts.html`(목록 열·상세 항목)뿐이고 공개 DTO에는 없다(로그인 ID). 감사 로그가 원본이며 첨부 조작은 `POST_UPDATE`를 추가로 남기지 않는다. 수용한 한계: 첨부 업로드·삭제 직후 모달의 수정일·수정자는 다시 열 때 갱신된다. 롤백 주의는 `docs/deployment.md` "게시글 최종 수정자".
- **통합 검색**: `AdminSearchService`의 `posts` 섹션 — ADMIN은 미삭제 게시판의 미삭제 게시글(노출 여부 무관), MANAGER는 `AdminPermissionEvaluator.readableBoardIds`(READ가 유효한 게시판)로 쿼리를 한정하고 그런 게시판이 없으면 섹션 키 생략. 결과 이동은 `/admin/board/posts?boardId=&id=`.

## 공지 게시판 흡수 (①-2, 2026-10-09, `adversarial-review/plan/PLAN-notice-to-board.md` — 적대적 리뷰 5라운드 ship)

공지는 **시스템 게시판 `board_key='NOTICE'`("공지사항")의 게시글**이다. 옛 `com.cms.admin.notice` 패키지(엔티티·서비스·컨트롤러·`notice/manage.html`·`NoticeContentImageController`)는 삭제됐고 `notice`·`notice_attachment` 테이블은 V3(2026-10-22)에서 제거됐다.

- **시스템 게시판**(`board.board_key` UNIQUE, `Board.isSystem()`): 키가 있는 게시판은 **비공개 전환 400**(`updateBoard`의 `publicYn=false`)이고, **공통 공지(`NOTICE`)만 삭제 409**(`deleteBoard`, 게시글 검사보다 먼저)다 — 사이트 전용 공지(`NOTICE:{siteId}`, PR ④)는 글이 없으면 삭제할 수 있다(아래 "사이트별 게시판·공지"). 이름·`attachmentYn`은 바꿀 수 있다. 공개 `/notices`가 이 게시판에 의존하기 때문이다(`BoardRepository.findIdByBoardKey` — 삭제된 게시판이면 empty).
- **관리 화면·API**: 공지 관리는 게시글 관리(`/admin/board/posts?boardId=공지게시판`)가 대신한다. 옛 `GET /admin/notice/manage[?id=]`는 **`NoticeRedirectController`가 302**로 보낸다(`@RestController` + `ResponseEntity` — 페이지가 아니라 사이드바 모델 주입이 필요 없다, `id`는 `^[1-9][0-9]{0,15}$`만 유지). 이 경로는 `AdminFeature.BOARD`의 게이트(기능 단위 READ = 어느 게시판이든 조회 권한)에 **정확 경로 1개**로 들어 있고 `menuUrls`에는 없다(`AdminEndpointAuthorizationConventionTest`의 `REDIRECT_ONLY_GATE_PATHS` 예외). `/admin/api/notices/**`는 사라졌다(ADMIN 404, MANAGER 403 — 게이트가 없어 `/admin/**` ADMIN 캐치올).
- **권한**: 공지 권한은 일반 게시판과 같은 게시판별 권한이다(`AdminFeature.NOTICE` 제거). 결과로 **`DELEGABLE`(기능 단위 위임) 기능이 0개**가 되어 `member_permission` 경로(`PermissionCache` 기능 행·`MemberPermissionService` grants·권한관리 화면의 기능 표)는 코드만 남고 실제 기능 픽스처가 없다 — 그 시험은 `BOARD_SCOPED` 판으로 옮기거나 삭제했다(공백 목록은 `PLAN-notice-to-board.md` "구현·검증 결과"). 다음 `DELEGABLE` 기능(②배너)이 들어올 때 복구한다.
- **본문 이미지**: 공지 편집기도 게시판 업로드 경로(`POST /admin/api/boards/{noticeBoardId}/content-images`)를 쓰고, `notice-editor.js`의 기본 업로드 URL은 삭제됐다(`uploadUrl`이 없으면 이미지 업로드는 오류 안내만 한다).
- **통합 검색**: `notices` 섹션은 삭제됐고 공지 글은 `posts` 섹션에 게시판 이름 '공지사항'과 함께 나온다(권한 = 그 게시판 READ).
- **감사**: `NOTICE_*` 상수·라벨은 **과거 이력 표시용**으로 남기고 새 행위는 `POST_*`(`targetType=POST`)로 기록된다.
- **시험 이식**: 옛 `admin/notice/**` 시험 9개를 `PostServiceTest`·`PostAttachmentServiceTest`·`PostControllerTest`·`PostAttachmentControllerTest`·`PostRepositoryDataJpaTest`·`PostRepositoryImplSortTest`·`PostConcurrencyIntegrationTest`·`PostAttachmentTransactionIntegrationTest`로 옮겼고, 접근 매트릭스는 `AdminPermissionMatrixIntegrationTest`(공지 게시판 대상)가 고정한다.

## 게시글 예약 게시 — 노출 기간 (로드맵 ④, 2026-10-11, `adversarial-review/plan/PLAN-post-publish-period.md` — 적대적 리뷰 5라운드 ship)

- **공개 조건 = `useYn ∧ [publishStart, publishEnd)`**(`post.publish_start`·`publish_end` `datetime(6) NULL`): 시작 포함·종료 **미포함**, 한쪽이 null이면 그쪽은 열림, 둘 다 null이면 `useYn`만. 판정은 스케줄러 없이 조회 조건에서 한다. 공지는 공지 게시판의 게시글이라 따로 넣지 않았다(공개 공지는 2026-10-28 PR 4b부터 게시판 경로로만 열린다). 규칙의 원본은 `common/display/DisplayPeriod`(배너와 공유 — `parseKstLocal`·`requireInRange`·`normalize`·`requireValid`·`isActive`·`statusOf`)이고 상태 enum은 `DisplayStatus`(배너는 자체 enum을 그대로 둔다, 통합은 ⑦ 팝업 때 판단).
- **API**: 생성·수정 요청에 선택 필드 `publishPeriod {start, end}`(`PostPublishPeriodRequest`). PATCH 의미는 **키 없음·명시 `null` = 기간 유지, 객체가 있으면 시작·종료를 통째로 교체**(`{}` = 비움, 한쪽만 주면 나머지는 열림 — 기존 값과 병합하지 않는다). 기간만 바꾸는 PATCH도 유효하고 "변경 필드 없음" 400 검사에 포함된다. 응답(상세·목록)에 평평한 `publishStart`·`publishEnd`·`status`(`HIDDEN` > `SCHEDULED` > `EXPIRED` > `ACTIVE`, 서버 `Clock` 기준)가 나온다. 권한은 기존 `@RequireBoardPermission`(CREATE/UPDATE) 그대로 — 새 권한·경로 없음.
- **입력은 Jackson에 맡기지 않는다 — 기간을 잘못 읽으면 글이 즉시 공개된다**(리뷰 1~4라운드가 고정 Jackson 3.1.7로 재현): 시작·종료를 `String`으로 받아 `DisplayPeriod.parseKstLocal`이 `uuuu-MM-dd'T'HH:mm[:ss]` + `ResolverStyle.STRICT`로 읽는다. 오프셋(`Z`·`+09:00`)·빈 문자열(Jackson은 `""`을 null로 읽어 기간을 지운다)·공백·소수 초·날짜만·존재하지 않는 날짜(`2026-02-30`을 2월 28일로 보정)·`24:00`·숫자/배열/객체 값은 전부 400이고 메시지에 입력 원문을 싣지 않는다. 범위는 2000-01-01 이상 2100-01-01 미만(DB `datetime(6)` 범위 안의 제품 범위, 밖은 DB 예외가 아니라 입력 400). 검사 순서는 범위 → 분 절단 → `start < end`(초 절단 뒤 같아지면 400). 검증은 행 잠금 **전에** 한다.
- **중복·오타 키 거부(전역 `fail-on-unknown-properties: false`는 메뉴 계약이라 못 바꾼다)**: `PostPublishPeriodRequest`가 `@JsonAnySetter`로 알 수 없는 키(`publishStart` 오타)를, `start`·`end` 세터와 `PostCreateRequest`·`PostUpdateRequest`의 `publishPeriod` 세터가 **같은 키의 두 번째 호출**을 예외로 거부한다(뒤 값이 앞 값을 덮어쓰면 나쁜 값이 null = 기간 비움으로 바뀐다). **세 클래스의 생성자에는 `@JsonCreator(mode = DISABLED)`가 필수다** — Jackson 3는 매개변수 이름으로 생성자를 creator로 자동 인식하고, creator 경로에서는 같은 키의 마지막 값이 이겨 세터 검사가 동작하지 않는다(실서버 스택 시험이 잡았다 — 이 어노테이션을 지우면 `PostPublishPeriodApiIntegrationTest`의 중복 키 6건이 실패한다). 이 필드들에 Lombok `@AllArgsConstructor`/클래스 `@Builder`를 되돌리지 않는다. **중복 검사의 상태 플래그(`startSet`·`endSet`·`publishPeriodSet`)는 JSON 속성이면 안 된다** — 클래스 `@Getter`로 getter가 생기면 Jackson이 비공개 필드를 mutator로 추론해 요청이 `{"startSet":false}`로 플래그를 되돌려 검사를 우회한다(코드 리뷰 R1이 재현, 지우면 `PostPublishPeriodApiIntegrationTest`의 플래그 우회 5건이 실패). 그래서 세 플래그는 `@JsonIgnore` + `@Getter(NONE)`(+ 요청 DTO는 `@Setter(NONE)`)이고 `@Schema(hidden)`만으로는 바인딩이 막히지 않는다.
- **공개 경로 다섯 곳이 한 쌍이다 — 한 곳을 바꾸면 모두 바꾼다**: ① 목록·검색·COUNT `PostRepositoryImpl.searchPublished`(QueryDSL `isPublished` 조건 객체를 SELECT·COUNT가 공유) ② 메인 `findLatestPublished`(같은 `isPublished`) ③ 상세·첨부 `PostRepository.findPublishedById`(JPQL, `findByIdAndBoardIdAndDeletedFalseAndUseYnTrue`는 제거됨 — 시각 없는 우회 경로를 컴파일 단계에서 없앴다) ④ 본문 이미지 `ContentImageRefRepository.existsPublishedPostRef`(JPQL — 빠지면 글은 404인데 그 글의 이미지가 미리 공개된다). 네 표현이 `DisplayPeriod.isActive`와 같은 의미임은 `PostRepositoryDataJpaTest`가 저장→flush→clear→재조회로 경계(시작 직전·시작·종료 직전·종료, 시작만·종료만·양끝 null)를 대조해 고정하고, 실제 스택 경로 전부는 `PostPublishPeriodPublicIntegrationTest`가 `MutableClock`으로 고정한다(변이 실험: 이미지 JPQL·상세 JPQL·QueryDSL 조건을 각각 지우면 시험이 실패함을 확인).
- **판정 시각은 요청당 1회 주입된 KST `Clock`**: 공개 서비스 3곳(`PublicBoardService`·`PublicHomeService`·`PublicContentImageService`)이 `LocalDateTime.now(clock)`을 메서드 호출당 한 번 산출해 쿼리에 넘긴다(공개 메인은 공지·새 글 두 쿼리가 같은 시각을 쓴다). `PostService`는 `PostResponse.from(post, now)`·`PostSummaryResponse.from(post, now)`에 같은 `now`를 넘긴다.
- **수용한 한계**: 기간은 통째 교체 + **마지막 저장 우선**이다 — 게시글에 낙관적 락이 없어 낡은 편집 화면이 다른 관리자가 줄인 기간을 되돌릴 수 있다(제목·본문·`useYn`도 같은 규칙). 화면은 기간이 바뀐 경우에만 `publishPeriod`를 보낸다. 미리보기: 그 게시판 READ 권한자(ADMIN 포함)는 예약·만료 글의 본문 이미지를 기간과 무관하게 본다(`PublicContentImageService`의 권한자 분기).
- **화면**(`posts.html`): 폼에 노출 시작·종료(날짜 + 시·분 select — 배너 화면과 같은 방식으로 `datetime-local`을 피한다, 시·분만 고르고 날짜를 비우면 오류), 목록에 "노출 상태"(노출 중/예약됨/만료/비노출 배지)·"노출 기간" 열, 상세에 상태·기간. `badge-status-scheduled`·`badge-status-expired`는 이 화면의 `<style>`에만 있다. 변경 감지는 시작·종료 중 하나라도 바뀌었을 때만 `publishPeriod`를 통째로 보낸다.
- 시험: `PostPublishPeriodApiIntegrationTest`(관리 API — 입력 계약 위반 전부 400 + 기존 기간·제목 불변, 중복·오타 키, 범위 경계 왕복, PATCH 유지/교체/비움), `PostPublishPeriodPublicIntegrationTest`(모든 공개 경로 경계 매트릭스·시작만/종료만·`useYn=false` 겹침·COUNT 누수·공유 이미지·READ 권한자 미리보기), `PostRepositoryDataJpaTest`(DB 경계 대조), `DisplayPeriodTest`(파서·범위·상태).

## 게시판 표시 설정·`version`·쓰기 중지 (2026-10-27, V6, `PLAN-board-definition.md` PR 1 — 적대적 리뷰 3라운드 ship)

- **새 설정 7개**(`board`): `description`(평문 500자)·`list_page_size`(10·20·30·50)·`author_label`(공개 화면의 **고정 작성자 표시명 — 로그인 ID를 공개하지 않는다**, 50자)·`show_view_count`·`new_badge_days`(0..30, 0 = 끔)·`writable_yn`·`version`. 전부 `NOT NULL DEFAULT <현행 동작>`(문자열 둘은 NULL)이라 이전 앱이 만든 행도 지금과 같게 보이고, 엔티티는 `@Builder.Default`라 빌더 호출·직접 SQL INSERT 시험이 손대지 않아도 된다. 범위·정리는 **`BoardService` 한 곳**이 한다 — 요청 DTO에 이 문자열들의 `@Size`를 두지 않는다(`@Valid`가 정리 전 길이로 먼저 400을 내 "공백 포함 502자 → 정리 후 500자"·"긴 공백만 = 삭제"가 서비스에 못 닿는다).
- **PATCH 3상태**: 설명·작성자 표시명은 **키 누락·`null` = 유지, `""`·공백만 = 삭제(NULL 저장)**, 그 밖 = `strip()` 후 저장. 서비스가 최종값을 계산해 `Board.update(…, BoardDisplay, now)`에 **전부 대입**한다(`BoardDisplay` record) — 엔티티에서 "지움"과 "유지"가 섞이지 않게 기존 "null = 유지" 인자(이름·공개·첨부)와 분리했다. "변경할 필드 없음" 400은 새 필드를 포함해 판정하고 `version`만 보낸 PATCH도 400이다.
- **`version`**(정적 페이지·배너·팝업과 같은 방식, 1부터): PATCH 본문·DELETE `?version=`에 **필수** — 누락·0 이하 400(**행 잠금 전**), 잠근 뒤 다르면 **409**("다른 관리자가 먼저 수정했습니다…"), 성공하면 정확히 +1(`Board.update`가 올리고 `changeSite`는 같은 요청의 `update` 뒤에만 불려 올리지 않는다 — 한 요청이 +2 되지 않는다), 소프트 삭제도 +1. DELETE는 쿼리 파라미터라 Bean Validation을 거치지 않아 서비스가 400을 만든다. **시험이 게시판 PATCH·DELETE를 직접 부르면 `version`이 필요하다**(`BoardSiteScopeApiIntegrationTest`는 DB의 현재 버전을 붙이는 `patchBoard`·`deleteBoard` 헬퍼를 쓴다). 화면은 편집 시작 시점의 `version`을 보내고 409면 모달을 닫고 안내 후 목록을 다시 읽는다.
- **쓰기 중지(`writable_yn = 0`, 화면 이름은 "사용(쓰기 허용)")**: `publicYn`(공개 노출)과 의미가 독립이라 **공개 경로 다섯 곳은 바뀌지 않는다**(보관 게시판도 공개를 유지할 수 있다). 막는 것 — 게시글 생성·수정(**노출만 끄는 수정 포함**)·첨부 업로드·본문 이미지 업로드, 전부 **400** `Board.WRITE_STOPPED_MESSAGE`(한 문구를 세 서비스가 공유). 허용 — 조회·**첨부 삭제**·게시글 삭제(첨부가 남은 글은 삭제가 409라 첨부 삭제를 막으면 보관 게시판의 글을 못 지운다). **공통 공지 게시판은 끌 수 없다**(400, 사이트 전용 공지는 가능). 새 쓰기 경로를 만들면 이 판정과 잠금을 같이 넣는다.
- **쓰기 중지 잠금**: 막아야 할 쓰기는 모두 게시판 행을 **`FOR SHARE`**(`findByIdAndDeletedFalseForShare`)로 잡고 그 안에서 판정한다 — 전환(PATCH의 `FOR UPDATE`)과 직렬화된다. 순서는 **게시글 `FOR UPDATE` → 게시판 `FOR SHARE`**(수정은 `PostService.lockPostForWrite`, 첨부 업로드는 `PostAttachmentService.upload`; 삭제·첨부 삭제는 판정이 없어 잠금 없는 확인 그대로). 게시판 쪽 잠금(PATCH·삭제)은 게시글 행을 잠그지 않아 순환이 없고, 이미지 참조 교체(`replaceRefs`의 이미지 `FOR SHARE`)보다 먼저 잡는다. 본문 이미지 업로드(`ContentImageService.uploadForBoard`)는 **권한 403을 먼저** 판정한 뒤 게시판 `FOR SHARE` → 400(권한 없는 사용자에게 게시판 상태를 알려 주지 않는다). 시험은 `BoardDisplaySettingsConcurrencyIntegrationTest`(변이 실험으로 수정의 공유 잠금을 일반 읽기로 바꾸면 "전환 중 수정이 400" 시험이 실패함을 확인, 시험 쪽 잠금은 MariaDB 구문 `LOCK IN SHARE MODE`).
- **공개 반영**(`com.cms.publicweb.board`): 목록 크기·조회수·배지·설명·표시명을 `PublicBoardService`가 **DTO를 만들 때** 거른다(조회수 꺼진 게시판은 `PublicPostSummary.viewCount`·`PublicPostDetail.viewCount`가 null — 템플릿이 아니라 서비스). 일반 게시판과 **공지 템플릿(`public/notice/*`)에 같게** 넣는다(공지는 같은 서비스·DTO에 위임하는 어댑터지만 템플릿이 두 벌이다). 새 글 배지는 `NewBadge.isNew` 한 곳 — 기준 = `createDate`·`publishStart` 중 **NULL 아닌 값의 최댓값**(예약 글은 공개 시각부터), N×24시간 이내(경계 포함), 둘 다 NULL(`post.create_date`는 스키마상 NULL 허용)이면 배지 없음. 허용 페이지는 **OFFSET 10,000(포함) 고정**이라 `page ≤ 10000 / 목록 크기`(10→1000, 20→500, 30→333, 50→200), 넘으면 0으로 보정. **알려진 한계(기존 동작)**: 글이 상한보다 많으면 마지막 허용 페이지의 `hasNext`가 참이라 '다음' 링크가 0페이지로 돌아간다(크기 10·page 1000에서 이미 같음).
- **롤백**: 이전 앱은 모든 새 컬럼이 DEFAULT라 그대로 동작하지만 **쓰기 중지를 무시**하고 `version`을 올리지 않는다(`docs/deployment.md` "게시판 표시 설정·쓰기 중지").
- 시험: `BoardServiceTest`(검증은 잠금 전·version 비교·3상태), `BoardDisplaySettingsApiIntegrationTest`(관리 API 계약 전부), `BoardDisplaySettingsConcurrencyIntegrationTest`, `BoardDisplaySettingsPublicIntegrationTest`(`publicweb.board`, 일반·공지 템플릿), `NewBadgeTest`, `BoardDisplaySettingsUpgradeTest`(루트 패키지 — V5 → V6 기존 행).

## 게시판 작성 정책 (2026-10-28, V7, `PLAN-board-definition.md` PR 2 — 적대적 리뷰 2라운드 ship)

- **새 설정 5개**(`board`): `attach_max_count`(1..5)·`attach_max_size_mb`(1..10)·`attach_extensions`(전역 허용 목록의 부분집합, **NULL = 전체**)·`body_image_yn`·`publish_period_yn`. 전부 현행 동작 DEFAULT라 이전 앱이 만든 행도 지금과 같다. 쓰기는 PR 1의 `BoardDisplay`와 분리한 record `BoardWritePolicy`로 `Board.update`에 최종값을 넘긴다. 범위·정규화는 `BoardService` 한 곳이고(요청 DTO에는 `attachExtensions`의 원소 수 `@Size(max = 50)`만 — 개수는 정리 전후가 같다), "변경할 필드 없음" 판정에 새 필드가 포함된다.
- **전역 상한이 천장이다 — 검증 진입점은 `AttachmentFilePolicy` 하나**(`requireAllowedExtension(filename, boardSet)`가 전역 검사를 먼저 하고 게시판 제한을 뒤에 한다). `PostAttachmentService`는 게시판 값을 `min(게시판 값, 전역 상수)`로 쓰므로 DB를 직접 고쳐 전역 밖 확장자·초과 크기를 넣어도 막힌다(시험 고정). 0개(첨부 금지)는 두지 않는다 — 그 뜻은 `attachmentYn=false`가 가진다.
- **확장자 표현은 하나**: `normalizeExtensions`가 소문자·중복 제거·정렬 후 **전역 전체와 같으면 null**로 돌려준다 — "전체"를 NULL과 "모든 확장자 나열" 두 표현으로 두면 전역에 확장자가 늘 때 게시판마다 결과가 갈린다. 요청은 키 누락·null = 유지, 배열 = 통째 교체, 빈 배열 400. **응답은 전역 `non_null` 설정 때문에 전체 허용이면 `attachExtensions` 키가 빠진다**("키 누락 = 전체"). `MyBoardResponse.attachExtensions`는 실효 목록(전체면 전역 전체를 펼침, 항상 있음).
- **본문 이미지를 끈 게시판 = 기존 이미지 유지 + 새 이미지만 400**: `ContentImageService.replaceRefs(…, allowNewImages)` 오버로드가 **실제로 존재하는** 이미지 중 이 글이 지금 참조하지 않는 것을 보면 삭제·쓰기 전에 400이다(기존 5인자판은 `true`로 위임 — 배너·팝업·미디어 호출부 무변경). **존재하지 않는 ID는 허용 게시판처럼 조용히 뺀다** — sanitizer는 형식이 맞는 ID를 남기므로 깨진 ID가 든 기존 글이 있을 수 있고, 거부하면 그 글은 정책을 끈 뒤 오타도 못 고친다. 이미지 업로드(`uploadForBoard`)도 쓰기 중지 판정 뒤에 400. `ContentBodyPolicy.sanitize`는 그대로(이미지를 불허하는 sanitizer로 바꾸면 저장 때 이미지가 조용히 사라진다).

## 게시판 슬러그 — 공개 주소 (2026-10-28, V9·V10, `PLAN-board-definition.md` PR 4a — 적대적 리뷰 3라운드 ship)

- **기본 슬러그는 저장하지 않는다**: `board.slug`(UNIQUE, NULL 허용)에는 관리자가 정한 슬러그만 있고 NULL이면 `board-{id}`다(`BoardSlug.effective`, `Board.publicSlug()`). 그래서 백필이 없고 **SQL `INSERT INTO board`·`Board.builder()`로 만든 게시판(시험 픽스처·롤백한 이전 앱)도 그대로 `board-{id}`로 열린다** — 시험에서 슬러그를 신경 쓸 필요가 없다. 공개 URL을 시험에서 쓸 때는 `/main/boards/board-{id}`다(숫자 id 경로는 404).
- **1회 변경·영구 예약**: 바꿀 수 있는 것은 NULL → 값 한 번뿐이고(`Board.assignSlug`, `isSlugChangeable()`) 그래서 옛 슬러그는 언제나 `board-{id}`라 별칭 테이블 없이 301 대상을 계산한다. **소프트 삭제는 `slug`를 비우지 않는다**(`board_key`·`site_id`와 다름) — 삭제된 게시판이 UNIQUE를 계속 쥐어 한 번 쓴 슬러그를 다른 게시판이 못 가져간다(브라우저가 301을 캐시하므로 재사용은 엉뚱한 게시판으로 보낸다). 이 성질을 바꾸려면 301 정책부터 다시 본다.
- **형식(`BoardSlug.isAssignable`)**: 정적 페이지 슬러그와 같은 `^[a-z0-9]+(-[a-z0-9]+)*$` 2~50자, **숫자만 금지**(옛 id 주소와 혼동), **`board-{숫자}` 금지**(기본 슬러그 이름 공간 — 이게 있어야 사용자 슬러그와 기본 슬러그가 겹치지 않는다). 컬럼 정렬이 `general_ci`라 **조회 전에 반드시 형식 검사**를 한다(`News`가 `news`에 맞지 않게). 기본 슬러그 식별 `parseDefault`는 정규형(`board-12`)만 — `board-012`·`board-+12`는 404.
- **관리 API**: 생성 `slug` 선택(누락·공백 = 기본), PATCH `slug`(null = 유지, **지금 값과 같으면 무변화**라 화면이 현재 값을 그대로 보내도 된다). 순서: 형식 400(잠금 전, 기본 슬러그 형태는 잠근 뒤 "지금 값인가"로 판정) → 이미 바꾼 게시판의 다른 값 400 → 중복 사전 검사 → flush 중 `uk_board_slug` 위반. **중복은 `DuplicateResourceException`(409 `DUPLICATE_RESOURCE`)** — 화면이 낡은 버전 409(`RESOURCE_CONFLICT`)와 코드로 구분해 모달을 닫지 않는다. 제약 이름은 `NestedExceptionUtils.getMostSpecificCause` 메시지로 고른다(공지 중복 `uk_board_board_key`와 구분). 공지 게시판도 바꿀 수 있다. 응답 `slug`(현재 값, 항상 있음)·`slugChangeable`.
- **숫자 게시판 경로 금지**(`common.web.BoardLinkPaths` — 퍼센트 디코딩·점 세그먼트 정리 뒤 `/{아무 세그먼트}/boards/{PathIds로 읽히는 값}`): 본문(`InternalLinkPaths` → sanitizer가 `href`만 제거)·배너/팝업 링크(`SafeLinkUrlValidator` 400, 안내 문구)·메뉴 링크(`SiteLinkPolicy` 400, 출력 재검증으로 남은 행은 라벨만)가 같은 함수를 쓴다. id 해석은 `common.web.PathIds`(`Long.parseLong`과 비음수 구간 같은 의미 — `+12`·전각 숫자 포함) 하나다.

## 게시글 대표 이미지 (2026-10-29, V12, `PLAN-board-definition.md` PR 5 — 적대적 리뷰 5라운드 ship)

- **대표 이미지 = 그 글 본문이 참조하는 이미지 중 하나**(`post.cover_image_id`, FK `ON DELETE SET NULL`): 공개 판정은 기존 `content_image_ref`가 그대로 하므로 새 공개 규칙이 없다. 불변식 "대표 ∈ 그 글의 저장 후 참조"는 **서비스가 저장 때** 지킨다(`PostService.applyCoverImage` — 참조 집합은 `replaceRefs`의 반환값, 본문이 안 바뀌는 수정은 `findReferencedImageIds`). 본문에 없는 이미지·존재하지 않는 이미지는 같은 400(`COVER_NOT_IN_BODY`). 썸네일 생성·실패 계약·메모리 방어는 `com.cms.admin.contentimage`의 `CLAUDE.md`.
- **API `coverImageId` 3상태(PATCH)**: 키 없음 = 유지, `null` = 해제, 정수 = 지정(생성은 누락·`null` = 없음). **세터가 `Object`로 받아 `CoverImageIdInput.parse`가 엄격 파싱**한다 — 정수 1 이상과 `null`만, 문자열(`""`·`"12"`)·소수·불리언·배열·객체·0·음수·`long` 초과는 400. `Long` 필드로 바꾸지 않는다(Jackson이 `""`를 `null`(= 해제)로 읽어 화면 버그가 대표를 조용히 지운다 — 팝업 기간의 함정과 같다). 중복 키는 거부하는 플래그(`coverImageIdSet`)가 `publishPeriodSet`과 같은 이유로 `@JsonIgnore` + `@Getter/@Setter(NONE)`이다(JSON 속성이면 우회된다). `PostUpdateRequest.hasCoverImageId()`가 "키 있음"을 가르고, 빌더로 만든 요청은 값이 있을 때만 "있음"이라 **해제(명시 null)를 만드는 시험은 `clearCoverImage()`를 쓴다**. "변경할 필드 없음" 400 판정에 대표 키 존재가 포함된다(대표만 바꾸는 PATCH도 유효).
- **자동 해제는 서버가 저장 시점의 DB 값으로 정한다**: 본문이 바뀌었고 요청에 키가 없는데 현재 대표가 새 참조에 없으면 `null`로 바꾼다. 키가 있으면 그 값이 우선. **화면은 사용자가 직접 고른 경우에만 키를 보낸다**(본문에서 대표를 지워 자동으로 "없음"이 된 것은 보내지 않는다) — 그래야 낡은 화면이 다른 관리자가 그 사이 바꾼 대표를 덮어쓰지 않는다(`PostCoverImageApiIntegrationTest.staleScreenDoesNotOverwriteOtherAdminsCover`, 실기 확인: 페이로드에 `coverImageId` 키가 없다).
- **잠금·트랜잭션 변경 없음**: 대표 지정은 기존 `createPost`·`updatePost`(`READ_COMMITTED` 최상위) 안에서 일어나고 새 잠금이 없다 — 게시글 행 `FOR UPDATE`가 같은 글의 동시 저장을, 이미지 참조 잠금이 라이브러리 삭제를 막는다. 판정 순서: 쓰기 중지 → 예약 → 고정 → (참조 교체) → 대표 지정 → 썸네일. 쓰기 중지 게시판은 대표 변경도 400이다. 썸네일 400(디코딩 실패·CMYK·계수 버퍼 초과 등)·409(카운터 용량)·503(생성 자리 없음)은 **본문 저장까지 전부 롤백**한다(화면은 입력을 보존한다).
- **응답**: `PostResponse.coverImageId`(상세·생성·수정 응답)만이다. 관리 목록 DTO·공개 상세 DTO에는 없고, **공개 목록 DTO(`PublicPostSummary`)에는 PR 6(게시판 유형)부터 있다**(아래 "게시판 유형").
- **롤백 후 깨진 불변식**: 이전 앱이 본문에서 대표를 빼면 "대표 ∉ 참조"가 남을 수 있고, 그 상태에서 그 글 수정과 그 이미지 삭제(FK `SET NULL`이 글 행 잠금을 기다림)가 겹치면 교착 → 전역 핸들러 **409 "다시 시도"**다. 재배포 직후 복구 SQL로 전제를 없앤다(`docs/deployment.md` "게시글 대표 이미지·썸네일").
- **화면**(`posts.html`): 편집 폼 "대표 이미지" 묶음 — 편집기 본문의 이미지(`NoticeEditor.getImageIds()`, `onChange` 옵션이 본문 변경 때 선택지를 다시 그린다)를 미리보기 라디오 + "없음"으로 보인다(이미지가 없으면 숨김). 보기 모드는 `/content-images/{id}?size=thumb` 미리보기. 변경 감지는 `coverUserChanged ∧ 선택값 ≠ 연 시점 값`일 때만 `coverImageId`를 보낸다.
- 시험: `PostCoverImageApiIntegrationTest`(지정·썸네일·카운터 바이트만·공유 이미지·동시 지정·검증 롤백·503·409·PATCH 3상태·엄격 파싱 9값·중복 키·자동 해제·낡은 화면·쓰기 중지·삭제 수명주기), `PostCoverImageUpgradeTest`.

## 게시판 유형 (2026-10-29, V13, `PLAN-board-definition.md` PR 6 — 적대적 리뷰 2라운드 ship)

- **`board.board_type`**(`VARCHAR(20) NOT NULL DEFAULT 'LIST'`, CHECK 없음): 공개 목록의 **모양만** 정한다 — `LIST` 목록형(현행)·`GALLERY` 대표 이미지 격자·`WEBZINE` 대표 이미지 + 요약. 공개 경로·공개 조건·레이트리밋은 유형과 무관하다. 공지 게시판(공통·전용)도 바꿀 수 있고 쓰기 중지 게시판도 바꿀 수 있다(정의 변경이라 게시글 쓰기가 아니다).
- **저장 원본과 해석값을 분리한다 — `BoardDisplay.boardType`은 문자열 원본이다**(리뷰 R1-1): `Board.getBoardType()`은 DB 원본, `Board.type()`은 해석값(`BoardType.fromStored` — null·알 수 없는 값은 `LIST`, 읽기 전용 소비자인 공개 화면·응답용). 해석값을 `BoardDisplay`에 넣으면 "누락 = 현재값" 계산과 `Board.update`의 전체 대입이 알 수 없는 저장값을 관계없는 수정에서 `LIST`로 덮어써 다음 버전으로 재배포해도 복구되지 않는다. **새 코드가 `BoardDisplay`에 `type()`을 넣지 않는다**(`BoardTypeApiIntegrationTest.unknownStoredValueSurvivesUnrelatedEdits`가 고정, 변이 실험으로 확인).
- **API**: 생성·수정 요청의 `boardType`은 **문자열로 받아 서비스가 `BoardType.parse`로 엄격 파싱**한다 — 이름과 정확히 같은 문자열만(대소문자 구분, 앞뒤 공백 불허, `""`는 400, 문구에 입력 원문 없음). `Integer`·enum 필드로 바꾸지 않는다(Jackson이 `""`를 null로 읽는 함정 — 팝업·대표 이미지와 같다). 생성: 누락 = `LIST`. 수정: **누락·`null` = 저장 원본 유지**, 값이 있으면 그 이름 저장, 검증은 행 잠금 전. "변경할 필드 없음" 판정에 `boardType`이 포함된다. 응답 `BoardResponse.boardType`은 해석값이다(알 수 없는 원본은 `LIST`로 보인다 — 원본은 응답에 싣지 않는다). **`MyBoardResponse.boardType`도 같은 해석값**이다(2026-10-31, `PLAN-board-type-editor-note.md` — 게시판 정의 API를 못 쓰는 READ 권한 MANAGER도 유형을 받는다, 인가 변경 없음).
- **게시글 편집 폼의 유형 안내**(`posts.html` `coverTypeNote`, 2026-10-31): 모달을 연 게시판(`modalBoard`)이 갤러리·웹진이면 편집기 아래에 "공개 일반 목록에 대표 이미지가 쓰이고 대표 없는 글은 자리표시" 안내를 보인다. **대표 이미지 묶음(`coverGroup`) 밖에 둔다** — 그 묶음은 본문에 이미지가 없으면 숨어서 안내가 가장 필요한 순간에 안 보인다. 문구는 "일반 목록"으로 한정한다(상단 고정 영역은 유형과 무관하게 이미지 없는 한 줄, 웹진 요약은 본문 글자가 있을 때만). 본문 이미지를 끈 게시판은 "넣은 뒤 고르세요" 꼬리를 뺀다. `applyWritePolicy`가 모달을 열 때마다 다시 계산한다. 안내일 뿐 서버 판정과 무관하다.

## 조회수·다운로드 수 + 대시보드 콘텐츠 현황 (2026-10-13, `adversarial-review/plan/PLAN-view-download-count.md` — 적대적 리뷰 2라운드 ship)

- **저장**: `post.view_count`·`post_attachment.download_count`(`bigint NOT NULL DEFAULT 0`). 엔티티 필드는 **`@Column(updatable = false)`** — 관리자 수정이 로드된 낡은 값으로 전체 컬럼 UPDATE를 해도 카운터는 SET에서 빠진다(제거하면 `ContentCountIntegrationTest.entityUpdate_doesNotOverwriteCounter`가 실패 — 변이 확인). 요청 DTO에는 카운터가 없고(수정 불가) 응답(`PostResponse`·`PostSummaryResponse`·`PostAttachmentResponse`)에는 읽기 전용으로 나온다. 정렬 화이트리스트에 `viewCount`가 있다.
- **증가는 두 빈으로 나눈다**: 비트랜잭션 `ContentCounterService`(중복 억제 + 호출 전체 try/catch)가 `@Transactional` 별도 빈 `ContentCounterWriter`(JdbcTemplate)를 부른다 — 메서드 안 try/catch는 트랜잭션 시작·커밋 실패를 못 잡는다. Writer의 UPDATE는 `SET STATEMENT max_statement_time=3, innodb_lock_wait_timeout=1 FOR UPDATE … SET n = n + 1`(관리자가 행을 `FOR UPDATE`로 잡고 있어도 공개 응답이 오래 붙잡히지 않고, 초과하면 카운트 1회만 유실). 일반 `@Modifying @Query`로 바꾸지 않는다(문장 제한이 안 걸린다).
- **동시 쓰기 상한**: `ContentCounterService`가 동시에 DB에 쓰는 집계를 **3개로 제한**한다(`Semaphore.tryAcquire`, 대기 없음 — 관리자가 행을 잡은 동안 서로 다른 IP가 몰려도 카운터가 공용 풀 연결을 줄줄이 쥐지 못하게, 코드 리뷰 R1). 자리가 없으면 이번 집계를 버리고 중복 억제 키도 되돌린다 — 폭주 시 카운트가 일부 유실될 수 있는 것은 의도다(최선 노력).
- **무엇을 1회로 세나**: (IP = `getRemoteAddr()`, 종류, 대상)당 **30분에 1회**(Caffeine, 최대 10만 키, 재기동·포화 시 중복 집계 가능 — 레이트리밋과 같은 fail-open 수용). 프록시 뒤에서는 한 IP로 보여 과소 집계된다(ingress 도입 시 재평가). 최선 노력 지표라 감사 로그가 아니며 어떤 실패도 응답에 영향이 없다(예외 클래스명만 WARN).
- **집계 시점은 공개 컨트롤러**(`PublicBoardController` — 공지 공개 컨트롤러의 복제는 PR 4b에서 사라졌다): 조회는 **공개 판정이 통과한 상세 GET**만(HEAD는 암묵 매핑으로 같은 핸들러라 `request.getMethod()`로 제외), 다운로드는 **파일 열기에 성공한 GET**만(`try-with-resources` 안, HEAD 핸들러 제외, "내려받기 시작" 기준). 404·비공개·예약 글은 호출 자체가 없다. 관리자 열람도 센다.
- **대시보드 "콘텐츠 현황"**(`ContentStatsService`·`ContentStatsQueryRepository`, `AdminMainController`가 `contentStats` 모델로 전달): 총 조회수·총 다운로드·상위 5 게시글·상위 5 첨부. **MANAGER는 READ가 유효한 게시판만**(`readableBoardIds`, 통합 검색과 같은 규칙 — 없으면 쿼리 없이 0·빈 목록), ADMIN은 미삭제 게시판 전부. 삭제된 글·게시판은 제외, 비노출 글은 포함. 방문자 지표와 **폴백이 분리**돼 실패 시 `contentStats`만 null(화면 안내 문구). 상위 N은 인덱스 없이 정렬한다(규모가 작아 수용 — 느려지면 새 마이그레이션으로 인덱스).
- **수용한 한계**: 기간별 추이·이벤트 테이블·공개 화면 조회수 노출·카운터 초기화는 범위 밖. 롤백하면 카운트가 멈출 뿐 값은 보존된다.

## 사이트별 게시판·공지 (PR ④, 2026-10-14)

게시판에 소속 사이트 `site_id`(NULL = 모든 공개 사이트 공통, FK `RESTRICT`)가 생겼고, 사이트마다 자기 공지 게시판(키 `NOTICE:{siteId}`)을 둘 수 있다. **규칙·잠금·삭제·롤백의 원본은 `com.cms.admin.site`의 `CLAUDE.md` "사이트별 게시판·공지"** — 여기에는 이 패키지에서 조심할 것만 둔다: ① 공개 조회는 `BoardRepository.findPublicById(id, siteId)`(옛 `findByIdAndDeletedFalseAndPublicYnTrue` 제거)와 `findLatestPublished(boardId, siteId, excludeSystemBoards, …)`가 소속 조건을 쿼리에 고정한다 — 공개 경로 조건을 바꿀 때 `ContentImageRefRepository.existsPublishedPostRef`의 사이트 조건도 함께 본다 ② `Board.softDelete`는 `site_id`·`board_key`를 비운다(삭제된 행이 사이트 삭제 FK·키 유일성을 붙잡지 않게) ③ 게시판 PATCH의 `siteScope`는 명시한 경우에만 대상을 바꾸고 공지 게시판은 바꿀 수 없다 ④ 사이트 전용 공지 게시판의 권한은 일반 게시판과 같은 게시판별 권한이다(MANAGER에게 주려면 권한관리 화면에서 부여) ⑤ `NoticeRedirectController`(`/admin/notice/manage`)는 공통 공지 게시판으로만 간다.
