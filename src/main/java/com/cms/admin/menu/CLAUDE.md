이 디렉터리(메뉴 도메인) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조.

## Menu

- **노출 범위(`access_role`)는 권한관리 PR ②(2026-10-02)에서 코드에서 제거**됐다 — `Menu.accessRole`·`MenuAccessRole`·DTO 필드·화면 select·권한 불변식(ALL 메뉴의 조상에 ADMIN 없음) 전부 삭제. DB 컬럼은 PR ②·③ 동안 롤백 호환을 위해 존치했다가 PR ④(2026-10-02)의 V16이 `DROP COLUMN`했다(되돌릴 수 없음, 배포 전 백업 필수 — `docs/migration-guide.md`). 낡은 클라이언트가 `accessRole`을 보내도 Jackson이 조용히 무시한다(400 아님)
- 사이드바는 `AdminSidebarAdvice` → `MenuService.getSidebarMenus(Predicate<String> urlVisible)`가 활성 메뉴를 **권한 판정기에서 도출한 URL 가시성**으로 가지치기해 동적 렌더링한다(`MenuVisibility` 순수 함수 — 아래 "노출 계산"). **최대 3단(최상위 + 하위 + 하위의 하위, `MenuService.MAX_MENU_DEPTH`)까지** 그린다(2026-10-01, `PLAN-menu-structure-apply.md` PR A). SB Admin 2는 2단까지만 제공하므로 3단은 `sidebar.html`이 2단 `collapse-inner` 안에 **중첩 collapse**로 그리고, 현재 페이지가 안에 있으면 `SidebarMenuResponse.hasDescendantUrl`로 조상 그룹을 펼친다. 생성 API(`createMenu`)도 같은 상한을 검증한다 — 부모 깊이가 이미 3이면(결과 4단) 400. 생성 깊이 검증은 잠금 없이 조상 사슬을 읽지만 전체 행 잠금(`findAllForUpdate`)을 첫 조회로 써 구조 반영과 직렬화된다
- 기본 메뉴 시드는 Flyway `V3__seed_default_menus.sql`이 담당한다 — menu 테이블이 **완전히 비었을 때만** 전체 시드하며, 행이 하나라도 있으면 건드리지 않는다 (보충 기능 없음)
- **메뉴 구조 일괄 반영 API**(`MenuService.applyStructure`, 2026-10-01 PR B, 계획서 `adversarial-review/plan/PLAN-menu-structure-apply.md` — 적대적 리뷰 4라운드 ship): `PUT /admin/api/menus/structure`(ADMIN 전용, 본문 `{menus:[{menuNo, baseUpMenuNo, baseOrd, upMenuNo}...]}`). 화면이 드래그로 만든 초안(**비활성 포함 전체 메뉴의 최종 구조**)을 한 번에 받는다. 같은 `upMenuNo` 안의 **배열 순서가 새 `ord`(0..n-1)** 이고 `base*`는 초안을 만든 시점의 값이다. 기존 `PUT /order`(형제 재조정)·`PATCH /{id}/parent`(부모 이동)와 `MenuService.reorderMenus`·`moveMenu`·관련 DTO·테스트는 **PR C(2026-10-01)에서 삭제**했다(규칙이 이 API 한 곳에만 남는다). `MENU_REORDER`·`MENU_MOVE` 감사 액션 상수·라벨은 과거 감사 로그 호환으로 유지한다. **잠금**: 첫 애플리케이션 테이블 조회가 `findAllForUpdate`(전체 행 `menuNo` 오름차순 PESSIMISTIC_WRITE) — 구조 반영·**생성**이 같은 순서로 전체를 잠가 서로 직렬화된다(이 두 경로끼리 교착 없음). 비활성화·재활성화(자식→부모 개별 잠금)와의 교착은 InnoDB 탐지 → 409(가용성 문제로 허용, 정합성은 잠금 후 최신값 재검증). 수정은 항상 단일 행 잠금(`accessRole` 제거 후 전체 행 잠금 경로 없음). **낙관적 검사(409)**: 요청 집합이 현재 **트리 도달 가능** 집합과 다르거나 어떤 행의 현재 (부모, ord)가 base와 다르면 409 — 고아·루트 없는 순환 행은 비교에서 빼고 건드리지 않는다(화면이 못 보는 행 때문에 영구 409가 되는 것 방지). 요청 개수 상한은 없다 — **요청 집합이 도달 집합과 다르면 항상 409**이며(메뉴 영구삭제로 현재 행 수보다 항목이 많아진 낡은 초안도 400이 아니라 409라 화면이 초안을 폐기·재조회한다, 2026-10-02 `PLAN-menu-permanent-delete.md` PR B에서 개수 초과 400 분기를 집합 비교 뒤로 옮겨 제거) 요청 집합이 도달 집합과 같으면 요청 수 ≤ 전체 행 수는 저절로 성립한다. **검증(400)**: 같은 메뉴 번호 중복·요청에 없는 부모·순환(전체)·**부모가 바뀐 메뉴의 서브트리에 한해** 깊이 > 3(`MAX_MENU_DEPTH`)·활성 메뉴가 비활성 부모 아래. 이동하지 않은 서브트리의 기존 위반(4단)은 이 반영을 막지 않는다. **저장 범위**: 현재 표시 순서와 요청 순서가 다른 부모 그룹만 `0..n-1`로 다시 매기고 값이 같은 행은 쓰지 않는다(`ord`가 100·200이어도 손대지 않은 그룹은 그대로, `updateDate` 보존). 요청 토큰은 항목 네 필드 모두 `JsonNode`로 받아 `menuNo`는 **null 아닌 정수만**(`1.9`가 `1`로 잘려 엉뚱한 메뉴가 옮겨지는 것을 코드 리뷰가 재현해 추가), `baseUpMenuNo`·`upMenuNo`는 정수 또는 명시적 `null`, `baseOrd`는 int 정수 또는 `null`만 허용하고 **필드 누락도 400**이다(트리 응답이 `non_null`이라 최상위 `upMenuNo`·레거시 null `ord`가 생략되므로 **화면이 `?? null`로 명시해서 보내야 한다**). 감사 `MENU_STRUCTURE_APPLY`(`targetId` 없음). (과거의 "ALL 메뉴의 조상에 ADMIN 없음" 권한 불변식은 PR ②에서 삭제 — 판정기가 가지치기로 대신한다.) **생성의 `ord` 오버플로**: 같은 그룹 최대 `ord`가 `Integer.MAX_VALUE`면 `+1`이 음수로 넘쳐 맨 앞에 놓이므로 그 경우에만 그룹을 표시 순서 그대로 `0..n-1`로 재번호한 뒤 마지막에 생성한다. 통합 테스트(`MenuConcurrencyIntegrationTest`): 서브트리 이동·한 건 감사, 전체 잠금 보유 트랜잭션 대기 후 반영·생성·단일 행 수정, INSERT 커밋 뒤 낡은 초안 409, 동시 생성의 `ord` 직렬화.
- **메뉴 구조 편집 화면 — 드래그 초안 + [반영] 버튼**(`templates/admin/menu/manage.html`, 2026-10-01 PR C): 트리 드래그(`jstree dnd`)는 **서버를 호출하지 않고** 화면의 초안만 바꾼다. 트리 하단 **[반영]**(`PUT /structure`)을 눌러야 저장되고 **[취소]**는 서버 상태로 되돌린다. 별도 "상위 메뉴 변경" 폼과 "순서" 입력은 제거됐다. **편집은 비활성 포함 전체 트리(`treeScope==='all'`)에서만** 가능해(요청이 전체 메뉴 집합이어야 하므로) "비활성 포함"이 **기본 켜짐**이고 끄면 드래그가 막히며 안내가 뜬다. `check_callback`은 서버 규칙과 같은 범위로 만든다 — **같은 부모 안 재정렬은 깊이·권한과 무관하게 항상 허용**(기존 4단 메뉴도 재정렬 가능, 서버도 `ord`만 바뀐 행은 검증하지 않음), **부모가 바뀌는 드롭만** 순환(자기·자손 아래)과 깊이(새 부모 깊이 + 이동 서브트리 높이 ≤ `MAX_DEPTH`=3)를 막고, 비활성 부모 아래 활성 메뉴는 서버가 400으로 판정해 메시지로 알린다. **반영 대기 건수**는 부모가 바뀐 메뉴 + 같은 부모 안에서 상대 순서가 바뀐 메뉴(기준 인덱스의 최장 증가 부분 수열 밖) — 한 메뉴를 옮기면 형제 인덱스가 전부 밀리므로 위치 차이를 그대로 세면 부풀려진다. 초안이 있는 동안 저장·삭제·추가·"비활성 포함" 토글·폼 입력은 잠기고(트리 재조회가 초안을 지우므로) 페이지를 떠나려 하면 `beforeunload` 경고가 뜬다. 반영 요청의 `baseUpMenuNo`·`baseOrd`는 트리 조회 시점 값을 `?? null`로 명시해 보낸다(트리 응답이 `non_null`이라 최상위·레거시 행은 키가 생략됨 — 서버는 필드 누락을 400으로 거부). **409**(낡은 초안)면 서버 메시지 + "서버의 최신 구조로 새로고침했습니다"를 표시하고 초안을 버리며, **400**(구조 위반)이면 초안을 남겨 고치거나 취소할 수 있게 한다. 반영 성공 시 사이드바까지 갱신하려고 페이지를 다시 읽고 성공 메시지(`sessionStorage`)를 표시한다. 생성·수정 요청에서 `ord`는 제거돼(DTO·폼) 낡은 폼이 확정된 순서를 되돌릴 수 없다 — 생성은 항상 맨 끝, 수정은 `ord`를 바꾸지 않는다(요청 본문에 `ord`가 와도 무시됨).
- **영구삭제(하드 삭제)와 비활성화**(2026-10-02, `PLAN-menu-permanent-delete.md` PR B — 적대적 리뷰 5라운드 ship): `DELETE /admin/api/menus/{id}`(ADMIN 전용)는 **영구삭제**다(`MenuService.deleteMenu`). **비활성 상태이고 하위 메뉴가 하나도 없는 메뉴만** 지운다 — 활성이면 409("먼저 비활성화"), 하위 메뉴가 있으면(활성·비활성 무관 `existsByUpMenuNo` — 비활성 자식도 재활성화되면 부모가 필요하다) 409, 없는 메뉴는 404. 시드 메뉴(V3·V9)도 제한 없이 삭제할 수 있고 Flyway는 이미 적용된 마이그레이션을 재실행하지 않으므로 지운 시드는 수동 SQL 없이 돌아오지 않는다. **비활성화는 `PATCH /{id}` `{useYn:false}`가 유일한 경로**다(활성 하위 메뉴가 있으면 409 — `updateMenu`가 같은 단일 행 잠금·불변식을 갖는다). 이전에 비활성화였던 `DELETE`의 의미가 바뀐 것이므로 `deactivateMenu`·`Menu.deactivate()`는 삭제했고 `MENU_DEACTIVATE` 감사 상수·라벨은 과거 로그 호환으로만 남는다(비활성화는 이제 `MENU_UPDATE`로 기록). **잠금**: 대상 행 하나만 `findByIdForUpdate`로 잠근다 — 생성·구조 반영은 전체 행(대상 포함), 수정·재활성화는 대상 행을 잠그므로 모두 직렬화되고(하위 생성이 먼저면 삭제는 자식을 발견해 409, 삭제가 먼저면 생성은 부모 없음 404, 구조 반영은 집합 불일치 409), 비잠금인 `existsByUpMenuNo`는 **잠금 읽기 뒤에** 호출해야 스냅샷이 잠금 이후에 고정된다. `MenuConcurrencyIntegrationTest`가 비활성 자식 동시 INSERT·재활성화·이중 삭제·낡은 초안을 실제 락 대기로 검증한다. **감사**: `MENU_DELETE`(targetId = 삭제된 메뉴 번호, `targetLabel` = `"이름 (URL)"` — URL이 없으면 이름만). 응답이 사라진 행은 이름을 알 수 없으므로 서비스는 **삭제 전에 만든 `MenuDeleteResult` 스냅샷**을 반환하고 컨트롤러는 204로 버린다(공지 DELETE와 같은 이유 — 반환 객체 getter로만 targetId·targetLabel을 추출). 감사 저장이 실패하면 삭제는 성공하고 라벨 기록은 유실될 수 있다(최선 노력, `com.cms.admin.log`의 `CLAUDE.md` 참조). **화면**(`manage.html`): 활성 메뉴를 선택하면 [비활성화](`PATCH {useYn:false}`만 전송 — 저장하지 않은 폼 값을 싣지 않음), 비활성 메뉴를 선택하면 [영구삭제]만 보인다. 버튼 노출과 삭제 대상은 폼의 체크박스가 아니라 **상세 조회가 서버 응답으로 확정한 스냅샷**(`selectedMenuSnapshot`)으로 정하고, [영구삭제] 모달을 여는 순간 `{menuNo, menuName}`을 **복사해 고정**한다(상세 응답이 늦게 도착해 전역 선택이 바뀌어도 이름 확인과 `DELETE`는 고정본만 쓴다). 메뉴명을 직접 입력해야 확정 버튼이 켜지는데, 단일행 입력창은 CR/LF를 제거하므로 **개행·유니코드 줄바꿈이 든 이름은 가역 이스케이프한 확인 문자열**(`\\`·`\r`·`\n`·`\t`·`\uXXXX`)을 표시·비교한다(서버 로그 이스케이프와 같은 규칙, 정규식 리터럴이 아니라 코드 값으로 판정 — `U+2028`이 리터럴 안에 원문으로 들어가면 구문 오류). 서버는 입력을 검증하지 않는다(UX 안전장치, 서버 계약은 위 409·404). 구조 편집 초안이 있는 동안 두 버튼은 다른 저장 동작처럼 잠긴다.
- **같은 행 쓰기의 비관적 잠금 일관화**(`MenuService.updateMenu()`, 2026-09-27, 감사 M-04): 생성/재활성화 시 부모 row, 비활성화 시 대상 row를 잠그는 것과 동일하게, **일반 수정(이름 등)도 최초 조회부터 `findByIdForUpdate()`를 쓴다** — 과거에는 `useYn=false`(비활성화) 분기만 잠그고 그 외 일반 수정은 잠금 없는 `findById()`를 써서, "일반 수정 조회 → 비활성화 커밋 → 일반 수정 커밋" 순서가 겹치면 방금 커밋된 비활성화가 되돌아가는 lost update가 실 MariaDB 경합으로 재현됐다(위 `AdminMemberService.updateMyInfo` 행 잠금 누락, 감사 H-02와 같은 결함군). **범위 밖으로 남은 잔여 위험**: `templates/admin/menu/manage.html`의 `buildPayload()`(저장 버튼)는 편집 필드와 무관하게 매 PATCH에 화면 로드 시점의 `useYn` 체크박스 상태를 항상 포함한다(별도인 [비활성화] 버튼은 `{useYn:false}`만 보내 이 위험을 키우지 않는다) — 따라서 "화면에서 이름만 수정"해도 다른 관리자가 그 사이 비활성화한 것을 모른 채 저장하면 명시적 `useYn=true` 재전송으로 비활성화가 되돌아갈 수 있다(고전적 stale-form 문제, 행 잠금만으로는 해결 불가). 상세는 `docs/troubleshooting.md`·`adversarial-review/remediation-plan.md` "PR 4" 섹션 참조.

## 노출 계산 (`MenuVisibility`, 권한관리 PR ②, 2026-10-02)

사이드바 렌더링과 메뉴 관리 화면의 "노출 대상" 안내가 **같은 순수 함수**(`service/MenuVisibility.evaluate`)를 쓰므로 안내와 실제가 어긋나지 않는다. 계획서 `adversarial-review/plan/PLAN-menu-permission-management.md` §7.

- **URL 가시성**은 `AdminPermissionEvaluator.menuUrlVisibility(snapshot, authentication)`가 만든다: ADMIN → 항상 true(URL null·미분류 포함), MANAGER → 메뉴 URL이 어떤 기능의 `AdminFeature.menuUrls`와 **문자열 완전 일치**할 때만 그 기능의 READ 허용 여부를 **그 회원 본인의 허용 행으로** 따르고 그 밖(미분류·외부 URL·쿼리스트링·후행 슬래시·URL null)은 false(fail-closed). 역할은 `Authentication` 권한에서 읽는다(`AdminSecurityService.hasAdminAuthority()`는 삭제). `AdminSidebarAdvice`는 MANAGER일 때만 요청당 `PermissionSnapshot`을 한 번 지연 조회해 판정을 만든다(ADMIN은 캐시를 호출하지 않는다).
- **가지치기**(아래에서 위로, 표시 깊이 3 안): 보이는 자식이 남으면 그 노드는 **그룹으로 노출**(자기 URL은 쓰이지 않는다 — `sidebar.html`이 자식 있는 노드의 URL을 그리지 않는다), 남은 자식이 없으면 **리프로서 자기 URL**이 보일 때만 노출. 그래서 ADMIN 전용 부모 아래 공지 메뉴가 있어도 MANAGER에게 부모가 그룹으로 보이고(권한 불변식 불필요), `/admin` URL 부모 아래 ADMIN 전용 자식만 있으면 자식이 사라지고 부모는 대시보드 링크 리프가 된다.
- **노출 안내(`exposure`)**: `GET /admin/api/menus/tree` 노드 `data.exposure`(코드)·`data.exposureLabel`(한국어) — 트리 API가 **카탈로그 분류만**(`anyManagerMenuUrlVisibility` — "권한을 받으면 MANAGER가 볼 수 있는가", 권한이 사용자별이라 "MANAGER 한 명의 시점"이 없고 캐시 스냅샷이 필요 없다, 2026-10-03)으로 계산한다. 그래서 위임 가능 기능 URL만 담은 그룹도 `VISIBLE_BY_CHILDREN`이다. 코드: `ALL_ADMINS`(상시 기능 URL) / `PERMISSION:<기능>`(위임 가능 기능 URL) / `VISIBLE_BY_CHILDREN`(가지치기 후 자식 있음) / `ADMIN_ONLY`(카탈로그 밖·위임 불가·URL null·자식 전부 가지치기된 URL null 그룹) / `NOT_SHOWN`(비활성·비활성 조상 아래·깊이 3 밖). 계산은 필터와 무관하게 **전체 메뉴**로 하고 응답만 `useYn` 필터를 적용한다. `MenuResponse`(상세 API)에는 없고 화면은 선택한 트리 노드의 `data.exposureLabel`을 읽기 전용으로 표시한다. 시험: `MenuServiceTest`(5개 반례)·`MenuExposureSidebarIntegrationTest`(실제 스택에서 트리 `exposure`와 MANAGER 사이드바 HTML 대조).
- 메뉴를 MANAGER에게 보이게 하는 방법은 이제 메뉴 관리가 아니라 **권한관리**(위임 가능 기능 READ)다. 메뉴 URL이 카탈로그에 없으면 ADMIN 전용이다.
