# CLAUDE.md — com.cms.admin.menu

이 디렉터리(메뉴 도메인) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조.

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

## Menu

- `MenuAccessRole`: `ALL`(공용, ADMIN·MANAGER 노출) / `ADMIN`(ADMIN 전용 노출). DB 컬럼 null은 ALL로 정규화(레거시 행 호환)
- 사이드바는 `AdminSidebarAdvice` → `MenuService.getSidebarMenus()`가 활성 메뉴를 역할 필터링해 동적 렌더링한다. **최대 3단(최상위 + 하위 + 하위의 하위, `MenuService.MAX_MENU_DEPTH`)까지** 그린다(2026-10-01, `PLAN-menu-structure-apply.md` PR A). SB Admin 2는 2단까지만 제공하므로 3단은 `sidebar.html`이 2단 `collapse-inner` 안에 **중첩 collapse**로 그리고, 현재 페이지가 안에 있으면 `SidebarMenuResponse.hasDescendantUrl`로 조상 그룹을 펼친다. 생성 API(`createMenu`)도 같은 상한을 검증한다 — 부모 깊이가 이미 3이면(결과 4단) 400. 부모 이동 API(`moveMenu`)는 PR B~C 전까지 여전히 결과 2단 이하만 허용한다(자식 있는 메뉴 이동 불가). 생성 깊이 검증은 잠금 없이 조상 사슬을 읽으므로 동시 이동·생성 경합은 PR B의 전체 행 잠금에서 정리한다
- 기본 메뉴 시드는 Flyway `V3__seed_default_menus.sql`이 담당한다 — menu 테이블이 **완전히 비었을 때만** 전체 시드하며, 행이 하나라도 있으면 건드리지 않는다 (보충 기능 없음)
- `accessRole`은 사이드바 **노출** 제어일 뿐이며, 실제 접근 차단은 Security(`@PreAuthorize` 등)가 담당한다
- **형제 순서 재조정 API + 트리 드래그 앤 드롭**(`MenuService.reorderMenus`, 2026-09-30, 계획서 `adversarial-review/plan/PLAN-menu-reorder.md`): `PUT /admin/api/menus/order`(본문 `{upMenuNo, scope, menuNos}`, ADMIN 전용 — URI에 동사를 못 쓰는 API 컨벤션 때문에 `reorder`가 아니라 명사 `order`). 같은 부모 아래 **형제 전체의 `ord`를 0..n-1로 다시 매긴다**(멱등). `scope=ALL`은 형제 전체, `scope=ACTIVE`는 활성 형제만 담고 — 서버가 현재 표시 순서 F(`ord` 오름차순, **null 먼저**, 동률 `menuNo`)를 만든 뒤 **비활성 형제는 F의 자리에 그대로 두고 활성 자리에만 요청 순서를 채운다**(예: F=[A,B(비활성),C,D], 요청 [D,A,C] → D0 B1 A2 C3). 요청이 스냅샷 기준 scope 집합과 다르거나, 잠근 최신 엔티티로 활성 집합을 **다시 검증**해 달라졌으면 409(롤백). **잠금 규약**: 형제 id를 엔티티가 아닌 값 프로젝션(`SiblingRow`)으로 먼저 읽고(`Menu`에 `@DynamicUpdate`가 없어 잠금 전 엔티티를 올리면 오래된 값이 전체 컬럼 UPDATE로 동시 수정을 덮어씀) **형제 전체를 `menuNo` 오름차순으로 `findByIdForUpdate`로 하나씩 잠근다 — 부모 행은 잠그지 않는다**(재활성화의 자식→부모 순서와 반대 방향 사이클 방지, 잠금 순서는 `(-깊이, menuNo)` — 단 **계층이 고정된 동안에만** 성립한다. 부모 이동이 생긴 뒤에는 낡은 스냅샷 순서와 현재 계층이 어긋날 수 있어 교착은 409로 허용한다, 아래 "메뉴 부모 이동" 항목 참조). `menu` 테이블엔 PK 외 인덱스가 없어 집합 조건 `FOR UPDATE`를 쓰면 REPEATABLE READ에서 테이블 전체가 잠기므로 쓰지 않는다. **약한 계약**: 요청한 형제들끼리의 상대 순서만 보장하고, 스냅샷 이후 **동시에 생성된 형제의 위치는 보장하지 않는다**(명시·중복 `ord` 때문에 끼어들 수 있음 — "항상 맨 뒤"는 틀린 주장이었다). 같은 집합의 순서를 다른 관리자가 먼저 바꿨다면 마지막 쓰기가 이긴다(순서 stale 미검출). 요청 상한 1000개(초과 400). 감사 로그 `MENU_REORDER`, `targetId`는 **부모 메뉴 번호**(최상위는 null, 새 순서 payload는 남지 않음). 화면(`manage.html`): 같은 부모 안 이동만 허용(`check_callback`은 드롭 후 최종 검사에 `more.dnd`가 없으므로 `dnd`를 요구하지 않는다 — `docs/troubleshooting.md` 참조), 실제로 그려진 트리 범위(`treeScope`)를 `scope`로 전송, `loadSeq`·`selectSeq` 세대 번호로 늦게 온 응답 폐기, 저장·삭제·재정렬은 `busy`로 상호 배제, 실패 메시지는 재조회 **후에** 표시.
- **메뉴 부모 이동 API + "상위 변경" 폼**(`MenuService.moveMenu`, 2026-09-30, 계획서 `adversarial-review/plan/PLAN-menu-move.md`): `PATCH /admin/api/menus/{id}/parent`(ADMIN 전용). menuNo를 유지한 채 부모를 바꾼다(이전엔 삭제 후 재생성뿐이라 감사 로그 targetId 참조가 끊겼다). **결과는 항상 2단 이하** — 새 부모 N은 최상위여야 하고 이동 대상 T에 자식이 하나라도 있으면(비활성 포함, `existsByUpMenuNo`) 거부. 위치는 새 부모 아래 **맨 끝**(`resolveNextOrd`, 최상위 승격은 최상위 맨 끝 — 순서는 재조정 API로). **검사 우선순위(두 잠금을 모두 얻었을 때)**: 자기 자신(락 전 400) → 404 → **무변경(이미 그 부모/최상위)은 200이고 자식·깊이 검사보다 먼저 판정** → N이 최상위 아님 400 → 자식 있음 400 → 활성 T를 비활성 N 아래로 400 → 이동. 공용(`ALL`) T를 관리자 전용 부모 아래로 옮기는 것은 **400으로 거부**한다(2026-10-01 PR B — MANAGER에게는 부모가 제외돼 사이드바에서 사라지는 구조라 경고가 아니라 거부; 응답 `warnings`는 항상 빈 배열이고 필드는 PR C에서 API와 함께 삭제). **요청 본문은 `JsonNode`로 받아 정수와 명시적 JSON `null`(최상위 승격)만 허용**한다 — Jackson 기본 강제 변환이 `""`·`"null"`을 `null`로, `10.9`를 `10`으로 바꿔 잘못된 입력이 실제 승격·이동이 되고, `{}`(필드 없음)는 자바 `Long`으로는 `null`과 구분되지 않기 때문이다(`docs/troubleshooting.md`). 응답 `upMenuNo`는 `@JsonInclude(ALWAYS)`라 최상위 결과에서도 키가 null로 존재한다(전역 `non_null` 우회). **잠금 규약**: 요청의 두 id(T, N — 승격이면 T만)를 **menuNo 오름차순**으로 잠그고 원래 부모는 잠그지 않는다. **이 트랜잭션의 첫 애플리케이션 테이블 조회가 잠금 읽기여야 한다**(잠금 전 비잠금 읽기가 REPEATABLE READ 스냅샷을 일찍 고정하면 뒤이은 `existsByUpMenuNo`·`max ord`가 오래된 값을 봄 — 통합 테스트로 고정). **교착은 정합성이 아니라 가용성 문제로 허용한다**: 스냅샷으로 잠금 목록을 정하는 재조정과 부모가 바뀔 수 있는 이동이 함께 있으면 어떤 정적 잠금 순서로도 교착을 완전히 막지 못한다(예: 낡은 루트 스냅샷으로 잠그던 재조정 ↔ 이동 커밋 ↔ 재활성화 3자 경합, 결국 거부될 이동 ↔ 재활성화 2자 경합). InnoDB가 한쪽을 롤백하고 기존 핸들러가 **409**로 응답하며 정합성은 잠금 후 최신값 검증이 보장한다 — `MenuConcurrencyIntegrationTest`가 일반 경합(루트 재조정 ↔ 최상위 이동)의 무교착과 알려진 교착의 "잠금 예외는 정확히 하나·HTTP 409는 피해자에 따라 하나 또는 둘·이동 유지" 계약을 고정한다. 전역 뮤텍스는 모든 변경 경로를 손대야 해 채택하지 않았다. **재조정 보정**: 부모가 더 이상 불변이 아니므로 `reorderMenus`가 잠근 각 형제의 `upMenuNo`를 요청 부모와 재검사해 다르면 409(다른 그룹 행에 ord를 쓰는 오염 방지). 감사 액션 `MENU_MOVE`(성공: `targetId`=이동한 메뉴, 서비스 검사 실패: FAIL·`targetId` null, `@Valid` 거부는 미기록, 이전·새 부모는 남지 않음). **알려진 한계**: 생성 API는 3단까지 허용하므로(위 "사이드바" 항목) 이동 뒤 2단 메뉴에 하위를 만들면 3단이 만들어질 수 있다("항상 2단"은 이동 완료 시점의 제한이며 PR B에서 3단 규칙으로 통일 예정). 화면(`manage.html`): 편집 모드에서만 "상위 메뉴 변경" 영역(후보 = 지금 그려진 트리 세대 `lastTreeData`의 최상위 메뉴, 자식 있으면 비활성화), 이동·재조정의 결과 메시지는 폼이 아니라 **트리 영역 알림**(`#treeAlert`·`#treeWarning`)에 `queuedNotice`로 대기시켰다가 **재조회가 실제로 적용될 때** 표시(밀려 폐기된 조회는 소비하지 않음), `busy` 중 노드 선택 무시, 사이드바는 `loadTree()`가 갱신하지 않으므로 **페이지 재로드 후** 반영.
- **메뉴 구조 일괄 반영 API**(`MenuService.applyStructure`, 2026-10-01 PR B, 계획서 `adversarial-review/plan/PLAN-menu-structure-apply.md` — 적대적 리뷰 4라운드 ship): `PUT /admin/api/menus/structure`(ADMIN 전용, 본문 `{menus:[{menuNo, baseUpMenuNo, baseOrd, upMenuNo}...]}`). 화면이 드래그로 만든 초안(**비활성 포함 전체 메뉴의 최종 구조**)을 한 번에 받는다. 같은 `upMenuNo` 안의 **배열 순서가 새 `ord`(0..n-1)** 이고 `base*`는 초안을 만든 시점의 값이다. 이 PR에서는 API만 추가했고 기존 `PUT /order`·`PATCH /{id}/parent`는 화면이 아직 쓰므로 **PR C(화면)에서 삭제**한다. **잠금**: 첫 애플리케이션 테이블 조회가 `findAllForUpdate`(전체 행 `menuNo` 오름차순 PESSIMISTIC_WRITE) — 구조 반영·**생성**·**`accessRole`이 포함된 수정**이 같은 순서로 전체를 잠가 서로 직렬화된다(이 경로들끼리 교착 없음). 비활성화·재활성화(자식→부모 개별 잠금)와의 교착은 InnoDB 탐지 → 409(가용성 문제로 허용, 정합성은 잠금 후 최신값 재검증). 이름 등 `accessRole` 없는 수정은 기존 단일 행 잠금. **낙관적 검사(409)**: 요청 집합이 현재 **트리 도달 가능** 집합과 다르거나 어떤 행의 현재 (부모, ord)가 base와 다르면 409 — 고아·루트 없는 순환 행은 비교에서 빼고 건드리지 않는다(화면이 못 보는 행 때문에 영구 409가 되는 것 방지). 요청 개수 상한은 없고 요청 수 > 전체 행 수만 400. **검증(400)**: 같은 메뉴 번호 중복·요청에 없는 부모·순환(전체)·**부모가 바뀐 메뉴의 서브트리에 한해** 깊이 > 3(`MAX_MENU_DEPTH`)·활성 메뉴가 비활성 부모 아래·**공용(ALL) 메뉴가 관리자 전용(ADMIN) 조상 아래**. 이동하지 않은 서브트리의 기존 위반(4단·권한 불일치)은 이 반영을 막지 않는다. **저장 범위**: 현재 표시 순서와 요청 순서가 다른 부모 그룹만 `0..n-1`로 다시 매기고 값이 같은 행은 쓰지 않는다(`ord`가 100·200이어도 손대지 않은 그룹은 그대로, `updateDate` 보존). 요청 토큰은 항목 네 필드 모두 `JsonNode`로 받아 `menuNo`는 **null 아닌 정수만**(`1.9`가 `1`로 잘려 엉뚱한 메뉴가 옮겨지는 것을 코드 리뷰가 재현해 추가), `baseUpMenuNo`·`upMenuNo`는 정수 또는 명시적 `null`, `baseOrd`는 int 정수 또는 `null`만 허용하고 **필드 누락도 400**이다(트리 응답이 `non_null`이라 최상위 `upMenuNo`·레거시 null `ord`가 생략되므로 **화면이 `?? null`로 명시해서 보내야 한다**). 감사 `MENU_STRUCTURE_APPLY`(`targetId` 없음). **권한 불변식 전역 적용**(`ALL` 메뉴의 조상 사슬에 `ADMIN`이 없어야 함): 구조 반영·`createMenu`(ALL 기본값 포함 → 관리자 전용 조상 아래 400)·`updateMenu`의 `accessRole` 변경(ADMIN→ALL이면 관리자 전용 조상 없어야, ALL→ADMIN이면 공용 자손 없어야)·`moveMenu`가 모두 같은 규칙을 지킨다. **생성의 `ord` 오버플로**: 같은 그룹 최대 `ord`가 `Integer.MAX_VALUE`면 `+1`이 음수로 넘쳐 맨 앞에 놓이므로 그 경우에만 그룹을 표시 순서 그대로 `0..n-1`로 재번호한 뒤 마지막에 생성한다. 통합 테스트(`MenuConcurrencyIntegrationTest`): 서브트리 이동·한 건 감사, 전체 잠금 보유 트랜잭션 대기 후 반영, INSERT 커밋 뒤 낡은 초안 409, 생성의 전체 잠금 대기. `LockProbe`는 `findAllForUpdate` 호출을 락 대기 진입으로 기록한다(생성이 이제 `findByIdForUpdate`보다 먼저 전체 잠금에서 대기).
- **같은 행 쓰기의 비관적 잠금 일관화**(`MenuService.updateMenu()`, 2026-09-27, 감사 M-04): 생성/재활성화 시 부모 row, 비활성화 시 대상 row를 잠그는 것과 동일하게, **일반 수정(이름 등)도 최초 조회부터 `findByIdForUpdate()`를 쓴다** — 과거에는 `useYn=false`(비활성화) 분기만 잠그고 그 외 일반 수정은 잠금 없는 `findById()`를 써서, "일반 수정 조회 → 비활성화 커밋 → 일반 수정 커밋" 순서가 겹치면 방금 커밋된 비활성화가 되돌아가는 lost update가 실 MariaDB 경합으로 재현됐다(위 `AdminMemberService.updateMyInfo` 행 잠금 누락, 감사 H-02와 같은 결함군). **범위 밖으로 남은 잔여 위험**: `templates/admin/menu/manage.html`의 `buildPayload()`는 편집 필드와 무관하게 매 PATCH에 화면 로드 시점의 `useYn` 체크박스 상태를 항상 포함한다 — 따라서 "화면에서 이름만 수정"해도 다른 관리자가 그 사이 비활성화한 것을 모른 채 저장하면 명시적 `useYn=true` 재전송으로 비활성화가 되돌아갈 수 있다(고전적 stale-form 문제, 행 잠금만으로는 해결 불가). 상세는 `docs/troubleshooting.md`·`adversarial-review/remediation-plan.md` "PR 4" 섹션 참조.
