## Site

- **시드 2행(V2, 고정 ID)**: `id=1` 관리자 사이트(`admin`, `ADMIN`, 외부 링크 항상 불가)·`id=2` 기본 공개 사이트(`main`, `PUBLIC`, 외부 허용). `Site.ADMIN_SITE_ID`(=1)는 **사이드바가 쿼리 없이 쓰는 상수이자 `menu.site_id`의 DB `DEFAULT`**다 — 시험(`BaselineSchemaTest`)이 고정한다. 시드는 삭제·비활성화 불가(409), 이름은 바꿀 수 있다. 사이트 종류(`site_type`)·키는 생성 후 바뀌지 않는다(`@Column(updatable=false)`, 수정 DTO에 필드 없음 — 요청에 와도 **무시**, 400 아님). 새로 만들 수 있는 것은 **공개 사이트뿐**(생성 DTO에 종류 없음).
- **사이트 키(`SiteKey`)**: `^[a-z0-9]+(-[a-z0-9]+)*$` 2~30자, 대문자 자동 변환 없음. 공개 경로 접두어(`/{siteKey}/…`)가 될 값이라 **예약어(`SiteKey.RESERVED`)를 쓸 수 없다**. **새 최상위 공개·정적 경로를 추가하면 예약어에도 넣어야 한다** — `SiteKeyReservedConventionTest`가 `src/main/java`의 컨트롤러 요청 매핑(클래스 수준 `@RequestMapping`이 있으면 그것만, 없으면 메서드 수준)과 `SecurityConfig`의 경로 리터럴 첫 세그먼트를 스캔해 CI에서 잡는다. 사이트 키 형식을 만족하지 않는 세그먼트(점 포함 `favicon.ico`·`swagger-ui.html`, `{…}`·`*`)는 키가 될 수 없어 검사에서 제외한다.
- **링크 정책(`SiteLinkPolicy`, 서비스 계층 판정)**: DTO `@SafeMenuUrl`은 **형식**(내부 경로 또는 외부 http(s))만 본다. 사이트 정책은 이 빈이 판정한다 — 관리자 사이트는 내부 경로만(외부는 같은 출처 절대 URL이어도 거부), 공개 사이트는 내부 경로 + `allow_external_link`이면 외부. **공개 사이트의 내부 경로**는 비공개 접두어(`admin`·`actuator`·`error`·`v3`·`swagger-ui*` — `/swagger-ui.html` 포함)를 가질 수 없다(`?#` 앞에서 자르고 한 번 퍼센트 디코딩·소문자화, `.`/`..` 세그먼트·잔여 `%` 거부). `app.base-url`과 출처(스킴·호스트·포트)가 같은 절대 URL은 출처를 떼어낸 경로로 보고 같은 규칙을 적용한다 — **별칭 호스트는 탐지하지 않는 수용한 한계**다(이 규칙은 인가가 아니라 심층 방어, 편집자는 ADMIN뿐이고 `/admin/**`은 게이트가 막는다). **호스트를 Java가 읽지 못하는 절대 URL(퍼센트 인코딩 호스트 `https://%63ms.example/…` 등)은 거부한다** — `URI.getHost()`가 null이라 같은 출처 판정이 건너뛰어지지만 브라우저는 정규화해 같은 출처로 이동하기 때문이다(PR ⑤ 코드 리뷰, `hasParsableHost`). 오류 문구에 입력 원문을 싣지 않는다(400 `INVALID_REQUEST`).
- **저장된 URL 불변식**: 링크 정책 강화(외부 허용 → 불가)는 외부 URL 메뉴가 있으면 409다. 메뉴 URL을 쓰는 모든 쓰기가 같은 사이트 행 잠금을 먼저 지나므로 검사와 쓰기가 경합하지 않는다 → **저장된 메뉴 URL은 항상 현재 정책을 만족한다**(`SiteMenuConcurrencyIntegrationTest`의 정책 강화 경합 시험이 고정, 변이로 잠금을 빼면 실패함을 확인).
- **삭제 가드("내용")는 메뉴 ∨ 전용 배너 ∨ 전용 팝업 ∨ 전용 FAQ 카테고리 ∨ 전용 정적 페이지 ∨ 전용 게시판 존재**다(`SiteService.hasContent`, PR ③·④). **`site_id`를 가진 새 테이블을 추가할 때는 그 FK도 `ON DELETE RESTRICT`로 두고 `hasContent`에 포함시킨다.** 삭제는 하드 삭제이고 감사에 `targetLabel`=사이트 키 스냅샷(`SiteDeleteResult`)을 남긴다.
- **권한**: 사이트 API(`/admin/api/sites`)는 전부 `@PreAuthorize("hasRole('ADMIN')")`, URL 게이트는 `/admin/**` ADMIN 캐치올 — **`AdminFeature`·권한관리·`SecurityConfig` 변경 없음**(MANAGER 403). 화면은 **`/admin/site/manage`(2026-10-16, 사이드바 "사이트 관리" 그룹의 "사이트 설정")** — ADMIN 전용 셸 `admin/site/manage.html`이 패널 조각 `admin/site/fragments/site-tab.html`(`sitePanel`·`siteScript`, 모달 없음·삭제 확인은 `confirm`, 래퍼 `#siteTabPanel` 유지 — 조각 CSS가 의존)을 포함한다. `SiteManagePageController`(`@AdminPage`, 카탈로그 밖 URL이라 캐치올이 막아 MANAGER 403). 다른 화면과의 이벤트 결합은 없다(사이트를 바꿔도 메뉴·정적 페이지 화면은 다음 진입 때 갱신) — 사이트 문자열은 MANAGER 응답에 없다(`ContentManagePageIntegrationTest`).
- **감사**: `SITE_CREATE`/`SITE_UPDATE`/`SITE_DELETE`(`targetType=SITE`). 사이트 변경은 `AdminActionTypes.ALL`·활동 로그 화면 라벨과 함께 갱신한다. 메뉴 감사(`MENU_*`)는 행위와 메뉴 ID만 기록하고 URL 이력은 남기지 않는다(수용한 한계).

## 잠금 규약 (메뉴·사이트 쓰기 공통, PLAN-site-menu.md D4)

- **사이트 행 `FOR UPDATE` 하나가 그 사이트의 쓰기 문(gate)** 이다 — 메뉴 생성·수정·재활성화·비활성화·영구삭제·구조 반영과 사이트 수정·삭제가 모두 이 행을 **먼저** 잠근다(빈 사이트도 직렬화). 그 뒤 메뉴 행(사이트 범위 `findAllBySiteIdForUpdate` 또는 대상 행)을 menuNo 오름차순으로 잠근다. **다른 사이트의 행은 어떤 경로에서도 잠그지 않는다** — 부모는 이미 잠근 그 사이트의 집합에서만 찾고(없는 번호와 다른 사이트 소속은 같은 404, 존재 비노출) 별도 부모 잠금 쿼리를 쓰지 않는다. 메뉴 행 전체 잠금은 사이트 문과 중복이지만 사이트 문을 모르는 쓰기(롤백 구간의 이전 앱)에 대한 방어와 검증된 기존 동작 보존을 위해 유지한다.
- **쓰기 서비스 메서드는 컨트롤러가 호출하는 최상위 트랜잭션 진입점**이며 `@Transactional(isolation = READ_COMMITTED)`다(선례 `BannerService`·`MediaService`·`PopupService`). REPEATABLE READ의 **갭·범위 잠금과 읽기 뷰 고정**이 처음 설계의 교착(같은 사이트 부모·자식, 서로 다른 빈 사이트의 갭 락 순환)과 낡은 존재 검사의 뿌리였다 — RC에서는 잠금 읽기가 일치 행만 잠그고 비잠금 읽기도 문장마다 최신 커밋을 본다. `REQUIRED` 전파라 이미 열린 트랜잭션에 참여하면 격리 선언이 무시되고 감사 커밋 순서 계약도 깨진다 — **다른 서비스가 안쪽에서 이 메서드를 부르지 않는다**(시험이 외부 트랜잭션을 만들 때도 RC로 연다).
- **메뉴 번호만 아는 연산(수정·삭제)**: 스칼라 투영 `findSiteIdByMenuNo`(엔티티를 영속성 컨텍스트에 올리지 않는다) → 사이트 행 `FOR UPDATE` → 메뉴 행 `FOR UPDATE`로 다시 읽고 `site_id` 일치 확인(다르면 409, 정상 경로에서는 불가능한 방어).
- 시험: `SiteMenuConcurrencyIntegrationTest`(부모 삭제 ↔ 자식 재활성화, 같은/다른 빈 사이트 동시 첫 생성, 양방향 교차 사이트 부모, 정책 강화 ↔ 외부 URL 쓰기, 사이트 문이 다른 사이트를 막지 않음, 쓰기 진입점이 실제로 RC), `MenuConcurrencyIntegrationTest`의 `verifyOrderedWrites`는 **대기 관측 프로브를 사이트 잠금 쿼리**에 둔다(후행 호출은 메뉴 쿼리에 닿기 전에 사이트 문에서 먼저 대기한다 — 프로브를 메뉴 쿼리에 두면 시험이 타임아웃한다).

## 공개 라우팅과 기본 사이트 (PR ②, 2026-10-13)

- **사이트 키 = 공개 경로 접두어**: 활성 `PUBLIC` 사이트의 `site_key`가 `/{siteKey}/…`로 공개된다. **새 사이트를 만들면(또는 비활성 사이트를 활성화하면) 즉시 무인증 공개 경로가 하나 늘어난다** — `PublicSiteInterceptor`가 요청마다 DB로 판정하므로(캐시 없음) 비활성화는 즉시 404다. 콘텐츠(배너·팝업·FAQ·정적 페이지·푸터)는 `site_id`로 사이트마다 분리된다(PR ③, 아래 "사이트별 콘텐츠"). 게시판·공지도 `board.site_id`로 분리된다(PR ④, 아래 "사이트별 게시판·공지"). 상세는 `com.cms.publicweb.support`의 `CLAUDE.md`, 인가 정책 표는 `com.cms.config`의 `CLAUDE.md`.
- **기본 공개 사이트(`site.default_yn`)**: 접두어 없는 `/`가 302로 이동하는 곳. **정확히 1개의 활성 `PUBLIC` 사이트**여야 하고(아니면 `/`는 오류 로그 + 404 fail-closed) DB 제약은 없다 — 서비스 잠금과 시험이 지킨다. 시드는 `main`(id=2). **비활성화·삭제할 수 없다**(시드 보호 `isSeed()`에 더해 `defaultYn` 검사 — 시드 `main`은 기본이 아니게 된 뒤에도 시드 보호가 계속 막는다).
- **기본 사이트 변경**: `PATCH /admin/api/sites/{id}`에 `defaultSite: true`(활성 `PUBLIC` 대상만, `false`는 400 — 기본은 다른 사이트를 지정해야만 바뀐다, 이미 기본이면 멱등). **잠금 규약의 명시적 예외**: 옛 기본·새 기본 두 행을 함께 바꾸므로 **처음부터 모든 `site` 행을 id 오름차순으로 `FOR UPDATE`**(`findAllForUpdate`)한다 — 대상 행을 먼저 잠근 뒤 확장하면 잠금 순서가 깨져 교착할 수 있으므로 `updateSite()`는 `defaultSite=true`이면 단일 행 잠금을 건너뛴다. 다른 쓰기(메뉴 쓰기·사이트 수정/삭제)는 사이트 행 하나를 잡은 뒤 메뉴 행만 기다리고 기본 변경은 메뉴 행을 쥐지 않으므로 순환하지 않는다(`SiteDefaultConcurrencyIntegrationTest` — 동시 기본 변경·비활성화와의 경합·메뉴 쓰기와의 경합, 변이로 잠금을 빼면 실패함을 확인). 복합 요청 `{defaultSite:true, useYn:false}`는 **최종 상태 기준** 400. 감사는 기존 `SITE_UPDATE`(대상=사이트 ID) 재사용. UI는 사이트 설정 화면의 "기본" 열과 [기본으로 지정] 버튼(활성 공개 비기본 사이트에서만, 미저장 입력이 없을 때만 — 요청은 폼이 아니라 `defaultSite`만 보낸다, `SiteDefaultBrowserTest`).
- **사이트 키 예약어**: 공개 경로 둘째 세그먼트 이름(`notices`·`boards`·`pages`·`faq`·`inquiry`)은 옛 최상위 경로를 404로 종료하고 키 충돌을 막기 위해 **계속 예약어**다(`SiteKeyReservedConventionTest.legacyTopLevelNamesStayReserved`·`siteScopedSecondSegmentsAreReserved`).
- **구·신 앱 혼합 운영 금지**: 공개 경로 체계가 다른 앱 버전을 섞지 않는다(`docs/deployment.md` "공개 경로").

## 사이트별 콘텐츠 (PR ③, 2026-10-13,`PLAN-site-menu.md` "PR ③ 상세 설계" P3-v6, 적대적 리뷰 6라운드 ship)

- **스키마**: `banner`·`popup`·`faq_category`·`site_page`에 `site_id bigint NULL DEFAULT NULL` + FK `ON DELETE RESTRICT`. **NULL = 모든 공개 사이트 공통**(생략한 INSERT도 공통). `banner.version`·`faq_category.version`(`int NOT NULL DEFAULT 1`)은 낡은 화면 검사용 — 팝업은 기존 `revision`(시작값 **0**), 정적 페이지는 기존 `version`을 쓴다. FAQ **항목**에는 `site_id`가 없고 카테고리를 따른다. 공개 사이트(`PUBLIC`)만 가리킬 수 있다(서비스 검증, DB 제약 없음).
- **대상 지정 검증과 잠금(`ContentSiteScope.requireAssignable`)**: 대상 사이트 행을 `FOR SHARE`(`SiteRepository.findByIdForShare`)로 읽어 존재·`PUBLIC`을 확인한다(없음·관리자 사이트는 400, 비활성 공개 사이트는 허용). **잠금 순서는 기능 가드/대상 행 → 사이트 행(공유)**이고 `MANDATORY` 전파(트랜잭션 안에서만). 사이트 삭제(`FOR UPDATE` → `hasContent`)와 직렬화되어 결과가 둘 중 하나로 갈린다 — 지정이 먼저면 삭제 **409**, 삭제가 먼저면 지정 **400**(FK 예외·500·교착 아님). `ContentSiteScopeConcurrencyIntegrationTest`가 `LockWaitObserver`로 두 순서를 모두 고정한다(`findByIdForShare`를 일반 읽기로 바꾸면 첫 시나리오가 깨진다).
- **요청 계약(`SiteScope`)**: 필드 `String siteScope` = `"COMMON"` 또는 양의 정수 문자열(사이트 ID), `@Pattern(SiteScope.PATTERN)`. **등록은 선택(누락 = 공통), 수정(PUT 전체 교체)은 필수**(누락·빈 문자열·형식 위반 400 — 전체 교체에서 누락이 조용히 "모든 사이트 공개"가 되지 않게). 19자리 범위 초과 값은 `SiteScope`가 `InvalidRequestException`(400)으로 바꾼다(500 방지). FAQ 카테고리는 POST·PUT이 같은 DTO였던 탓에 **수정용 `FaqCategoryUpdateRequest`를 분리**했다. 응답에는 `siteId`(null = 공통).
- **낡은 화면의 공개 범위 확대 방지(S6b)**: 수정 요청에 **버전 필수**(배너 `version`≥1, 팝업 `revision`≥0, FAQ 카테고리 `version`≥1, 정적 페이지 `version`≥1) — 행 락/가드를 잡은 **뒤** 비교해 다르면 409. 순서 변경(`changeOrder`)은 버전을 올리지 않고 `replace`/`replaceMetadata`만 올린다. **FAQ 항목** 수정은 `baseCategoryId`(편집 시작 때의 소속)가 필수이고 현재 소속과 다르면 409(다른 관리자가 전용 카테고리로 옮긴 항목을 낡은 폼이 공통으로 되돌려 재공개하는 경로 차단). 이로써 배너·팝업·FAQ 카테고리의 stale-form 한계(예전 "수용한 한계")는 **해소**됐다 — FAQ 항목의 질문·답변 덮어쓰기와 메뉴 관리의 stale-form은 그대로다.
- **공개 필터는 쿼리에 고정**: `(x.siteId is null or x.siteId = :siteId)`가 `BannerRepository.findDisplayable`·`PopupRepository.findDisplayable`(**LIMIT 전**에 적용)·`FaqRepository.findPublicRows`(카테고리 기준)·`SitePageRepository.findPublicCurrent/Revision/Header/findFooterLinks`에 있다. 공개 서비스는 `siteId`를 **필수 파라미터**로 받고(`PublicSite.requireId` — null이면 `IllegalArgumentException`) 컨트롤러가 `PublicSiteRoutes.current(request).id()`를 넘긴다(`PublicHomeService.getHome(siteId)` 안에서 배너로 전달). 다른 사이트 전용 페이지·개정·개정 목록은 없는 슬러그와 같은 404다(존재 비노출). 정렬은 전역 `ord`/`id` 그대로.
- **이미지 id 경로(`/banners/{id}/image`·`/popups/{id}/image`)는 사이트 무관**을 유지한다(PR ② 결정). 대신 `findDisplayableById`·`findDisplayableImageById`가 **소속 사이트가 비활성이면 제외**한다 — 사이트를 끄면 전용 콘텐츠가 이미지 URL로도 새지 않는다. 다른 사이트 접두어 아래에서 id로 직접 여는 것은 막지 않는다(노출 중인 공개 이미지, **수용한 한계**).
- **정적 페이지 슬러그는 전역 유일 유지**(`uk_site_page_slug`) — 사이트마다 같은 슬러그를 쓸 수 없다(`privacy-a`/`privacy-b`). 푸터(`footer_yn`)는 같은 소속 필터를 따른다. 대상만 바꾸면 `version`이 오르고 개정은 쌓이지 않는다.
- **순서·가드·상한은 전역**: `banner_lock`·`faq_lock`·`ord`·`faq_lock.version`·상한(배너 10·팝업 30·FAQ 카테고리 30·FAQ 200)은 전체 합계 기준이다(사이트별로 쪼개지 않았다 — 다중 사이트에서 합계 상한이 빡빡해지는 것이 비용). 기능 단위 위임 권한(`BANNER`·`POPUP`·`FAQ`·`SITE_PAGE`)은 **모든 표시 대상에 적용**된다(사이트별 위임 없음, `member_permission` 변경 없음).
- **MANAGER에게 사이트 목록 주기**: `/admin/api/sites`가 ADMIN 전용이라 `ContentScopeOptions`가 공개 사이트 목록과 기본 공개 사이트 키를 읽어 네 `*PageController`가 모델 `scopeSites`·`scopeDefaultKey`로 **서버 렌더링**한다(새 API·인가 변경 없음). 템플릿은 `th:text`/`textContent`만 쓴다. `@WebMvcTest` 슬라이스가 이 컨트롤러를 포함하면 `ContentScopeOptions` 목 빈이 필요하다(`AdminSidebarAdviceTest`).
- **화면(`static/js/admin/content-scope.js`)**: 선택 박스(`COMMON` + 사이트)·목록 배지·**없는 사이트 ID는 "사이트 #ID (목록에 없음)" 옵션으로 보존**(문서를 연 뒤 생긴 사이트의 전용 항목이 조용히 공통으로 저장되지 않게). **편집 스냅샷 규칙**: 버전(`version`/`revision`/`baseCategoryId`)은 폼을 서버 값으로 채우는 순간 **별도 변수**(`editBase`/`categoryBase`/`faqBase`)에 고정하고 PUT은 이 값만 보낸다 — 목록 갱신(`loadList`)이 편집 중 객체를 최신으로 바꿔도 검증 기준은 바뀌지 않는다. 사용자가 바꾸는 값(`siteScope`, 이동할 `categoryId`)은 **폼 입력에서 읽는다**(스냅샷에 넣으면 변경이 무시된다). 저장 성공 시에만 응답의 새 버전으로 기준을 갱신한다. FAQ는 상세의 `categoryId`를 트리 선택 박스에 복원하지 못하면 저장하지 않고 목록을 다시 읽는다. 정적 페이지의 공개 주소·개정 링크는 `/{사이트 키}/pages/…`(전용 = 소속 사이트, 공통 = 기본 공개 사이트, 비활성이면 링크 없음)이다.
- 시험: `ContentSiteScopeApiIntegrationTest`(PUT 계약·낡은 버전 409·팝업 `revision` 0 경계·FAQ 항목 재공개 방지·삭제 가드 4종)·`ContentSiteScopeConcurrencyIntegrationTest`·`PublicContentSiteScopeIntegrationTest`(홈·FAQ·페이지 교차 노출)·`BannerRepositoryDataJpaTest`/`PopupRepositoryDataJpaTest`(소속 필터·LIMIT 전 판정·비활성 사이트 이미지)·**`ContentScopeAdminBrowserTest`(실제 브라우저 — 대상 변경 전송·목록 갱신 후 옛 폼 거부·보존 옵션·정적 페이지 공개 주소·FAQ 상세/트리 불일치)**.

## 사이트별 게시판·공지 (PR ④, 2026-10-14,`PLAN-site-menu.md` "PR ④ 상세 설계" P4-v2, 적대적 리뷰 1라운드 ship)

- **스키마**: `board.site_id bigint NULL DEFAULT NULL` + FK `ON DELETE RESTRICT`. **NULL = 모든 공개 사이트 공통**(시드 공지 게시판·생략한 INSERT 모두 공통). 공개 사이트(`PUBLIC`)만 가리킨다(`ContentSiteScope`가 사이트 행 `FOR SHARE`로 검증 — PR ③과 같은 계약: 지정이 먼저면 사이트 삭제 409, 삭제가 먼저면 지정 400). 게시글에는 소속이 없다(게시판을 따른다).
- **공개 규칙**: 게시판이 현재 사이트에 보이는 조건은 `publicYn ∧ ¬deleted ∧ (site_id IS NULL ∨ site_id = 현재 사이트)` — `BoardRepository.findPublicById(id, siteId)`가 옛 `findByIdAndDeletedFalseAndPublicYnTrue`를 대체했고(옛 메서드는 제거돼 필터 없는 우회가 컴파일되지 않는다), 메인 새 글 `PostRepositoryImpl.findLatestPublished(boardId, siteId, excludeSystemBoards, now, limit)`는 같은 조건을 게시판 조인에 가진다. 공개 서비스(`PublicBoardService` — 옛 `PublicNoticeService`는 PR 4b에서 지웠다)는 `siteId`를 필수로 받는다(`PublicSite.requireId`). 다른 사이트 전용 게시판은 없는 ID·비공개와 **같은 404**다. **본문 이미지 `/content-images/{id}`는 사이트 무관 경로**를 유지하되 `existsPublishedPostRef`가 소속 사이트 비활성이면 제외한다(배너·팝업 이미지와 같은 모델 — 다른 사이트 접두어 아래에서 id로 직접 여는 것은 **수용한 한계**).
- **공지 게시판의 사이트별 해석**: 공통 공지 게시판은 키 `NOTICE`(V2 시드), **사이트 전용 공지 게시판은 키 `NOTICE:{siteId}`**(`Board.noticeKeyFor`, 서버만 만든다 — 사용자 입력 아님). 기존 `UNIQUE(board_key)`가 사이트당 하나를 보장하므로 인덱스 변경이 없고. 해석은 `BoardRepository.findNoticeBoardId(siteId)`(default 메서드) — 그 사이트의 전용 공지가 있으면 그것, 없으면 공통이다. **전용이 공통을 대체**한다(합치지 않음). 메인 공지 섹션과 `/{key}/notices`(PR 4b부터 그 게시판으로 302)가 같은 해석을 쓰고, 메인 새 글은 시스템 게시판(공통·전용 공지 모두, `board_key IS NULL`만 허용)을 뺀다. 관리자 옛 주소 `/admin/notice/manage`는 공통 공지로만 간다.
- **관리 API**(`BoardService`, ADMIN 전용 그대로): 생성 `siteScope`(선택, 누락 = 공통)·`noticeBoard`(선택) — 공지 게시판은 사이트를 골라야 하고(`COMMON`이면 400)·공개여야 하며(비공개 400)·같은 사이트에 이미 있으면 409(사전 `existsByBoardKey` + 동시 생성은 `saveAndFlush`에서 `UNIQUE` 위반을 같은 409로 번역). 수정 PATCH `siteScope`는 **명시한 경우에만** 바꾼다(누락 = 유지; 게시판에는 `version`이 없지만 PATCH가 이미 부분 수정이라 낡은 화면이 대상을 되돌리려면 선택을 바꿔 명시해야 하고, 화면은 편집 시작 시점 값에서 바뀐 경우에만 전송한다). 키가 있는 게시판(공지)의 대상 변경은 400, 같은 값은 통과. 잠금: 수정은 게시판 행 `FOR UPDATE` → 사이트 행 `FOR SHARE`(사이트 삭제는 게시판 행을 잠그지 않아 순환 없음).
- **삭제**: **공통 공지만 409**(`Board.isCommonNotice`). 전용 공지 게시판은 살아 있는 글이 없으면 삭제할 수 있다(막으면 그 사이트를 영구히 지울 수 없다) — 삭제 뒤 그 사이트는 공통 공지로 돌아간다. 비공개 전환 400은 키가 있는 모든 게시판(`isSystem`). **소프트 삭제는 `site_id`와 `board_key`를 비운다**(`Board.softDelete`) — 삭제된 행이 사이트 삭제의 FK와 `board_key` 유일성을 붙잡지 않게. `SiteService.hasContent`의 `boardRepository.existsBySiteId`는 삭제된 행도 센다(소속을 비우지 않고 지운 행이 있어도 FK 500이 아니라 409가 되게).
- **화면**(`admin/board/manage.html`): 목록 "표시 대상" 배지(+공지 배지), 폼의 표시 대상 선택 박스(`BoardPageController`가 `ContentScopeOptions`를 `scopeSites`로 서버 렌더링, `content-scope.js` 재사용), 생성 모드의 "이 사이트의 공지 게시판으로 만들기"(사이트를 고르고 공개일 때만 활성), 공지 게시판을 열면 박스 잠금. 게시글 관리 화면(`posts.html`)·`MyBoardResponse`·통합 검색은 바꾸지 않았다.
- 시험: `BoardSiteScopeApiIntegrationTest`(생성/수정/공지 규칙/삭제/사이트 삭제 가드)·`BoardSiteScopeConcurrencyIntegrationTest`(사이트 삭제 ↔ 게시판 지정 3경로)·`PublicBoardSiteScopeIntegrationTest`(`com.cms.publicweb.support` — 목록·상세·공지 해석·메인·이미지 비활성 사이트)·`PostRepositoryDataJpaTest`(소속 필터·공지 해석·`existsBySiteId`)·`BoardScopeAdminBrowserTest`(실제 브라우저).

## 공개 메뉴 렌더링 (PR ⑤, 2026-10-14, `PLAN-site-menu.md` "PR ⑤ 상세 설계" P5-v3, 적대적 리뷰 2라운드 ship)

- **스키마·인가 정책 변경 없음**(`SecurityConfig`·레이트리밋·`AdminFeature`·관리 화면·API 그대로). 공개 사이트 메뉴(`menu.site_id` = 공개 사이트)가 `/{siteKey}/…`의 모든 정상 공개 화면에 내비게이션으로 그려진다 — 구성·규약·시험은 `com.cms.publicweb.support`의 `CLAUDE.md` "공개 사이트 메뉴". 이로써 PR ① 계획의 R5("공개 사이트 메뉴는 어디에도 렌더링되지 않는다")는 해소됐다 — **관리자가 저장한 메뉴가 곧바로 공개 화면에 보인다**(캐시 없음).
- **`SiteLinkPolicy.permits(site, url)`**: 편집 시점(`validate`)과 **출력 시점**이 같은 규칙 한 벌(`violation`)을 쓰도록 추출한 예외 없는 판정이다. 의미 차이: `validate`는 null·빈 URL을 "URL 없음"으로 통과시키고 `permits`는 링크로 쓸 수 없으므로 `false`다. `validate`의 동작·문구는 그대로이며 `SiteLinkPolicyTest`가 `permits` ↔ `validate` 동치(사이트 3종 × 입력표)를 고정한다. 정책 규칙을 바꾸면 이 한 곳만 고친다.
