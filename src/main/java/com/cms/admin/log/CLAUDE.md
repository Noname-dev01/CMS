# CLAUDE.md — com.cms.admin.log

이 디렉터리(관리자 행위 감사 로그 도메인) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조.

**AdminActionLog**: 관리자 행위 감사 로그. `@AdminActionLogged`가 붙은 메서드 호출 시 성공/실패·요청 IP·URI가 자동 기록된다. `AdminActionLogAspect`가 처리한다.

- **독립 트랜잭션**: `AdminActionLogService.log()`는 `Propagation.REQUIRES_NEW`로 실행된다. 원 비즈니스 트랜잭션이 롤백되어도 FAIL 로그는 별도 트랜잭션으로 커밋된다.
- **예외 격리**: Aspect 내부에서 로그 저장 실패를 try-catch로 격리한다. 로그 저장이 실패해도 원 요청 결과(성공/실패)는 뒤집히지 않는다.
- **커밋 순서 보장(감사 H-03·M-01, 2026-09-28)**: `AdminActionLogAspect`에 `@Order(Ordered.LOWEST_PRECEDENCE - 1)`이 붙어 `@Transactional` 어드바이저(기본값 `LOWEST_PRECEDENCE`)보다 확실히 바깥에 위치한다 — 순서가 동률이면 어느 쪽이 안쪽인지 Spring 내부 구현에 의존하는 비결정적 상태가 되어, 감사 SUCCESS가 원 트랜잭션 커밋 전에 먼저 커밋될 수 있었다. 이 순서 덕분에 커밋 실패는 `@AfterThrowing`으로 자동 전환돼 FAIL로 정확히 귀속된다. **보장 범위는 `@AdminActionLogged`가 붙은 메서드가 해당 요청의 최상위 트랜잭션 진입점일 때로 한정**된다 — 이미 열린 다른 `@Transactional` 메서드 안에서 참여 호출되면 이 보장이 깨질 수 있다(업무 롤백 + SUCCESS 감사 잔존, `AdminActionLogCommitOrderIntegrationTest`의 "알려진 한계 재현 테스트"가 이 경계를 고정 기록). 오늘 기준 감사 대상 5개 서비스 13개 메서드(메뉴 구조 반영·`RolePermissionService.replace` 포함) 전부가 최상위 진입점이다. 프로브가 아닌 **실제 서비스 메서드**로 이 보장을 확인하는 것은 `MenuService.applyStructure`뿐이다(`MenuConcurrencyIntegrationTest`가 정상 커밋의 SUCCESS 1건·`targetId` 없음(`applyStructure_movesSubtreeToPosition_andLogsOnce`)과 **실제 커밋 단계 예외** 시 SUCCESS 없이 FAIL만 남고 변경이 롤백됨(`applyStructure_commitTimeFailure_recordsFailNotSuccess`)을 검증 — 리포지토리 프록시 advice로 `beforeCommit` 예외를 주입한다. 이전에는 `moveMenu`가 이 역할이었으나 2026-10-01 PR #75에서 API와 함께 삭제되며 테스트가 사라졌다가 복원했다. 변이 실험으로 Aspect의 `@Order`를 `LOWEST_PRECEDENCE`로 훼손하면 이 테스트가 실패함을 확인했다). 나머지 메서드는 위 "오늘 기준" 사실이 유일한 방어선이다.
- **대상 이름 스냅샷 `targetLabel`**(2026-10-01, V12 `admin_action_log.target_label VARCHAR(500) NULL`, `PLAN-menu-permanent-delete.md` PR A): 하드 삭제처럼 대상 행이 사라지는 액션은 `targetId`만으로 사후에 무엇이었는지 알 수 없어, `@AdminActionLogged(targetLabelExpression = "...")`가 결과 객체의 **String getter** 값을 로그 시점 문자열로 남긴다(`targetIdExpression`과 같은 리플렉션 방식). **성공 로그에만** 기록하고(실패 로그는 `targetId`처럼 null), 500자를 넘으면 자르며, 표현식이 없거나 getter가 없거나 문자열이 아니면 null로 흡수한다 — 기존 액션은 표현식을 지정하지 않으므로 동작 불변. `AdminActionLogService.log(...)`의 시그니처는 `targetId` 다음에 `targetLabel`이 추가됐다(연속 `String` 인자가 많아 위치 매핑을 `AdminActionLogServiceTest`가 필드별로 고정). 직접 호출처는 Aspect 외에 `AdminAccountAutoLockListener`(`targetLabel=null`)다. 활동 로그 화면은 목록 "대상" 열(`MENU #12 · 이름`)과 상세 모달 "대상 이름" 행에 표시하며 **모든 값을 `escapeHtml`로 이스케이프**한다(라벨은 관리자 입력). **보존은 최선 노력**: 감사 저장이 실패하면(예외는 격리돼 본 작업은 성공) 이름 기록이 유실될 수 있어, `AdminActionLogAspect.logSuccess`의 저장 실패 `log.error`에 `actionType`·`targetId`·라벨을 남긴다. 이때 라벨은 사용자 입력이라 개행 등이 가짜 로그 줄을 만들 수 없도록 `escapeForLog`로 이스케이프한다 — 역슬래시·제어문자(Cc)·줄/문단 구분자(Zl·Zp: `U+2028`·`U+2029`, `U+0085` 포함)를 가역 형태(`\\`·`\r`·`\n`·`\t`·`\uXXXX`)로 치환(Java 17 `\p{Cntrl}`은 ASCII 제어문자만 잡아 유니코드 줄바꿈을 놓치므로 문자 종류로 판정). DB에 저장하는 값은 원문을 유지한다.
- **IP 신뢰 정책**: `getClientIp()`는 `com.cms.common.web.ClientIpResolver.resolve()`(정적 유틸)에 위임한다. 이 프로젝트에는 실제 리버스 프록시가 없으므로(Gate H NOT RUN) `X-Forwarded-For`/`X-Real-IP` 등 전달 헤더는 전혀 신뢰하지 않고 `request.getRemoteAddr()`만 사용한다(레이트리밋과 동일 정책). 같은 유틸을 `VisitLoggingAuthenticationSuccessHandler`·`LockingAuthenticationFailureHandler`·`PasswordResetController`도 함께 쓴다 — 실제 ingress 도입 시 이 유틸 한 곳만 재검토하면 된다. 상세는 `adversarial-review/plan/PLAN-audit-log-integrity.md` 참조.
