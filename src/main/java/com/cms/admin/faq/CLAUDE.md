# CLAUDE.md — com.cms.admin.faq

이 디렉터리(FAQ 카테고리·FAQ 관리) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조. 설계 결정·적대적 리뷰 6라운드 기록은 `adversarial-review/plan/PLAN-faq.md`(2026-10-12). 공개 측은 `com.cms.publicweb.faq`의 `CLAUDE.md`(공개 `/faq`·즉시 필터).

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

- **권한 — 네 번째 기능 단위 위임(`DELEGABLE`) 기능 `FAQ`**: 카테고리와 FAQ가 **한 기능**이다. 핸들러 분류: 트리·FAQ 상세 = READ, 카테고리·FAQ 등록 = CREATE, 수정·**순서 반영(`PUT /order`)** = UPDATE, 삭제 = DELETE. URL 게이트(`/admin/faq/manage`·`/admin/api/faqs`·`/admin/api/faqs/**`·`/admin/api/faq-categories`·`/admin/api/faq-categories/**`)는 `AdminFeature.FAQ.gatePatterns`에서 `SecurityConfig`의 `DELEGABLE` 루프가 만든다(관리 쪽 `SecurityConfig` 수정 없음). 배너·팝업·정적 페이지 권한과 서로 독립이다(`FaqPermissionMatrixIntegrationTest`). 화면 버튼은 `myPermissions`(`"FAQ:CREATE"` 등)로 숨길 뿐 서버 판정(403)이 최종이다. **새 `DELEGABLE` 기능을 추가하면 열거하는 시험이 함께 바뀐다**: `AdminSidebarAdviceSnapshotTest`·`AdminPermissionEvaluatorTest`(ADMIN 전 동작 키)·`MenuExposureSidebarIntegrationTest`(위임 READ 시드는 카탈로그에서 생성).
- **스키마**: `faq_category`(이름 50자·`ord`·`use_yn`)·`faq`(`category_id` FK **RESTRICT**·질문 300자·`answer_html` MEDIUMTEXT·`ord`·`use_yn`)·`faq_lock`(가드 행 id=1 + `version`). 둘 다 **하드 삭제**, 연관관계 매핑 없이 `categoryId`만 가진다. 날짜 컬럼은 `datetime(6)`. 공개는 `카테고리.use_yn ∧ FAQ.use_yn`이고 카테고리를 숨기면 그 안의 FAQ가 모두 숨는다.
- **동시성 — 모든 쓰기 메서드의 첫 DB 조회가 가드 행 `faq_lock` `FOR UPDATE`** (`FaqService.lockGuard`): 규칙이 하나(가드 → 끝)라 교착 추론이 필요 없고 행 락·`@Version`이 필요 없다. 비잠금 읽기(`count`·최대 `ord`·목록)는 가드를 잡은 **뒤에** 한다. 가드 행이 없으면 `IllegalStateException`(500) — 조용히 잠금 없이 진행하지 않는다. 이름·질문·답변·노출만 바뀌는 수정도 가드를 잡지만 `version`은 올리지 않는다. **`version`은 구조가 바뀔 때만 +1**: 카테고리·FAQ 등록·삭제, FAQ의 카테고리 이동, **실제로 바뀐** 순서 반영. 시험: `FaqConcurrencyIntegrationTest`(`LockWaitObserver` 락 대기 관측, 빈 테이블 12개 동시 등록 = `ord` 0..11·버전 +12, 상한 직전 6개 동시 등록 = 정확히 하나만, 같은 version으로 서로 다른 순서를 동시 반영 = 정확히 하나만 성공·하나 409). **변이 실험으로 `lockGuard()`를 잠금 없는 `findById`로 바꾸면 3건이 실패함을 확인**했다(락 대기 시험은 `bumpVersion`의 UPDATE가 같은 행을 잠그므로 변이에서도 통과 — 정확한 상한·`ord` 유일·순서 경합 시험이 검출한다).
- **조회는 version과 트리를 한 읽기 트랜잭션(같은 REPEATABLE READ 스냅샷)에서 읽는다**(`getTree`, 잠금 없음): 쓰기만 직렬화해서는 "옛 순서 + 새 version" 응답을 막지 못하고, 그 응답으로 만든 순서 초안은 다른 관리자의 변경을 409 없이 덮는다(`treeRead_versionAndOrderComeFromOneSnapshot`가 순서 반영이 계속 커밋되는 동안 version 짝홀과 순서의 일치를 본다).
- **`ord` 불변식: 각 부모(카테고리는 전체, FAQ는 카테고리)의 `ord`는 항상 정확히 0..n-1**: 등록은 맨 끝, **삭제·카테고리 이동은 영향받은 목록을 같은 트랜잭션에서 즉시 재번호**(값이 다른 행만 쓴다), 이동한 FAQ는 대상 카테고리의 맨 끝에 들어간다. 배너는 삭제 후 압축하지 않지만(순서 저장이 한 번에 고친다) FAQ는 "같은 순서 재저장 = 쓰기·버전 없음"이 값 비교에 기대므로 연속성을 항상 유지한다.
- **상한은 정확하다**: 카테고리 30·FAQ 200(초과 409). 가드로 직렬화되므로 동시 등록에도 넘지 않는다(팝업의 소프트 상한과 다르다).
- **순서 반영 `PUT /admin/api/faqs/order`**: 요청 `{version, categories:[{id, faqIds:[…]}]}` — 전체 카테고리 순서와 각 카테고리의 전체 FAQ 순서. 검사 순서: 형식(중복) 400 → 가드 잠금 → **`version` 불일치 409** → 집합이 현재와 다르면 **400**(버전이 같은데 집합이 다르면 클라이언트 오류 — 다른 카테고리로 옮기는 요청도 여기서 400) → 값이 다른 행만 쓰고 **바뀐 것이 있을 때만** 버전 +1 → 응답은 같은 트랜잭션에서 만든 새 트리. **카테고리 간 이동은 FAQ 수정(`categoryId` 변경)으로만** 한다. `PUT /order`와 `PUT /{id}`는 같은 컨트롤러에 있고 리터럴 경로가 우선하며 `FaqApiIntegrationTest.routing_orderVersusId`가 고정한다.
- **API 응답과 감사**: 등록·수정·삭제 서비스는 최상위 `getId()`를 가진 결과(`FaqResponse`·`FaqCategoryResponse`)를 돌려준다 — 감사 Aspect가 **반환 객체의 최상위 숫자 getter**로만 `targetId`를 뽑기 때문이다(트리만 돌려주면 `targetId=null`로 조용히 누락). 등록 응답은 트리가 아니라 **생성된 항목**이고 화면이 `GET`으로 트리를 다시 읽는다. 감사: `FAQ_CREATE`·`FAQ_UPDATE`·`FAQ_DELETE`(`targetType=FAQ`), `FAQ_CATEGORY_*`(`targetType=FAQ_CATEGORY`), `FAQ_ORDER`(`targetId` 없음). 질문·이름·답변은 사용자 입력이라 `targetLabel` 없음, 실패 행 `errorMessage`는 고정 문구(`safeErrorMessage`)다. `AdminActionTypes`와 `templates/admin/log/manage.html` 라벨은 동기화 시험이 고정한다.
- **답변 본문**: `ContentBodyPolicy.sanitizeFaq`(**이미지 불허** — 본문 이미지 공개 판정에 FAQ를 끌어들이지 않으려고, 보이는 글자 5,000자, 정리 후 30,000바이트, 요청 원문 60,000바이트(`@MaxUtf8Bytes`로 파싱 전에 거름))와 출력 시 재정리 `sanitizeForFaqOutput`(결과의 `SanitizedHtml.blank()`가 참이면 공개에서 건너뜀). 편집기는 `NoticeEditor.create(…, {allowImages:false})`다.
- **카테고리 삭제**는 FAQ가 하나라도 있으면 409(먼저 옮기거나 지운다). 존재하지 않는 카테고리를 FAQ 등록·이동에 지정하면 **400**(본문 참조 오류), 대상 FAQ·카테고리 자체가 없으면 404.
- **화면은 React 아일랜드다**(2026-11-22, `adversarial-review/plan/PLAN-react-admin-faq.md` — 관리자 화면 React 점진 도입 1단계): 템플릿은 head·사이드바·상단바·제목·`<style>`만 그리고, 본문은 `frontend/src/admin/faq`(`FaqManage`·`FaqTreeView`·`FaqModal`·순수 로직 `state.ts`)가 `#faqManageRoot`에, 모달은 `#faqModalRoot`(옛 화면처럼 `#wrapper` 밖)에 그린다. 서버 데이터는 **인라인 스크립트 없이** `#faqManageRoot[data-permissions]`(`#strings.setJoin(myPermissions, ',')`)와 숨긴 `#faqScopeSites > li[data-id][data-active]`(텍스트 = 사이트 이름)로만 넘긴다. API 호출은 화면 무관 모듈 `frontend/src/api/{http,faq}.ts`. **옛 인라인 스크립트의 동작과 DOM 계약(id·클래스·`data-*`·`disabled`·`d-none`·`#faqModal[data-state]`·`confirm` 문구)을 그대로 유지한다** — 아래 동작 설명은 React 판에도 그대로 적용된다. React로 옮기며 생긴 규칙: ① 이벤트 핸들러가 즉시 최신 값을 읽도록 화면 상태를 ref에 동기 반영하고(`update()`), 세대(`loadSeq`·`detailSeq`)·모달 전환(`modalState`)·미저장 기준값은 ref에만 둔다. ② 폼은 controlled이고 미저장 기준값은 DOM이 아니라 폼 모델로 만든다. 모달은 `flushSync`로 모드·폼을 반영한 뒤 연다. ③ **모달은 네이티브 `<dialog>`다**(2026-11-25, 이슈 #298 1단계, `adversarial-review/plan/PLAN-dialog-faq-modal.md` — 공용 규칙은 루트 `CLAUDE.md`): `open`은 브라우저가, `data-state`(`closed`·`open`·`closing`)는 처음 값만 prop이고 이후는 직접 쓴다. ×·[닫기]는 `requestClose`(미저장 확인), 저장·삭제 성공과 상세 실패는 `closeModal`(확인 없음)이며 정리는 `close` 이벤트에서만 한다. ④ 편집기(`NoticeEditor`, 이미지 없음)는 React가 자식을 관리하지 않는 빈 호스트(`.faq-editor`)에 `#faqAnswerEditor`를 직접 만들어 한 번만 만든다(Quill이 툴바를 끼워 넣는다, 파괴 API 없음). ⑤ **GET 요청에는 `method`를 싣지 않는다**(`fetch(url, {headers})` — 브라우저 시험의 fetch 가로채기가 "`options.method`가 없으면 GET"으로 상세 조회를 식별한다, 넣었다가 3건이 깨졌다). 화면을 고친 뒤에는 `./gradlew frontendBuild` 또는 `bootRun`이 번들을 다시 만든다(IntelliJ 자체 실행은 번들이 없어 화면이 빈다).
- **화면 동작**(옛 `templates/admin/faq/manage.html` 인라인 스크립트 → React): 왼쪽 카테고리 카드 안에 FAQ 행, 오른쪽에 카테고리 폼·FAQ 폼(편집기). 순서는 **새 라이브러리 없이 포인터 드래그(마우스·터치·펜) + ▲▼ 버튼**이 같은 **초안**(`order`)을 바꾸고 [순서 반영]이 `PUT /order`를 보낸다([취소]는 서버 상태로). 같은 카테고리 안 FAQ와 카테고리 순서만 끈다(종류·카테고리가 같은 대상 위에서만 표시가 생기고, 놓으면 대상의 위치로 들어간다). 상태 플래그: `busy`(쓰기 요청부터 후속 목록 갱신 완료까지·목록 조회 중), `loadingDetail`, `syncFailed`, 초안 `isDirty()`. **잠금 규칙**: 목록 조작(드래그·▲▼·[반영])은 `busy`/`loadingDetail`/`syncFailed` 중 막히고 **이벤트 핸들러 안에서도 검사**한다(버튼 `disabled`만 믿지 않음). 폼 전체(`fieldset`)와 Quill 편집기(`editor.quill.enable(false)`)는 위에 **초안이 있는 동안**도 잠근다(재조회가 초안을 지우므로). 목록 GET은 요청 세대(`loadSeq`)를 갖고 초안이 시작되면 세대를 올려 이전 응답을 폐기한다. **잠금 상태가 바뀌면 `sync()`로 목록을 다시 그려야 한다** — 손잡이·▲▼의 활성 여부가 그리는 시점의 잠금으로 정해져, 목록 조회 중에 그려진 화면이 조회 뒤에도 잠긴 채 남는 결함을 브라우저 시험이 잡았다. **쓰기 결과와 목록 동기화를 분리**한다: 쓰기 2xx 뒤 재조회가 실패하면 `syncFailed`("저장은 완료됐지만 …")로 [새로고침]만 허용, 쓰기 응답을 잃으면 "저장 여부를 확인할 수 없습니다 … 직접 확인"으로 폼을 잠그고 **자동 재전송하지 않는다**(멱등 키는 두지 않았다 — 수용한 한계). 409(낡은 화면·상한·자식 있는 카테고리)면 서버 메시지 + 최신 목록 재조회(초안 폐기), 400이면 초안을 남긴다. 이름·질문은 `textContent`로만 삽입. 메서드 보안 403의 `message`가 영문이라 고정 한국어 문구를 쓴다.
- **순서 이동의 접근성·터치**(2026-11-25, 이슈 #300): 드래그는 `FaqTreeView`가 포인터 이벤트로 처리한다 — 상태 전이 `admin/shared/dragState.ts`와 자동 스크롤 `admin/shared/dragScroll.ts`는 메뉴 편집과 **공용**이고 놓기 규칙만 화면별이다(계약은 `com.cms.admin.menu`의 `CLAUDE.md` "드래그는 포인터 이벤트"). ① 끄는 항목·대상은 순번이 아니라 **ID**(`OrderItem`)로 들고 놓을 때 초안에서 다시 찾는다. 목록이 잠기면 진행 중인 드래그를 취소한다. ② `touch-action: none`은 **쓸 수 있는 손잡이에만** 둔다(빼면 터치 드래그가 죽고, 넓히면 터치 스크롤이 막힌다). ③ 끝에 닿은 ▲▼는 `aria-disabled`(포커스 유지, 눌러도 무시), 목록 잠금·권한 없음은 `disabled`다. 이동 뒤 같은 버튼에 포커스를 되돌리고 행을 화면 안으로 스크롤한다. 놓을 자리 선은 행이면 안쪽 그림자, 카테고리 카드면 `::before`·`::after`다(카드의 안쪽 그림자는 머리글·행 배경에 가려진다 — 실기에서 발견). ④ 안내 `#orderMoveStatus`(polite)는 목록 **밖**에 항상 두고 비운 뒤 500ms 늦게 채우며 취소·재조회 때 비운다(드래그도 같은 안내). 변이 실험: `touch-action`·끝 버튼·안내 비우기(취소·재조회)·`blur` 취소·자동 스크롤 표시 갱신·카테고리 간 검사·화면 안 스크롤·잠금 취소 제거는 모두 검출된다. 포커스 복귀 호출은 빼도 시험이 통과한다(React가 커밋 때 되돌린다 — 문서화된 계약이 아니라 명시적으로 남겼다).
- **수용한 한계**: FAQ **항목** 단건 수정의 질문·답변 stale-form 덮어쓰기는 수용한다(카테고리 수정은 PR ③부터 `version`으로 막고, 항목의 **소속 카테고리**는 `baseCategoryId`로 막는다). 실제 터치 기기와 화면 낭독기에서는 확인하지 못했다(터치는 CDP 터치 입력, 안내는 DOM으로 확인). 쓰기 응답이 유실된 뒤의 늦은 커밋은 막지 않는다(재조회가 성공해도 원래 요청이 뒤늦게 커밋될 수 있다 — 다른 관리 CRUD와 같은 한계).
