# CLAUDE.md — com.cms.admin.contentimage

이 디렉터리(편집기 본문 이미지) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조. 설계 결정·적대적 리뷰 7라운드 기록은 `adversarial-review/plan/PLAN-html-editor.md`.

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

- **미디어 라이브러리(2026-10-12) 이후 이 테이블이 라이브러리 원본이다** — 배너·팝업·라이브러리 업로드 이미지도 `content_image`에 있고(`scope_type` `BANNER`·`POPUP`·`LIBRARY`, `namespace`(빈 문자열 = 루트)·`original_name` 추가, 유일성은 `UNIQUE(namespace, storage_key)`), 배너·팝업과의 연결은 `content_image_ref`의 `owner_type` `BANNER`/`POPUP`이며, **카운터 `content_image_usage`는 배너·팝업 이미지까지 센다**. 등록은 `MediaImageRegistrar`, 제거는 `MediaImageRemover`, 가시성·권한·잠금 순서·격리 수준은 `com.cms.admin.media`의 `CLAUDE.md`가 원본이다. 아래 서술 중 "본문 이미지 전용"으로 읽히는 부분은 게시판 출처(`BOARD`) 이미지에 대한 것이다.
- **세 테이블**: `content_image`(파일 메타·업로더 userId 스냅샷), `content_image_ref`(어느 콘텐츠가 어느 이미지를 참조하는지 — `(owner_type, owner_id, image_id)` 복합 키, `image_id` FK RESTRICT), `content_image_usage`(전체 바이트·개수 카운터 행 1개, id=1, V2 시드). owner는 `POST`(게시글 — 공지도 공지 게시판의 게시글)다(`ContentImageService.OWNER_POST`). 옛 `NOTICE` owner·`OWNER_NOTICE`·`SCOPE_NOTICE`·`existsPublishedNoticeRef`는 공지 흡수(2026-10-09, `PLAN-notice-to-board.md` 쟁점 7)와 함께 코드에서 제거됐다.
- **업로드 출처(2026-10-08, `PLAN-board.md` 쟁점 9)**: `content_image.scope_type`(`BOARD`·`LIBRARY`·`BANNER`·`POPUP`, 기본값 없음 — V3가 옛 기본값 `NOTICE`를 없앴다)·`scope_id`(게시판 ID). 새 업로드는 항상 값을 넣는다(게시판 본문 이미지는 `BOARD:{boardId}`). **참조 자격**: `replaceRefs(ownerType, ownerId, scopeType, scopeId, imageIds)`가 콘텐츠 출처와 이미지 출처가 다르면 400(다른 게시판의 비공개 이미지를 자기 공개 글에 넣어 공개하는 경로 차단 — 거부는 삭제·쓰기 전이라 기존 참조가 남는다). 게시글은 **같은 게시판 출처 이미지만** 참조한다(`replaceRefs("POST", postId, "BOARD", boardId, …)`). **공개 판정**: `PublicContentImageService.findViewable`이 값싼 순서로 ① `existsPublishedPostRef`(공개 게시글 + 공개·미삭제 게시판 + 이미지 출처 = 그 게시판; **`r.imageId = :imageId` 연결 조건 필수**) ② BOARD 출처 ∧ **그 게시판의 현재 READ**(`allowsBoard`, 업로더 본인 조건 없음 — 권한 회수 즉시 404) 중 하나면 200.
- **새 이미지 거부 오버로드(2026-10-28, 게시판 작성 정책)**: `replaceRefs(…, boolean allowNewImages)`가 `false`면(게시판 `body_image_yn=0`) **존재하는** 이미지 중 이 콘텐츠가 지금 참조하지 않는 것이 하나라도 있을 때 삭제·쓰기 전에 400이다 — 이미 참조 중인 이미지는 유지하고 존재하지 않는 ID는 조용히 뺀다. 5인자판은 `true`로 위임하므로 배너·팝업·미디어 호출부는 그대로다. `uploadForBoard`는 쓰기 중지 판정 뒤에 같은 정책으로 400. 상세는 `com.cms.admin.board`의 `CLAUDE.md` "게시판 작성 정책".
- **본문 src 계약**: 본문 이미지는 `/content-images/{id}`(같은 사이트, `Long` 범위)만 허용된다 — 외부 URL·`data:`는 `HtmlContentSanitizer`가 `img`째 지우고, 편집기(`static/js/admin/notice-editor.js`)도 붙여넣기 단계에서 버린다. 경로 상수는 `HtmlContentSanitizer.CONTENT_IMAGE_PATH_PREFIX`와 공개 컨트롤러 매핑이 같아야 한다.
- **업로드**: 진입점은 게시판 업로드(`POST /admin/api/boards/{boardId}/content-images`) 하나다(옛 공지 업로드 `/admin/api/notices/content-images`는 제거). 핸들러 선언은 `@RequireBoardPermission(READ)`이고 `ContentImageService.uploadForBoard`가 **같은 게시판의 CREATE∨UPDATE를 `allowsBoard`로 재판정**(403)한 뒤 삭제된 게시판이면 404 — 작성 중(게시글 ID 없음)과 수정 중 모두 이미지가 필요한데 선언은 동작 하나만 받기 때문. 검증은 공용 `ImageFileValidator`(png·jpeg·gif, 5MB, 한 변 4096px·4096² 픽셀, 단일 프레임·APNG·GIF 논리 화면 검사, **전체 디코드 없음** — 힙 보호). 카운터 행을 `findByIdForUpdate`로 잠그고 바이트(`cms.content-image.max-total-bytes`, 기본 1GB)·개수(`max-count`, 기본 10,000) 상한을 정확히 집행한다(초과 409, 업로드가 직렬화된다). 파일은 `FileStorage` **루트(네임스페이스 없음)**에 저장하고 롤백 시 정리(`FileStorageTransactionSupport.deleteOnRollback(storage, key)`) — 카운터 증가도 같은 트랜잭션이라 함께 롤백된다. 감사 로그 `CONTENT_IMAGE_UPLOAD`.
- **카운터 보장 범위는 DB 등록 이미지뿐**: 커밋 전 강제 종료 등으로 남은 "행 없는 파일"은 집계되지 않는다. 미참조·삭제 게시글 이미지의 자동 정리는 없다 — ADMIN이 미디어 라이브러리에서 직접 지우거나(출처 "게시판 본문"·"사용 안 함만" 필터) 수동 회수 절차로 정리한다(`docs/deployment.md` "편집기 본문 이미지", 미디어 라이브러리 도입 후 ②·⑤가 개정됨)(②는 살아 있는 게시글 참조를 제외하고 ⑤는 `post_attachment` 키를 보존한다).
- **참조 교체**(`replaceRefs`): 대상 이미지를 id 오름차순 `FOR SHARE`로 읽어(존재 확인과 삭제 방지를 한 번에 — 삭제가 먼저면 그 ID는 조용히 빠지고, 이 잠금이 먼저면 삭제는 대기 후 409) 라이브러리 계열 이미지는 **저장하는 사람의 현재 `MEDIA` 읽기 권한**을 요구한다(이미 이 콘텐츠가 참조 중인 것은 권한이 회수돼도 유지). **현재 참조를 읽을 때는 엔티티가 아니라 이미지 ID 투영(`findImageIdsByOwner`)을 쓴다** — 참조 엔티티를 영속성 컨텍스트에 올려 두면 이어지는 벌크 삭제가 컨텍스트를 비우지 않아 `saveAll`이 "이미 관리 중"으로 보고 INSERT를 건너뛰어 참조가 사라진다(`MediaLibraryApiIntegrationTest.postSaveRequiresMediaReadForLibraryImages`가 처음 잡았다). 벌크 삭제 후 삽입이며 `@Modifying(flushAutomatically = true)`만 쓴다 — `clearAutomatically`를 켜면 호출한 게시글 저장 트랜잭션의 `Post` 더티 체킹이 사라진다. 존재하지 않는 이미지 ID는 참조하지 않는다.
- **공개 다운로드**(`com.cms.publicweb.contentimage`, `GET/HEAD /content-images/{id}`): 공개 게시판(공지 게시판 포함)의 공개 게시글이 참조하고 **그 게시판 출처 이미지**일 때만 익명 200, 또는 요청자가 **그 게시판의 현재 READ 권한자**(ADMIN 포함 — 작성 중·비노출 글 미리보기)면 200, 그 외(비숫자·범위 밖·없음·비공개만 참조·미참조·다른 게시판 권한만 가짐) 동일 404. 저장된 `image/*` 그대로 인라인, `nosniff`·`no-store`, 스트리밍(조회 트랜잭션과 파일 열기 분리).
- **대표 이미지 썸네일(2026-10-29, V12, `PLAN-board-definition.md` PR 5 — 적대적 리뷰 5라운드)**: 게시글의 대표 이미지(`post.cover_image_id`, 상세는 `com.cms.admin.board`의 `CLAUDE.md` "게시글 대표 이미지")를 지정하면 `ContentImageThumbnailService.ensureThumbnail`이 **게시글 저장 트랜잭션 안에서**(`Propagation.MANDATORY`) 이미지 단위 썸네일을 만든다 — 테이블 `content_image_thumb`(PK `image_id`, FK `CASCADE`), 파일은 스토리지 **예약 네임스페이스 `thumb`**(`LocalDiskFileStorage.RESERVED_NAMESPACES`에 추가됨 — 루트 API는 `thumb/…` 키를 해석하지 않는다). 순서: 이미 있으면 끝 → 생성 자리 획득(`Semaphore(2)`, 2초 대기 실패 시 `ServiceBusyException` 503 + `Retry-After`) → 원본 읽기·생성 → `store` + `deleteOnRollback` → **`INSERT IGNORE`**(0행이면 동시에 앞선 트랜잭션이 만들었으므로 자기 파일을 즉시 지운다) → 카운터 `FOR UPDATE`(마지막 잠금) + `reserveBytes`. **일반 INSERT/컬럼 UPDATE로 바꾸지 않는다** — 같은 이미지를 두 글이 동시에 대표로 지정하면 둘 다 이미지 `FOR SHARE`를 쥐고 있어 S→X 승격 교착이 난다. 카운터는 **바이트만** 센다(`reserveBytes`/`releaseBytes`, 개수는 업로드한 이미지 수의 약속이라 제외).
- **생성기 `common/image/ImageThumbnailer`(순수 함수)**: 긴 변 480px(원본이 더 작으면 `Optional.empty()` — 행·파일 없음, 단 **작은 원본도 전체 디코딩으로 검증**한다), JPEG → JPEG(품질 0.85)·PNG·GIF → PNG(알파 유지). 모든 위반은 400(`FAILED_MESSAGE`·`TOO_LARGE_MESSAGE`)이고 저장 전체가 롤백된다. 방어 — ① 축소 디코딩 계수 `ceil(긴 변/960)`, 리더는 메타데이터 무시(GIF 제외) ② **디코딩 경고(`IIOReadWarningListener`)가 하나라도 오면 실패**(잘린 JPEG를 EOI 보충으로 통과시키지 않는다 — 이 검사를 빼면 `ImageThumbnailerTest.truncatedJpegRejected`가 실패, 변이 실험) ③ JPEG는 SOF 마커에서 **컴포넌트 수 1·3만**(CMYK·YCCK 거부 — JDK 21은 CMYK를 디코딩하지만 색이 어긋난다)과 **libjpeg 계수 버퍼 추정(샘플링 계수 배수 패딩 포함) 48MiB 이하**(프로그레시브는 네이티브 메모리를 원본 해상도로 쓴다, 컨테이너 메모리 상한이 없다) ④ PNG는 청크를 허용 목록(`IHDR·PLTE·tRNS·IDAT·IEND`)만 남겨 **다시 조립**(팔레트 PNG는 `ignoreMetadata`가 안 먹어 압축 텍스트 청크가 누적 상한 없이 쌓인다)하고 **인터레이스 PNG는 긴 변 960 초과를 거부**(축소 디코딩이 건너뛰는 Adam7 패스의 손상은 경고 없이 통과한다) ⑤ GIF는 논리 화면 캔버스에 프레임을 오프셋대로 합성 ⑥ JPEG EXIF 방향(IFD0 0x0112)을 직접 파싱해 적용(깨지면 방향 1). **수용한 한계**: PNG zlib 끝(Adler-32)이 없어도 픽셀이 다 있으면 성공한다(썸네일이 원본과 같아 피해 없음).
- **공개 `GET/HEAD /content-images/{id}?size=thumb`**: 같은 핸들러가 `size`를 `request.getParameterValues`로 읽는다 — 없음 = 원본, **정확히 하나이고 `thumb`** = 썸네일, 그 밖(빈 값·대소문자 다름·두 개 이상·다른 값)은 **원본을 주지 않고 같은 404**. 판정은 원본과 같은 `viewableImage`(공개 글 참조 ∨ 그 게시판 READ ∨ MEDIA READ)이고 `PublicContentImageService.findViewableThumbnail`이 썸네일 행이 있으면 `thumb` 네임스페이스 파일, **없으면 원본**(작은 원본·대표가 아닌 이미지)을 준다. 헤더·레이트리밋 버킷(`content-image`)은 원본과 같다 — **갤러리가 한 페이지에 썸네일을 최대 50장 부르므로 PR 6에서 한도를 다시 본다**. `SecurityConfig`·공개 인벤토리·레이트리밋 설정은 바뀌지 않았다.
- **삭제**: 이미지를 지우는 유일한 경로 `MediaImageRemover.deleteLocked`가 이미지 `FOR UPDATE` 뒤에 썸네일 행을 읽어 `releaseBytes`로 돌려주고, 행은 FK CASCADE로 사라지며 **파일은 커밋 후 지운다**(원본·썸네일 둘 다). 대표로 쓰는 이미지는 참조가 있어 기존 규칙대로 409다. `replaceRefs`는 이제 **저장된 이미지 ID 집합을 반환**한다(대표가 "그 글의 참조 중 하나"인지 판정하는 근거 — 기존 호출자는 반환값을 무시한다)·`findReferencedImageIds`(본문을 바꾸지 않는 수정용).
- 시험: `ImageThumbnailerTest`(크기·형식·EXIF·손상·경고·CMYK·계수 버퍼 경계(4:2:2 3073×4073 패딩 포함)·팔레트 PNG 청크·인터레이스·GIF 논리 화면), `PostCoverImageApiIntegrationTest`(`admin.board` — 지정·PATCH 3상태·엄격 파싱·롤백·503·409·삭제 수명주기·동시 지정), `PublicContentImageThumbIntegrationTest`(`publicweb.contentimage`), `PostCoverImageUpgradeTest`(루트 — V11 → V12·FK 동작·복구 SQL).
