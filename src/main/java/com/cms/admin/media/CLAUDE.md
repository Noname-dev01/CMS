# CLAUDE.md — com.cms.admin.media

이 디렉터리(미디어 라이브러리) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조. 설계 결정·적대적 리뷰 5라운드(지적 21건 전부 수용) 기록은 `adversarial-review/plan/PLAN-media-library.md`(2026-10-12). 이미지의 원본 테이블·참조·카운터는 `com.cms.admin.contentimage`의 `CLAUDE.md`와 같이 읽는다.

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

- **새 테이블이 없다 — `content_image`가 라이브러리 원본이다**: 본문 이미지·배너·팝업·라이브러리 업로드 이미지가 한 테이블·한 카운터(`content_image_usage`, 기본 1GB·1만 개)·한 참조 테이블(`content_image_ref`)을 쓴다. `namespace`(빈 문자열 = 루트, `banner`·`popup`)는 **파일이 있는 `FileStorage` 영역**이다 — NULL이 아니라 빈 문자열인 이유는 MariaDB UNIQUE가 NULL 중복을 허용하기 때문이고, 유일성은 `UNIQUE(namespace, storage_key)`다. 공개 URL(`/banners/{id}/image`·`/popups/{id}/image`·`/content-images/{id}`)은 사이트 무관 경로이고 수동 회수 대상 디렉터리는 네임스페이스와 같다. **소비 코드는 `namespace`가 비면 루트 API(`open/load/delete(key)`), 아니면 네임스페이스 API를 쓴다**(`LocalDiskFileStorage`의 네임스페이스 API는 `[a-z0-9_-]+`만 받아 빈 문자열을 거부한다).
- **출처(`scope_type`)**: `BOARD`(게시판 본문, `scope_id` = 게시판 ID)·`NOTICE`(옛 공지 출처의 흔적, 컬럼 기본값)·`LIBRARY`(라이브러리 직접 업로드)·`BANNER`·`POPUP`(배너·팝업에서 직접 올림). `LIBRARY`·`BANNER`·`POPUP`이 **라이브러리 계열**(`ContentImageService.isLibraryScope`)이고 `BANNER`·`POPUP`은 소유자와 함께 사라지는 **소유 출처**(`isOwnedScope`)다. 게시판 출처 격리 규칙(다른 게시판 이미지는 못 넣음)은 그대로이고 **라이브러리 계열만** 어느 곳에서나 고를 수 있다.
- **배너·팝업 ↔ 이미지 연결은 `content_image_ref`(`owner_type` = `BANNER`/`POPUP`) 한 곳이다**: `banner`·`popup`에 `image_id` 컬럼이 없다(이중 장부 방지). 옛 `banner.storage_key`·`content_type`·`file_size`는 V3(2026-10-22)에서 제거됐다. 불변식 "배너와 이미지형 팝업은 참조 1개, HTML형 팝업은 0개"는 DB가 아니라 서비스·시험이 지킨다. 읽기는 `MediaImageLookup`의 **일괄 `IN` 조회 두 번**(참조 → 이미지)이고 복수 참조는 `image_id` 최솟값이다. 공개 조회는 소유자 쿼리에 `EXISTS(참조 ∧ 이미지)`를 넣어 **`LIMIT` 전에** 적격성을 판정한다(불완전한 이미지형 팝업이 5개 슬롯을 차지하지 않음 — `PopupRepositoryDataJpaTest`).
- **권한 — 다섯 번째 `DELEGABLE` 기능 `MEDIA`**(READ·CREATE·DELETE, UPDATE 없음): 핸들러는 `@RequirePermission(feature = MEDIA, …)`이고 게이트(`/admin/media/manage`·`/admin/api/media`·`/admin/api/media/**`)는 `SecurityConfig`의 `DELEGABLE` 루프가 만든다(코드 변경 없음). **고르기도 READ를 요구한다** — 배너·팝업 선택(`MediaImageSelector`)과 게시글 본문의 새 라이브러리 이미지(`ContentImageService.replaceRefs`, 이미 참조 중인 것은 권한이 회수돼도 유지)가 저장 시점에 현재 `MEDIA` 읽기를 판정한다(이미지 ID는 연속 정수라 짐작해 넣을 수 있기 때문). BANNER/POPUP 권한만 있는 MANAGER의 **직접 업로드는 그대로 된다**.
- **출처별 가시성**(`MediaService.visibleScopes`): ADMIN은 전부, MANAGER는 라이브러리 계열만. 게시판 본문 이미지는 목록·상세·파일·삭제가 **SQL 조건/404로** ADMIN에게만 보인다(페이지·총건수가 어긋나지 않고 ID를 짐작해도 같은 404). 사용처의 게시글 라벨은 호출자가 그 게시판 READ일 때만 제목을 보이고, 배너·팝업 제목은 해당 기능 READ일 때만 보인다. 관리 미리보기는 공개 경로를 넓히지 않는 **관리자 전용 `GET /admin/api/media/{id}/file`**(`no-store`·`nosniff`)이다.
- **공개 규칙(변경 없음, `SecurityConfig` 무변경)**: `/content-images/{id}`는 공개 게시글이 참조하는 이미지만(라이브러리 계열도 공개 글이 참조하면 공개 — `existsPublishedPostRef`가 `(BOARD ∧ 같은 게시판) ∨ 라이브러리 계열`) 익명 200이고, **배너·팝업만 참조하는 이미지는 익명 404**다(자기 경로의 노출 재검증으로만 나간다). 저장 전 편집기 미리보기는 `MEDIA` 읽기 권한자도 가능하다. `ContentImageMeta.namespace`가 파일 위치를 전달한다.
- **잠금 순서와 격리 수준(확정, 변경 시 `PLAN-media-library.md` D5 표 먼저)**: `banner_lock` → 소유자 행 → **이미지 행** → 참조 행 → 카운터. 핵심 규칙은 **참조를 지우기 전에 이미지 행을 먼저 `FOR UPDATE`로 잠그는 것**이다(상대 소유자가 서로의 참조 행을 기다리는 순환 방지). 배너/팝업 **선택**은 이미지 행 `FOR SHARE`만 잡고 카운터는 잡지 않는다(새 행이 없다). `replaceRefs`는 대상 이미지를 id 오름차순 `FOR SHARE`로 읽어 존재 확인과 삭제 방지를 한 번에 한다(삭제가 먼저면 그 ID는 조용히 빠지고, 이 잠금이 먼저면 삭제는 대기 후 409 — 존재 확인 후 삭제 커밋 → FK 위반으로 글 저장 전체 롤백이라는 세 번째 결과가 없다). **이미지를 지우는 최상위 진입점(`MediaService.delete`·`BannerService.deleteBanner`·`PopupService.deletePopup`)은 `@Transactional(isolation = READ_COMMITTED)`다** — `content_image_ref.image_id`는 비고유 인덱스라 REPEATABLE READ의 잠금 읽기가 빈 범위에 갭 잠금을 걸어 "카운터를 쥔 직접 업로드"와 "카운터를 기다리는 삭제"가 순환할 수 있다. 격리 수준은 `REQUIRED`로 외부 트랜잭션에 참여하면 무시되므로 **공통 제거 컴포넌트에는 선언하지 않는다**(최상위 진입점만). 참조 존재 확인은 반드시 **잠금 읽기**(`lockByImageId`)다.
- **호출 그래프·감사**: `@AdminActionLogged`(`MEDIA_UPLOAD`·`MEDIA_DELETE`, `targetType=MEDIA`, `targetId`=이미지 ID)는 **최상위 진입점에만** 있다(감사 Aspect의 커밋 후 기록 보장은 최상위에서만 유효). 이미지 등록(`MediaImageRegistrar` — 카운터 잠금·`reserve`·파일 저장·행 기록·롤백 시 파일 정리)과 제거(`MediaImageRemover` — `detachOwner`·`deleteLocked`·커밋 후 파일 삭제)는 **감사도 자체 트랜잭션 경계도 없는** 컴포넌트로 호출자 트랜잭션에 참여한다. 내부에서 `REQUIRES_NEW`로 바꾸면 업무 원자성이 깨진다.
- **삭제 규칙**: 라이브러리 삭제는 참조가 하나라도 있으면 **409**이고 메시지에 사용처 요약("배너 #3, 게시글 #12 외 N건" — 종류·ID만, 제목은 상세 조회가 권한에 맞춰 채움)을 싣는다(`ApiErrorResponse`에 구조화 필드를 추가하지 않았다). 배너/팝업 삭제는 자기 참조를 지우고 **소유 출처(`BANNER`/`POPUP`) 이미지이며 다른 참조가 없으면** 이미지 행·파일(커밋 후)·카운터까지 정리한다 — `LIBRARY` 출처는 소유자 삭제가 날리지 않는다. 카운터는 `release`로 되돌린다(음수로 내려가지 않는다). FK `RESTRICT`는 최후 방어선이며 새로 번역하는 매핑을 만들지 않았다(기존 핸들러가 일반 409로 바꾼다).
- **업로드 한도**: 라이브러리·게시판 에디터는 5MB·한 변 4096px·4096²(`ContentImageService.LIMITS`), 배너·팝업 직접 업로드와 **라이브러리에서 고를 때**는 2MB·2560px·400만 픽셀(`MediaImageSelector`가 이미지를 읽어 헤더 검증을 다시 한다 — 5MB를 한 번 읽는다). 전체 상한은 기존 카운터(`cms.content-image.*`) 하나다. `original_name`은 경로 요소를 떼고 NFC·제어문자 제거·200자(코드포인트)로 정리한 표시·검색용 값이며 저장 경로에 쓰이지 않는다.
- **화면**: `templates/admin/media/manage.html`(업로드·검색·출처/미사용 필터·썸네일 그리드·상세 모달 — 사용처 목록, 사용 중이면 삭제 버튼 숨김 + 서버 409). 선택 모달 `static/js/admin/media-picker.js`를 배너·팝업 폼과 본문 편집기(`pickLibraryImage` 옵션 → 툴바 "라이브러리" 버튼, 본문 `src`는 여전히 `/content-images/{id}`)가 공유한다. 목록은 `GET /admin/api/media?selectable=true`(고를 수 있는 출처만). 파일명 등 사용자 입력은 `textContent`로만 넣는다.
- 시험: `MediaLibraryApiIntegrationTest`(생명주기·사용 중 409·소유자 삭제 규칙·선택 거부·권한 조합·출처 가시성·게시글 본문 공개/권한)·`MediaConcurrencyIntegrationTest`(삭제 경합·공유 이미지 동시 삭제·갭 락 순환 방지), `MediaPickerNestedModalBrowserTest`(**실제 브라우저** — 게시글 모달 위에 중첩한 선택 모달을 닫아도 아래 모달의 `body.modal-open`·스크롤·포커스가 유지됨. 닫힘은 fade 뒤 `hidden.bs.modal`에서 끝나므로 시험은 `show`가 빠진 시점이 아니라 선택 모달 `display:none`까지 기다리고, 열 때도 포커스가 선택 모달로 옮겨간 뒤에 닫는다), 배너·팝업·공개 이미지 시험(`BannerApiIntegrationTest` 등)은 정리 도우미 `com.cms.support.MediaTestSupport.cleanLibrary`로 이미지 행·참조·파일·카운터를 되돌린다.
- **썸네일(2026-10-29, V12, `PLAN-board-definition.md` PR 5)**: 게시글 대표 이미지 지정이 이미지 단위 썸네일(`content_image_thumb`, 파일은 `thumb/` 네임스페이스)을 만든다. **카운터 `total_bytes`는 원본 + 썸네일, `total_count`는 원본만**이다 — 카운터를 재계산하는 모든 SQL(수동 회수 ③·운영 확인·복구 SQL, 시험 정리 도우미)은 썸네일 합을 더해야 한다(안 더하면 용량 상한이 느슨해진다; `MediaTestSupport.recomputeCounter`는 시험용이라 원본만 센다). `MediaImageRemover.deleteLocked`가 썸네일 바이트를 돌려주고 커밋 후 썸네일 파일도 지운다(행은 CASCADE). 미디어 라이브러리 화면·관리 미리보기는 원본만 쓴다(썸네일 사용은 범위 밖). 상세는 `com.cms.admin.contentimage`의 `CLAUDE.md`.
