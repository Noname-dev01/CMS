# CLAUDE.md — com.cms.admin.member

이 디렉터리(관리자 계정 도메인) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조.

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

## Member (관리자 계정)

- **관리자 상세 평문 렌더링** (`admin-manage.html`, 2026-09-24, remediation PR 1): 상세 항목의 `value`는 평문으로 유지하고 출력 경계에서 `escapeHtml()`을 한 번 적용한다. 내부에서 만드는 이메일 버튼만 `html` 항목으로 분리하며 이메일 값은 별도로 escape한다. 이름 저장/API 원문 정책은 바꾸지 않는다. 실제 DOM·이메일 복사·역할/CSRF 회귀 절차는 `docs/verification/admin-detail-rendering.md` 참조.

- **초기 관리자 계정**: dev는 회원이 없으면 `TestMemberLoader`(`@Profile("dev")`)가 `userId=admin` / `pwd=1234`(BCrypt) ROLE_ADMIN 계정을 자동 생성한다. prod는 `AdminBootstrapLoader`(`@Profile("prod")`)가 `ROLE_ADMIN` + `ACTIVE`/`LOCKED`/`PASSWORD_EXPIRED`(D-01 대안 A allowlist, `existsByUserTypeAndStatusIn`) 중 하나인 계정이 하나도 없을 때만 `ADMIN_BOOTSTRAP_USER_ID`·`_PASSWORD`·`_EMAIL` 환경변수로 계정을 생성한다 — 셋 중 하나라도 없거나 값이 유효하지 않으면(검증 계약은 `AdminBootstrapCredentials`) 기동을 실패시킨다(관리자 없이 조용히 뜨는 것보다 안전하다는 결정). 적격 상태의 ROLE_ADMIN이 이미 있으면 환경변수를 검사하지 않는다 — **잠금·비밀번호 만료로 지금 로그인 못 하는 관리자도 "관리자 없음"과 구분**해, 그 상태만으로 공개 서비스 전체의 재기동이 막히지 않는다(감사 H-02, 2026-09-24, remediation PR 2). bootstrap은 기존 계정의 상태·해시·`lockedAt`·`passwordChangedAt`·재설정 토큰을 변경하지 않으며, 잠금 해제·만료 복귀는 여전히 기존 로그인/재설정 경로(`LoginFailureService`·`Member#changePassword`)가 담당한다. `DISABLED`/`DELETED` ADMIN만 있으면 여전히 신규 자격증명이 필요하고(기존 계정 부활·덮어쓰기 없음), 동시 부트스트랩 경합의 재조회 흡수 조건도 같은 allowlist로 통일됐다(다른 역할·비적격 상태·다른 ID 충돌은 흡수하지 않고 원 예외 전파). 이 존재 질의와 INSERT는 원자적이지 않다 — 동일 설치의 모든 인스턴스가 같은 부트스트랩 자격증명을 쓴다는 운영 전제 위에서만 "신규 ADMIN 한 명"이 보장된다. 저장·동시성 재조회는 `PasswordResetService`와 동일하게 `TransactionTemplate`으로 트랜잭션 경계를 명시한다(같은 클래스 내부 호출은 `@Transactional` 프록시를 타지 않으므로). 최초 계정이 이미 있는 경우에는 `POST /admin/api/members`(관리자 인증 필요)로 추가 생성한다. 상세 설계 결정은 `adversarial-review/plan/PLAN-prod-profile.md`(최초 도입)·`adversarial-review/remediation-plan.md` PR 2(D-01 상태 분리) 참조.
- **회원 목록 정렬 tie-breaker**(`MemberRepositoryImpl.toOrderSpecifiers`, 2026-09-30, 로드맵 L-01): 요청 정렬에 `id`가 없으면 마지막에 항상 `id desc`가 붙는다 — `userName`·`createDate` 같은 동률 가능 키만으로 정렬하면 페이지 경계에서 행이 중복·누락될 수 있었다. **보장 범위는 조회 사이에 데이터가 변하지 않는 동안의 동률 순서 결정성뿐**이다(offset/limit 방식이라 페이지 요청 사이 가입·삭제가 끼면 여전히 가능). 관리자 화면은 `sort`를 보내지 않아(기본 `id desc`) 영향이 없고 API 직접 호출 시에만 해당한다. 상세는 `adversarial-review/plan/PLAN-member-list-sort-tiebreak.md` 참조.
- **역할 변경과 개별 권한**(`AdminMemberService.updateAdminMember`, 2026-10-03, `PLAN-member-permission.md` §5-E): 역할이 실제로 바뀌면(방향 무관) 같은 트랜잭션에서 그 회원의 `member_permission` 행을 전부 삭제하고 **삭제 건수와 무관하게 `member.permission_version`을 +1**한다(권한 0개 회원이 역할을 왕복해도 역할 변경 이전 권한 화면의 PUT은 409). 캐시 무효화 이벤트는 행이 지워졌을 때만 낸다. 신규 MANAGER(`createAdmin`)는 권한이 없다(0개). 같은 대상 행 잠금(`findByIdForUpdate`)을 권한 저장도 쓰므로 둘은 직렬화된다. 상세는 `com.cms.admin.permission`의 `CLAUDE.md`.
- `Role`: `ROLE_ADMIN`, `ROLE_MANAGER`, `ROLE_USER` / `MemberStatus`: `ACTIVE`, `LOCKED`, `DISABLED`, `DELETED`, `PASSWORD_EXPIRED`
- **비밀번호 재설정 구현 완료** (`PasswordResetService`): 이메일로 재설정 링크 발송(토큰은 URL fragment `#token=`) → 토큰 검증 → 재설정. 토큰은 SHA-256 해시로만 저장(평문·해시 모두 **로그 출력 금지** — 예외 객체 통째 로깅도 금지), 30분 TTL·일회용·60초 재발급 쿨다운(발급 시 계정 행 잠금으로 원자성 보장). 계정 존재 여부와 무관하게 항상 200 응답(열거 방지), 대상은 `ACTIVE`/`PASSWORD_EXPIRED` + `ROLE_ADMIN`/`ROLE_MANAGER` allowlist. 재설정 성공 시 기존 세션 만료(`AdminSessionRevokeEvent`) + `PASSWORD_EXPIRED`는 `ACTIVE` 복귀. **모든 비밀번호 변경 경로(`Member.changePassword()`)가 outstanding reset 토큰을 함께 클리어**한다. 상세 설계 결정은 `adversarial-review/plan/PLAN-password-reset.md` 참조
- **재설정 메일 발송 executor 상한**(2026-09-30, 로드맵 Top 5 ④ 잔여): `PasswordResetService`의 `TaskExecutor mailExecutor`는 전용 빈이 아니라 Boot 기본 공용 `applicationTaskExecutor`이고, `application.yml`의 `spring.task.execution.pool`(core 4 = max 4, queue 20)로 상한을 건다(기본값은 큐 무제한). 포화 시 제출은 `TaskRejectedException`으로 거부되고 서비스가 삼킨 뒤 오류 로그(memberId·예외 타입만) + 발급 토큰 조건부 클리어를 하며 응답은 항상 200이다. **보장 범위는 "동시 실행 ≤ 4·대기 ≤ 20"뿐** — 큐 대기로 만료된 링크가 발송되지 않음은 보장하지 않고(작업 전체 deadline 없음), 같은 계정이 60초 뒤 재요청해 거부되면 앞서 수락된 메일은 DB에 없는 토큰의 링크로 도착한다(`PasswordResetExecutorSaturationTest`가 동작을 고정한 잔여 위험). 이 executor를 다른 기능이 쓰게 되면 메일 전용 빈 분리를 재평가한다. 상세는 `adversarial-review/plan/PLAN-mail-executor-bound.md` 참조.
- **재설정 요청의 발급은 응답 경로 밖에서 실행한다**(2026-11-08, `PLAN-password-reset-async-issue.md`): `requestReset`의 요청 스레드는 이메일 정규화·접수 로그·작업 제출만 하고, 계정 조회(`findByEmailForUpdate`)·토큰 발급·발송 제출(거부 시 토큰 정리 포함)은 전용 빈 `passwordResetIssueExecutor`(core=max=2·큐 100, `PasswordResetExecutorConfig`)에서 실행한다. 이전에는 요청 스레드의 발급 트랜잭션 때문에 메일이 발급되는 계정이 중앙값 6.6ms 느려 **요청 1건으로 계정 존재가 드러났다**(측정 `PLAN-password-reset-timing.md` — 서비스 주석의 "무시할 수준" 판단이 틀렸음). **요청 경로에 DB 접근을 되돌리지 않는다** — `PasswordResetServiceTest`가 요청 스레드의 repository·트랜잭션 호출 0건을 고정한다. 계약: 발급 큐 포화(제출 거부)는 200 + WARN, 발급 작업의 모든 예외는 작업 안에서 끝난다(잠금 실패 WARN·그 밖은 ERROR, 예외 타입만 — 이전에는 잠금 실패 외 DB 예외가 500), 접수 후 **30초**(`MAX_ISSUE_WAIT`, 쿨다운의 절반)를 넘긴 작업은 작업 시작 때와 **행 잠금 직후·상태 변경 전** 두 곳에서 버린다(쿨다운이 실행 시각으로 판정되므로 함께 접수된 요청이 쿨다운을 넘겨 재발급되지 않게). 빈은 `@Bean(defaultCandidate = false)` + `@Qualifier`로만 주입한다 — 빼면 Boot가 `applicationTaskExecutor` 자동 구성을 거두고 메일 단계가 이 빈을 받는다(`MailExecutorPoolConfigurationTest`). 종료 때는 최대 5초 기다린 뒤 나머지 빈을 닫으며 작업은 중단되지 않는다(그 뒤 발급은 실패 로그). 통합 시험에서 동기로 바꾸려면 `@TestBean(name = PasswordResetExecutorConfig.ISSUE_EXECUTOR, …)`(`PasswordResetConcurrencyIntegrationTest`).
- **내 정보(이름·이메일) 수정 행 잠금**(`AdminMemberService.updateMyInfo`, 2026-09-05): 이 클래스의 다른 모든 쓰기 메서드(`updateAdminMember`·`updateMyProfileImage`·`changeMyPassword` 등)와 동일하게 `findByIdForUpdate`로 행 잠금을 건다 — 과거에는 이 메서드만 유일하게 잠금 없는 `findById`를 써서, 이메일 변경과 비밀번호 재설정 토큰 발급(`PasswordResetService.issueToken`의 `findByEmailForUpdate`)이 경합하면 `@DynamicUpdate` 더티체킹이 null→null로 오판해 옛 이메일로 발급된 토큰이 새 이메일과 함께 남을 수 있었다(외부 기술 감사 H-02). 상세 분석·테스트 설계는 `adversarial-review/plan/PLAN-member-self-update-row-lock.md` 참조.
- **로그인 상태 유지(remember-me)**(2026-11-10, 이슈 #222): 쿠키 자동 로그인은 비밀번호를 쓰지 않아 실패 카운트를 리셋·증가시키지 않는다. 이 패키지의 세션 만료 트리거(`AdminSessionRevokeEvent` — 역할·상태 변경, 본인 비밀번호 변경, 재설정)는 같은 트랜잭션에서 그 회원의 remember-me 토큰도 모두 지운다(지우기 실패면 변경이 롤백된다). 상세는 `com.cms.config`의 `CLAUDE.md`. **쿠키 자동 로그인 세션은 계정 생성·타 계정 수정·내 정보 수정·내 비밀번호 변경 전에 비밀번호 확인이 필요하다**(403 `REAUTHENTICATION_REQUIRED` → 화면 모달 → `POST /admin/api/members/me/reauthentication`(`AdminReauthenticationController`)으로 승격 후 재시도, 2026-11-11). 재인증 오답은 폼 로그인과 같은 실패 카운터다. 이 패키지 컨트롤러에 쓰기 핸들러를 추가하면 `@RequireFullAuthentication` 또는 사유 있는 면제가 필요하다(`com.cms.config` `CLAUDE.md` "민감 작업 재인증").
- **로그인 실패 잠금 구현 완료** (`LoginFailureService`, 2026-07-14): 연속 5회 실패(`BadCredentialsException`만 카운트) 시 `LOCKED` 자동 전이 + **30분 후 lazy 자동 해제**(로그인·비밀번호 재설정 진입점에서 조건부 벌크 UPDATE). 대상은 `ROLE_ADMIN`/`ROLE_MANAGER` allowlist — `ROLE_USER`는 오잠금되지 않는다. `locked_at null = 수동 잠금(영구)`, `locked_at 존재 = 자동 잠금(30분 해제)`로 구분되며, `changeStatus()`는 항상 `locked_at`을 정리한다. 잠금 전이는 `AdminAccountAutoLockEvent`(AFTER_COMMIT)로 `AdminActionLog`(`ACCOUNT_AUTO_LOCK`) 감사 기록 + 기존 세션 만료(`AdminSessionRevokeEvent`, 발행 순서상 세션 만료가 감사보다 먼저). 성공 핸들러(`VisitLoggingAuthenticationSuccessHandler`)는 인증 완료 직전 fresh 상태·역할·비밀번호 해시를 재확인해 불일치·예외 시 **fail-closed 거부**(경합으로 잠긴/강등된/구 비밀번호 세션 차단). **내 비밀번호 변경 성공 시 전 세션 폐기**(본인 포함 — 재로그인 필요). `Member`에 `@DynamicUpdate` 부착(더티체킹 경합의 잠금 소실 차단). 최후 ADMIN 잠금 복구는 `docs/troubleshooting.md` 참조. 상세 설계 결정은 `adversarial-review/plan/PLAN-login-failure-lockout.md` 참조. **IP 신뢰 정책(2026-09-28, 감사 H-03)**: `LockingAuthenticationFailureHandler`(물리적으로는 `com.cms.config.auth` 패키지)가 실패 카운트 기록에 쓰는 IP는 `com.cms.common.web.ClientIpResolver.resolve()`(`request.getRemoteAddr()`만 신뢰)로 해석한다 — 과거에는 `X-Forwarded-For`/`X-Real-IP`를 신뢰해 위조 가능했고, `X-Forwarded-For: ,`처럼 조작된 값은 파싱 예외로 **실패 카운트 기록 자체를 건너뛰어 자동 잠금 방어를 무력화**할 수 있었다(`docs/troubleshooting.md` 참조).
- **비밀번호 재설정 IP 신뢰 정책(2026-09-28, 감사 H-03 조사 중 발견)**: `PasswordResetController.requestReset()`이 `PasswordResetService`에 전달하는 IP도 같은 `ClientIpResolver.resolve()`로 통일됐다 — 이 IP는 `admin_action_log`가 아니라 `log.info()` 참고 로그에만 쓰여 감사 대상은 아니지만, 조작된 `X-Forwarded-For: ,` 헤더가 과거엔 예외를 던져 "이메일 존재 여부와 무관하게 항상 200 반환"이라는 계정 열거 방지 계약을 깨고 500을 반환했다(`docs/troubleshooting.md` 참조).
- **시간 기반 비밀번호 만료는 폐지됐고 `PASSWORD_EXPIRED`는 관리자의 변경 강제다**(2026-11-05, `PLAN-password-expiry-retirement-breach-check.md` — NIST SP 800-63B rev.4·OWASP가 주기적 변경을 권하지 않아 90일 전이·`PasswordExpiryService`·만료 임박 알림을 지웠다). ADMIN이 회원 수정에서 다른 계정을 `PASSWORD_EXPIRED`("비밀번호 변경 필요")로 지정하면 세션이 만료되고 로그인이 거부되며(`CredentialsExpiredException`, 실패 카운트 미증가), 재설정 메일로 **현재 값과 다른** 비밀번호를 정하면 `Member.changePassword()`가 `ACTIVE`로 돌린다. 최후 활성 ADMIN 가드가 적용되고, 세션 폐기는 best-effort라 동일값 재저장이 재시도 경로다(`idempotentRelock`). **한계**: 로그인 화면은 일반 실패 문구라 대상자가 사유를 모르므로 관리자가 알려야 하고, 재설정 메일을 받을 수 있어야 복구된다. `password_changed_at`은 변경 시각 기록과 이전 앱 롤백을 위해 남겼다(만료 판정에는 쓰지 않는다). V14가 옛 전이 행을 `ACTIVE`로 되돌렸다.
- **비밀번호 검증 정책 통일 + 이메일 정규화 구현 완료** (2026-09-22, 외부 기술 감사 H-01·M-07): 관리자 생성(`AdminSignupRequest`)·내 비밀번호 변경(`AdminMyPasswordChangeRequest`)·비밀번호 재설정(`PasswordResetConfirmRequest`)·부트스트랩(`AdminBootstrapCredentials`) 4개 진입점 전부 `@MinCodePoints(15)`(최소 15 유니코드 코드포인트 — NIST SP 800-63B rev.4의 단일요소 인증 최소 길이·카운팅 규칙만 채택, 최대 길이·blocklist는 미채택) + `@MaxUtf8Bytes(72)`(BCrypt의 물리적 72바이트 제약, `dto/request/validation` 패키지의 커스텀 `ConstraintValidator`)로 통일됐다. `@MaxUtf8Bytes`는 `CharsetEncoder`(`CodingErrorAction.REPORT`)로 바이트를 계산해 고립 서로게이트 등 잘못된 형식의 UTF-16을 명시적으로 거부한다 — 기본 `getBytes(UTF_8)`는 이런 입력을 조용히 치환 문자로 바꿔, 서로 다른 비밀번호 원문이 같은 BCrypt 해시가 될 수 있었다(실측으로 확인된 문제). `EmailNormalizer`(`service` 패키지, 정적 유틸)가 `AdminMemberService`(`normalizeEmail` 중복 제거)·`PasswordResetService`·`AdminBootstrapLoader` 전체의 이메일 정규화(trim + `Locale.ROOT` 소문자화)를 통일하며, 정규화 후 길이가 `Member.email` 컬럼 길이(100)를 넘거나(İ 등 일부 유니코드 문자는 소문자화 시 길이가 늘어남) 잘못된 형식의 UTF-16을 포함하면 `InvalidRequestException`(400)을 던진다. 상세 설계 결정(적대적 리뷰 4라운드, 3라운드는 codex·1라운드는 codex 사용량 한도로 자체 수행)은 `adversarial-review/plan/PLAN-password-policy-unification.md` 참조.

- **유출 비밀번호 차단**(2026-11-05, `PLAN-password-expiry-retirement-breach-check.md`): 비밀번호를 정하는 네 지점(`createAdmin`·`changeMyPassword`·`resetPassword`·`AdminBootstrapLoader`)이 `BreachedPasswordChecker`(구현 `HibpBreachedPasswordChecker`, JDK `HttpClient`, 전체 3초 상한, SHA-1 앞 5자만 전송)로 판정한다. **판정과 거부를 분리한다** — 판정은 외부 호출이라 트랜잭션·행 잠금 밖에서 받아 지역 변수에 두고, 거부는 트랜잭션 안에서 기존 검증(중복·현재 비밀번호·토큰·만료·자격)을 통과한 뒤에 한다. 그래서 세 서비스 메서드는 `@Transactional` 대신 내부 `TransactionTemplate`을 쓰고, 비밀번호 변경 경로에 외부 호출을 추가하거나 `@Transactional`을 되돌리면 안 된다. 재설정은 토큰이 없으면 외부로 나가지 않는다(무인증 경로). **판정 불가는 통과 + WARN(fail-open)** — 외부 장애가 탈취 의심 시의 긴급 변경을 막으면 안 된다. 응답은 엄격히 해석한다: 횟수 1 이상 일치면 유출, 그 밖에는 모든 줄이 유효해야 미유출이고 손상·빈 응답은 판정 불가다(패딩 행은 횟수 0). 변경·재설정은 **현재 값과 같은 비밀번호도 거부**한다(잠금 안 BCrypt 1회, HIBP와 무관). 거부는 400 `PASSWORD_REJECTED`(`PasswordRejectedException`, 상수 메시지)이고 쓰기가 없어 재설정 토큰이 살아 있으며, `password-reset-confirm.html`은 이 코드일 때만 서버 메시지를 보여 준다(나머지 400은 링크 안내). 부트스트랩은 유출이어도 기동을 막지 않고 WARN만 남긴다. **Spring의 `CompromisedPasswordChecker`를 빈으로 등록하지 않는다** — `DaoAuthenticationProvider`가 집어 로그인마다 검사한다(`PasswordBreachRejectionIntegrationTest`가 고정). 테스트 JVM은 `build.gradle`이 `CMS_PASSWORD_BREACH_CHECK_ENABLED=false`를 주입한다(IDE에서 개별 실행하면 켜져 실제 HIBP로 나갈 수 있다). 운영은 `docs/deployment.md` "유출 비밀번호 검사".

- **관리자 관리 화면의 상세 모달 비동기 보호와 `?id=` 진입**(`admin-manage.html`, 2026-10-05, 상단바 통합 검색): `loadAdminDetail`에 모달 세대(`detailSeq`)·`AbortController`·응답 `id` 일치 검사를 두어 다른 회원을 열거나 모달을 닫을 때 늦게 도착한 응답이 `currentDetail`(수정 PATCH 대상)을 덮지 못하게 한다 — 과거에는 응답 순서가 뒤집히면 A의 입력이 B에게 저장될 수 있었다. `saveEdit`의 대상 ID는 요청 시작 시점에 고정하고 응답이 올 때 세대·대상이 달라졌으면 화면을 건드리지 않고 목록만 갱신한다(서버 저장은 이미 반영됨). 상세는 본인 ID 조회(`currentAdminReady`) 뒤에 그려 본인 계정에 수정 버튼이 뜨지 않는다. 검색 결과 링크 `?id=`(`^[1-9]\d{0,15}$`)는 본인 ID를 기다린 뒤 모달을 열되, 기다리는 동안 사용자가 직접 회원을 열었으면(세대 변화) 자동 진입을 버린다. 연 직후 `id`를 쿼리에서 지운다.

- **로그인 성공·자동 잠금과 알림**(2026-10-05, `PLAN-admin-notification.md`): `VisitLoggingAuthenticationSuccessHandler`는 재확인 통과 뒤 읽은 알림 정리를 **자기 트랜잭션·try/catch**로 호출한다(로그인을 막지 않는다). `AdminAccountAutoLockEvent`에 `canonicalUserId`(DB 정규 아이디)·`lockedAt`이 추가됐다 — 기존 `userId`는 로그인 요청 **원문**이라 알림에 쓰지 않는다. 상세는 `com.cms.admin.notification`의 `CLAUDE.md`.

## 프로필 이미지 (Base64-in-DB → FileStorage 이관 완료, 2026-08-10)

업로드된 이미지는 더 이상 DB에 Base64로 저장되지 않는다 — `com.cms.common.storage.FileStorage`(공지 첨부파일용, 2026-07-22 도입)의 **`"profile"` 네임스페이스**에 실파일로 저장된다. `FileStorage`에 네임스페이스 인자 오버로드 3종(`store`/`load`/`delete`)이 추가되어(하위 호환 default 메서드) 프로필 이미지는 공지 첨부파일과 **물리적으로 분리된 디렉터리**(`root/profile/...`)에 저장된다 — `member.profile_image_url`에는 storageKey(공지 첨부파일과 같은 `yyyy/MM/dd/uuid.ext` 형태)가 그대로 들어가도, 네임스페이스가 다르므로 물리 경로가 겹치지 않는다. 네임스페이스 없는 기존 `load()/delete()`는 예약된 최상위 세그먼트(`"profile"`)로 시작하는 storageKey를 아예 해석하지 않는다(공지 첨부파일 storageKey가 오염되어 `profile/...` 형태가 되어도 프로필 파일에 접근 못함 — 반대 방향도 마찬가지).

- **`member.profile_image_kind`**(enum, `NONE`/`PRESET`/`UPLOADED` — `LEGACY_INLINE`은 V3가 제거): "이 값이 지금 무슨 의미인지"를 문자열 생김새 추론이 아니라 명시적으로 관리한다. `UPLOADED`일 때만 `FileStorage`를 호출한다. `member.profile_image_content_type`(nullable)은 `UPLOADED`일 때만 채워져 다운로드 응답의 `Content-Type`을 확장자 추론 없이 재생한다.
- **`Member` 도메인 메서드**: `changeProfileImage(url)` 단일 메서드 대신 `changeUploadedProfileImage`/`changePresetProfileImage`/`resetProfileImage` 3종으로 분리해 "preset인데 content-type이 남아있는" 등 불가능한 상태 조합을 구조적으로 차단한다.
- **검증**(`AdminMemberService`, `ProfileImageValidator`): 화이트리스트는 `image/png`·`image/jpeg`·`image/gif`(**WebP 제외** — JDK 표준 `ImageIO`가 WebP를 지원하지 않아 신규 의존성 추가 대신 화이트리스트에서 뺌). `ImageReader`로 헤더만 먼저 읽어(`getWidth(0)/getHeight(0)`, 아직 픽셀 디코딩 전) 변 길이 2000px·총 픽셀 200만 상한을 넘으면 거부한 뒤에만 실제 디코딩(`reader.read(0)`)한다(decompression bomb 방어). `getNumImages(true) != 1`이면 애니메이션(다중 프레임)으로 거부(아바타에 애니메이션 불필요, GIF 폭탄 방지). `ImageReader.getFormatName()`으로 선언 MIME과 실제 포맷 일치도 검증한다. 신규 의존성 없음(JDK 표준 API만 사용). **2026-10-07부터 실제 검사는 공용 `com.cms.common.image.ImageFileValidator`가 하고 `ProfileImageValidator`는 프로필 상한(2000px·200만 픽셀·전체 디코드)만 넘긴다**(편집기 본문 이미지와 공유 — `PLAN-html-editor.md` 쟁점 8). 이때 기존 정책의 구멍 두 개가 함께 막혔다: APNG(`acTL` 청크 — JDK PNG reader는 1프레임으로 보고)와 GIF 논리 화면 크기 우회(1×1 프레임 + 큰 캔버스, 프레임이 화면 밖인 GIF). 그 밖의 런타임 예외(손상 메타데이터 등)도 500이 아니라 400 "이미지를 해석할 수 없습니다"가 된다.
- **다운로드 라우트**: `GET /admin/api/members/me/profile-image`(ADMIN·MANAGER, `SecurityConfig`의 기존 `/admin/api/members/me/**` 매처가 그대로 커버 — 코드 변경 없음), `GET /admin/api/members/{id}/profile-image`(ADMIN 전용, 기존 `/admin/**` 캐치올이 커버). `ResponseEntity<byte[]>`로 실제 바이트를 직접 반환, `Content-Disposition` 미설정(인라인 렌더링 — 첨부 다운로드와 반대), `Cache-Control: private, no-store` + `X-Content-Type-Options: nosniff`. 응답 URL에는 storageKey를 SHA-256 해시한 캐시 버스팅 토큰(`?v=...`)이 붙는다(고정 경로 재사용 시 브라우저가 이미지 교체를 인식 못 하는 문제 방지).
- **`LEGACY_INLINE` 값은 V3가 제거했다**. 이 값의 행이 남은 DB는 V3의 enum 축소가 엄격 모드 오류로 멈추므로 `NONE`으로 정리한 뒤 `flyway repair` → 재기동한다(`docs/migration-guide.md`). `profile_image_url`은 Base64를 담던 `LONGTEXT`였고 V4(2026-10-24, `PLAN-profile-image-url-shrink.md`)가 `varchar(255)`로 줄였다 — 값은 `FileStorage` 키(최대 58자)나 프리셋 경로뿐이라 길이 검증 코드는 없다. 엔티티는 `@Column(length = 255)`(`@Lob` 없음)이라 이전 앱 매핑과는 `validate`가 맞지 않는다(롤백 절차는 `docs/migration-guide.md`).
- 상세 설계 결정·적대적 리뷰 5라운드 기록은 `adversarial-review/plan/PLAN-profile-image-storage.md` 참조.
