# CLAUDE.md — com.cms.publicweb.notice

이 디렉터리(공개/비로그인 공지 화면) 작업 시에만 로드된다. 공통 규칙은 프로젝트 루트 `CLAUDE.md` 참조. 관리자 측 공지사항 도메인은 `com.cms.admin.notice`의 `CLAUDE.md` 참조.

(필드 목록은 엔티티 코드가 원본이다. 여기에는 코드만 봐서는 알기 어려운 사실만 기록한다.)

- **공개(비로그인) 공지 페이지 구현 완료** (`PublicNoticeController`·`PublicNoticeService`, `com.cms.publicweb.notice`, 2026-07-28): `/notices`(목록)·`/notices/{id}`(상세)에서 `useYn=true` AND `deleted=false`인 공지만 노출한다. 이 불변식은 admin `NoticeService`와 별도 클래스(`PublicNoticeService`)·별도 Repository 파생 쿼리(`findByDeletedFalseAndUseYnTrue`, `findByIdAndDeletedFalseAndUseYnTrue`)로 타입 단위로 격리되어, admin의 선택적 `useYn` 필터와 혼동될 수 없다. 공개 DTO(`PublicNoticeSummary`/`PublicNoticeDetail`)는 `authorId`(관리자 로그인 userId)를 필드 자체에서 제외한다. **`id`·`page`는 Spring 바인딩에 맡기지 않고 컨트롤러가 문자열로 받아 직접 파싱**한다 — `GlobalApiExceptionHandler`가 전역 `@RestControllerAdvice`라 페이지 컨트롤러의 타입 변환 예외까지 JSON으로 응답해버리기 때문(파싱 실패는 404/0으로 흡수, 존재 여부 열거 방지 목적으로 미노출·삭제·비숫자·없는 ID를 모두 동일한 404로 응답). 남은 예외(DB 장애 등)는 `com.cms.publicweb.support.PublicWebExceptionAdvice`(`basePackages="com.cms.publicweb"`, `@Order(HIGHEST_PRECEDENCE)`)가 HTML 500으로 흡수하며, 이 보장은 컨트롤러·Service 실행 중 예외로 한정된다(Thymeleaf 렌더링 단계 예외는 앱 전체의 기존 한계로 이번 범위에서 다루지 않음). 페이지 크기는 10으로 고정, `page`는 음수·`MAX_PAGE`(1000, 인덱스 없는 테이블의 대형 OFFSET 방어) 초과 시 0으로 보정. `SecurityConfig`는 `/notices`·`/notices/**`에 GET/HEAD만 `permitAll`, 나머지 메서드는 `denyAll`로 명시 차단(뒤에 남은 `anyRequest().permitAll()`에 기대지 않음). 검색·첨부파일은 후속 구현 완료(아래 참조). 상세 설계 결정·적대적 리뷰 4라운드 기록은 `adversarial-review/plan/PLAN-public-notice.md` 참조
- **공개 첨부파일 다운로드 구현 완료** (`GET /notices/{id}/attachments/{attachmentId}`, `com.cms.publicweb.notice`, 2026-08-03): `PublicNoticeService`에 메서드로 확장(별도 클래스 신설 안 함 — 위 "노출+미삭제 불변식 타입 단위 격리"를 유지하는 게 목적이지 클래스 수를 늘리는 게 목적이 아님). admin `NoticeAttachmentService`는 재사용하지 않는다(`useYn` 미검증이라 공개 조건이 뚫림). **다운로드 시점 재검증(TOCTOU)은 "재검증 SELECT를 실행한 시점에 공개 상태였음"만 보장하는 약한 보장**이다 — 락은 쓰지 않는다(무인증 엔드포인트가 admin의 `PESSIMISTIC_WRITE`를 블로킹하는 DoS 표면이 되므로). `findByIdAndNoticeId` 복합 조건으로 IDOR 차단, `StorageFileNotFoundException`은 `Optional.empty()`로 흡수해 404 fail-closed. 실패 3종(비숫자 id·비공개 notice·없는 첨부)은 모두 동일한 404(`response.sendError(404)`로 기존 `error/404.html` 재사용). 응답은 admin 다운로드와 동일하게 `application/octet-stream`+`ContentDisposition`+`nosniff`에 더해 **`Cache-Control: no-store`**(캐시가 TOCTOU 재검증을 우회하지 못하게). `PublicNoticeAttachment` DTO는 `storageKey`(서버 내부 경로) 필드 자체를 두지 않음. `/notices/**`가 이미 GET/HEAD `permitAll`이라 이 라우트는 **SecurityConfig 수정 없이** 자동으로 무인증 공개됨(`SecurityConfigTest`로 명시 고정). **스트리밍 전송(2026-09-29)**: 파일을 힙에 통째로 올리지 않고 4KB 버퍼로 응답에 흘려보낸다(`FileStorage.open()` → `StoredFileStream`). 컨트롤러가 `HttpServletResponse`에 직접 쓰고 열린 스트림을 `try-with-resources`로 단독 소유한다(`ResponseEntity<Resource>`는 Range 처리·쓰기 전 예외 시 누수 경로 때문에 쓰지 않음). 서비스는 둘로 나뉜다 — `findPublishedAttachment()`(`@Transactional(readOnly)`, 공개 조건 재검증·IDOR 차단 후 `PublicNoticeAttachmentRef` 메타데이터만 반환)와 **트랜잭션 없는** `openAttachment()`(파일 열기). 열린 스트림이 트랜잭션 프록시를 통과하면 commit 실패 시 닫을 수 없으므로 반드시 분리 유지한다. HEAD는 전용 핸들러가 GET과 같은 경로로 404를 판정하고 핸들만 잠깐 열어 크기를 얻은 뒤 닫는다(본문 미독). Range는 지원하지 않는다(무시, 이전과 동일). **TOCTOU 창은 전송 시간만큼 길어진다**(약한 보장 계약 자체는 불변 — 전송 중 비공개 전환·첨부 삭제는 진행 중 다운로드를 막지 않는다; 열린 핸들은 삭제 후에도 끝까지 읽힘 — Windows에서 실측, 리눅스는 unlink 시맨틱상 동일하며 `LocalDiskFileStorageTest`가 회귀를 고정). **전송 중 실패는 응답 상태 3구간으로 처리**한다: (1) 첫 청크를 헤더 설정 전에 먼저 읽어 실패 시 기존 HTML 500, (2) 미커밋이지만 오염된 상태는 컨트롤러가 `response.reset()` 후 재던짐 → HTML 500, (3) 커밋 후에는 `PublicWebExceptionAdvice`가 뷰를 렌더링하지 않고 예외를 재던져 컨테이너가 연결을 중단하게 한다 — **예외를 삼키면 Tomcat은 연결을 끊지 않고 클라이언트가 남은 바이트를 무한정 기다린다**(실서버 테스트로 실측). 복사 버퍼(4KB)는 컨테이너 출력 버퍼(Tomcat 8KB)보다 작아야 "첫 청크 직후 미커밋"이 성립한다. 남은 자원 위험: 동시 연결 수·디스크 IO·Tomcat 스레드 점유는 그대로이며 `cms.rate-limit`은 요청 진입 빈도만 완화한다(동시 전송 수 상한은 없음). 상세 설계 결정·적대적 리뷰(다운로드 4라운드 + 스트리밍 전환 3라운드) 기록은 `adversarial-review/plan/PLAN-public-notice-attachment.md` 참조
- **공개 목록 제목 검색 구현 완료** (`GET /notices?keyword=…`, 2026-10-07): 검색 대상은 **제목만**(관리자 목록·상단바 통합 검색과 같은 의미, 본문 `TEXT` LIKE의 무인증 비용 회피). 키워드가 있을 때만 공개 전용 QueryDSL 메서드 `NoticeRepositoryCustom.searchPublishedByTitle`를 쓰고, 없으면 기존 `findByDeletedFalseAndUseYnTrue` 경로를 그대로 쓴다. 이 메서드는 노출·미삭제 조건을 구현에 하드코딩하고 **목록 SELECT와 COUNT가 같은 `BooleanBuilder`를 쓴다** — COUNT에서 공개 조건이 빠지면 비공개 일치 공지의 존재가 총건수·페이지 수로 드러나기 때문이다(admin `searchNotices`의 선택적 `useYn`을 재사용하지 않는 이유와 같음). LIKE 와일드카드(`%`·`_`)와 이스케이프 문자 `!`는 QueryDSL `contains`가 이스케이프해 문자 그대로 검색된다(실 SQL `title like ? escape '!'`, `NoticeRepositoryDataJpaTest`가 MariaDB로 고정 — 이스케이프 없는 `like`로 바꾸면 실패함을 확인). 대소문자는 콜레이션(`utf8mb4_general_ci`)에 따라 구분하지 않는다. `keyword`는 문자열 그대로 받아(바인딩 실패 없음) 서비스가 정규화한다: `strip()` 후 비면 검색 없음, **`String.length()`(UTF-16 코드 유닛) 100 초과면 DB 조회 없이 빈 페이지**(200) — 화면 입력란의 `maxlength="100"`과 같은 단위다. 서비스는 `PublicNoticeListResult(page, keyword)`로 정규화한 키워드를 돌려주고, 템플릿은 검색 중일 때만 페이지 링크에 `keyword`를 붙인다(`null` 파라미터 렌더링에 기대지 않고 `th:if`로 링크를 나눔). 상세의 "목록으로"는 검색어를 유지하지 않는다(범위 밖). **비용**: 인덱스가 없어 검색도 기존 무검색 목록처럼 요청마다 전체 행(비노출·삭제 포함) 스캔 + COUNT를 한다 — 실측(dev Docker MariaDB, 캐시가 데워진 상태): 1만 행 목록+COUNT 약 7~9ms, 5만 행 약 32~39ms(기본 목록과 같은 차수, 검색어 유무 차이 수 ms). **전체 행수가 5만을 넘거나 운영에서 검색 응답이 100ms를 넘으면 FULLTEXT(ngram) 등 검색 인덱스를 재평가**한다. 레이트리밋은 기존 `public-notice` 규칙(IP당 버스트 120 + 초당 2토큰, 동시 진입 제한 없음)을 그대로 쓴다. 상세 설계·적대적 리뷰 2라운드 기록은 `adversarial-review/plan/PLAN-public-notice-search.md` 참조
