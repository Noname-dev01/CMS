- 슬라이스 테스트(`@WebMvcTest`, `@DataJpaTest`)를 우선하고, 통합 테스트(`@SpringBootTest`)는 필요한 경우에만 사용한다.
- **DB에 실제로 접속하는 테스트는 Testcontainers를 사용한다** (2026-07-27 도입, `com.cms.support.MariaDbContainerSupport`). 대상 테스트 클래스가 이 베이스 클래스를 `extends`하면 실행 시점에 일회용 MariaDB 컨테이너가 자동 기동된다 — **로컬 DB 기동(`make dev-db`)이나 `DB_PASS`/`MAIL_USER`/`MAIL_PASS` 환경변수 주입 없이 `./gradlew test`만으로 전체 테스트가 통과**한다. 필요한 건 Docker뿐이다. `build.gradle`의 `maxParallelForks=1`+`forkEvery=0`으로 테스트 JVM(워커)당 컨테이너 1개를 보장하며, 재사용(`reuse.enable`)은 쓰지 않아 매 실행이 깨끗한 DB에서 시작한다(Flyway가 V1부터 전체 마이그레이션 적용). 상세 설계 결정은 `adversarial-review/plan/PLAN-testcontainers.md` 참조.
- **동시성 시험에서 "실제 DB 락 대기"를 관측할 때는 `com.cms.support.LockWaitObserver`를 쓴다**(2026-10-11, 이슈 #119·#121): `information_schema.INNODB_LOCK_WAITS`·`INNODB_TRX`는 InnoDB가 **캐시로** 돌려줘서, 짧은 간격(예: 25ms)으로 계속 읽으면 첫 조회 시점의 스냅샷이 갱신되지 않고 남아 이미 존재하는 락 대기를 수 초~15초 넘게 놓친다. 첫 조회가 대기자의 락 요청보다 먼저 나가는 순서(대기자 경로가 느린 CI)에서 시험이 실패한다 — 로컬에서는 관측용 연결을 맺는 동안 대기자가 먼저 락에 걸려 드러나지 않는다. 같은 캐시가 **반대 방향**으로도 작용한다 — 직전 관측이 100ms 이내에 읽은 스냅샷은 갱신되지 않아 이미 끝난 대기를 새 관측이 "있음"으로 받을 수 있으므로 헬퍼는 첫 조회 전에 간격만큼 쉰다(캐시 위생, 증거 아님). 전역인 `awaitAnyWaiter`는 이 낡은 스냅샷에 특히 취약하니 대기자를 특정할 수 있으면 연결 ID로 좁히는 변형을 쓴다. 헬퍼가 폴링 간격(150ms, **100ms 초과 필수**)을 한 곳에 두므로 시험에서 직접 폴링하지 않는다 — `LockWaitPollingConventionTest`가 헬퍼 밖의 직접 조회를 CI에서 잡는다. 헬퍼는 `awaitAnyWaiter`(아무 대기자)·`awaitWaiterFor(holder)`(특정 연결이 쥔 락을 기다리는 대기자)·`awaitWaiterPair(holder, waiter)`(연결 쌍, 대기 중인 문장 반환)를 제공하고, `LockWaitObserverTest`가 "대기자가 첫 폴링 뒤에 생기는" 순서를 시험용 훅으로 결정적으로 만들어 고정한다. 캐시를 거치지 않는 관측 수단은 `SHOW ENGINE INNODB STATUS`(TRANSACTIONS 섹션의 "TRX HAS BEEN WAITING … FOR THIS LOCK TO BE GRANTED")와 `PROCESSLIST`다. 락 대기를 `Thread.sleep`으로 갈음하는 시험(`BannerConcurrencyIntegrationTest`의 `sleep(500)` 등)은 거짓 실패는 없지만 느린 환경에서 회귀를 놓칠 수 있는 약한 검출이다.
- **시각 경계를 실제 스택으로 시험할 때는 `com.cms.support.MutableClock`을 `@Primary` 빈으로 올린다**(2026-10-11, 게시글 예약 게시 `PostPublishPeriodPublicIntegrationTest`): 시험 클래스 안의 `@TestConfiguration static class`로 `MutableClock`(KST, `set(LocalDateTime)`)을 선언하고 **클래스에 `@Import(…ClockConfig.class)`를 붙인다** — `@Import` 없이는 이 프로젝트 설정(`@SpringBootTest(classes = CmsTestApplication.class)`)에서 중첩 `@TestConfiguration` 빈이 잡히지 않아 "No qualifying bean"으로 실패하는 것을 실측했다(원인 규명은 하지 않았다). 판정 시각이 항상 주입된 `Clock`에서 나온다는 규약(`ClockUsageConventionTest`)이 있어야 성립하는 방식이고, 이 빈이 있는 컨텍스트는 다른 시험과 캐시를 공유하지 않는다(추가 컨텍스트 1개). "직전"은 `datetime(6)`의 최소 단위인 마이크로초 하나 앞이다(나노초는 DB에서 반올림될 수 있다).
- **배너·팝업·라이브러리 이미지를 만드는 통합 시험은 정리에 `com.cms.support.MediaTestSupport`를 쓴다**(2026-10-12, 미디어 라이브러리): 이미지는 `content_image` 행·`content_image_ref`·파일·카운터(`content_image_usage`)로 남으므로 소유자 행(`banner`·`popup`)만 지우면 시험 간 상태가 쌓인다 — `cleanLibrary(jdbc, fileStorage)`가 라이브러리 계열 출처의 이미지·참조·파일을 지우고 카운터를 원본에서 재계산한다. 배너·팝업 픽스처를 JDBC로 직접 넣을 때는 `attachImage(jdbc, ownerType, ownerId, key, size)`가 이미지 행과 참조를 함께 만든다(소유자 테이블에는 더 이상 이미지 컬럼을 쓰지 않는다). 서비스를 스레드에서 직접 부르는 시험은 업로더 아이디가 필요해 `SecurityContextHolder`에 인증된 주체를 심어야 한다(`BannerConcurrencyIntegrationTest.authenticate`). **잠금 계약 시험은 `@MockitoSpyBean`으로 `MediaImageRemover`/`AdminPermissionEvaluator`를 감싸 "원하는 지점"에서 다른 스레드를 끼워 넣는다**(`MediaConcurrencyIntegrationTest` — 격리 수준 단언은 `TransactionSynchronizationManager.getCurrentTransactionIsolationLevel()`, 갭 락은 삭제 트랜잭션 안에서 다른 이미지의 참조 INSERT가 막히는지, 존재 확인과 INSERT 사이에 삭제가 끼는지).
- **요청 DTO의 JSON 입력 계약(중복 키·오타 키·빈 문자열·오프셋·날짜 보정)은 Java에서 DTO를 직접 만드는 시험으로 검증하지 않는다** — Jackson 3.1의 관대한 역직렬화는 실제 `MockMvc`/서버 바인딩에서만 드러난다(예: 매개변수 이름으로 자동 인식된 생성자 creator가 중복 키 거부 세터를 우회하는 것은 실서버 스택 시험이 처음 잡았다 — `PostPublishPeriodApiIntegrationTest`). 원문 JSON 문자열을 그대로 보내고 "400이고 DB가 그대로"를 단언한다.
- **브라우저 기본 동작·화면 JS는 실제 브라우저(Playwright)로 시험한다**(2026-10-12, 팝업 관리 화면의 종류 전환 폼 검증 — `PopupAdminFormBrowserTest`): MockMvc는 브라우저의 기본 폼 검증(숨겨진 invalid 입력이 제출을 조용히 막는 것 등)과 화면 JS를 재현하지 못한다. 베이스 클래스 `com.cms.support.BrowserTestSupport`(`MariaDbContainerSupport` 상속)를 상속하고 `@SpringBootTest(webEnvironment = RANDOM_PORT)`로 실제 서버를 띄운다. **로그인은 실제 폼 로그인**이라 `TestMembers.save`로 만든 회원에 `enableFormLogin(jdbc, member)`를 호출해야 한다 — 앱은 `BCryptPasswordEncoder`만 쓰므로 `TestMembers`의 `{noop}` 비밀번호로는 폼 로그인이 안 된다(MockMvc 시험은 인증 주체를 직접 만들어 이 경로를 타지 않는다). 기본 대기는 15초다. **느리다(Spring 컨텍스트 + 브라우저) — 브라우저가 필요한 동작에만 쓰고 서버 로직은 기존 MockMvc·통합 시험에 둔다.** **속도 규약(2026-10-22, `adversarial-review/plan/PLAN-e2e-browser-speedup.md` — 15개 클래스 합 254초 → 106초)**: ① 브라우저는 **테스트 JVM당 한 번** 띄워 공유하고 종료 훅에서 닫는다(격리는 시험마다 새 `BrowserContext`). Playwright 객체는 스레드 안전하지 않아 처음 띄운 스레드 밖에서 쓰면 `IllegalStateException` — JUnit 병렬 실행을 켜려면 공유 방식부터 바꾼다. ② `loginAsAdmin`은 화면을 그리지 않고 페이지 컨텍스트와 쿠키를 공유하는 요청 컨텍스트로 `POST /admin/login`을 보낸다(성공 판정은 302 + Location 경로가 정확히 `/admin` — 실패는 `/admin/login-error`). 로그인 **화면** UI는 이 시험들의 대상이 아니다. ③ **Bootstrap `fade` 전환은 기본으로 꺼져 있다**(컨텍스트 초기화 스크립트의 CSS — 앱 JS·모달 상태 기계는 그대로 돌고 Bootstrap은 0초 전환도 비동기로 완료한다). 전환 자체가 시험 조건이면 **화면 이동 뒤** `restoreModalTransitions(page)`를 부른다 — 지금은 FAQ·팝업·정적 페이지의 "상세 조회가 즉시 404로 실패해도(열림 전환 중)" 3건이다. 전환이 꺼진 상태에서만 돌린 시험은 실사용자의 300ms 전환 중 경합을 잡지 못하므로, 새 전환 경합은 전환을 켠 시험으로 따로 쓴다("모달은 표시됐으나 `shown` 전" 구간의 응답 시험은 아직 없다 — 로드맵 후속 후보). ④ **고정 `waitForTimeout`은 쓰지 않는다**(0건) — 대기는 `waitForFunction`·자동 대기, 부정 단언은 양성 증거 뒤에 한다: ESC·배경 클릭으로 닫히지 않음은 `countHidePrevented`/`assertHidePrevented`(정적 백드롭 거부 시 키·마우스 이벤트 처리 안에서 동기 발생하는 `hidePrevented.bs.modal` — 누른 직후 바로 횟수를 단언해 회귀가 시간 초과가 아니라 즉시 실패한다), "요청이 나가지 않음"은 브라우저가 동기적으로 막는 지점(첫 무효 입력의 포커스)과 **요청 장벽** `awaitRequestBarrier(page)`(표지 요청이 시험 쪽에 도착한 뒤 요청 수를 단언 — 앱이 직전 동기 처리에서 보낸 요청은 그보다 먼저 도착한다), 확인창 취소 뒤 상태는 확인창이 세어진 시점(`confirm()`은 핸들러가 닫을 때까지 클릭을 막는다), 늦게 온 응답은 `holdFirstResponse`/`releaseHeldResponse`(응답을 붙잡아 두고 `json()`을 미리 파싱한 값으로 덮어써 앱 후속이 마이크로태스크로만 끝나게 한 뒤 다음 태스크까지 기다린다 — 네이티브 본문 소비는 완료 시점이 보장되지 않는다), 붙잡은 목록 응답의 처리 완료는 목록에 넣은 표지 행이 `replaceChildren`으로 사라지는 것 + 한 태스크(`setTimeout(0)`)로 본다. 변이 실험 40건(정적 백드롭 제거·검증 우회 요청·확인 취소 무시·열기 가드 제거·순번 검사 제거·목록 응답의 마이크로태스크 잠금 해제 등)이 전부 의도한 단언에서 실패함을 확인했다 — 목록은 계획 문서. 한계: 목록 응답 뒤 **한 태스크보다 늦게**(예: `setTimeout(…, 50)`) 미뤄진 잠금 해제 회귀는 잡지 못한다(변이로 확인 — 옛 500ms 고정 대기는 잡았다, 고정 대기 0건 규약과 맞바꾼 수용 한계). `waitForFunction`의 인자로 `long`은 직렬화되지 않는다(`Unsupported type of argument` — 문자열·`Integer`를 넘긴다). **브라우저 설치**: 로컬은 첫 실행 때 Playwright가 드라이버와 Chromium을 자동으로 내려받고(수 분·약 115MB), **CI는 `./gradlew installPlaywrightBrowsers`(`ci.yml`의 `Install Playwright browsers` 단계)로 Chromium과 시스템 의존성(apt)을 미리 설치한다.** 변이 실험으로 확인한 것: 숨겨진 높이 입력의 비활성화를 제거하면 4건 중 3건이 실패하고, 높이 입력 `min`을 144에서 100으로 바꾸면 범위 시험 1건이 실패한다.
